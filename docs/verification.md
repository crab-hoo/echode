# 変更に応じた検査

エージェントが検査を選ぶ入口は `make verify`。対応の定義は [scripts/verification.json](../scripts/verification.json) に一つだけ置き、[AGENTS.md](../AGENTS.md)、終了フック、CI は同じ実行器を使う。`make check` は通常の検査として残す。

## 実行する時

着手時に `make verify-plan` で対象を確認する。作業中は関係する単体テストを先に実行し、変更が終わったら `make verify` を使う。既定では HEAD と作業ツリーの差分を読み、ステージ済み、未ステージ、未追跡、削除、移動前後のパスを含める。すでにコミットした変更には `VERIFY_BASE=<変更前のref> make verify` を使う。存在しない ref は失敗にする。

`scripts/verify.py --all` は全自動検査と全計測候補を選ぶ。`--only ID` は対象を分けて検査する時に使えるが、他の検査が終わったことにはならない。計測を `--only` で明示した場合の実行には `--run ID` も付ける。有効な合格も任意の見送り記録もないまま、その項目の成功とはしない。エージェントが完了を報告する前には、`--only` を使わずに `make verify` を実行する。

通常の検査はすべての変更で選ぶ。モデル、エンジン、プラグイン、描画、保存、入力、橋渡しの依存関係もパスの対応に含める。共通の依存やツールチェーン、検査の仕組み、CI の変更では自動の検査をすべて選ぶ。計測などの候補は、関係する領域の変更がある場合だけ選ぶ。Cargo.lock の変更だけで全計測を候補にしない。依存の脆弱性検査は、依存の変更に対応する候補として選ぶ。パスで処理の意味までは判定できないため、影響がある検査を追加する時は `--all --only ID` を使う。計測なら `--run ID` も付ける。

## 自動で動かす検査

- `check`: Rust の単体テスト、ランダムな編集の不変条件・Undo / Redo・保存の往復、音声の基準との比較、保存形式のスナップショット、ブロック長による比較、プラグインのクラッシュとハング、Swift の橋渡し、lint、FFI、ライセンス。`check-verification` で検査の選択と記録の仕組みも確かめる
- `rtsan`: 検出を有効にしたテスト用シンセ、計画の受け渡し、製品の再生・トランスポート操作・出力バッファ。HAL 自体や未実装の音源まで無条件に網羅した検査ではない
- `check-input`: Swift の入力の単体テスト。確認ウィンドウは開かない
- `check-bridge-features`: 橋渡しの全 feature の Rust テスト、clippy、生成器を含む依存のライセンス
- `check-bridge-asan`、`check-bridge-tsan`、`check-bridge-miri`: 橋渡しの寿命、完了、停止と競合の検査。[ADR 0044](decisions/0044-swift-bridge.md) の範囲に限定する。Miri は橋渡しの Rust 側を検査し、Rust 全体や Swift の実行を網羅しない。ASan は両言語を別プロセスで、TSan は同じプロセスで検査する

製品の橋渡しも動的検査へ含める。ASan は `echode-ffi` と製品の音声出力バッファの Rust テスト、Swift の実際の編集・保存・再読込を別々に検査する。TSan は標準ライブラリを含む Rust の製品静的ライブラリと Swift を同じプロセスで検査する。Miri はパッケージ I/O を含めず、製品の保持したスナップショット、UTF-8 の借用、可視列の容量と null の契約を seed 1・17・42 で検査する。これらは Metal の GPU の動作の検査とは別である。

自動の検査は失敗すると非ゼロで終わる。見送りでは代用できない。環境に必要なツールがなければ、`make setup`、`make setup-bridge` で用意する。製品の既定の Rust は変更しない。隔離された環境がソケットのテストなどを拒否した場合も、検査済みとせず、許可された環境で実行する。

アプリの通常の Swift 検査には、ワークスペースの配置と保存、文書・トラック・ノートの選択と入力の下書き、コマンドの有効条件、ファイル一覧の非同期更新、ネイティブ View を作り直す際の表示位置、描画結果の世代と版の検査も含める。これらはウィンドウを開かずに実行し、キーやマウスで実際に操作したという確認とは区別する（ADR 0053）。

## 計測、実機とネットワーク

この種類は候補として示し、未実行のままでも `make verify` の完了を止めない。終了フックは音声デバイスを使ったり、確認ウィンドウを開いたりしない。変更が性能や実機の挙動に影響するなら、関係する候補を次のように明示して実行する。

```sh
python3 scripts/verify.py --run spike-draw
python3 scripts/verify.py --run spike-bridge --run spike-render
```

- `spike-isolation`: プラグインの往復の release 計測。隔離を変更した時は S3 の文書の数値も更新する。製品の CLAP 再生の実時間のブロック期限を使う検査もここで release 実行する。通常検査のプラグイン出力の比較は、性能の期限と分ける
- `spike-draw`: Metal の描画と可視判定の実機計測
- `spike-arrange-frame`: ウィンドウ・表示リンク・画面操作を使わず、製品と同じ Metal の描画器でトラックヘッダとタイムラインを描いて読み戻す。倍率 1・2、部分行、縦横のズーム・スクロール、幅の変更、選択、文字、クリップがヘッダへはみ出さないことを検査する。結果は `target/spike-arrange-frame.json`、画像は同じ名前の PNG。実際の画面への表示時刻や入力の遅延の検査とは別
- `spike-piano-frame`: 画面操作なしで製品と同じ Metal の描画器を使う。倍率 1・2、部分行、縦横のスクロールとズーム、幅変更、調の変更を含めて、鍵盤と背景の白黒が固定であること、鍵盤とノートの音高行、ディグリー欄の文字・スケール内外の色・区切り線を GPU へ描いて読み戻す。結果は `target/spike-piano-frame.json`、画像は同じ名前の PNG。実際の画面への表示時刻や入力遅延は測らない
- `spike-app`: 製品のアレンジとピアノロールを実機で描き、メインスレッドを 0.5 秒間ふさいでも両方の描画が続くこと、可視のアクセシビリティ要素を ID で保持することを確認する。アレンジを縦にも動かし、トラックヘッダがタイムラインと同じ数のフレームを描くこと、共有フレームの行位置、双方のアクセシビリティも確認する。小さいプロジェクトの接続確認であり、S1 の大きいシーンの性能測定ではない。結果は `target/spike-app.json`。今回のピアノロールとトラックヘッダの実機確認は未実施
- `spike-history`: 大きいプロジェクトの保存と復元の release 計測
- `spike-input`: 確認ウィンドウでピンチ、触覚、感圧を確認し、終了する。単にウィンドウを閉じたことを機能の確認とはしない
- `spike-engine`: 音声デバイスを使い、10 分間のエンジンの計測をする
- `spike-audio`: 製品の CoreAudio 出力を無音で開き、コールバックと停止・再起動、機器の一覧・通知登録、再生中の計画更新と位置移動を検査する。画面や computer use は使わない。実物の抜き差しや聴感の検査を代用するものではない
- `spike-bridge`: スナップショットと配列の受け渡しを計測する
- `spike-render`: WAV の一括書き出しの時間を release で測る。通常の音声の正しさの検査には時間の閾値を入れない
- `advisories`: ネットワークを使って依存の脆弱性情報を調べる

対象外の項目を列挙したり、見送り理由を書いたりする必要はない。必要な確認を実行できず、結論に制約が残る場合は、その制約だけを最終報告で伝える。記録を残したい場合は `--defer` を任意に使える。例えば CI に触覚の実機がないなら、次のようにする。

```sh
python3 scripts/verify.py --defer spike-input --reason 'CI に触覚を確認できる実機がない。入力の単体テストは別に実行する'
make verify
```

候補の未実行や見送りは検査の合格ではない。明示して実行した検査が失敗した場合は非ゼロで終わり、次の `make verify` でも失敗が残っていることを伝える。修正後に `--run ID` で再実行する。音声、描画、入力やプラグインの性能を変更したなら、機器が使える環境で測る。未解決の不具合の再現は作業の前に `make known-bugs` か該当の無視したテストで行い、修正後は `#[ignore]` を外して通常の検査へ入れる。`make bless` は意図した音の変更の基準を記録する時だけ使い、検査の失敗に合わせて自動で基準を作り直さない。

## 記録と終了フック

結果は `target/verification/report.json` と `report.md`、各検査の出力は同じディレクトリの `<ID>.log` に残る。状態は `passed`、`failed`、`pending`、`running`、`stale`、`not_run`、`deferred`。自動検査は `pending` のまま終えられない。候補の `not_run` は完了を止めず、理由も不要。任意に使う `deferred` には理由を記録する。

記録は、Git が管理するファイルと無視されていない未追跡ファイルの内容、削除、実行属性、変更範囲、ツールの版と設定をハッシュで識別する。同じソースとツールの合格は再利用して、手動の実行と終了フックで同じ検査を重ねて走らせない。ソースやツールが変わると、見送りの理由も含めて無効にするが、候補の理由を再記録する必要はない。依存は Cargo.lock の内容に基づく。リポジトリの外の可変の path 依存や環境を使う検査を追加する時は、その入力も識別に含める。`--force` は同じ状態でも再実行する時に使う。

検査中の別の編集を検出したら、合格として再利用せずに再実行を求める。同時に二つの実行器が記録を書かないようロックする。各検査には実行の期限があり、期限を超えたら Cargo のテストの子も含めて止める。この期限は検査の予算であって、製品の性能の閾値ではない。

Cursor の stop hook は JSON の `status=completed` を読み、同じ実行器を呼ぶ。自動検査の失敗、有効な結果を確認できない場合、明示して実行した計測の失敗、入力の不備があれば、結果を読むよう続きの指示を返す。候補の未実行だけでは続きの指示を返さない。フックがない、または発火を確認できないエージェントでも、AGENTS.md に従って `make verify` を使う。フックのスクリプトの検査と、アプリの実際の終了イベントで発火したことの確認は別である。

## CI と新しい検査

GitHub Actions は `--all --only ID` で同じ定義を使い、通常の検査と追加の自動検査を分けて実行する。実機の操作や性能測定はこの CI の合格に含めない。失敗時も記録とログを保存する。設定があることだけを、GitHub で実際に検査した証拠にしない。

新しい検査は Makefile と verification.json に登録し、変更範囲に応じて選ばれるテストも足す。必要なら CI の分割先も足す。ファジング、互換性の一覧、耐久試験など設計書にある未実装の検査は、現時点で実行できるものとして登録しない。
