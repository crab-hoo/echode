## 確定した指摘

### REA-01 / P1: 通常再生にも総ノート数×ブロック長のイベント領域を確保する

- 区分: PRO-06の修正による回帰。
- 根拠: [playback.rs](../../crates/echode-engine/src/playback.rs)、207行。
- 再現・結果: ループもプラグインもない100ノートの準備で、最大1 / 128 / 512フレームの要求確保量は120,416 / 10,531,876 / 42,012,196バイト。プロジェクト生成は計数の外。
- 原因: 全ノート数×3を最大ブロック長で無条件に倍増し、Event列3本相当と整列の番号列を用意する。各プラグイントラックのsource_events/chased_ons、各Stageのrouted、共有領域にも全曲の容量を複製する。
- 対応・必要な検査: 実際のループ長と区間ごとの需要に基づいて作業領域を再利用する。追跡は同時発音数、配送は各トラックの需要で準備する。通常再生のメモリ量を測る。
- 対応済み: ループに掛かるノートだけを回数ぶん確保する。`audit_rea01_a_loop_free_plan_does_not_scale_events_with_the_block`。


### REA-02 / P1: 新しいヘルパーへ追跡ノートを時刻順で渡さない

- 区分: PRO-05の残余。
- 根拠: [plugins.rs](../../crates/echode-engine/src/plugins.rs)、478行。
- 再現・結果: 長音の途中で楽器を追加し、次の256フレームの44サンプル目に別ノートを開始すると、時刻順を検査する独立CLAPがprocessを拒否し出力0。未来のノートがなければピーク0.17677669で成功。
- 原因: 整列済みの通常イベントの末尾へ時刻0のchased_onsを追加し、入力列が[44,0]になる。ヘルパーもその順番を維持する。
- 対応・必要な検査: 追跡イベントを通常イベントへ時刻順に統合する。同一時刻のオフ・オン順序も維持する。件数だけでなく時間を解釈する楽器で検査する。
- 対応済み: 時刻順に混ぜる。`audit_rea02_chased_notes_merge_before_future_events`。


### REA-03 / P1: 最初の処理より前の二度目の編集で追跡ノートオンを落とす

- 区分: PRO-05の残余。
- 根拠: [plugins.rs](../../crates/echode-engine/src/plugins.rs)、234行。
- 再現・結果: 長音を再生→CLAP追加でreplace→最初のrenderより前に空トラック追加でreplace→render。受信オン数0、failed=false、plugin_failure=None。二度目のreplaceがなければ1。公開再生APIで実行。
- 原因: 保持する全Stageのawaiting_notesをfalseにする。まだ1ブロックも処理していない新規ヘルパーを受信済み扱いする。
- 対応・必要な検査: 保持したStageの未配送状態を保つ。追跡を実際に配送できたときにだけ解除する。複数編集と計画キューの滞留を検査する。
- 対応済み: 保持した段の未配送を消さない。`audit_rea03_two_replacements_before_callback_keep_chase`。


### REA-04 / P1: 同じデバイスの保存状態を変えても既存ヘルパーへ復元しない

- 区分: PRO-03の製品接続の残余。
- 根拠: [playback.rs](../../crates/echode-engine/src/playback.rs)、888行。
- 再現・結果: 同じDevice IDで状態バイト64→128をset_routesとreplaceへ渡した。ピークは0.17677669のまま、期待0.35355338。エラーなし。公開再生APIで実行。
- 原因: 同じチェインはensure_eventsだけで、reconcileも復元も行わない。reconcile時も保持したStageは状態を比較せず、restore_stateはspawn_stage時だけ。OutputStream.replaceは履歴から読み直した状態をこの経路へ渡す。
- 対応・必要な検査: 適用済み状態のIDを保持し、状態だけが変わったデバイスへ制御側から復元する。無関係なヘルパーと長音は保持する。履歴復帰・Undo/Redo・同一CLAPの複数デバイスを音で照合する。
- 対応済み: バイトが変わった段だけ作り直す。`audit_rea04_same_device_state_change_updates_sound`、`audit_rea04_two_devices_keep_their_own_state`。


### REA-05 / P1: dirty通知と実際のstate保存を製品の自動保存へ接続していない

- 区分: PRO-03の未接続部分。
- 根拠: [playback.rs](../../crates/echode-engine/src/playback.rs)、908行。
- 再現・結果: コード確認。save_stateの呼出はhosted_playbackテストにしかなく、製品のengine/audio-io/history/ffi/API/Swiftは呼ばない。poll_noticeも製品チェインから呼ばない。
- 原因: PlaybackControl.serviceは返却資源と計画の再配送だけで、CLAP Dirtyを収集しない。set_device_stateとwrite_objectは個別APIとしてあるが、実際のヘルパーから取得してジャーナルへ確定する経路がない。
- 対応・必要な検査: 制御側でdirtyを収集し、ヘルパーのメインスレッドでsaveし、オブジェクトとモデルのハッシュ更新をジャーナルへ確定する。再読込の音と状態を製品経路で検査する。
- 対応済み: 制御側で保存を依頼し、文書ホストがオブジェクトとジャーナルへ載せる。`audit_rea05_dirty_reaches_durable_product_state`。


### REA-06 / P1: 書き出しの失敗で以前からあった出力ファイルを消す

- 区分: PRO-07の修正による回帰。
- 根拠: [lib.rs](../../crates/echode-cli/src/lib.rs)、213行。
- 再現・結果: 一時パッケージの出力先へ既存内容を置き、正規ポートを持ちprocessを拒否するCLAPで実際のrender_to_wavを実行。Err(process refused)を返した後、出力先はNotFound。
- 原因: File::createで既存出力を先にtruncateし、処理失敗で同じパスをremove_fileする。失敗した新規WAVを残さない対策が、既存の完成品も失わせる。
- 対応・必要な検査: 同じディレクトリの別の一時ファイルへ書き、flushと完成を確認してから置換する。失敗時は今回の一時ファイルだけを消す。既存出力・新規出力・write/finish失敗を検査する。
- 対応済み: 排他的な一時ファイルをリネームで公開する。`audit_rea06_failed_plugin_export_preserves_existing_output`。


### REA-07 / P2: 共有コンテンツへのノート編集で別のリンクの絶対時刻が溢れる

- 区分: PRO-13の残余。
- 根拠: [placement.rs](../../crates/echode-model/src/placement.rs)、115行。
- 再現・結果: 0開始・長さ2の固定窓をMAX-3へリンクし、不変条件Okを確認。元窓のノート長を8へ編集、又は位置1・長さ8を挿入すると、操作はOkのままcheck_invariantsが終端overflowを返す。公開モデルAPIで実行。
- 原因: リンク作成時は全ノートの絶対時刻を検査するが、その後の編集・挿入はlocal+lengthだけを検査する。他の固定窓のorigin+note.start+lengthを再検証しない。
- 対応・必要な検査: 共有Contentを変更する全操作で全参照配置の時刻契約を確定前に検査する。モデルAPIでエラーにし、Sessionのdebug_assertや再読込で初めて拒否しない。
- 対応済み: 変更した中身の全配置を確定前に検査する。`audit_rea07_edit_of_shared_content_checks_all_origins`、`audit_rea07_insert_into_shared_content_checks_all_origins`。


### REA-08 / P2: 読取スレッドのjoinがスキャンの5秒期限を越えて待つ

- 区分: PRO-15の修正の境界漏れ。
- 根拠: [scan.rs](../../crates/echode-plugin-host/src/scan.rs)、230行。
- 再現・結果: 正常な1件のJSONを出して親が終了し、stdout/stderrを継承した子が7秒残る独立プローブは、7.040 / 7.046秒後にOk(1)。SCAN_BUDGETの5秒を越える。
- 原因: 終了・killのあとread_to_stringのスレッドを無期限joinする。派生プロセスに書込端が残るとEOFが来ず、期限のループへ戻れない。子が終了しなければ待機も終わらない。
- 対応・必要な検査: パイプ読取・子と派生プロセスの終了まで一つの期限で管理する。非ブロック読取とpoll、又は中断できる読取とプロセスグループの回収を検討する。
- 対応済み: 一つの期限で poll し、そのプロセスグループだけを回収する。`audit_rea08_descendant_pipe_does_not_extend_deadline`。


### REA-09 / P2: 復旧で使った親ではなく読めない先端のIDを出力に付ける

- 区分: PRO-16の残余。
- 根拠: [host.rs](../../crates/echode-history/src/host.rs)、227行。
- 再現・結果: 監査用パッケージの先端コミットのproject.json blobだけを除いた。recoverは1トラックの親を選んだが、recovered_labelは2トラックを記録した先端IDとseq=1を返した。公開DocumentHost APIで実行。
- 原因: recover/applied_journal_seqはfirst_readable_commitを使う一方、IDはrevisions().next()から無条件に取得する。読める親の選択結果を引き継がない。
- 対応・必要な検査: 復旧時に選んだ基点コミットIDと適用連番を保持し、スナップショットと同じ確定状態からラベルを返す。先端のblob欠損とcommit自体の欠損を両方検査する。
- 対応済み: 読めた親の id を開いたときに保持する。`audit_rea09_export_label_uses_readable_parent`。


### REA-10 / P2: トリム後の波形が鳴る範囲ではなく素材全体を示す

## 検査の適切さと修正順

今の通常回帰は修正前の小さい条件を検査している。ただし、次の軸が欠ける。

1. 件数だけを返すTest Gainではなく、時刻を解釈するCLAPを使う。
2. 1回の編集→1回のcallbackだけでなく、callback間の複数編集・計画の滞留を検査する。
3. 起動時にテストから状態を直接注入するだけでなく、dirty→製品save→ジャーナル→再読込と、同一Deviceの履歴復帰を通す。
4. 短ループを通すだけでなく、通常再生の準備時間・要求メモリをノート数とトラック数を増やして測る。
5. 失敗した新規出力を消すだけでなく、既存出力の保護を確認する。
6. リンク作成の瞬間だけでなく、後から共有中身を変える順序、親へ戻る復旧、派生プロセスのパイプを含む終了条件を検査する。

修正順はREA-06の出力保全とREA-01のメモリ設計、REA-02/03の追跡配送、REA-04/05の状態永続化を先にする。続いてREA-07/08/09の境界契約とREA-10の表示・再生の時間変換をそろえる。意図的な怠慢という証拠はないが、単一ケースの成功を製品の保証へ拡張した検査不足がある。
