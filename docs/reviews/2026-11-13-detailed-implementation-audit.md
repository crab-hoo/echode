## 総評

読んだ層の個々の処理は、前の 2 件の評価どおり丁寧である。
ノートのカーソル、時間換算、制御ソケットの枠と記述子の規則、モデルの検査付きの算術に、誤りは見つからなかった。

弱いのは、**失敗した後の続き方**である。IQA は「読めない」を「無い」に畳む型を挙げた。
今回見つけたのは、その隣の 2 つの型である。

1. **失敗を一度きりの出来事として扱い、後始末の状態を戻さない。**
   確定に失敗したデバイスは「編集中」のまま残り、以後の保存が記録されない（DIA-02）。
   断られた背景の保存は、変更の印ごと消える（DIA-04）。どちらも記録を残さない。
2. **失敗を間隔なしで繰り返す。**
   読めない機器の一覧は、文書ワーカーの周期（毎秒 50 回）で読み直され、同じ警告を書き続ける（DIA-03）。
   記録できないプラグインの保存も、同じ周期で保管物を丸ごと読み直す（DIA-05）。

もう 1 つは、境界の大きさの決め方である。
MCP は、セッションの応答を要求と同じ 1 MiB で読む。応答は要求より長いので、
確定した編集が「失敗、結果は不明」として返る（DIA-01）。

| 観点 | 評価 | 根拠 |
|---|---|---|
| 再生の走査と時間換算 | A | カーソルの配置・前進・引継ぎと、テンポの積分を手で追った。指摘なし |
| 隔離の制御の枠 | A- | 枠・分割・記述子・期限は正しい。通知の取り出しに偏りがある（DIA-10） |
| 失敗した後の状態 | B- | 編集中の印と変更の印が、失敗で正しく戻らない（DIA-02・04） |
| 失敗の繰り返し方 | C+ | 間隔のない再試行が 2 か所。ログも同じ速さで埋まる（DIA-03・05） |
| API の結果の報告 | B- | 確定した編集を失敗と報告する大きさと時間がある（DIA-01） |
| 規模 | B | 1 つのトランザクションの時間が件数の 2 乗で伸びる（DIA-06） |

## 指摘の詳細

### DIA-01 MCP が確定済みの編集を失敗として返す

- **事実**: `mcp.rs` の `exchange`（459 行）は、セッションの応答を `read_line`（419 行）で読む。
  `read_line` は、MCP の利用者からの 1 行と同じ上限 `MAX_REQUEST_LINE`（1 MiB、`serve.rs` 18 行）を使う。
  セッションの側（`serve_connection`）は、応答の長さを制限しない。
  トランザクションの応答は、確定した全アクションである。作った ID が加わるので、要求より長い。
  `note.insert` は 1 件あたり要求 130 バイトに対し応答 271 バイト、`track.add` は 32 バイトに対し 307 バイトだった。
- **再現**: `crates/echode-api/tests/audit.rs` の
  `audit_dia01_a_committed_transaction_with_a_long_reply_is_reported_as_done`（`#[ignore]`）。
  長い名前の `track.add` 200 件（要求は約 1.02 MB）を `echode.actions.transaction` で送る。
  編集は確定し（`history.usage` の Undo は 1 段）、MCP の結果は `isError: true` で、文は
  `Session request failed: MCP message exceeds the single-message size limit. Inspect the project before retrying an edit; its outcome may be unknown.` だった。
- **境目**: 応答が 1 MiB を超えるのは、`note.insert` で約 3,870 件、`track.add` で約 3,415 件からである。
  要求はその時 0.5 MB と 0.1 MB で、上限に遠い。MIDI の取込みを 1 つのトランザクションにまとめる使い方で届く。
- **もう 1 つの経路（時間）**: `backend` は、応答の読取りにも `READ_TIMEOUT`（30 秒）を掛ける。
  編集が 30 秒を超えると、読取りが `EAGAIN` で終わり、同じ「失敗、結果は不明」になる。編集は後で確定する。
  デバッグビルドでは、4,400 件の `note.insert` がこの経路で失敗した（65 秒）。
  リリースでは同じ編集が 1.9 秒である（DIA-06）。長い音声を多く取り込むトランザクションは、リリースでも届き得る。
- **影響**: データは失わない。文は確認を案内しており、嘘ではない。
  ただし、エージェントは失敗と受け取る。確かめずに再送すると、同じ編集が 2 回入る。
  `project.summary` も同じ読取りを通る（1 トラック約 90 バイトで、1 万トラックを超えると届く）。
- **直し方の案**: 応答の読取りは、要求の上限と分ける。同じ利用者のセッションの応答なので、長さは制限しないか、別の大きい上限にする。
  時間は、編集の完了を待つ読取りに固定の 30 秒を使わない（進行中を知らせる行を返すか、期限を要求の種類で分ける）。
  完了条件は上のテストの `#[ignore]` を外して通ること。

### DIA-02 確定に失敗したデバイスが編集中のまま残る

- **事実**: デバイスビューの値の変更（`device.parameter.set`）は、`Waiting::ready`（`device.rs` 184 行）で
  そのデバイスを `editing` に入れる。`editing` の間、そのデバイスの背景の保存は記録を待つ（`saves.rs` の `record`）。
  `editing` から外すのは、`commit`（246 行）が `record_state` に成功した後の 1 行だけである。
  - 取り込み（`capture_state`）が失敗すると、`record_returned`（`worker.rs` 265 行）は `commit` を呼ばずにエラーを返す。
  - 記録（保管物の書込み、ジャーナル）が失敗すると、`commit` は `?` で抜ける。
  - Swift の `record`（`DeviceParameters.swift` 341 行）は、エラーを表示して終わる。確定をやり直さない。
- **再現**: `crates/echode-document/src/device.rs` の
  `audit_dia02_a_failed_commit_does_not_hold_later_background_saves`（`#[ignore]`）。
  保管庫を書けなくして `commit` を失敗させた後、同じデバイスの背景の保存を足すと、`record` はそれを一度も差し出さない。
- **影響**: 確定に失敗したデバイスは、次に確定が成功するか、そのデバイスの記録済みの状態が変わるまで、
  プラグイン自身の保存を記録しない。`Worker` の `Drop` は待っている保存を書かないので、閉じると捨てる。
  出力を開き直すと、ヘルパーは記録済みの状態から作り直される（ADR 0229）。
  起こる場面は、取り込みの 2 秒の期限を超える保存の遅いプラグインと、ディスクの失敗である。
  利用者は確定の時にエラーを 1 回見る。その後の変更が残らないことは、どこにも出ない。
- **直し方の案**: 確定が失敗したら、その編集を終える（`editing` から外す）。
  以後の背景の保存が通常どおり記録され、失敗した変更も次の保存で残る（Undo の段にはならない）。
  取り込みの失敗と記録の失敗の両方を、`record_returned` の 1 か所で扱う。

### DIA-03 読めない機器の一覧を毎周期読み直す

- **事実**: `Session::service`（`session.rs` 668 行）は、機器の変化の番号が見た番号と違う間、`refresh` と `reconcile` を呼ぶ。
  `refresh`（784 行）は、成功した時だけ見た番号を進める。失敗すると番号は違ったままなので、次の `service` がまた読む。
  失敗のたびに `fail`（945 行）が警告を 1 行書く。文書ワーカーは `service` を 20 ms ごとに呼ぶ（準備中は 1 ms）。
- **再現**: `crates/echode-audio-io/src/session_tests.rs` の
  `audit_dia03_a_failed_inventory_read_is_not_retried_on_every_service_turn`（`#[ignore]`）。
  2 回目から失敗する一覧で `service` を 100 回呼ぶと、一覧を 100 回読んだ。
- **IQA-06 との関係**: IQA-06 は、1 台の問い合わせの失敗が一覧の全体を失敗にすると挙げた。
  その機器が在る間、この経路は毎秒 50 回の HAL の問い合わせと、毎秒 50 行の警告を続ける。
- **影響**: 製品のログは 1 MiB で交代し、前の 1 個だけを残す（`echode-log`）。
  1 行を 300 バイトとすると、約 70 秒で 1 個が埋まり、数分で両方が同じ警告だけになる。
  最初の原因や、その前の記録は消える。統合ログ（`os_log`）にも同じ速さで出る。
  一時的な失敗（`coreaudiod` の再起動など）では、直るまでの間だけ起こる。
- **直し方の案**: 失敗した読取りは、間隔を空けてやり直す（倍々で数秒まで）。同じ失敗の警告は、最初と、内容が変わった時だけ書く。
  IQA-06 の修正（読めない機器を外す）と同じ作業で入れる。

### DIA-04 断られた背景の保存が、変更の印を消す

- **事実**: `poll_state_save`（`echode-sandbox` の `session.rs` 238 行）は、保存の応答が拒否
  （`StateRejected`）の時、`dirty_again` を偽にして `None` を返す。記録は書かない。
  拒否には、やり直せば通るものがある。`Refusal::Busy` の説明は「始まらず、何も変えていない。後の要求は成功し得る」である。
  ヘルパーの 2 秒の期限切れ（`TimedOut`）も同じ枝を通る。
  保存の途中に届いた新しい dirty の印も、同じ代入で消える。
- **再現**: 同じ crate の `session_tests.rs` の
  `audit_dia04_a_busy_refusal_keeps_the_plugins_change_waiting_for_a_save`（`#[ignore]`）。
  dirty の通知、保存の要求、`Busy` の拒否の後、100 回ポーリングしても保存は再要求されない。
- **影響**: プラグインの変更は、プラグインがもう一度 dirty を知らせるまで、プロジェクトに入らない。
  知らせなければ、閉じる・開き直す時に失われる。
  `Busy` は、前の要求（窓の表示の 8 秒、保存の 2 秒）が期限を過ぎてもプラグインの中で続いている間に返る。
  保存に 2 秒を超えるプラグインでは、背景の保存は毎回時間切れになり、毎回ここで消える。
- **直し方の案**: 拒否を種類で分ける。`Busy` と期限切れは印を残し、間隔を空けて再要求する。
  プラグインが保存を持たない・断った場合は、最初の 1 回を警告として書き、印を消す。

### DIA-05 記録できない保存を毎周期やり直す

- **事実**: `record_plugin_saves`（`worker.rs` 220 行）は、周期ごとに、待っている保存を `commit_plugin_state` へ渡す。
  失敗した保存は残り、次の周期にまた渡る（`saves.rs` の `record`）。間隔も回数の上限もない。
  `commit_plugin_state`（`host.rs` 260 行）は、最初に `write_object` を呼ぶ。
  同じ名前の保管物が在ると、`stage_object` は中身を全部読んで比べる。ハッシュの計算もやり直す。
  - 文書スレッドが「耐久性が不明」で止まった後（`reply_halted`）は、全ての保存が失敗し続ける。
  - ジャーナルへ書けない間（ディスクが一杯）も同じで、こちらは失敗のたびに警告も書く。
- **計測**（release、この機器）: 既に在る保管物への `write_object` は、1 MiB で 1.3 ms、8 MiB で 9.3 ms、
  32 MiB で 36 ms、128 MiB で 143 ms だった。
  文書ワーカーの周期は 20 ms なので、32 MiB の状態 1 つでワーカーは保存のやり直しだけで埋まる。
  ワーカーは再生・停止・位置移動も運ぶので、止まった文書で音の操作が遅れる。
- **未再現**: 「耐久性が不明」を注入する仕組みがなく、製品の経路では起こしていない。読んで確かめ、費用だけを測った。
- **直し方の案**: 失敗した保存は、間隔を空けてやり直す。文書が編集を断っている間は試さない。
  保管物の確認は、一度書いた名前を覚えて省く（中身は名前で決まる）。

### DIA-06 トランザクションの時間が件数の 2 乗で伸びる

- **計測**（release、この機器、`actions.transaction` を 1 回、空のプロジェクトから）:

  | 件数 | `note.insert`（1 トラックへ） | 件数 | `track.add` |
  |---|---|---|---|
  | 550 | 0.041 秒 | 500 | 0.066 秒 |
  | 1,100 | 0.128 秒 | 1,000 | 0.237 秒 |
  | 2,200 | 0.479 秒 | 2,000 | 0.917 秒 |
  | 4,400 | 1.856 秒 | 4,000 | 3.758 秒 |

  件数が 2 倍で時間は約 4 倍である。デバッグビルドでは 4,400 ノートが 65 秒だった。
- **既知との関係**: [統合表](2026-11-08-open-items-register.md) の E1（モデルの ID 探索が線形）の、API から見た大きさである。
  1 件ごとの費用がプロジェクトの大きさに比例するので、1 つのトランザクションで 2 乗になる。新しい指摘ではない。
- **影響**: 文書スレッドは 1 つなので、この間はほかの編集も Undo も待つ。DIA-01 の時間の経路の入口でもある。
- **案**: E1 の作業の測定項目に、この 2 つの表を足す。どの処理が比例するかは、今回は分けていない。

### DIA-07 保管庫の「既にある」の近道と取下げ

- **事実**: `stage_object`（`objects.rs` 123 行）は、同じ名前の保管物が在って中身が一致すれば、一時ファイルを書かない。
  その段階は、後の `publish` で何も作らず、名前だけを返す。
  `withdraw`（106 行）は、自分の `publish` が名前を作った時に、その名前を消す。
  取込みの段階は別スレッドで動き（ADR 0331）、`publish` と `withdraw` は文書スレッドで動く。
  次の順で、ジャーナルが名指す素材が保管庫から消える。
  1. 編集 A が素材 X を `publish` する（名前を作った）。
  2. 別スレッドの編集 B の段階が、X が在るのを見て、一時ファイルを書かない。
  3. A のジャーナルへの書込みがきれいに失敗し、A が X を `withdraw` する。
  4. B が `publish` する。持っているのは名前だけで、X は無い。B のジャーナルは X を名指す。
- **影響**: 3 の失敗（ディスク）と、同じ中身の取込みが 2 と重なることが要る。窓は 1 と 3 の間で、狭い。
  起これば、次に開いた時にその音声が読めない。
- **未再現**: 順序を固定する仕組みがなく、読んで確かめた。
- **案**: 近道を使った段階も、`publish` の時に名前が在ることを確かめ、無ければ中身を書く（段階が中身を持ち続ける）。
  または、`withdraw` をやめ、参照のない保管物として残す（掃除は ADR 0272 の残り）。

### DIA-08 終了監視の join と、再起動の失敗

- **事実**:
  - `PluginHost::shutdown`（`session.rs` 929 行）は、`closed` を真にした後、`try_wait()?` で抜けることがある。
    その時、`stop_watch` を呼ばない。`Drop` の 2 回目の `shutdown` は `closed` を見てすぐ戻る。
    監視スレッドは、共有領域の中の原子変数を生のポインタで持つ（`WatchSlots`）。
    コメントは「監視を join してから領域を落とす」と書くが、この経路では join されない。
  - `restart`（613 行）は、新しいヘルパーを起動した後の `finish_launch` が失敗すると、そのまま返る。
    `spawn` は同じ失敗で `force_stop` を呼ぶ。`restart` は呼ばないので、準備に失敗したヘルパーが、次の再起動か破棄まで残る。
- **影響**: `waitpid` が失敗するのは、子が別の所で回収された時などで、通常は起こらない。
  その時、監視は終了を既に見て抜けていることが多い。起これば、解放した領域への書込みになる。
  残るヘルパーは、固まったプラグインを抱えた 1 プロセスである。
- **未再現**: 読んで確かめた。
- **案**: `stop_watch` を `Drop` で無条件に呼ぶ。`restart` の `finish_launch` の失敗でも `force_stop` を呼ぶ。

### DIA-09 無関係な編集の Undo が、背景で保存した状態も巻き戻す

- **事実**: Undo は、プロジェクトの版を丸ごと戻す（`echode-actions` の `Session::undo`）。
  背景の保存の取り込み（`absorb_plugin_state`）は、現在の版だけを書き換える。前の版には入れない。
  [ADR 0109](../decisions/0109-placement-bounds-and-plugin-capture.md) は「取り込んだハッシュを、その版へ後から合成しない」と決めている。
- **確かめた結果**（監査中の試行。テストには入れていない）: デバイスのあるプロジェクトで、トラックを 1 つ足し、
  そのデバイスの背景の保存を取り込み、Undo を 1 回行う。トラックが消え、デバイスの状態もハッシュから「なし」へ戻った。
  Redo で両方が戻る。開き直すと Redo の後の状態である。
- **利用者に見える形**: 音符を 1 つ置く。プラグインが自分で状態を変える（読込みの完了、窓を閉じた後の変化）。
  音符を Undo する。プラグインが前の状態へ戻る。状態が「なし」へ戻る時は、ヘルパーが作り直される。
- **判断の確認**: 設計どおりで、誤りではない。ただし [現在の制約](../status.md) は、
  そのデバイス自身の Undo についてだけ書く。無関係な Undo がプラグインを戻すことは、利用者の制約に載っていない。
  聴感と操作に関わるので、このままでよいか、取り込みを前の版へも運ぶかは、ユーザーが決める。
  status.md は上限まで 6 バイトで（PCA-03）、今回は足せない。

### DIA-10 ヘルパーの通知の取り出し

- **事実**: `poll_notice`（`session.rs` 419 行）は、`Dirty`・`PluginRestarted`・`RequestProcess` のうち、
  列の先頭の 1 件だけを取り出す。`poll_state_save` は 1 回に 1 度これを呼び、`Dirty` 以外は捨てる。
  - `RequestProcess` を使う製品のコードはない（停止中もプラグインを処理するため）。それでも列に入り、1 回に 1 件ずつ捨てられる。
  - `Dirty` の前に別の通知が k 件あると、保存の要求は k 回のポーリング（20 ms ずつ）だけ遅れる。
  - 列（`inbox`）に長さの上限はない。
  - `drain` は、相手が送り続ける間は戻らない。`try_recv_tagged` の「1 回の呼出しは 1 枠分まで」の約束が、この輪で外れる。
- **影響**: 今のヘルパーは通知を 20 ms に 1 回へまとめるので、実害は小さい。
  通知の種類を足す時と、ヘルパーの送る速さを変える時に、遅れと列の伸びが出る形である。
- **案**: 使わない通知は `accept` で受けた時に落とす。`poll_state_save` は、列の中の `Dirty` を全部まとめて 1 回にする。

### DIA-11 接続していない間引き

- **事実**: `thin.rs`（489 行）は既定のビルドに入り、`pack_and_thin` などを公開する。製品からの呼出しはない（テストだけ）。
  `rewrite_chain` は残すコミットを新しい ID で書き直し、`repack_reachable` は新しいパック以外のパックと、
  ばらのオブジェクトを全て消す。
  - 書き直した後、`.git/echode-commit-chain`（ADR 0230）の行は、消えた ID を指す。
  - 自動保存のスレッドが同時に書いたばらのオブジェクトは、パックに入らずに消える。
  - パックは全体をメモリに組み立て、件数を `u32` へ切り詰める。
- **影響**: 今は無い。履歴の間引き（PLAN の §6.4）を接続する時に、このまま呼ぶと保存の耐久性の前提を壊す。
- **案**: SPG-10 の Phase 0 のコードと同じく、非既定の feature へ移す。接続の時は、チェーンと自動保存との排他を先に設計する。

### DIA-12 小さい指摘

- **走査キャッシュの畳み込み**: `resolve_cached`（`scan.rs` 812 行）は、キャッシュが読めない時に空を返す。記録は書かない。
  ライブの再生では、プロジェクトの全ての第三者プラグインが無音になる（書出しは拒否する）。
  次のカタログの更新が走査し直して直すが、その間の原因は残らない。IQA の「読めない」を「無い」に畳む型である。
- **停止の失敗の後の印**: `perform_requested` の `Pause`・`Stop` は、`stream.pause()?` と `stream.rewind()?` の失敗で、
  `sync_activity` を呼ばずに抜ける。`playing` は偽で、「再生中」の活動の印だけが次の成功する命令まで残る。
- **MCP の ID の集合**: 旧い版の接続は、使った要求 ID を `legacy_ids` に全て持つ。接続が続く限り増える。
- **空の条件**: `Socket::recv_tagged` の `if !poll_read(..)? && self.incoming.len() < 4 { continue; }` は、
  どちらの枝も輪の先頭へ戻る。意図が読めない。

### DIA-13 確かめて問題がなかった項目

- **ノートのカーソル**: `place` の 2 つの二分探索と区間木の追跡、`advance` が `place` と同じ集合を残すこと、
  `emit` のオンとオフの順（同じ標本ではオフが先）、`take_over` の 3 つの輪（引継ぎ・対応付け・交換）を手で追った。
  失敗する処理は交換の前に終わるので、エラーの時に前のカーソルは壊れない。
- **時間換算**: `from_tempos` の前後 2 方向の積分、負の tick の右端からの換算、`div_round` の検査。
  テンポの上限（999）から、1 tick は 60 flick 以上なので、境界の flick は必ず増える。`with_tempo` の `expect` は届かない。
- **制御ソケット**: 枠の長さ（12〜64 MiB）、`PART` の連結と ID の照合、記述子は 1 読取りに 1 つで次の前に使うこと、
  送信中の読取りと期限、途中で切れた送信の後の `SHUT_WR`、`SO_NOSIGPIPE`、補助データの切詰めで全部を閉じること。
- **共有領域の記録**: `wire.rs` は固定長の記録を欄ごとに復号し、タグ・真偽・対象の範囲外を `None` にする。
- **モデル**: `placement.rs` と `clip_move.rs` の位置の算術は、全て検査付きである。分割の右側の ID は種から導く。
- **API のソケット**: 相手の uid の確認、1 行 1 MiB と改行のない EOF の拒否、ID のない要求を MCP が実行しないこと。
- **文書の完了**: `Ticket` は落とされても 1 回だけ完了する。レーンは投入順に 1 件ずつ動く。
- **ログ**: 待ち行列は 1,024 行で、あふれは数えて次の行に書く。ファイルは 1 MiB で交代する。
- **波形キャッシュ**: 形は見出しのフレーム数から導き、信頼しない段数では確保しない。値は有限で `min <= max` だけを通す。
- **走査**: バンドルごとに別プロセス・別プロセスグループで、期限・標準出力の上限（64 MiB）・親の終了の監視がある。
  キャッシュは改名で置き換える。
- **ヘルパーの状態の入出力**: `state_read` は残りと要求の小さい方だけを写す。ポートの 0 チャンネルは拒否する。
