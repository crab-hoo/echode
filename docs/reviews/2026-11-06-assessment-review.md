# 2026-11-06 課題一覧の精査

## 対象と判定の境界

- 対象: ユーザーから受け取った課題一覧。検証基盤 7 項目、製品 9 項目、今後の機能追加のリスクからなる。
  一覧の優先度は暫定の評価で、既存の監査の P1〜P3 とは別である。
- 精査は `8e50063` で行った。コード、監査の記録、GitHub の API（ワークフローの実行とジョブ、ブランチ保護、Dependabot）と照合した。
- 判定は「事実」「一部事実」「解決済み」「既決」に分けた。既決は、ADR で方針を決めてある項目である。
- 一覧にない 2 件を EXT-01・02 とした。`#[ignore]` の `audit_ext*` テストとして登録し、`make known-bugs` で失敗を確かめられる。
- 実機・音声機器・アプリの操作は使っていない。

## 結論

- gix-pack の脆弱性は、一覧より前に解決していた（[ADR 0270](../decisions/0270-gix-0-90-and-github-advisories.md)）。
- CI の `full` の所要時間は、重複したテストよりも、ランナーの同時実行数による待ちが主因である。
- 検証基盤の保守費用は計測でも裏付けられた。実行の費用で最も大きいのは、Swift の反例のビルドである。
- 長尺音声の配置窓の PCM 複製（EXT-01）と、拒否した取込みの素材が残ること（EXT-02）を再現した。どちらも既存の監査になかった。
- FCA の各項目の状態は、[コード全体の監査](2026-11-03-full-code-audit.md) の一覧とコードの両方に一致した。

- 契約の増え方は鈍っている（6 日で 108 件、3 日で 35 件、4 日で 20 件）。
- 10/30 以降の 75 コミットでは、製品だけが 26 件、製品と基盤の両方が 39 件、基盤だけが 7 件だった。
  製品を変えた 65 件のうち 35 件が `verification.json` も変えた。追加行は製品 30,448 行に対し、基盤 5,641 行だった。
- `verification.json` の 211 KB のうち、契約の登録が約 205 KB を占める。中央値は 1 件 836 バイトである。
- Swift の契約 146 件は、すべて同じ `package_path` と `build_product` を書く。登録の機械的な重複である。
- 手元の全体の段階（2026-11-05、M4）では、通常テストが 110 秒、反例が 2,489 秒だった。
  反例のうち Swift は 1,767 秒（ビルド 233 回、ビルドの延べ 3,799 秒）、Rust は 686 秒だった。
  反例 1 件ごとに EchodeAppTests を作り直すことが、追加の費用の中心である。

### ローカルと CI の結果

- ADR 0269 は、CI の合格を `report.md` に記録せず、節目に `gh run list` で確かめると決めた。
- `make agent-context` は、GitHub で合格していても全体の段階を「合格なし」と表示する。不具合ではないが、読み手が CI を別に確かめる手間は残る。

### ブランチ保護

- `gh api repos/crab-hoo/echode/branches/main` は `protected: false`、ルールセットは空だった。
- 今は `main` へ直接コミットしている。PR と必須の検査を入れると、運用が変わり、約 40 分の `full` を待つことになる。
- 運用を変えずにできるのは、強制プッシュと削除だけを禁じるルールセットである。

### M4 と M1

- ADR 0269 で決めてある。M4 専用の命令は `Illegal instruction` で落ち、反例の検出とは数えない。その時は CI だけ apple-m1 でビルドする。
- 残るのは、SME などの M4 専用の経路を CI では実行できないことである。SME は未実装である。

### EXT-01: 長尺音声の配置窓の PCM 複製

- [clips.rs](../../crates/echode-audio-io/src/clips.rs) の `WindowKey` は、素材・先頭位置・長さである。
  形の違うトリムごとに、窓の PCM を新しく作って持つ。同じ形の配置どうしは共有する。
- 窓を作る前に、素材をファイル全体で読み、チャンネルを分け、レートを変換する。その間は一時的に複数の複製を持つ。
- 短いトリムで素材全体を常駐させない設計（M27-03）は正しい。長いトリムが多いと、素材 1 つ分を超えて増える。
- 再現: `clips::tests::audit_ext01_long_trims_of_one_source_hold_one_copy_of_its_pcm`。
  1 秒のステレオ素材（384,000 バイト）を 8 か所に別のトリムで置くと、準備後に 2,856,000 バイトを持つ（7.4 倍）。
  48 kHz ステレオ 1 時間の素材なら、1 コピーは約 1.38 GB である。
- ADR 0241 は「未準備の配置形状の窓の生成は、引き続き全体準備である」とだけ書いていた。ディスクストリーミングは未実装である（ADR 0108）。
- 2026-11-06 の対応: [ADR 0273](../decisions/0273-shared-source-clip-windows.md) で、窓の和が素材以上の時は共有の面の範囲を読むようにした。
  再現の `#[ignore]` を外した。上の 7.4 倍は修正前の観測として残す。

### EXT-02: 拒否した取込みの素材が残る

- [host.rs](../../crates/echode-history/src/host.rs) は、素材を保管庫へ書いてから配置の編集を行う。配置や同じ要求の後続が失敗しても、素材は消さない。
- 保管庫から消す処理はどこにもない（`objects.rs` の `unreferenced` は判定だけ）。掃除の規則は ADR 0031 で決めてある。
  今のパッケージと、残るすべてのコミットが指すハッシュの和に無いものだけを消す。
- 外部音声の値の検証（NaN・無限大）で拒否した取込みは、何も書かない。残るのは、検証を通った後で失敗した場合である。
- 再現: `audio_import_validation` の `audit_ext02_a_rejected_import_leaves_no_media_in_the_package`。
  無いトラックへの取込みと、後続が失敗するトランザクションの後、文書は変わらないが、素材 2 つと `media/index.json` が残る。
- 2026-11-06 の対応: [ADR 0272](../decisions/0272-staged-import-media.md) で、受理した編集だけが素材を公開するようにした。
  再現の `#[ignore]` を外した。参照の消えた素材の掃除は残る。上の観測は修正前のものとして残す。
