## 判定（監査時点）

実装の方向と変更範囲は妥当であり、この差分について重大な製品不具合は確認していない。
ただし、追加した必須契約は製品コールバックとの接続を検査しておらず、回帰防止の保証が不足する。
OMP-01（P2、未対応）としてテストの補強を勧める。
実画面で JNK-03 が解消したとの判定は行わない。

## OMP-01 の対応（2026-10-24）

- 状態: 対応済み。下記の共通経路と独立した負の対照で、監査時に見逃していた誤りを検出した。

ユーザーの修正・コミット・main への統合の依頼を受け、監査した実装を作業ブランチへ取り込み、提出経路を共通化した。
`CanvasRenderer.submit` を製品コールバックと `CanvasSubmissionTests` が共有する。
検査は画素に加え、描画済みの版と同じ入力への不一致サイズ、新しい版の消費保留、休止の保留、
一致サイズの再試行後の版の消費と休止復帰、ゼロサイズを確認する。
製品側の提出処理を背景だけに戻す変更、版を無条件に消費する変更、休止判断への不一致の引渡しを外す変更を、
必須契約の独立した負の対照へ追加した。
元の参照画像とラベルの境界の負の対照も含め、各変更でコンパイル成功後の期待値の不一致を確認した。
元の失敗の証拠と再現 JSON は監査時点の記録として保持し、修正後の結果は `target/verification/report.md` に記録する。

## OMP-01（P2）: コールバックで旧動作を戻しても新しい必須契約が失敗しない

- 場所: 対象ツリーの `swift/EchodeApp/Tests/EchodeAppTests/ArrangeTests.swift:326–331`。
  製品側の接続は `CanvasRenderer.swift:275–281`、休止判断は同ファイルの `publishLinkState`、版の更新は `:337`。
- 状態: テストの不足。現行製品コードが背景だけを描いているという指摘ではない。
- 影響: 今回直した JNK-03 を製品コールバックへ戻しても、追加した必須契約を含む関連テストが成功する。
  描画部品と判断関数の検査が、実際の提出・再試行・版の消費の検査として扱われている。

`renderOffscreen` は `ArrangePainter.encode` を直接呼び、`CanvasRenderer.metalDisplayLink` を通らない。
テスト末尾は `CanvasDrawablePolicy.resolve` と `canvasLinkPaused` を直接呼び、戻り値だけを確認する。
製品コールバックがその判断を使うか、描画へ進むか、版の消費を保留するかは観測していない。

未変更のコピーに対する関連テストの実行後、次の変更を一つずつ入れて再ビルド・再実行した。
どれもコンパイルし、対象の必須契約と関連テストは失敗しなかった。
故障を検出しないことが監査の証拠であり、これを製品の合格とは扱わない。

1. `staleDrawable = submission.mismatched` の直後で、サイズ不一致なら `present` で背景だけを提出して戻る。
   判断関数は変えず、製品コールバックに旧動作を戻す変更。
2. `if submission.consumesRevision { drawnRevision = revision }` を無条件の代入へ変える。
   サイズ不一致でも描画済みの版を進める変更。
3. `publishLinkState` が `canvasLinkPaused` へ渡す `staleDrawable` を `false` に固定する。
   判断関数は変えず、呼出し側で未解消のサイズ不一致を無視する変更。

登録済みの負の対照は判断関数の戻り値、オフスクリーン側の描画呼出し、ラベルのクリップを変更する。
これらは有用だが、製品コールバックの接続を検査する負の対照にはなっていない。

### 修正の受入条件

- 表示リンクやウィンドウなしで実行できる提出処理を、製品コールバックと検査で共有する。
  または、実際のコールバックと同じ分岐・状態更新を観測できる検査入口を用意する。
- サイズ不一致で背景だけにせず描くこと、版を消費しないこと、休止しないことを、その入口から確認する。
  続く一致サイズの提出で版を消費し、停止中なら休止できることも確認する。
- 特に上記 1 の変更を製品コールバックへ入れた時、必須契約が期待値の不一致で失敗することを確認する。
  補助関数の戻り値だけを変える負の対照で代替しない。
- 追加した経路と負の対照は既存の `drawable-mismatch-ui` と選択のテストへ接続する。

## 実装の評価

- レイヤーのサイズを主スレッドが所有する境界を維持し、取得済み drawable の実寸を描画の座標変換に使っている。
  不一致のフレームにも入力の画素位置で描く方針と整合する。
- 入力の高さを超える行とラベルを切り、拡大した drawable の余白を背景に保つ処理は妥当。
  背景色を Metal・オフスクリーン・レイヤーで共有する変更も局所的である。
- `publishedRevision` と `drawnRevision` の分離は、不一致の再試行で同じジオメトリ通知を繰り返さないために有効。
  `staleDrawable` は、既に描画済みの版と一致する時も再試行を続ける判断になっている。
- ADR、領域別設計、現状、検査選択と診断の更新を伴い、実画面での未確認も明記されている。
  モデルの価格・所要時間・対話履歴は監査していないため、モデル一般の性能や費用対効果は判定しない。

## 検証の範囲と証拠

基準は対象ツリーの `make agent-context` と `make verify`。
最終の `make verify` は、入力・ツールが一致する既存結果と理由付き見送りを再利用した。
記録は対象ツリーの `target/verification/report.md` にある。

監査資料を追加した main 側の検査では、初回に反例用ビルドが空き容量不足（`Errno 28`）で失敗した。
その後、ユーザーによる `target/` の整理と検査が競合し、反例用コピーの欠落によっても失敗した。
ユーザーから整理の完了を確認し、空き容量を確保してから再実行した。
この競合で main 側の一時ログ・専用コピーも削除されたため、永続する再現条件と故障注入の観測結果は上記 JSON に残す。
最終状態は main 側の `target/verification/report.md` に記録する。

独立したコピーで、該当必須契約・休止判断・実 View のサイズ変更の関連テストを実行した。
さらに、アレンジとピアノロールの実描画について、ノートのある文書を使い、
倍率 1・2、端数サイズ、極小サイズ、高さがルーラー以下の条件、縦横で大小が逆のテクスチャーを確認した。
重なる領域の画素の差と、広がった余白の背景以外の画素は確認されなかった。
これは描画部品の確認であり、OMP-01 の未検証部分を補うものではない。

実行スクリプト・追加検査・ログ・差分は main の `target/audits/omp-dual/` に一度保存したが、
上記の整理で削除された。再現の正本は、削除前に作成した上記 JSON とする。
