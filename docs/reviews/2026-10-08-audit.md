- 未解決の不具合の多くは、`audit_<ID>_...` という名前の無視したテストになっている（例: `audit_mod3_children_follow_their_parent`）。`make known-bugs` で失敗を確かめられる。項目を直したら、そのテストの `#[ignore]` を外す。

## 4. 項目

### 4.1 保存と履歴（HIS）

#### HIS-1 自動保存のキャッシュが、トラックのアドレスの値だけで照合している

- 優先度: P0 ／ 種類: 不具合
- 場所: `crates/echode-history/src/autosave.rs` の `save`（176〜187 行）
- 事実: 前回保存したトラックの `Arc` のアドレスを `usize` で覚え、`Arc` 自体は持たない。その版が解放され、新しいトラックが同じアドレスに確保されると、変わったトラックを変わっていないと判断して、古い blob をコミットする。作業ツリーのファイルは正しく書くので、コミットとファイルが食い違う。
- 根拠: 次の手順を 50 回試すと、49 回でコミットがセッションと食い違い、`recover()` も古い状態を返した。スパイクの `store.rs` は `Arc<Track>` を持ったまま `Arc::ptr_eq` で比べており、この問題はない。
- 再現（テストにする。アドレスの再利用は割り当て器しだいなので、20 回繰り返す）:

  ```rust
  let autosave = Autosave::create(&directory).unwrap();
  let mut session = Session::open(Project::new());
  let Action::AddTrack { id: track, .. } = session
      .perform(Command::AddTrack { name: "piano".into() })
      .unwrap()
  else {
      panic!("add track");
  };
  session.perform(Command::InsertNote { track, draft: note(0) }).unwrap();
  autosave.save(Arc::new(session.project().clone())).unwrap().wait().unwrap();
  std::thread::sleep(Duration::from_millis(5)); // the worker drops its snapshot
  session.undo().unwrap();
  session.perform(Command::InsertNote { track, draft: note(8) }).unwrap();
  session.perform(Command::InsertNote { track, draft: note(16) }).unwrap();
  let commit = autosave.save(Arc::new(session.project().clone())).unwrap().wait().unwrap();
  assert_eq!(autosave.load(commit).unwrap(), *session.project());
  ```

- やること: キャッシュに `Arc<Track>` を持ち、`Arc::ptr_eq` で比べる（`store.rs` と同じ）。MOD-1 の ChangeSet ができたら、それで変わったトラックを決める。
- 完了の条件: 上のテストを 20 回繰り返して通る。
- 参照: ADR 0009、`docs/spikes/S4-history.md`

#### HIS-2 ジャーナルを先行書き込みログにする

- 優先度: P0 ／ 種類: 設計
- 場所: `crates/echode-history/src/document.rs` の `write_journal`、`recover`、`read_journal`。`autosave.rs` の `save`（197 行の `write_journal`）
- 事実:
  - コミットのあと、自動保存スレッドがジャーナルを空にして書き直す。スナップショットを渡してからコミットが終わるまでに確定した操作は、次に誰かがジャーナルを書くまでディスクにない。
  - UI 側が古い基点のままジャーナルを書くと、`recover` は「基点が最新のコミットと違うジャーナルは捨てる」ので、その操作を失う。
  - 書き手が 2 つ（UI 側と自動保存スレッド）あるのに、同じ一時ファイル `journal.jsonl.tmp` を使う。
  - 書くたびに全体を書き直し、fsync しない。PLAN §1.0 の「電源断のあとでも復旧」に届かない。
  - ジャーナルが壊れていると、正常なコミットがあっても `recover` 全体が失敗する。先頭行が途中で切れた状態で `journal base: EOF while parsing a string` を確認した。
- やること（ADR の案を書いて確認を得る）:
  - 書き手を 1 つ（HIS-4 のホスト）にし、Undo の単位ごとに連番を付けて追記する。
  - コミットには、取り込んだ最後の連番を残す（コミットメッセージかトレーラー）。
  - 復旧は「読める最新のコミット」に「それより大きい連番の記録」を再生する。末尾の壊れた行は捨てる。コミットが読めなければ親のコミットへ、それも駄目なら作業ツリーへ戻る。
  - 追記は `File::sync_all`（macOS では F_FULLFSYNC になる）で確定させる。数 ms ごとにまとめてよい。圧縮で rename する時は、ディレクトリも fsync する。
  - Undo と Redo は記録として追記する。ファイルを書き直すのは圧縮の時だけにする。
  - 記録の中身は、MOD-1 の結果の操作にする。
- 完了の条件:
  - ジャーナルを任意の位置で切り詰めても `recover` が成功し、切った位置より前に確定した操作がすべて残る（テスト）。
  - コミットの最中に確定した操作が、コミットのあとも復旧で残る（テスト）。
  - ADR 0009 を置き換える ADR がある。
- 依存: HIS-4、MOD-1
- 参照: ADR 0008、ADR 0009、ARCHITECTURE §5、§6.4

#### HIS-3 製品版の自動保存が、毎回すべてを描いて書き直す

- 優先度: P1 ／ 種類: 不具合
- 場所: `autosave.rs` の `save`（162〜163 行の `render` と `write_files`）、`document.rs` の `write_files`
- 事実: 保存のたびに全トラックを JSON にし、全ファイルを書く。ファイルは一時ファイルを経ずに直接上書きする。キューに溜まった保存要求をまとめない。§6.4 の「変更のあったファイルだけを書く」と、S4 の測定の前提に反する。
- 根拠: 1,000 トラック × 100 ノートで、1 トラックを編集した後の保存が 147 ms（S4 のスパイクは 1.3 ms）。1,000 ファイルすべての更新時刻が変わった。
- やること: 変わったトラックだけを描き、ファイルごとに一時ファイルから rename で置き換える。キューには最新の要求を 1 つだけ残す。
- 完了の条件: 同じ条件で、1 トラック編集後の保存が S4 の数値と同程度（数 ms）で、書き換わるのはそのトラックのファイルと `project.json` だけ。
- 依存: HIS-1（MOD-1 があれば、それを使う）
- 参照: ARCHITECTURE §6.4、`docs/spikes/S4-history.md`

#### HIS-4 ドキュメントのホストを作る

- 優先度: P1 ／ 種類: 設計
- 場所: 新規。今は `echode-api` の `ApiSession` が自分の `Session` を持つ。`echode serve`（`crates/echode-cli/src/lib.rs` の `serve_command`）は `read_package` で読み、メモリ上だけを変える。
- 事実: API で行った編集は、プロセスが終わると消える。`recover` も通らない。アプリ、API、MCP、LLM が同じドキュメントを変えるのに、持ち主が決まっていない。
- やること:
  - ドキュメント 1 つにつき 1 つのスレッド（アクター）が `Session` を持ち、コマンドをキューで受ける。
  - 変更のたびにスナップショットを公開する。UI と API は読むだけにする。エンジンへの受け渡しは ENG-3 で決める。
  - ジャーナルの追記（HIS-2）と自動保存の依頼も、このスレッドが行う。
  - `echode serve` とアプリは、このホストを使う。開く時は `recover` を通す。
- 完了の条件: `echode serve` で編集してプロセスを kill しても、次に開くと編集が残る（テスト）。
- 依存: HIS-2 と一緒に設計する
- 参照: ARCHITECTURE §2、§5、§15、ADR 0020

#### HIS-5 gix でできないことを確かめ、履歴の間引きの方式を決める

- 優先度: P2 ／ 種類: 検証・技術選定
- 事実:
  - 自動保存は、変わったトラックごとに loose object を書く。長い作業で、オブジェクトのファイルが増え続ける。
  - gix 0.78 には、パックを作る下位の部品（`gix-pack` の `data::output`）はあるが、gc、repack、prune の高水準の API はない。
  - §6.4 の間引き（直近 24 時間は全部、それ以降は 1 時間ごと、など）には、コミットの鎖を書き換え、届かなくなったオブジェクトを消す処理が要る。§6.4 の定期バックアップは `git bundle` を使う。
  - 利用者の Mac で git コマンドを使えるとは限らない。Command Line Tools がないと、`/usr/bin/git` は導入を促すだけで動かない。
- やること: パック化、届かなくなったオブジェクトの削除、bundle の作成を gix の部品で組めるか、小さく試す。組めなければ、間引きの方式を変える（例えば、自動保存の鎖を一定の期間ごとに切る）。結果を ADR にする。
- 完了の条件: 1 日分の自動保存（例えば 10 秒ごとに 8 時間）を模したリポジトリで、パック化と間引きの後のサイズとファイル数が測ってある。
- 参照: ARCHITECTURE §6.4、PLAN §6（履歴の容量と速度）

#### HIS-6 プラグインの状態とメディアを、内容アドレスの保管庫に置く

- 優先度: P1 ／ 種類: 設計
- 事実: §6.1 は、プラグインの状態を `devices/<id>.state`（バイナリ）としてパッケージに置き、Git の管理下に入れる形にしている。プラグインの状態は MB 単位になることがあり、頻繁に変わるので、Git に入れると履歴が膨らむ。メディアの保管庫（§6.3）のハッシュの方式も決まっていない。
- やること: プラグインの状態も `media/objects/` と同じく、内容のハッシュで名前を付けて Git の外に置き、トラックの JSON からはハッシュで参照する。ハッシュは BLAKE3（`blake3` crate、CC0-1.0 / Apache-2.0）などから選び、保存形式に書く。どの版からも参照されなくなった状態の掃除は、メディアと同じ規則にする。
- 完了の条件: ADR があり、スキーマに状態の参照の形がある。CLAP のホスティングで状態を保存し始める前に済ませる。
- 参照: ARCHITECTURE §6.1、§6.3、§9.4

#### HIS-7 同期フォルダとファイルの協調を、書き込みの経路と一緒に決める

- 優先度: P2 ／ 種類: 設計
- 事実: macOS では、書類のフォルダを iCloud Drive と同期していることがよくある。パッケージの中の `.git` やジャーナルのように、細かいファイルを頻繁に書き換える構成は、同期サービスと相性が悪い（競合の複製や、ストレージの最適化による退避）。§6.2 の外部編集の検出も、Rust から直接書く今の経路では仕組みがない。
- やること: 同期されている場所かどうか（`URLResourceValues` の ubiquitous の属性など）を調べ、扱いを決める（警告する、履歴だけを外に置く、など）。外部編集の検出（FSEvents と、最後に書いた内容のハッシュとの比較）と、NSFileCoordinator を使うかどうかを決める。
- 完了の条件: 同期されている場所での扱いと、外部編集の検出の方式が ADR にある。
- 参照: ARCHITECTURE §6.1、§6.2

#### HIS-8 パッケージの読み込みが、検証していない文字列からファイル名を作る

- 優先度: P1 ／ 種類: 不具合
- 場所: `document.rs` の `read_package`（`header.track_ids` の各要素から `format!("{id}.json")` を作る）
- 事実: `project.json` の `tracks` の文字列を、そのままパスに使う。`../../x` のような値で、`tracks/` の外の `.json` を読みにいく。設計原則 4（入力を信用しない）に反する。
- やること: 先に `Id::parse` で UUID として検証し、検証した ID からファイル名を作る。パッケージの中のシンボリックリンクも辿らない。
- 完了の条件: `tracks` に `../` を含む値を入れたパッケージが、ファイルを読む前にエラーになる（テスト）。
- 参照: ARCHITECTURE §1（原則 4）

### 4.2 ドキュメントモデルと保存形式（MOD）

#### MOD-1 操作の結果を ChangeSet として返し、ジャーナルにも結果を残す

- 優先度: P1 ／ 種類: 設計
- 場所: `crates/echode-actions/src/action.rs` の `Action::apply`、`crates/echode-model`
- 事実:
  - §4.2 は、アクションを 1 つ適用するたびに新しい版と「何が変わったか」の一覧（ChangeSet）ができるとしているが、ChangeSet はない。自動保存はポインタの比較で代用している（HIS-1 の原因）。
  - ジャーナルはコマンド（意図）を残し、復旧時にモデルの処理（スマートクリップの伸縮など）をもう一度走らせる。アプリを更新してスマートクリップの規則が変わると、同じジャーナルから別のプロジェクトができる。
  - PLAN §5 の「変更をプロパティ単位の操作として記録する」（セマンティック・マージと共同編集の布石）になっていない。
- やること（ADR の案を書いて確認を得る）:
  - `apply` は、新しい `Project` と、変わったオブジェクトとその値の一覧を返す。粒度はオブジェクトとプロパティにする（例: クリップ X の start と length、ノート Y の追加、トラック Z の削除）。
  - ジャーナルには、コマンドに加えてこの結果を残す。復旧は結果を当てるだけにし、モデルの規則を再実行しない。
  - UI の更新、エンジンの差分、自動保存（HIS-3）、履歴の要約（§6.5）は、この一覧を使う。
- 完了の条件: すべてのアクションで、「結果を前の版に当てると次の版になる」ことと「結果を逆に当てると前の版に戻る」ことを、DEV-5 のランダムな操作列で確かめる。
- 依存: MOD-2、MOD-4 と同時に形を決める
- 参照: ARCHITECTURE §4.2、§6.5、§6.7、PLAN §5（リアルタイム共同編集）

#### MOD-2 クリップの中身と配置を分ける

- 優先度: P1 ／ 種類: 設計
- 場所: `crates/echode-model/src/model.rs` の `Clip`、`Track`
- 事実: クリップは、位置とノートを 1 つの値で持つ。PLAN §5 は、クリップランチャーのために「クリップを配置と切り離して持つ」、テイクのために「クリップが複数のテイクを参照できるようにしておく」としている。§4.7 のリンクした複製も、中身を共有する形が要る。
- やること: 中身（ノート列、オーディオの参照、テイクの一覧）と、配置（レーン上の位置と範囲、中身の ID）を別のオブジェクトにする。レーンは今はタイムライン 1 本だけでよい。保存形式にも、この形を入れる。配置には、Phase 1 のクリップのゲインとフェードも持たせる。今エンジンがすべてのオーディオクリップの端に固定でかけている 5 ms のフェード（`voice.rs` の `edge_gain`）は、その既定値としてモデルに移す（打楽器の立ち上がりが丸まるので、0 も選べるようにする）。
- 完了の条件: ADR があり、スキーマとモデルが「配置から中身への参照」を持つ。中身を共有する 2 つの配置で、片方の編集がもう片方に見えるテストがある。
- 依存: MOD-1、MOD-4
- 参照: PLAN §5、ARCHITECTURE §4.1、§4.7

#### MOD-3 フォルダの親子と並び順が食い違える

- 優先度: P1 ／ 種類: 不具合・設計
- 場所: `model.rs` の `set_parent`（246〜264 行）、`validate_forest`（454〜468 行）、`try_assemble`。`project.json` の `tracks` 配列
- 事実: `set_parent` は配列の位置を変えないので、子が親より前に並ぶ。読み込みも並びを検査しない。[A, a1, B] で A の親を B にすると「A（親 B）、a1（親 A）、B」の順になり、保存と読み込みも通った。§4.3 と PLAN §5 は、並び順を分数インデックスで持つとしているが、今は配列の順番で持つ。
- やること: 親ごとに、兄弟の並びのキー（分数インデックス）を持つ。平らな並び（アレンジ画面の順）は木から作る。分数インデックスの実装は、`fractional_index` crate（MIT）などを AGENTS.md の規則どおりに先に調べる。
- 完了の条件: どの `set_parent` の後も「子は親の直後に連続して並ぶ」ことを、MOD-11 の不変条件と DEV-5 で確かめる。並べ替えで変わるのが、動かしたトラックのキーだけになる。
- 参照: ARCHITECTURE §4.3、§8.4、ADR 0017

#### MOD-4 ノートの基準点と見える範囲を分け、ノートを並べて持つ

- 優先度: P1 ／ 種類: 設計
- 場所: `model.rs` の `refit_auto`（725〜762 行）、`push_note`、`resize_clip`
- 事実:
  - ノートはクリップの開始からの相対位置なので、自動クリップが前に伸びると全ノートの値が変わる。1 小節目に 8 ノートある時に前の小節へ 1 ノート足すと、トラックのファイルで 11 行が変わった。§6.2 の「1 ノートの編集が 1 行の差分」が崩れる。
  - クリップの中のノートは追加した順で、並んでいない。S1 の描画の二分探索も、ENG-1 のカーソルも、並んでいることを前提にできない。
- やること: クリップに、ノートの基準点（origin）と、見える範囲（start、length）を別に持たせる。伸縮は範囲だけを、移動は基準点と範囲を変える。ノートは（開始、音高、ID）の順に保ち、保存もこの順にする。
- 完了の条件: 自動クリップが伸びても既存のノートの行が変わらないことを、保存形式のスナップショットテスト（MOD-10）で確かめる。ノートの並びを MOD-11 の不変条件で検査する。
- 依存: MOD-2
- 参照: ARCHITECTURE §4.5、§6.2

#### MOD-5 クリップの範囲の外のノートが鳴る

- 優先度: P1 ／ 種類: 不具合
- 場所: `model.rs` の `resize_clip`（667〜695 行）、`crates/echode-engine/src/sequence.rs` の `schedule`
- 事実: クリップの範囲を変えても、範囲外のノートは残る。スケジューラはクリップの範囲を見ない。1 拍目にノートを置いてから、クリップを 3 拍目からの 2 拍に縮めても、1 拍目でノートオンが出た。
- やること: 「範囲の外のノートは鳴らさない。範囲をまたぐノートは、範囲の終わりでノートオフを打つ」といった規則をモデルで決める。ENG-1 の実行計画を作る時に、クリップの範囲で切る。
- 完了の条件: 上の場合にノートオンが出ないテストと、範囲の終わりでノートオフが出るテストがある。
- 参照: ARCHITECTURE §4.5

#### MOD-6 スマートクリップの結合が、ノートの置き始めで変わる

- 優先度: P2 ／ 種類: 不具合
- 場所: `model.rs` の `insert_note`、`place_inside`（470〜517 行）
- 事実: 0 小節目と 2 小節目（4/4）に自動クリップがある時、0 小節目の中から始まって 2 小節目に届くノートは `Overlap` エラーになる。同じ終点で 1 小節目から始まるノートは、2 つのクリップを 1 つに結合する。
- やること: 自動クリップの中に置く場合も、ノートが触れる自動クリップをすべて集めて結合する（`place_outside` と同じ規則）。MOD-4 と一緒に直してよい。
- 完了の条件: 上の 2 つの場合が、同じ結果（1 つのクリップ）になるテストがある。
- 参照: ARCHITECTURE §4.5

#### MOD-7 拍子を 1 つしか持てず、一様な小節長を前提にしている

- 優先度: P2 ／ 種類: 設計
- 場所: `model.rs` の `with_meter`（150〜160 行）、`occupied_bars`、`clip_bars`
- 事実: 小節の計算が `div_euclid(bar)` に固定され、クリップがあると拍子を変えられない。Phase 2 で拍子の変化を入れる時に、スマートクリップの計算を作り直すことになる。
- やること: 小節の境界を返す「小節の格子」（今は区間が 1 つだけの拍子マップ）を挟み、スマートクリップはそれだけを使う。拍子を変えたら自動クリップを合わせ直し、拒否しない。
- 完了の条件: `occupied_bars` などが小節の格子を通る。クリップのあるプロジェクトで拍子を変えても拒否されない。
- 参照: ARCHITECTURE §4.4、§4.5

#### MOD-8 パラメータのモデルを作り、フェーダーもパラメータにする

- 優先度: P1 ／ 種類: 設計
- 場所: 新規。今はモデルに音量、パン、ミュート、ソロがなく、`echode-engine` の `TrackFader` だけがある。
- 事実: Phase 1 で音量、パン、ミュート、ソロを保存し、Phase 2 以降でオートメーション、MIDI の割り当て、コントロールサーフェス、MCP がそれを動かす。§4.6 は `track/<id>/device/<id>/param/<id>` の安定したアドレスを予定している。フェーダーを特別なフィールドにすると、オートメーションと MCP で別の経路が要る。
- やること: パラメータ（ID、範囲、既定値、ベース値）をモデルに置き、トラックのフェーダーもその 1 つとしてアドレスを持たせる。変更はアクション（例えば `param.set`）で行う。
- 完了の条件: ADR があり、フェーダーの値をパラメータとして保存でき、Undo でき、API から操作できる。
- 参照: ARCHITECTURE §4.6、§4.7、PLAN §5（コントロールサーフェス）

#### MOD-9 ノートの表現の形式を、スキーマを固める前に決める

- 優先度: P1 ／ 種類: 設計
- 場所: `model.rs` の `Note`、トラックの JSON
- 事実: ベロシティは 0〜127 の `u8`。CLAP のベロシティは 0〜1 の実数で、MIDI 2.0 は 16 ビット。Phase 3 の MPE（ノートごとの表情の曲線）、Phase 4 のアーティキュレーション、リリースベロシティの置き場所もない。スキーマ 1 に後から足すと、マイグレーションが要る。
- やること: ベロシティの精度、リリースベロシティ、ノートごとの表情の曲線の置き場所、アーティキュレーションの参照を決める。表情の曲線は、「1 ノート 1 行」を崩さないように、ノート ID で参照する別の配列に置くなどの形を選ぶ。今は使わない項目も、保存形式に予約しておく。
- 完了の条件: ADR があり、スキーマにこれらの置き場所がある。
- 参照: ARCHITECTURE §4.1、§13.5、§14

#### MOD-10 スキーマのマイグレーションの仕組みと、保存形式のスナップショットテスト

- 優先度: P1 ／ 種類: 整理
- 場所: `document.rs` の `parse_header`、`parse_track`（`schema != 1` でエラーにする）、`render`、`render_track`、`json_string`
- 事実: スキーマの版を見て拒否するだけで、移行の仕組みがない。JSON は手で組み立てているので、出力の形が変わってもテストが気づかない。`deny_unknown_fields` なので、項目を足すたびに古いアプリでは開けなくなる（それ自体は意図どおりでよいが、方針として書いておく）。
- やること:
  - 古い版を読んで今の版に直す関数を、版ごとに並べる（`serde_json::Value` の上で行う）。各版の見本ファイルを、テスト用に残す。
  - 出力の形を、`insta`（Apache-2.0）などのスナップショットテストで固定する。保存形式を変える時は、スナップショットの差分を見て意図を確かめる。
  - 各行の値は serde で書き、改行の位置だけを手で決める。エスケープを手書きしない。
- 完了の条件: 版 1 の見本ファイルを読むテストと、出力のスナップショットのテストがある。
- 参照: ARCHITECTURE §6.2

#### MOD-11 モデルの不変条件を 1 つの関数にまとめる

- 優先度: P1 ／ 種類: 整理
- 場所: `crates/echode-model/src/model.rs`
- 事実: 不変条件（ID が一意、同じトラックのクリップが重ならない、自動クリップがノートに合っている、子は親の直後に並ぶ、ノートが並んでいる、など）が、あちこちの関数に散っている。MOD-3 と MOD-6 は、まとめて検査していれば捕まった。
- やること: `Project::check_invariants()` を作り、`try_assemble` の最後と、デバッグビルドでのすべての `apply` の後と、DEV-5 のテストで呼ぶ。不変条件の一覧を `echode-model` の crate の文書に書く。
- 完了の条件: 関数と一覧があり、DEV-5 がそれを使う。
- 参照: ARCHITECTURE §16

#### MOD-12 Undo のメモリと編集の計算量を測る

- 優先度: P2 ／ 種類: 検証
- 場所: `model.rs` の `write_track`、`id_in_use`、`crates/echode-actions/src/session.rs`
- 事実: 編集のたびに、トラック全体（全クリップと全ノート）を複製する。Undo は段数の上限なしに版を積む。ADR 0007 は「重いと分かってから imbl に替える」としているが、それを判断するベンチがない。`id_in_use` はプロジェクトの全ノートを走査する。1 つのクリップに順にノートを足すと、1 回あたり 2,000 ノートで平均 10 µs、8,000 ノートで平均 31 µs と、ノート数に比例して遅くなった。
- やること: 100 トラック × 1,000 ノートで 1 万回のランダムな編集を流し、メモリと時間を測るベンチを置く。まずクリップ（MOD-2 の中身）の単位で `Arc` を共有し、それで足りなければ imbl（MPL-2.0）を測る。ID から位置を引く索引も、同じ時に決める。
- 完了の条件: ベンチの結果が、ADR 0007 の判断の材料として記録されている。
- 参照: ADR 0007、ADR 0008

#### MOD-13 ドラッグのような操作を、FFI 越しに使える形で表す

- 優先度: P2 ／ 種類: 設計
- 場所: `crates/echode-actions/src/session.rs` の `Session::transaction`
- 事実: トランザクションをクロージャで表すので、UI のイベントをまたいで続く操作（数秒のドラッグ）を表せない。Swift から呼ぶ時も、クロージャは渡しにくい。また、失敗した時に戻すため、トランザクションを始めるたびに Redo の積み（`redo` と `journal_redo`）を丸ごと複製している。
- やること: `begin`、途中の更新（ジャーナルに残さないプレビュー）、`commit`、`cancel` の API にする。ドラッグの途中の版は UI に見せるが、確定するまで Undo とジャーナルに入れない。Redo の積みは `commit` の時に消すことにし、始める時の複製をやめる。
- 完了の条件: 途中で `cancel` すると操作前に戻り、`commit` すると 1 つの Undo の単位になるテストがある。
- 参照: ARCHITECTURE §5（トランザクション）

#### MOD-14 テンポのランプの式と、決定的な数学関数を決める

- 優先度: P2 ／ 種類: 設計
- 場所: `crates/echode-model/src/time.rs`
- 事実: 一定のテンポは、整数の有理数で正確に変換できる。§4.4 の「直線的なテンポ変化」は、閉じた式に対数か平方根が入るので、整数では表せない。原則 5 の「時間は整数で持つ。丸め誤差を持ち込まない」は、ランプでは成り立たなくなる。
- やること: ランプの定義（tick に対して直線か、時間に対して直線か）と、丸める位置（flick に 1 回だけ丸める）を決める。浮動小数点の計算は `libm` crate（MIT）で行い、OS の数学ライブラリの違いに左右されないようにする（ENG-9）。
- 完了の条件: ADR がある。
- 参照: ARCHITECTURE §1（原則 5）、§4.4

### 4.3 エンジン（ENG）

#### ENG-1 実行計画を制御スレッドで作り、オーディオスレッドはモデルに触れない

- 優先度: P1 ／ 種類: 設計（性能の不具合を含む）
- 場所: `crates/echode-engine/src/sequence.rs` の `schedule`（45〜97 行）、`crates/echode-model/src/time.rs` の `integrate`、`tempo_covering`（267〜305 行）
- 事実:
  - `schedule` は毎ブロック、全トラックの全ノートについて、tick からサンプルへの変換を 2 回ずつ行う。変換はテンポマップを先頭から線形に辿り、区間ごとに辿り直すので、テンポの点の数の 2 乗に比例する。
  - オーディオスレッドが、`Arc<Track>` などモデルの型を直接読む形になっている。
  - オーディオクリップも同じ形で、`voice.rs` の `render_audio_clips` は、サンプルごとにすべてのクリップを調べる。
- 根拠: 128 フレーム・48 kHz のブロック 1 つあたり、100 トラックで 1 万ノートなら 311 µs、10 万ノートなら 3,117 µs かかった。PLAN §1.0 の基準はエンジン全体で 266.7 µs で、ブロックの長さは 2,667 µs。テンポの点が 64 あると、1 万ノートで 809 µs。
- やること:
  - スナップショットの公開時（テンポ、サンプルレート、ループの変更時も）に、制御スレッドがトラックごとに「サンプル位置で並べたノートの開始と終了」の配列を作る。クリップの範囲（MOD-5）もここで切る。
  - オーディオスレッドはカーソルを進めるだけにし、シークとループの戻りは二分探索にする。
  - テンポマップは、各点までの累積 flick を前もって計算し、二分探索で引く。
  - オーディオスレッドで動くコードは、モデルの型に依存しない場所に置く。clippy の禁止リスト（`disallowed-methods`、`disallowed-types`）は crate の単位で効くので、`Mutex`、`Vec::push`、`Box::new` などを禁じたい場合は専用の crate にする。crate は、その機能に着手した時に作る（空の crate を先に作らない）。
- 完了の条件: 1 ブロックの処理時間が、プロジェクト全体のノート数ではなく、そのブロックで起きるイベントの数とトラックの数に比例する（ベンチ）。10 万ノートで、266.7 µs を十分に下回る。
- 参照: ARCHITECTURE §7.2、ADR 0010、PLAN §1.0（音声処理の性能）

#### ENG-2 ブロックの切り方で音が変わる処理を直し、確かめるテストを置く

- 優先度: P1 ／ 種類: 不具合
- 場所: `sequence.rs` の `render_metronome`、`write_click`（148〜204 行）。`crates/echode-engine/src/voice.rs` の `fade_loop_seam`（93〜121 行）。`crates/echode-engine/src/render.rs` の `BLOCK_FRAMES`（64 に固定）
- 事実:
  - クリックは鳴り始めのブロックでしか書かず、続きを次のブロックで書かない。
  - ループの継ぎ目のフェードは、同じブロックの中で span が 2 つに分かれた時だけかかり、長さも span の長さで切られる。
- 根拠:
  - 5 ms のクリック（240 サンプル）が、64 フレームずつ描くと 64 サンプルで途切れ、-0.166 から 0 への段差ができた。
  - 1 拍のループ（120 BPM・48 kHz で 24,000 サンプル。64 × 375）を 64 フレームで回すと、フェードしたサンプルは 0。512 フレームでは 302、ブロックの途中で戻る長さ（24,032 サンプル）では 62。設計では約 478。
- 今の不具合の再現:

  ```rust
  fn span(start: i64, frames: u32) -> PlayedSpan {
      PlayedSpan { start_sample: start, frames, block_offset: 0, release_at: None }
  }

  // Metronome: one 512-frame span and eight 64-frame spans must match.
  let tempo = TempoMap::new(Tempo::quarters_per_minute(120).unwrap());
  let mut whole = vec![0.0f32; 512];
  render_metronome(&[span(0, 512)], &tempo, Meter::four_four(), 48_000, &mut whole).unwrap();
  let mut split = vec![0.0f32; 512];
  for block in 0..8usize {
      let at = block * 64;
      render_metronome(&[span(at as i64, 64)], &tempo, Meter::four_four(), 48_000, &mut split[at..at + 64]).unwrap();
  }
  assert_eq!(whole, split); // fails today

  // Loop seam: a 24,000-sample loop played in 64-frame blocks must be faded.
  let mut transport = Transport::new(48_000, tempo.clone()).unwrap();
  transport.set_loop(Some((Tick::new(0), Tick::quarters(1).unwrap()))).unwrap();
  transport.play();
  let mut spans = [span(0, 0); 4];
  let mut faded = 0;
  for _ in 0..(30_000 / 64) {
      let count = transport.pull(64, &mut spans).unwrap();
      let mut out = [1.0f32; 64];
      fade_loop_seam(&spans[..count], seam_fade_frames(48_000), &mut out).unwrap();
      faded += out.iter().filter(|sample| **sample < 1.0).count();
  }
  assert!(faded > 0); // 0 today
  ```

- やること:
  - ゲインとクリックを、プロジェクト上のサンプル位置から決める（ループの端までの距離と、拍の位置。span の前に鳴り始めて、まだ続いているクリックも含める）。
  - エンジンの処理を 1 つにし、それを呼ぶドライバを 2 つにする（デバイスのコールバックと、オフラインのループ）。オフラインの描き出しは、ブロック長を引数で受ける。
  - ブロック長 1、7、64、512 で同じプロジェクトを描き、ビット単位で一致することを確かめるテストを置く（メトロノーム、ループ、テスト用シンセ、オーディオクリップ）。
- 完了の条件: 上のテストが通る。これは、ライブとプレビュー用キャッシュの音の一致（§7.8）の前提になる。
- 参照: ADR 0010、ADR 0011、ARCHITECTURE §7.5、§7.8

#### ENG-3 オーディオスレッドへの受け渡しと、古いデータの解放を決める

- 優先度: P1 ／ 種類: 設計
- 事実: §7.2 は「ロックなしでオーディオスレッドに渡して差し替える」「古い実行計画の解放は制御スレッドで行う」としているが、仕組みがない。参照カウントの最後の解放がオーディオスレッドで起きると、メモリの解放を禁じる規則に反する。
- やること: 書き手と読み手が 1 つずつのキュー（`rtrb`、MIT OR Apache-2.0）を 2 本使う。1 本で新しい実行計画とパラメータの変更を渡し、もう 1 本で古い計画を制御スレッドへ返して、そこで解放する。オーディオスレッドでは `Arc` を最後に落とさない。
- 完了の条件: 計画を 1 万回差し替えても、オーディオスレッドでの確保と解放が 0 であることを、ENG-12 の検査で確かめる。
- 参照: ARCHITECTURE §1（原則 1）、§7.2

#### ENG-4 エンジン内部のイベントを CLAP のイベントの形に合わせる

- 優先度: P1 ／ 種類: 設計
- 場所: `sequence.rs` の `MidiEvent`、`MidiKind`
- 事実: 今のイベントはノートの開始と終了だけで、ベロシティは `u8`、トラックとノートの ID を 16 バイトずつ持つ。CLAP が主な形式で、内蔵デバイスも「CLAP と同じ考え方」（§10）にする。パラメータの値、変調、ノートの表情、トランスポートの情報も、同じ列で流す必要がある。
- やること: ブロックごとのイベント列を、CLAP のイベント（note on、note off、choke、note expression、param value、param mod、transport）に対応する型にする。ノートの識別は CLAP の note_id のような小さな整数にし、モデルの ID との対応は実行計画が持つ。
- 完了の条件: ADR があり、テスト用シンセとプラグインのホストが同じイベント列を受ける。
- 依存: ENG-1
- 参照: ARCHITECTURE §4.6、§9.3、§10

#### ENG-6 チャンネルとバスの形を決める

#### ENG-7 プラグインの処理を「依頼して、後で受け取る」形にする

- 優先度: P1 ／ 種類: 設計
- 事実: プラグインは別プロセスで動くので、エンジンが 1 つずつ同期的に往復すると、往復の時間が足し算になる。例えば 50 本のチェインで 1 本あたり 20 µs なら 1 ms で、64 フレームの予算 1.33 ms の大半になる。並列にする手段は、エンジンのワーカーよりも、複数のヘルパーのプロセスに同時に依頼することにある。
- やること: グラフのノードの処理を「依頼（待たない）」と「受け取り（締め切りまで待つ）」に分け、スケジューラは入力のそろったヘルパーのノードをすべて依頼してから待つ。同じヘルパーで続くノードは、まとめて 1 往復にする（PLAN §6）。
- 完了の条件: ADR があり、ヘルパーを 2 つ並べたテストで、往復の合計時間が 1 つ分に近い。
- 依存: PLG-3、PLG-4
- 参照: ARCHITECTURE §7.1、§7.2、§9.3、ADR 0003

#### ENG-8 サンプルレート変換を、ディスクスレッドで行う

- 優先度: P2 ／ 種類: 設計
- 場所: `crates/echode-engine/src/resample.rs`、ADR 0014
- 事実: `resample_into` は、呼ぶたびに rubato の変換器を作り、出力を確保して、クリップ全体を一度に変換する。§7.5 の「オーディオスレッドで状態を持ってブロックごとに変換する」使い方には使えない。一方で §7.5 は、ディスクスレッドがクリップごとの先読みバッファを満たし、オーディオスレッドはそこから読むだけ、ともしている。
- やること: 変換は、ディスクスレッドが先読みバッファを満たす時に行う。こうすると、ADR 0014 で「オーディオスレッドの規則を守れないのでオフラインでだけ選べる」とした実装も、再生に使える。比率が途中で変わる場合（バリスピード）も、テンポマップから先の比率が分かるので、同じ形で先読みできる。
- 完了の条件: ADR 0014 の該当部分を更新する ADR がある。
- 参照: ARCHITECTURE §7.5、ADR 0014、PLAN §2.1

#### ENG-9 浮動小数点の結果を、OS の版によらず同じにする

- 優先度: P2 ／ 種類: 設計
- 場所: `sequence.rs` の `click_sample`（`exp`、`cos`）、`mix.rs` の `pan_gains`（`cos`、`sin`）
- 事実: Rust の `f32::exp` や `cos` は、OS の数学ライブラリを呼ぶ。macOS を更新すると最下位ビットが変わる可能性があり、そうなるとビット単位のゴールデンテストとプレビュー用キャッシュの鍵が、OS の版に依存する。テスト用シンセの wavesynth は `libm` crate を使っている。
- やること: 音を決める計算は `libm` crate で行うか、表を前もって作る。依存ライブラリ（rubato の係数の計算など）が OS の数学ライブラリを使う場合は、キャッシュの鍵に macOS の版を含める。足し算の順番も固定する（並列にしても、足す順を変えない）。
- 完了の条件: 方針が ADR か ARCHITECTURE §7.8 に書いてある。
- 参照: ARCHITECTURE §7.8、§16（ゴールデンテスト）

#### ENG-10 オフラインの書き出しが、曲全体のノート数に比例して遅くなる

- 優先度: P2 ／ 種類: 不具合
- 場所: `render.rs` の `render_offline`（78〜89 行）、`synth.rs` の `mix_synth`（249〜255 行）
- 事実: トラックのノートの数だけ声を作り、毎サンプル、すべての声を回す。
- 根拠: 同じ 10 秒（鳴るのは 80 ノート）を書き出すのに、曲全体が 80 ノートなら 0.11 秒、1,000 ノートで 1.19 秒、4,000 ノートで 4.71 秒かかった。
- やること: 最大の同時発音数（ノートの区間の重なりの最大）だけ声を用意し、鳴っている声だけを回す。同時発音数は、ENG-1 の実行計画を作る時に数えられる。
- 完了の条件: 鳴るノートが同じなら、曲全体のノート数によらず、書き出しの時間がほぼ同じ（ベンチ）。

#### ENG-11 S2 のワーカーを、Apple が勧める設定で測り直す

- 優先度: P1 ／ 種類: 検証
- 場所: `crates/echode-engine/src/graph.rs` の `worker_main`（212〜232 行）、ADR 0003、`docs/spikes/S2-engine.md`

#### ENG-12 リアルタイムの規則を rtsan で検出し、例外を AGENTS.md に書く

- 優先度: P1 ／ 種類: 整理
- 場所: `crates/echode-engine/src/realtime.rs`、`AGENTS.md`
- 事実:
  - AGENTS.md は、ロックやシステムコールでの待機もデバッグビルドで検出するとしているが、検出しているのはメモリの確保だけ。
  - ライブラリの crate が `#[global_allocator]` を定義しているので、リンクしたすべてのバイナリの割り当て器が置き換わり、ほかの割り当て器と共存できない。違反すると、メッセージなしで abort する。
  - プラグインとの往復は、締め切りまでオーディオスレッドが待つ設計（§9.3。S3 の `os_sync_wait_on_address_with_timeout`）。AGENTS.md の「システムコールによる待機をしない」と字面が食い違う。

  - 確保の検出を残すなら、`global_allocator` はバイナリかテストの側で設定する。
  - AGENTS.md に「締め切りを持つ、プラグインのヘルパーとの往復の待ちだけは許す」と書く（ユーザーの確認を得る）。
- 完了の条件: `make check` か専用のターゲット（例えば `make rtsan`）で、オーディオスレッドの関数を rtsan の下で動かすテストがある。
- 参照: AGENTS.md、ARCHITECTURE §1、§16

#### ENG-13 ミックスの加算の精度と、フェーダーの補間

  - `crates/echode-plugin-host/src/watch.rs`: CoreFoundation（7 関数と 2 つの静的変数）、FSEvents（6 関数）、`FSEventStreamContext`
  - `crates/echode-engine/src/graph.rs`: `os_workgroup_join`、`os_workgroup_leave`、`pthread_set_qos_class_self_np`、`os_workgroup_join_token_s`
  - `crates/echode-engine/src/wait.rs` と `crates/echode-sandbox/src/sync.rs`: `os_sync_wait_on_address` の系統を 2 か所で別々に宣言し、errno の値も手で書いている
  - `crates/echode-draw/src/ffi.rs`（Swift へ書き出す関数）と `spikes/draw/CEchodeDraw/include/echode_draw.h`: C のヘッダを手で書き、`Instance` の形を Rust、C、Metal のシェーダーの 3 か所で持つ
- 事実（2026-10-08 に macOS 27 の SDK と突き合わせた）:
  - 定数（FourCC 11 個、FSEvents と `os_sync` のフラグ、時計の ID、QoS の値、errno）と、構造体の大きさとフィールドの位置は、すべて SDK と一致した。SDK のヘッダを読み込む C のプログラム（`/tmp/echode-review/ffi_check.c`）で値を出して比べた。
  - 使っている関数は、すべて公開ヘッダにある（非公開の API は使っていない）。
  - `Instance` は、Rust、C、Metal で 32 バイトにそろっている。Rust 側に大きさの検査がある。
  - 一方で、宣言を手で書くと、ヘッダにある非推奨の印、使える OS の版、CF の参照の所有の規則が消える。PLG-9 の 3 つの不具合（非推奨の API、解放の漏れ、`drop` で止まる）は、どれもこれが原因。
  - Phase 1 と Phase 2 で、CoreAudio の入力と通知、CoreMIDI、AudioToolbox（デコード、AU）、Metal（`echode-gpu`）が加わり、手で書く宣言は桁で増える。
  - 置き換え先の多くは、既に Cargo.lock にある。`libc` 0.2.190 は `os_sync_*`、`OS_SYNC_WAIT_ON_ADDRESS_SHARED`、`thread_policy_set`、`THREAD_TIME_CONSTRAINT_POLICY`、`pthread_set_qos_class_self_np`、`qos_class_t`、`mach_absolute_time`、`mach_timebase_info` を宣言している。objc2 の系統（`objc2-core-foundation`、`dispatch2` など）は、clack-host が引き込んでいる。どの crate にもないのは、今は `os_workgroup_*` だけ。
- やること:
  - `os_sync_*`、mach の時刻、スレッドのポリシーと QoS（ENG-11 で使う）は、`libc` の宣言を使う。2 か所に分かれた宣言は 1 か所にまとめる。
  - CoreFoundation と FSEvents は、`objc2-core-foundation`、`objc2-core-services`、`dispatch2` にする（PLG-9）。
  - CoreAudio は、製品のデバイスのコードに着手する時に、`objc2-core-audio`（AudioHardware の feature）と `objc2-core-audio-types`（`AudioTimeStamp`、`AudioBufferList`）にし、ARCHITECTURE §3.1 の `echode-audio-io` に分ける。CoreMIDI、AudioToolbox、Metal も、同じ系統の crate を使う。MIDI は MIDI 2.0（UMP）の API から使う。ライセンスは、どれも Zlib OR Apache-2.0 OR MIT（`objc2` と `objc2-foundation` は MIT）。
  - どの crate にもないもの（今は `os_workgroup_*`）だけを、1 つのモジュールに手で書く。そのモジュールには、SDK のヘッダから値と大きさを出して Rust の宣言と比べるテストを付ける（`ffi_check.c` の方法を `cc` crate でテストに組み込むか、bindgen の出力と比べる）。
  - Swift へ書き出す関数のヘッダは、手で書かずに cbindgen で作る（UI-2 で UniFFI を選んだ場合は、その生成物を使う）。Metal のシェーダーも同じヘッダを読み込み、構造体の定義を 1 か所にする。
  - FFI のコールバック（`extern "C"`）の中で panic すると、プロセスが abort する。オーディオのコールバックで abort すると DAW 全体が落ちるので、そこから呼ぶコードは panic しないように書く。ENG-1 の専用の crate で、clippy の `indexing_slicing`、`unwrap_used`、`expect_used`、`panic` を禁じる。
- 完了の条件: OS のフレームワークの宣言が手書きでなくなり、残った手書きの宣言には、SDK と突き合わせるテストがある。
- 参照: ARCHITECTURE §3.1、§13.3、ADR 0015、AGENTS.md（非公開の Apple API を使わない）、PLG-9

#### ENG-16 波形のピークを GPU で作る計画を、CPU と測ってから決める

- 優先度: P3 ／ 種類: 技術選定
- 事実: PLAN の Phase 1 は「ピークは GPU で生成」としている。ピークの計算はメモリの帯域で決まる単純な処理で、律速はデコードであることが多い。GPU にすると、CLI でも Metal を使う仕組み（`echode-gpu`）が要る。
- やること: CPU（NEON、vDSP）と GPU で、デコードを含めた時間を測ってから選ぶ（AGENTS.md の「既存の実装を調べて測る」と同じ考え方）。
- 完了の条件: 測定と判断が ADR にある。
- 参照: ARCHITECTURE §11、§12

### 4.4 プラグインのホスティング（PLG）

#### PLG-1 監視フォルダの直下しか探さず、CLAP_PATH も見ない

- 優先度: P1 ／ 種類: 不具合
- 場所: `crates/echode-plugin-host/src/catalog.rs` の `list_bundles`（110〜142 行）、ADR 0016

- 完了の条件: 一時フォルダのサブフォルダに置いたバンドルと、CLAP_PATH に入れたフォルダのバンドルが、一覧に出るテストがある。

#### PLG-2 更新を、バンドル直下の更新日時で判定している

- 優先度: P1 ／ 種類: 不具合
- 場所: `catalog.rs` の `list_bundles`（121〜130 行）、`PluginCatalog::observe`
- 事実: ディレクトリの更新日時は、直下の項目が増減した時にしか変わらない。バンドルの中のバイナリを上書きしても、置き換えても、`Synth.clap` の更新日時は変わらなかった。プラグインを更新しても一覧に出ず、失敗したプラグインも再スキャンされない。
- やること: `Contents/Info.plist` の版（CFBundleVersion）と、実行ファイルの更新日時とサイズを鍵にする。§9.6 も「パス、更新日時、版」をキーにするとしている。
- 完了の条件: バンドルの中の実行ファイルだけを書き換えると、再スキャンの対象になるテストがある。
- 参照: ARCHITECTURE §9.6、ADR 0016

#### PLG-3 本番の IPC プロトコルを設計する

- 優先度: P1 ／ 種類: 設計
- 場所: `crates/echode-sandbox`
- 事実:
  - スパイクのマッピングは、ステレオ、512 フレームまでで、イベントを運ばない。
  - 共有メモリは、`$TMPDIR` の一時ファイルを `MAP_SHARED` でマップしている。親が落ちるとファイルが残り、ページはファイルへの書き戻しの対象になる。
  - バッファが 1 組なので、締め切りに遅れた応答が、次のブロックの入力と競合する。
  - 制御の経路（状態の保存と復元、GUI、パラメータの情報、プラグインからの要求）がない。
  - 親は、ヘルパーの標準エラーを上限なしに文字列へためる（`session.rs` の `PluginHost::spawn`）。出力の多いプラグインで、メモリが増え続ける。
- やること（ADR を書く）:
  - リアルタイムの経路: 任意のポートとチャンネル数、ENG-4 のイベント列、遅れた応答を捨てられるブロックごとのスロットか世代番号、`shm_open` か Mach のメモリと `mlock`。
  - 制御の経路: 別のソケットか Mach ポートにし、リアルタイムの経路と分ける。
  - ヘルパーの終了の検知（kqueue）と、再起動（§9.4）。
- 完了の条件: ADR があり、可変のチャンネル数とイベントが往復するテストがある。AGENTS.md の規則どおり `make spike-isolation` を実行し、`docs/spikes/S3-plugin-isolation.md` の数値を更新してある。
- 依存: ENG-4、PLG-4
- 参照: ARCHITECTURE §9.3、§9.4、`docs/spikes/S3-plugin-isolation.md`

#### PLG-4 Workgroup をヘルパーへ渡せるかを確かめる

- 優先度: P1 ／ 種類: 検証
- 事実: §9.3 は「Workgroup を Mach ポートで受け渡す」としているが、確かめていない。macOS 27 の SDK には、`os_workgroup_copy_port` と `os_workgroup_create_with_port`（`os/workgroup_object.h`）、子プロセスへ Mach ポートを渡す `bootstrap_check_in` と `bootstrap_look_up`（`servers/bootstrap.h`）、`posix_spawnattr_setspecialport_np`（`spawn.h`）が、公開ヘッダとしてある。
- やること: 親が Workgroup のポートを作ってヘルパーへ渡し、ヘルパーの時間制約ポリシー付きのスレッドが参加する、という流れを小さく作る。両方のスレッドをリアルタイムにした状態で、S3 の往復と末尾の遅延を測り直す。
- 完了の条件: `docs/spikes/S3-plugin-isolation.md` に結果がある。渡せない場合は、§9.3 を直す ADR がある。
- 参照: ARCHITECTURE §9.3、`docs/spikes/S3-plugin-isolation.md`、ENG-11

#### PLG-5 ヘルパーのスレッドの構成を直す

- 優先度: P1 ／ 種類: 設計
- 場所: `crates/echode-plugin-host/src/lib.rs` の `serve`、`serve_clap`、`HostShared`
- 事実: 今のヘルパーは、プロセスのメインスレッドで共有メモリを待ち、プラグインを処理する。このままでは、CLAP の main-thread の呼び出しと GUI（Cocoa はメインスレッドでしか動かない）を扱えない。`request_callback` と `request_restart` も無視している。
- やること: メインスレッドは run loop（GUI、CLAP の main-thread の呼び出し、タイマー）にし、処理は別のリアルタイムのスレッド（PLG-4 の Workgroup に参加する）、制御の経路はさらに別のスレッドにする。CLAP の thread-pool 拡張を提供する時は、そのスレッドも Workgroup に入れる。
- 完了の条件: ヘルパーがメインスレッドで run loop を回しながら、別のスレッドで処理できるテストがある。
- 参照: ARCHITECTURE §9.1、§9.5

#### PLG-6 ヘルパーを .app にして、署名と権限を本体と分ける

- 優先度: P2 ／ 種類: 設計
- 事実: バンドルのない実行ファイルでもウィンドウは出せるが、バンドル ID がないと、許可の確認（TCC）の表示やウィンドウの扱いで不便が出る。プラグインがファイルやネットワークに触れた時の確認には、ヘルパーの名前と署名が出る。将来公証する時（PLAN §6）は Hardened Runtime が要り、他社のプラグインを読み込むには library validation を外す権限が要る。
- やること: ヘルパーを `Echode.app/Contents/Helpers/` の中の .app（LSUIElement）にする。library validation を外す権限は、ヘルパーだけに付ける。本体と同じ自己署名の証明書で署名する。
- 完了の条件: アプリのバンドルの構成が、ARCHITECTURE §17 に書いてある。
- 参照: ARCHITECTURE §2、§17、PLAN §6

#### PLG-7 AU は、OS の別プロセスでの読み込みと比べて決める

- 優先度: P2 ／ 種類: 検証
- 事実: AudioToolbox には、AU を OS が用意する別プロセスで読み込む `kAudioComponentInstantiation_LoadOutOfProcess` がある。ヘルパーの中で AU を読み込むと、隔離が二重になるか、OS の仕組みと食い違う可能性がある。
- やること: Phase 2 で AU に着手する前に、ヘルパーで読み込む方式と OS の別プロセスでの読み込みを、往復の時間、GUI、クラッシュした時の挙動で比べる。
- 完了の条件: 判断が ADR にある。
- 参照: ARCHITECTURE §9.1、§9.2

#### PLG-8 スキャン結果に、メーカー、版、機能を残す

- 優先度: P1 ／ 種類: 整理
- 場所: `crates/echode-plugin-host/src/scan.rs` の `ScannedPlugin`、`scan_report`、`push_json_string`
- 事実: スキャンは ID と名前だけを残す。§9.2 の既定（メーカー単位でプロセスをまとめる）には、メーカーが要る。§9.6 のキャッシュ（アプリと CLI で共有する）の形式も決まっていない。JSON は手で組み立てていて、`\n` 以外の制御文字をエスケープしない。
- やること: CLAP の記述子の vendor、version、features、url を残す。キャッシュの形式（パス、更新日時、版をキーにした JSON Lines など）を決め、serde で読み書きする。
- 完了の条件: スキャン結果にメーカーがあり、キャッシュの読み書きのテストがある。
- 参照: ARCHITECTURE §9.2、§9.6

#### PLG-9 フォルダの監視が、非推奨の API を使い、解放を漏らし、すぐ drop すると止まる

- 優先度: P1 ／ 種類: 不具合
- 場所: `crates/echode-plugin-host/src/watch.rs` の `watch_thread`（91〜149 行）、`FolderWatch::drop`（75〜89 行）
- 事実:
  - `FSEventStreamScheduleWithRunLoop` は macOS 13 で非推奨になっている（SDK のヘッダは `FSEventStreamSetDispatchQueue` を使うよう指示している）。宣言を手で書いているので、警告が出ない。生成されたバインディング（`objc2-core-services` の FSEvents）は `#[deprecated]` を付けているので、`-D warnings` の `make check` で止まる。
  - `CFStringCreateWithFileSystemRepresentation` で作った文字列（Create の規則で呼び出し側が持つ）を、配列を作ったあとに解放していない。監視を始めるたびに 1 つ漏れる。
  - `drop` は、監視のスレッドが run loop を公開して走らせ始めた後でないと止められない。`CFRunLoopStop` は、まだ走っていない run loop には効かない。
- 根拠: `FolderWatch::start` の直後に `drop` すると、1 回目で `drop` が戻らなくなった（3 秒で打ち切り）。既存のテストは、作った後に 200 ms 待ってから使うので、この競合を避けている。
- やること: `objc2-core-services`（FSEvents の feature）、`objc2-core-foundation`、`dispatch2` を使い、`FSEventStreamSetDispatchQueue` で監視する。run loop のスレッドは要らなくなり、止める時は `FSEventStreamStop` と `FSEventStreamInvalidate` を呼ぶだけになる。CF の参照は `CFRetained` で持つ。3 つの crate は、clack-host を通して既に Cargo.lock に入っている（`objc2-core-services` 以外。ライセンスはどれも Zlib OR Apache-2.0 OR MIT）。
- 完了の条件: 監視を始めた直後に `drop` しても戻るテストを、100 回繰り返して通る。非推奨の API を呼んでいない。
- 参照: ADR 0016、ENG-15

### 4.5 アクション、API、CLI（API）

#### API-1 アクションの定義を 1 つにし、名前をそろえる

- 優先度: P1 ／ 種類: 設計
- 場所: `crates/echode-actions/src/action.rs`（`Command`、`Action`、`SPECS`、`Action::spec`）、`crates/echode-actions/src/journal.rs`（`ActionRecord` と 2 方向の変換）、`crates/echode-api/src/rpc.rs`（`Requested`、`committed`）
- 事実:
  - アクションを 1 つ足すたびに、2 つの crate の 10 か所ほどを手で揃える。`spec()` は `&SPECS[6]` のように添字で引く。
  - `actions.list` は `track.add` を返し、`actions.perform` は `add_track` を受ける。一覧から呼び方が分からず、§15 の「登録簿から MCP のツールを自動で生成」もできない。
  - API の結果は、ジャーナルの文字列を作ってから JSON に読み戻している。
- やること: 1 つの定義（serde の derive と、ID を持つ登録簿）から、ジャーナル、API、カタログを作る。`Id` は文字列として serde で読み書きする。アクションの ID は 1 つ（例えば `note.insert`）にそろえる。引数の JSON Schema は `schemars`（MIT）で生成する。
- 完了の条件: アクションを 1 つ足すのに触る場所が、その定義とモデルの処理だけになる。`actions.list` の ID で `actions.perform` を呼ぶテストがある。
- 参照: ARCHITECTURE §5、§15、ADR 0020

#### API-2 API に、トランザクション、Undo と Redo、版の確認を入れる

- 優先度: P1 ／ 種類: 設計
- 場所: `crates/echode-api/src/rpc.rs`
- 事実: §15 の自然言語コマンドは「複数のアクションからなる実行計画を、1 回の Undo で戻せる単位として実行する」。MCP から操作するエージェントも同じことをする。今の API は 1 回に 1 つのアクションしか受けず、Undo と Redo もない。クライアントとサーバーの版を確かめる手段もない。
- やること: 複数のアクションを 1 つの Undo の単位で実行するメソッド（配列を受けるか、begin と commit）、Undo と Redo のメソッド、プロトコルの版を返すメソッドを足す。名前は API-1 にそろえる。
- 完了の条件: 3 つのアクションを 1 回で実行し、1 回の Undo で戻るテストがある。
- 依存: API-1、HIS-4
- 参照: ARCHITECTURE §15、ADR 0020

#### API-3 ソケットの扱いを固める

- 優先度: P2 ／ 種類: 不具合
- 場所: `crates/echode-api/src/serve.rs` の `bind_socket`（36〜44 行）、`serve_connection`（47〜64 行）、`serve`
- 事実: 指定したパスに何があっても、削除してからバインドする（ソケットでないファイルも消える）。接続相手の uid を確かめない。接続は 1 本ずつで、1 行の長さにも待ち時間にも上限がないので、黙っている接続が 1 本あるとほかの接続が止まる。
- やること: 既にあるものがソケットの時だけ消す。接続ごとに `getpeereid` で uid を確かめる。1 行の長さと読み込みの時間に上限を置く。複数の接続を受ける形は、HIS-4 と一緒に決める。
- 完了の条件: 通常のファイルのパスを渡すとエラーになり、ファイルが残るテストがある。
- 参照: ADR 0020

#### API-4 WAV の書き出しが、1 サンプルごとにシステムコールを出す

- 優先度: P1 ／ 種類: 不具合
- 場所: `crates/echode-cli/src/lib.rs` の `write_wav`（165〜172 行）、`render_to_wav`
- 事実: バッファなしの `File` に 1 サンプルずつ `write_all` しているので、サンプルごとにシステムコールが出る。60 秒のステレオで 15.3 秒かかった。まとめて書くと 0.028 秒で、バイト列は同じだった。書き出す前に、全体をメモリに持つ。
- やること: `BufWriter` で包む。長い書き出しに備えて、ブロックごとに書く形にする。
- 完了の条件: 60 秒の書き出しが 0.1 秒程度になる。
- 参照: ADR 0019

#### API-5 ゴールデンテストを基準と比べる

- 優先度: P1 ／ 種類: 整理
- 場所: `crates/echode-cli/tests/render.rs`、`crates/echode-engine/src/render.rs` のテスト
- 事実: 同じプロセスで 2 回書き出して比べているだけなので、変更で音が変わっても通る。Phase 1 の完了条件は「基準のファイルと一致する」こと。
- やること: 小さい基準の WAV か、そのハッシュをリポジトリに置いて比べる。意図して音を変えた時に基準を作り直すコマンド（例えば `make bless`）を用意し、作り直した理由を記録する。
- 完了の条件: テストが基準と比べ、基準を作り直すコマンドがある。
- 参照: PLAN の Phase 1 の完了条件、ARCHITECTURE §16

### 4.6 UI と橋渡し（UI）

#### UI-1 可視範囲の問い合わせが、ID と役割も返す形にする

- 優先度: P1 ／ 種類: 設計
- 場所: `crates/echode-draw`（スパイク）
- 事実: S1 の問い合わせは、色と矩形だけのインスタンスを返す。PLAN §6 は、Metal で描いた画面のアクセシビリティ要素の木を Phase 1 から作るとしている。ヒットテスト、選択、VoiceOver も、「今見えているもの」を知る必要がある。また S1 の二分探索は、ノートが 2 拍より短いこと（`MAX_NOTE_LENGTH`）を前提にしているが、製品のノートには長さの上限がない。
- やること: 製品の問い合わせは、モデルのスナップショットから、見えているオブジェクトの ID、種類（トラック、クリップ、ノート）、矩形を返す。描画のインスタンス、アクセシビリティの要素、ヒットテストを、同じ結果から作る。MOD-4 でノートが並んでいれば二分探索で引けるが、長いノートを取りこぼさないように、ノートの終わりの最大値を前もって持つなど、区間に対応した問い合わせにする。
- 完了の条件: 方針が ADR か ARCHITECTURE §13 に書いてある。
- 参照: ARCHITECTURE §13.2、§13.6、PLAN §6

#### UI-2 Rust と Swift の橋渡しの方式を、アプリの骨組みの前に確かめる

- 優先度: P1 ／ 種類: 検証
- 事実: §13.3 は、命令の経路に UniFFI を予定している。Swift 6.4 の strict concurrency（Sendable の検査）と、生成されるコードの相性は確かめていない。S1 は、C の関数とモジュールマップで呼んでいる。
- やること: UniFFI（非同期関数、コールバック）と、C ABI（cbindgen）に薄い Swift の包みを付ける方式の 2 案を、Swift 6.4 の strict concurrency で小さく作って比べる。スナップショットを複製せずに渡せるかも確かめる。
- 完了の条件: 判断が ADR にある。
- 参照: ARCHITECTURE §13.3

#### UI-3 描画のバッファと描画のスレッド

- 優先度: P2 ／ 種類: 不具合
- 場所: `spikes/draw/Sources/EchodeDraw/Renderer.swift`
- 事実: 描画中のフレームが最大 3 つある（`maximumDrawableCount = 3`）のに、CPU は毎フレーム同じインスタンスのバッファを書く。GPU が読んでいる最中に書き換えうる。描画はメインスレッドで行っていて、§13.2 の「専用のスレッドから描く」は確かめていない。
- やること: 製品の描画では、3 組のバッファとセマフォで回す。表示リンクを専用のスレッドで動かし、メインスレッドを忙しくしても描画が止まらないことを測る。
- 完了の条件: 製品の描画のコードで満たしている。
- 参照: ARCHITECTURE §13.2、`docs/spikes/S1-drawing.md`

#### UI-4 キーボードの割り当てを、キーコードで行う

- 優先度: P2 ／ 種類: 不具合
- 場所: `spikes/input/Sources/EchodeInputCore/Gesture.swift` の `midiNote(for:)`（224〜247 行）
- 事実: 文字で割り当てるので、キーボードの配列で結果が変わる（QWERTZ では y と z が入れ替わる）。z、x、c、v なども音に当てているが、§13.5 が倣う Live では、Z と X はオクターブ、C と V はベロシティの操作。
- やること: キーコード（物理的な位置）で割り当て、Live の配置に合わせる。
- 完了の条件: 製品の入力のコードで満たしている。
- 参照: ARCHITECTURE §13.5

#### UI-5 アクションの表示名と説明の多言語化を、どこで持つか決める

- 優先度: P3 ／ 種類: 設計
- 場所: `action.rs` の `ActionSpec`（`name_ja`、`name_en`、`description_ja`、`description_en`）
- 事実: 表示名を、Rust に日本語と英語で直に書いている。UI の文字列は String Catalog で管理する予定（§13.2）なので、言語を足すと 2 か所を直すことになる。
- やること: Rust は ID と英語の説明（MCP と LLM 用）を持ち、表示名は Swift の String Catalog で ID から引く、などの分担を決める。
- 完了の条件: 分担が ARCHITECTURE §5 に書いてある。
- 参照: ARCHITECTURE §5、§13.2

#### DEV-1 初回コミットを作る（ユーザーの作業）

#### DEV-2 ツールチェーンを固定し、`rust-version` を直す

- 優先度: P1 ／ 種類: 整理
- 場所: `Cargo.toml`（`rust-version = "1.87"`）
- 事実: コードは let chain を使う（`document.rs`、`synth.rs`、`transport.rs`、`sequence.rs`、`bin/spike.rs`）。let chain は Rust 1.88 で安定化したので、1.87 ではビルドできない。ツールチェーンを固定していないので、Rust の更新で clippy に新しい警告が入ると、`-D warnings` を付けた `make check` が突然失敗する。

#### DEV-4 `make check` を決定的にし、CI を置く

## 5. やってはいけないこと

この監査で見つかった誤りの型。新しいコードで繰り返さない。

- ポインタの値（`Arc::as_ptr` を整数にしたもの）で同一性を判断しない。比べるなら、`Arc` を持ったまま `Arc::ptr_eq` で比べるか、内容のハッシュで比べる。
- 音を、ブロックの中の span の並びや長さから決めない。プロジェクト上のサンプル位置から決め、ブロック長を変えても同じ出力にする。
- オーディオスレッドで、プロジェクト全体の大きさに比例する処理をしない。そのブロックで起きることの数に比例させる。
- オーディオスレッドでモデルの型を読まない。制御スレッドが作った実行計画だけを読む。参照カウントの最後の解放を、オーディオスレッドで起こさない。
- 一様な小節長、ステレオだけ、モノだけを前提にしない。
- ジャーナルとコミットの書き手を複数にしない。fsync していないものを「確定した」と扱わない。
- JSON を文字列の連結で組み立てる箇所を増やさない。値は serde で書き、改行の位置だけを決める。
- 外から来た文字列（プロジェクトのファイル、API の入力）を、検証せずにパスに使わない。
- OS の API を新しく手で宣言しない。`libc` か objc2 の系統の生成されたバインディングを使う。どちらにもないものだけを 1 つのモジュールに書き、SDK のヘッダと突き合わせるテストを付ける。CF の参照は `CFRetained` で持ち、手で `CFRelease` しない。
- スパイクの型（`echode_history::Project`、`echode_engine::Engine`、`echode-draw` の `Scene`）を、製品のコードから使わない。
- 「同じプロセスで 2 回実行して一致した」だけを、ゴールデンテストとしない。
- 時間を測って閾値と比べるテストと、実機が要るテストを、`make check` に入れない。
