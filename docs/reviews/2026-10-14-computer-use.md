## CU-01 / P2: 停止中の位置移動と停止中からの再生が描画を起こさない

前回の候補 C-01 を実画面で確定した。再生位置の数値と、アレンジ・ピアノロールのオレンジのプレイヘッドが食い違う。

### 再現と実測

1. ノートのあるプロジェクトを開き、再生を停止して描画が落ち着くまで待つ。
2. 再生開始位置に2拍を入力して「移動」を押す。
3. 数値表示は `2.00` に変わる。両画面のプレイヘッドは0拍に残る。
4. 再生を開始する。数値は進むが、両画面のプレイヘッドは同じ位置に残る。
5. ノートを編集するかトラックを追加すると描画が起き、位置が更新される。

最初の起動では、停止中に `1.17 → 0.00 → 2.00` と位置を変えても、両画面の縦線は約1.17拍に残った。再生中も数値が進む一方で縦線は残った。再起動後の独立した確認では、数値が `2.00`、縦線が0拍という画像を保存した。続く0〜4拍のループ再生で、数値 `2.58` の画面ツリーと、縦線が0拍に残る画像を保存した。

- [再起動後・停止中の再現画像](../../target/verification/computer-use-20261014/stopped-locate-after-restart.png)
- [再起動後・再生中の再現画像](../../target/verification/computer-use-20261014/playing-after-restart.png)

### 原因を示すコード

- `CanvasRenderer.swift:129` は、停止中かつ描画済みの版なら表示リンクを休止する。
- `ArrangeView.swift:98` と `PianoRollView.swift:263` は、同じ `PlaybackFeed` なら更新を返してしまう。再生・停止・位置移動で feed の同一性は変わらない。
- `ProjectController.swift` の `audioCommand` と `observeAudio` は音声状態を更新するが、休止した描画を起こす通知を送っていない。
- `ArrangeProbe` の計測は `beginMeasurement()` によって連続描画するため、この再現条件を検査できない。

### 実行役への修正指示

1. feed の差し替えと、その feed の再生状態・位置の変化を別に扱う。feed の同一性だけを更新の判定にしない。
2. 再生開始、停止、一時停止、停止中の位置移動について、制御側からアレンジとピアノロールの描画へ通知する。表示リンクの休止解除と1回の描画要求は、既存の描画 run loop 上で行う。
3. 停止中の位置移動は、位置の値が変わったことを理由に新しいフレームを要求する。現在の `playing == false && drawnRevision == revision` の条件を通すには、描画要求の版も更新する必要がある。
4. 再生中のフレームは引き続きライブ位置を読む。位置ポーリングでワークスペース全体を毎回作り直す方法や、停止中も常時連続描画する方法で症状を隠さない。音声コールバックから SwiftUI や描画のロックを触らない。
5. 文書切り替え、ペインの閉じる／開く、計画交換後にも通知先が正しいことを検査する。破棄した文書・ビューへの通知を残さない。
6. `beginMeasurement()` を呼ばない通常モードで、停止して表示リンクが休止した後に play と locate を行う回帰を追加する。フレームが実際に出たことと、描かれた位置を確認する。アレンジとピアノロールの両方を対象にする。

受け入れ条件は、停止中の0→2拍の移動が両画面に反映されること、再生開始後の縦線が数値表示と同じ位置へ進むこと、一時停止後は縦線も止まること、長く停止した後でも同じ操作が通ること。停止中の連続描画を有効にした計測だけで合格にしない。

**`spike-app` は2回とも失敗した。** 初回はアレンジ1フレーム、ピアノロール2フレーム、両方のメイン処理の負荷中のフレームは0だった。フレーム枠の不足は0。ヘッダとの位置合わせとアクセシビリティの同一性は通過した。テスト用Echodeを最小化し、この検査のために開いたアクティビティモニタを終了した再試行でも同じ件数だった。

## 対応

CU-01 は feed の同一性と、再生・一時停止・停止・位置移動を分けた。成功した操作だけ世代を増やし、アレンジとピアノロールはその世代で描画要求の版を上げる。表示リンクは描画スレッドで作り、休止フラグは値が変わるときだけ書く。コールバックの drawable は、描かないときも提出する。停止中は要求した版を描いたあと休止し、再生中は共有メモリの位置を毎フレーム読む。位置のポーリングでは世代を増やさない。

`PlayheadTests` は `beginMeasurement()` を呼ばない。停止してリンクが休止したあと、0拍から2拍への移動、進んだ再生位置の描画、破棄したビューへ通知が戻らないこと、計画の差し替えと文書の切り替えを確認する。ウィンドウが遮蔽されていないときは、再生中のコールバックが続くことと、一時停止のフレームも確認する。

`spike-app` の合格条件（フレームが10を超える、メインスレッド外、メイン処理中のフレームが5を超える）は変えていない。終了コード 0 は、その条件を満たしたときだけである。

対応後に2回測った。

- 1回目は終了コード 0、分類 `normal`。画面は1枚で点灯し、ウィンドウは表示中、アクティブなスペースにあり、遮蔽されていなかった。アレンジとピアノロールはどちらもコールバック 93、フレーム 93、メインスレッド外 93、メイン処理中 30、休止解除 1、`continuous` は true、空き枠の不足は 0。
- 2回目は終了コード 1、分類 `insufficient-environment`。画面は点灯しウィンドウは表示中だが、アクティブなスペースではなく遮蔽されていた。休止解除は両方 1。アレンジはコールバック 1、フレーム 1。ピアノロールはコールバック 2、フレーム 2。メイン処理中のフレームは 0。合格条件は下げていない。

この計測は、製品画面での CU-01 の再操作ではない。
