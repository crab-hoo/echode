## 総評

書き方の規律は高い。製品コードに `todo!`・`unimplemented!`・TODO の類は 0 件、`unwrap()` は 5 件、`panic!` は 3 件で、どれも届かない分岐か添字の実装である。
`#[allow]` は 12 件（引数の数 7、未使用の許可 5）で、`unsafe` には全て根拠がある（ADR 0321）。
書出しの WAV の見出し、RF64、TPDF、正規化は、手で数えて仕様と合っていた。

弱いのは 1 つの型に集まる。**「読めない」を「無い」に畳む書き方**である。
`.ok()?` や `Err(_) =>` で失敗を既定値へ寄せた箇所のうち、復旧の入口にあるものが実害になる。
自動保存の ref が読めないだけで、復旧は「コミットがまだ無い文書」として扱い、同期していない作業ツリーを正本にして、
通知なしに開く（IQA-01）。壊れたリポジトリは「初期化に失敗した」と報告され、原因が消える（IQA-02）。
そして、開けなかった理由は FFI の境界で捨てられ、画面にもログにも残らない（IQA-03）。
ADR 0291〜0320 でエラーを型にした成果が、最も必要な「開けない」場面で利用者に届いていない。

| 観点 | 評価 | 根拠 |
|---|---|---|
| 失敗を型で返す | A- | 全 crate の境界が列挙型。届かない先が 1 か所ある（IQA-03） |
| 失敗を畳まない | B- | 復旧の入口で「読めない」と「無い」を区別しない（IQA-01・02） |
| 失敗した後の状態 | B+ | 編集の巻戻しは丁寧。自動保存のキャッシュだけ戻さない（IQA-04） |
| 失敗が見える | B | 黙って止まる経路が 3 つ（IQA-05・11） |
| 関数とファイルの大きさ | B- | 2,000 行超のファイルが 3 つ、90 行超の関数が 28 個（IQA-07・08） |
| 数値と形式の正しさ | A | WAV・RF64・ディザ・正規化・フェーダー。読んだ範囲に指摘なし |
| テストの書き方 | A- | 待ちは期限付きのポーリング。固定の `sleep` で同期するテストは見つからなかった |

## 指摘の詳細

### IQA-01 自動保存の ref が読めないと、通知なしに作業ツリーから開く

- **事実**: `autosave_tip`（`document.rs` 879 行）は `gix::open(directory).ok()?` と `try_find_reference(...).ok()??` で先端を求める。
  ref が無い時と、ref が読めない時（空のファイル、壊れた内容）は、どちらも `None` になる。
  `recover_labeled` は `None` を「コミットがまだ無い」と読み、作業ツリーの JSON を文書にする。
  `DocumentHost::open` は続けて「最初のコミット」を親なしで作り、ref を上書きする。
- **再現**: `crates/echode-history/tests/audit_quality.rs` の
  `audit_iqa01_an_unreadable_autosave_ref_does_not_silently_drop_edits`（`#[ignore]`）。
  トラックを 2 つ足して閉じ、作業ツリーを 1 つ目の保存の時点へ戻し、ref を空にして開く。
  文書はトラック 1 つで開き、復旧の通知は `None`、履歴は 3 件から 1 件になった。
- **ほかの組合せ**（監査中の試行。テストには入れていない）:
  - ref だけが空で、作業ツリーは最新: 内容は正しいが、通知なしに履歴が 3 件から 1 件になる。
  - ref が空で、`save.pending` が残る（保存の途中で落ちた形）: `UnfinishedWorktree`（「コミットが無い」）で開けない。
  - どの場合も、`.git/echode-commit-chain` の最後の行は最新のコミットを指し、オブジェクトは残っている。
- **なぜ重いか**: 作業ツリーの JSON は同期しない（[ADR 0230](../decisions/0230-save-durability.md)）。
  ref が読めなくなる場面（電源断、同期フォルダ、ディスクの障害）では、作業ツリーも古いことがある。
  その時、確定済みの編集が通知なしに消え、次の自動保存がそれを新しい履歴の根にする。
  ADR 0230 は ref の更新が**遅れる**場合をチェーンで救ったが、ref が**読めない**場合は同じ入口で素通りする。
- **直し方の案**: `autosave_tip` を `Result<Option<ObjectId>>` にし、「無い」と「読めない」を分ける。
  読めない時は、同期済みのチェーンの最新の行を先端にする。次の保存の `follow_chain` が ref を直す。
  チェーンも使えなければ、作業ツリーへ落ちずに、型付きのエラーか復旧の同意（ADR 0183）にする。
  完了条件は上のテストの `#[ignore]` を外して通ること。

### IQA-02 開けないリポジトリを「初期化の失敗」として報告する

- **事実**: `open_or_init`（`autosave.rs` 145 行）は、`gix::open` のどの失敗も `gix::init` で受ける。
  `.git` が在って読めない時、`init` は「既存のディレクトリは初期化しない」と断り、その文だけが返る。
  `tip_journal_seq`・`first_readable_commit` の内側の `gix::open` も、失敗を 0 や `None` に畳む。
- **再現**: 同じファイルの `audit_iqa02_an_unreadable_repository_reports_why_it_did_not_open`（`#[ignore]`）。
  `.git/config` を壊して開くと、返るのは `Git { operation: Init, error: Refusing to initialize an existing directory }` である。
  設定が読めないという元の原因は、どこにも残らない。
- **既知との関係**: [現在の制約](../status.md) は「最初に Git の初期化が失敗した理由は未確定」と書く
  （[ADR 0121](../decisions/0121-startup-recovery-and-errno-validation.md)）。
  この経路は、開けなかった原因を初期化の失敗に置き換える。当時の原因がこれだったとは確かめていない。
- **直し方の案**: `.git` が無い時だけ初期化する。在って開けない時は `GitOperation::Open` で元のエラーを返す。

### IQA-03 文書を開けない理由が FFI で捨てられる

- **事実**: `echode_document_open` と `echode_document_create`（`echode-ffi/src/lib.rs` 432・456 行）は、
  失敗をヌルポインタだけで返す。Swift は固定の文（`could not recover the package`、`could not create the package`）を出す。
  `echode-ffi` と `echode-document` に、開く失敗を書くログの呼出しはない。
  編集の失敗は `finish` が文にして返す（ADR 0292）ので、落ちるのは開く・作るの 2 つである。
  プラグインの走査の失敗も、固定の文（`plugin scan failed`）になる。
- **影響**: 「既に開いている」「保存が途中」「読めるコミットが無い」「ジャーナルの何番が不変条件を破った」「どのパスの I/O」は、
  Rust の中では型で区別している。利用者と製品のログ（ADR 0322）には、その区別が届かない。
  開けない文書の報告を受けても、原因を分けられない。IQA-02 の「未確定」が残った理由でもある。
- **直し方の案**: 開く・作るに、編集と同じ形でエラーの文を返す引数を足し、失敗を `log::error!` で製品のログへ書く。
  既存のパスへの作成と書込みの失敗も、同じ経路で理由を返す。

### IQA-04 失敗した自動保存の後のキャッシュ

- **事実**: `save`（`autosave.rs` 365 行）は、`write_incremental` が作業ツリーを書き換えた後で失敗しても、
  `cache` を前回成功した時のまま残す。次の保存は、`Arc::ptr_eq` で「変わっていない」と判定したファイルを書き直さない。
  - 失敗した保存が書き換えたトラックを Undo で戻すと、そのファイルは失敗時の内容のまま残る。
  - 失敗した保存が新しく書いたファイルは、キャッシュに無いので、消す対象にもならない。
- **影響**: コミットは blob から作るので正しい。食い違うのは作業ツリーの JSON で、次に開いて全体を書き直すまで残る。
  パッケージを Git で見る利用者には、身に覚えのない差分になる。IQA-01 の経路では、その作業ツリーが文書になる。
- **未再現**: 自動保存の途中の失敗を注入する仕組みがなく、読んで確かめた。
- **直し方の案**: `save` が失敗したら `cache` を `None` に戻す。次の保存が全体を書き、列挙にないファイルを掃く。

### IQA-05 自動保存を頼めなかった時に何も残らない

- **事実**: `publish`（`host.rs` 936 行）は `if let Ok(pending) = commit.autosave.save(...)` で、失敗の枝を持たない。
  自動保存のスレッドが止まっている時、以後の全ての編集で保存が飛ばされる。
  編集はジャーナルで確定しているので、失われない。ただしジャーナルは短縮されずに伸び、履歴の一覧も増えない。
  終わった保存の失敗は `finish_saves` が警告を書くが、頼めなかった場合は書かない。
- **案**: 最初の 1 回を `log::error!` で書き、履歴の報告（`history.usage`）に自動保存の停止を出す。

### IQA-06 出力機器の一覧が 1 台の失敗で全体を失敗にする

- **事実**: `inventory`（`hardware.rs` 154 行）は機器ごとに、ストリーム・形式・レート・バッファ長・UID・名前を `?` で読む。
  整数でないレートは `return Err(HardwareFault::SampleRate)` である。生存の問い合わせだけは、失敗した機器を飛ばす。
  一覧が失敗すると、`HalOutputs::refresh` も失敗し、選んだ機器が正常でも出力を開けない。
- **起こり得る場面**: 抜かれる途中の機器（生存の確認の後で問い合わせが失敗する）、問い合わせに癖のある仮想ドライバ。
  前者は次の通知で読み直すので自然に直る。後者は、その機器が在る間ずっと続く。
- **未再現**: 実機が要る。読んで確かめた範囲である。
- **案**: 問い合わせに失敗した機器は一覧から外し、機器の番号と失敗をログへ書く。一覧自体の取得の失敗だけをエラーにする。

### IQA-07 文書スレッドの `worker` の定型

- **事実**: `worker`（`host.rs` 448 行）は 307 行の 1 関数である。
  状態（ディレクトリ、スナップショット、自動保存、進行中の保存、次の連番、セッション、停止）を引数と局所変数で持つので、
  `Publish` の組立てを 6 か所に書く。呼ぶ側も、要求を送って応答を待つ同じ 10 行を 8 回書く。
  `reply_halted` は 7 つの枝が同じ 1 行である。
- **もう 1 つ**: `apply_transaction` は、トランザクションを中断する合図として `ActionError::CorruptJournal` と `NotApplied` を返し、
  本当のエラーは別の変数（`failure`）で運ぶ。エラーの値が、読んだとおりの意味を持たない。
- **影響**: 今は正しい。要求の種類を足す時に、停止の応答・巻戻し・公開のどれかを 1 か所だけ書き忘れやすい形である。
- **案**: 状態を `struct Worker` にまとめ、公開と巻戻しをメソッドにする。送受信は 1 つの関数にする。
  中断は、トランザクションの閉包がエラーの型を選べる形にする。振る舞いは変えない。

### IQA-09 コミットチェーンと、開く時の読み直し

- **事実**: `echode-commit-chain` は保存ごとに 82 バイト伸び、切り詰めがない。
  `autosave_tip` と `commit_parent` は、呼ぶたびに全体を読んで表を作る。
  `DocumentHost::open` 1 回で、`gix::open` を 7 回呼び、ジャーナルを 2 回読んで復号する（末尾の修復の読込みは別）。
- **影響**: 保存 10 万回で約 8 MB である。開く時間への寄与は測っていない。堅牢性には影響しない。
- **案**: 開く時に 1 度読んだリポジトリ・先端・ジャーナルを、復旧から最初の保存まで渡す。IQA-01 の修正で入口をまとめる時に合わせる。

### IQA-10 モノの出力機器への畳み込み

- **事実**: `write_planes`（`stream.rs` 1081 行）は、1 チャンネルの機器へ `(左 + 右) × 0.707` を書く。
  左右に同じ音がある時、機器へは左右の各々より 3 dB 大きい値が出る。メーターは畳み込みの前を読む。
- **影響**: 通話モードの Bluetooth など、1 チャンネルの機器でだけ起こる。0 dBFS に近い中央の音は、機器の側で歪む。
- **判断の確認**: モノからステレオへの等電力（ADR 0095）は記録がある。ステレオからモノへの係数を決めた記録は見つからなかった。
  係数を −6 dB（`× 0.5`）にすれば歪まないが、左右に振った音は小さくなる。聴感に関わるので、決めるのはユーザーである。

### IQA-11 Swift の開く経路と、黙って止まる読取り

- **事実**:
  - `ProjectController.open`（182〜196 行）は、開いた後の `snapshot()`・`historyReport()`・`audioState()` が失敗すると、
    `shutdown()` を主アクターの外で呼ばずに抜ける。`Document` の `deinit` が主アクターで `echode_document_close` を呼び、
    文書スレッドの終了と自動保存の同期を待つ。ほかの枝は、先に主アクターの外で `shutdown()` を呼んでいる。
  - `PluginActivityReader`（`PluginWindows.swift` 16 行）は、1 回の失敗（復号を含む）でスレッドを終える。記録は残さない。
    以後、その文書ではプラグインの窓の開閉と、窓での変更が画面へ届かない。
  - `prepareOutput` は `try?` で失敗を捨てる。こちらは、ポーリングする音声の状態に出るとコメントにある。
- **案**: 開く経路は `defer` で 1 か所にまとめる。読取りは、終える前に理由を製品のログへ書く。

### IQA-12 確かめて問題がなかった項目

- **WAV の見出し**: 3 つの形式の長さ（44・58・68 バイト、RF64 は 104・116）を手で数えた。
  `ds64` の位置と大きさ、`fact`、拡張形式の GUID、`0xffffffff` の番兵は仕様どおりである。
- **量子化とディザ**: 丸めは f64 で 1 回、範囲は `-2^(n-1)`〜`2^(n-1) - 1`。TPDF は ±1 LSB の三角分布で、標本ごとに引く。
- **正規化**: 一時ファイルは作ってすぐ名前を消し、利得は f64 で求める。非有限の標本は拒否する。
- **取込みの長さ**: 一括の復号は見出しの長さで読み止める。試聴の読取りは EOF まで読む。
  WAV・ADTS の AAC・M4A・ALAC・FLAC と、長さの見出しがある・ない VBR の MP3 で、両者のフレーム数は一致した。
  見出しが実際より短い形式は、今回の入力では見つからなかった。
- **ヘルパーの音声スレッド**: `service_block`・`adopt`・`pump` は確保の禁止の中で動き、
