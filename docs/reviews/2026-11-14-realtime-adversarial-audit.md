# 2026-11-14 リアルタイム安全性の敵対的監査

## 対象と判定の境界

- 対象: `45515f9`（作業ツリーは clean）。
  Rust・Swift・CLAP・Metal の境界で、データ競合・優先度逆転・隠れた確保・寿命の競合を探した。
  RTSan・TSan・確保の検出が通っても残る、順序と契約の誤りを主に狙った。
- 精読した範囲は次のとおりである。全行の通読ではない。
  - 機器のコールバック: `echode-audio-io` の `stream.rs`・`io_cycle.rs`・`panic_log.rs`・`transport.rs`・`hardware.rs`・`workgroup.rs`・`audition.rs`。
  - エンジンのコールバック: `playback.rs` の `PlaybackAudio`（`step`・`render`・`Block`・計画と命令のリング・状態の公開）、
    `plugins.rs` の全体、`delay.rs`、`meter.rs`、`audio_log.rs`、`playback_preparation.rs`。
  - 隔離の境界: `echode-sandbox` の `region.rs`・`sync.rs`、`session.rs` の `PluginHost`・`PluginAudio`・終了の監視、`workgroup.rs` の時間制約。
  - ヘルパー: `echode-plugin-host` の `threads.rs` の全体、`relay.rs`、`main_requests.rs`。
  - Swift と FFI: `echode-ffi` の `lib.rs`・`document.rs`・`controls.rs`、`echode-document` の `live.rs`、
    `EchodeBridge` の `Document.swift`・`PluginActivity.swift`、`EchodeAppCore` の `CanvasRenderer.swift`・`PluginWindows.swift`。
- 抜き取りで見たのは、`echode-document` の `service.rs`、`echode-engine` の `graph.rs`（スパイク専用）、ヘルパーの GUI である。
- 機器・実画面・聴感・第三者プラグインは使っていない。
  ヘルパーは実プロセスで動かし、音は製品のバッファで確かめた。
- 製品のコードは変えていない。
  追加したのは、この記録、索引とデバッグ手順の追記、再現テスト 4 件、試験用プラグインの `restart-nested` と `count-wait:` である。

## 総評

機器のコールバックとエンジンの経路には、今回の読みで誤りを見つけなかった。
リング・世代・締め切り・パニックの捕捉は、読んだ範囲で互いに矛盾しない（RTA-09）。
Swift の文書の寿命と Metal の描画スレッドにも、確定した指摘はない。

見つけた 4 件は、どれも**ヘルパーとの境界で、プラグインが普通に行う呼び出しか、普通に起きる遅れ**から始まる。
既存の検査が通るのは、検査がその順序を通らないからである。

- 処理スレッドの中で CoreFoundation のロックを取る（RTA-01）。
  `make rtsan` は名前に `under_rtsan` を含むテストだけを動かし、`request_callback` のテストはその名前を持たない。
- 再起動の要求が重なると、ヘルパーの制御スレッドが戻らない（RTA-02）。
  既存のテストは、再起動の最中に次の要求が来る順序を通らない。
- 取りこぼしたブロックのイベントが、黙って消える（RTA-03・RTA-04）。
  既存のテストは 1 ブロックの取りこぼしだけを通る。2 ブロックを超える遅れと、その間のイベントを通らない。

重さの順は RTA-04、RTA-02、RTA-01、RTA-03 である。
RTA-04 は第三者のプラグインが 2 ブロックを超えて 1 回遅れるだけで起き、ノートが鳴り続ける。
128 フレーム・48 kHz なら約 5.3 ms を超える遅れである。

RTA-05〜08 は再現テストのない指摘で、コードから読んだ事実と、測った値だけを書いた。

## 指摘の詳細

### RTA-01 `request_callback` が処理スレッドでロックを取る

- **事実**: `HostShared::request_callback` は `callback_gen` を進めて `Bridge::signal` を呼ぶ。
  `signal` は `CFRunLoopSourceSignal` と `CFRunLoopWakeUp` を、呼んだスレッドでそのまま実行する。
  CLAP の `request_callback` はどのスレッドからも呼べ、プラグインは `process` の中から呼ぶ。
  同じ `signal` は `pump` の中にもある（`request_process` を受けた時にプロセッサがない場合の `OP_ARM`）。
  `pump` は `service_block` の先頭で、RTSan の `nonblocking` の中である。
- **再現**: `audit_rta01_a_callback_requested_in_process_under_rtsan`（`isolation.rs`、`rtsan` の feature の時だけコンパイルする）。
  試験用プラグインの `callback` は `process` の中で `request_callback` を呼ぶ。
  RTSan は次を報告してヘルパーを止め、ブロックは返らない。
  `Intercepted call to real-time unsafe function pthread_mutex_lock`、`CFRunLoopSourceSignal+0x4c`。
  実行は `RTSAN_ENABLE=1 cargo test -p echode-plugin-host --features rtsan --test isolation -- --ignored audit_rta01`。
- **なぜ既存の検査で見えないか**: `make rtsan` は `under_rtsan` を名前に含むテストだけを動かす。
  同じ呼び出しを通る `a_callback_runs_on_the_main_thread_and_a_restart_still_answers` はその名前を持たない。
  確保の検出（`ForbidAlloc`）はロックを見ない。
- **契約との差**: [ADR 0041](../decisions/0041-helper-threads.md) は処理スレッドに「ロック、メモリの確保、ファイルの読み書きをしない」と決めた。
  同じ ADR は `request_callback` で「処理スレッドは確保しない」ことだけを確かめ、ロックを見ていない。
- **なぜ重いか**: run loop のロックはメインスレッドが持つ。メインは時間制約を持たず、プラグインの GUI も動かす。
  メインがロックを持ったまま横取りされると、機器の Workgroup に入った処理スレッドがその間待つ。
  頻度は低いが、待つ長さに上限がない。パラメーターの表示を毎ブロック `request_callback` で更新するプラグインでは、毎ブロックこの経路を通る。
- **直し方の案**: 処理スレッドでは CoreFoundation を呼ばない。
  `ON_AUDIO` の時は `callback_gen`（または `op`）を進めて制御スレッドを起こすだけにし、制御スレッドが `signal` を呼ぶ。
  完了条件は、上のテストの `#[ignore]` を外して `make rtsan` が通ること。名前に `under_rtsan` があるので、そのまま `make rtsan` に入る。

### RTA-02 重なった再起動の要求で制御スレッドが戻らない

- **事実**: 再起動は 3 つのスレッドが順に進める。
  処理スレッドは `restart_request != restart_ack` を見てプロセッサを止め、`restart_ack` を進める。
  制御スレッドは `restart_ack` と `holds_started` を待ってメインに `deactivate`・`activate` をさせ、`main_done` を待つ。
  メインは終わると `need_start` を立て、処理スレッドが `start_processing` する。
  1 回目の再起動の途中（処理スレッドがプロセッサを持っていない間）に 2 回目の要求が来ると、次の順になる。
  1. 処理スレッドは止めるものがないまま `restart_ack` を 2 にする。
  2. メインが 1 回目を終え、処理スレッドは 1 回目の `activate` のプロセッサで `start_processing` する（`holds_started` が真になる）。
  3. 制御スレッドは 2 回目のために `holds_started` が偽になるのを待つ。`restart_request == restart_ack` なので、処理スレッドは止めない。
  制御スレッドはこの内側の待ちでソケットを読まない。
- **再現**: `audit_rta02_a_restart_requested_while_restarting_is_run_and_the_helper_keeps_answering`（`isolation.rs`）。
  試験用プラグインの `restart-nested` は最初のブロックで再起動を求め、その再起動の `activate` の中でもう一度求めてから 50 ms かけて戻る。
  3 回目の `activate` は来ず、その後の `set_chain` は 2 秒で `Timeout` になる。音声のブロックは返り続ける。
  50 ms を置かない形でも 10 回に 1〜3 回同じ結果になった（3 回の実行）。置くと 30 回の全部で起きた。
  順序によっては制御スレッドが先に進み、メインが `try_take` でプロセッサを取れず、何も再起動しないまま完了を知らせる経路もコードにある。
- **影響（確かめたもの）**: 2 回目の再起動が行われない。制御の要求が時間切れになる。
  その間ヘルパーは 1 コアの 90〜100% を使い続けた（RTA-05）。
- **影響（コードから読めるもの）**: 制御スレッドは、状態の保存と復元、パラメーターの一覧と変更、窓の表示と終了、共有領域の交換、
  プラグイン自身の変更の中継（`Dirty`・`ParamRelay`）の全部を受け持つ。
  音は出続けるので、失敗として見えるのは個々の要求の時間切れだけである。
  窓の中の変更は中継も保存も届かないので、開き直すと残らない。
  共有領域の交換（`prepare_mapping`）は準備スレッドで 2 秒ずつ待ち、閉じる時の join もその分待つ。
- **起こり得る場面**: 遅延の変わる値を続けて動かすと、プラグインは変更のたびに `request_restart` を呼ぶ。
  1 回目の `deactivate`・`activate` の間に次の呼び出しが来れば、この順序になる。`activate` が長いほど起きやすい。
- **直し方の案**: 処理スレッドが開始してよい条件を、制御スレッドが完了を記録した番号で決める。
  `main_done` が `restart_request` に追いつくまで `need_start` を消費しない。
  こうすると 2 回目の要求の時に処理スレッドはプロセッサを持たず、制御スレッドはそのまま 2 回目を進める。
  メインの `try_take` が空だった時に完了を知らせないことも、同じ修正で確かめる。完了条件は上のテストの `#[ignore]` を外して通ること。

### RTA-03 交換の直前に公開されたブロックが処理されない

- **事実**: ヘルパーの `adopt` は、新しい共有領域に世代が公開されていれば、ループの先頭で `current` を入れ替える。
  古い領域に未処理の世代が残っているかは見ない。入れ替えた後、古い領域の世代を読むものはない。
  親は、締め切りで諦めたブロックの次のブロックも、スロットが 1 つ空いていれば公開する（2 スロット）。
  エンジンは計画の交換を、ヘルパーの世代の状態と関係なく次のコールバックで行う（`step` の先頭）。
- **再現**: `audit_rta03_a_block_published_before_a_mapping_change_is_processed`（`isolation.rs`）。
  `process-wait:` でヘルパーを 2 つ目のブロックの中に止め、ノートを持つ 3 つ目のブロックを公開する。
  より大きい領域を準備して有効にし、止めたブロックを放す。3 つ目は 2 秒待っても完了しない。
  領域の交換を外した対照では、同じ 3 つ目が 0.3 秒以内に処理された。
- **契約との差**: `Block` の説明は「締め切りの後も親は公開するので、ヘルパーはそのブロックのイベントを聞く」と書く。
  交換が重なると、そのイベントは届かない。
- **起こり得る場面**: プラグインが 1 回の `process` で 2 ブロックを超えて遅れている間に、
  イベントの容量が増える編集（ノートの多いクリップの貼り付けなど）の計画が有効になる時。条件は狭い。
- **直し方の案**: `adopt` に処理済みの世代を渡し、古い領域の公開済みの世代を全部処理してから入れ替える。
  RTA-04 の「取れなかった段を次のブロックでリセットして追い直す」を先に入れれば、この経路も同じ手当で覆える。

### RTA-04 2 ブロック遅れたヘルパーへ送れなかったイベントが消える

- **事実**: `submit_planes` は、公開済みで未完了の世代が 2 つあると `Busy` を返す。
  エンジンはそれを `MISS_SUBMIT` の取りこぼしにして、音を 5 ms で減衰させる（[ADR 0245](../decisions/0245-plugin-deadline-fades.md)）。
  そのブロックのイベントは `source_events` にあるだけで、次のブロックの `remember` が上書きする。
  カーソルは、そのノートをプラグインへ送ったものとして進む。
  追跡のノートオン（`chase_pending`）には失敗の後に作り直す手順があるが、普通のイベントにはない。
- **再現**: `audit_rta04_a_note_off_in_a_block_the_busy_helper_refused_still_reaches_the_plugin`（`hosted_playback/event_loss.rs`）。
  製品のエンジンと実ヘルパーを使う。`count-wait:` は 2 回目の `process` を止め、ノートのイベントを数える。
  1 つ目のブロックでノートオンを聞かせ、2 つ目で止め、3 つ目を公開し、ノートオフを含む 4 つ目を描く。
  `plugin_missed_blocks` は 3 になる。ヘルパーが追いついた後、数えた値は 1（ノートオン 1、ノートオフ 0）で、期待は 17 である。
  ノートオフが 3 つ目（待たせて公開したブロック）にある対照では 17 になった。
- **契約との差**: [ADR 0042](../decisions/0042-plugin-ipc.md) は「2 つとも未完了なら、そのブロックは待たずに欠落とし、無音にする」と決めた。
  音の扱いは決めたが、イベントの扱いは書いていない。
  容量を超えるイベントは `dropped_events` で失敗にするという既存の契約（黙って落とさない）とも揃わない。
- **なぜ重いか**: 必要なのは、1 回の `process` が 2 ブロックを超えて遅れることだけである。
  128 フレーム・48 kHz で約 5.3 ms、64 フレームなら約 2.7 ms を超える遅れで、サンプルの読込みや確保をするプラグインでは普通に起きる。
  消えたのがノートオフなら、その音は次の停止・位置移動まで鳴り続ける。ノートオンなら、その音が抜ける。
  記録に残るのは `submit failed` の取りこぼしだけで、イベントが消えたことはどこにも出ない。
- **直し方の案**: 公開できなかったブロックにイベントがあった段は、次に公開できるブロックでリセットし、今鳴っているノートを追い直す。
  バイパスの切替と同じ既存の手順（`request_reset` と `awaiting_notes`）で足りる。
  鳴っている音は打ち直しになるが、その前にすでに 2 ブロック以上の欠落がある。
  イベントを貯めて次のブロックの先頭へ足す案は、経路の容量（`routed`）を超える時の扱いが要る。測って決める。
  完了条件は上のテストの `#[ignore]` を外して通ること。実機の聴感は、直した時にユーザー確認へ足す。

### RTA-05 制御スレッドの待ちが回り続ける

- **事実**: ヘルパーの制御スレッドは、ソケットがある時は `pause` で `socket.wait_readable(20 ms)` だけを待つ。
  再起動を待つ内側のループは、ソケットを読まずに `pause` を繰り返す。
  親の要求が 1 つでも届いていると `wait_readable` はすぐ戻り、ループは待たずに回る。
  `bump_control` は `control_alarm` を進めて起こすが、ソケットがある時はだれもその語を待っていない。
- **計測**: RTA-02 の再現で、`set_chain` を送った後のヘルパーは `ps` の %CPU で 90〜100% だった（8 回の標本）。
  正常な再起動でも、`deactivate`・`activate` の間に親の要求が届けば同じループを回る。その長さは測っていない。
- **影響**: 処理スレッドとメインの進みに制御スレッドが気付くのは、最長 20 ms 後である。
  再起動 1 回につき、止めた後とメインの完了の後の 2 か所でこの遅れが足される。
- **直し方の案**: ソケットと内部の起床を 1 つの待ちにまとめる（`kqueue` の `EVFILT_USER`、または起床用のパイプ）。
  RTA-02 を直す時に一緒に行う。

### RTA-06 状態の読み手が上限なく回る

- **事実**: `PlaybackControl::status` と `LiveState::position` は、世代が奇数の間、譲らずに読み直す。
  前者の書き手は機器のコールバック、後者の書き手は文書ワーカーである。読み手は文書ワーカー、Metal の描画スレッド、メインである。
  書き手が 2 回の加算の間で止まると、読み手は戻るまでコアを使って回る。
- **確かめたこと**: `publish_status` の書込みの区間に、今のコードでパニックする経路は見つけていない（換算は `Option` を返す）。
  見つければ、コールバックのパニックを報告する経路（[ADR 0238](../decisions/0238-audio-callback-panics.md)）より前に、
  `OutputStream::service` が `status` で止まる。
  文書ワーカーが書込みの区間で横取りされた時は、描画スレッドとメインがその間回る。区間は 2 つの格納だけである。
- **案**: 区間の中の計算（`sample_to_tick`）を区間の前へ出す。読み手は数回で譲る（`yield_now`）。急がない。

### RTA-07 親の音声メモリは固定していない

- **事実**: `mlock` で固定するのは、ヘルパーとの共有領域と合流の語だけである。
  素材の PCM、遅延線（上限は実メモリの 4 分の 1）、計画の面は普通のヒープにある。
  メモリが足りない時に圧縮・退避されたページをコールバックが読むと、ページの復帰をそのスレッドが待つ。
  RTSan と確保の検出は、この待ちを見ない。
- **確かめていないこと**: 再現していない。どの量から起きるかも測っていない。
- **案**: 判断の材料として残す。長い素材をディスクから読む構成（Phase 3 のキャッシュ）を作る時に、
  コールバックが読む範囲を先に触れておく手順と一緒に決める。

### RTA-08 使われない `reset_for_restart`

- **事実**: `MappedRegion::reset_for_restart` は世代を 0 に戻すが、親だけが持つ `abandoned` を戻さない。
  戻した後に同じ番号の世代が来ると、完了していても `Abandoned` として捨てる。
  製品は呼ばない（`PluginHost::restart` は新しい領域を作る）。呼ぶのは `region_tests.rs` だけである。
- **案**: 入口を消す。残すなら `abandoned` も戻す
  （[完了時の確認](../development.md#完了時の確認)の「使われなくなった入口を残していない」）。

### RTA-09 確かめて問題がなかった項目

- 機器のコールバック（`stream.rs`）: HAL へ問い合わせない。バッファの形を毎回確かめ、合わない時は無音にして失敗を立てる。
  構成の変更は世代の比較だけで見る。`Instant::now` と `mach_absolute_time` は待たない。
- 計画と命令のリング: 取り出す前に返却の空きを確かめる。返却の書き手はコールバックだけなので、`abort` へは届かない。
  古い計画・フェーダーの値・パニックの中身は、どれも制御側で解放する。
- 合流の語の待ち: 見た値を取ってから各トラックを調べるので、調べた後の完了を取り逃さない。
  ヘルパーが語を進め続けても、締め切りまで回るだけである。
- 共有領域の親側の読み: 公開した世代は親の値（`issued`）を使い、領域から読み戻さない。
  フレーム数は 1 回読んで上限と照らす。`completed` を偽るヘルパーが壊せるのは、自分のトラックの音だけである。
- 終了の監視: 監視スレッドが触るポインタは、スレッドを join してから手放す。`restart` も先に止めてから差し替える。
- パニックの捕捉: スロットは解放しない。印はコールバックの本体の間だけ立ち、出力と試聴が同じスレッドで順に動いても混ざらない。
- 試聴の IOProc: 復号と出力は専用のスレッドが持つ。IOProc の破棄に成功した時だけ文脈を解放する。
- 機器の通知: ブロックは HAL が複製して持つ。取り除いた後に届いた通知も、捕まえた世代を進めるだけである。
- Workgroup: 製品の出力は必ず Workgroup を渡す。ヘルパーの処理スレッドは時間制約を付けてから参加する。
  Workgroup なしでヘルパーを動かすのは、機器なしの出力と書出しだけである。
- `Instance` の `Mutex<PluginHost>`: コールバックは取らない。記録のための終了の確認は `try_lock` である。
- Swift の文書の寿命: `Document` は呼び出しの間 `self` を保つ。活動の読み手は文書を持ったまま最長 0.25 秒で終わる。
  完了のコールバックは文脈を 1 回だけ受け取る。
- Metal（`CanvasRenderer`）: リンク・エンコーダー・バッファの配列は描画スレッドだけが触る。
  停止の印と run loop の公開は同じロックの中で、どちらが先でも止まる。
  製品の描画は GPU の完了を待たず、完了のハンドラは枠を返すだけである。インスタンスのバッファは、枠が返った後だけ作り直す。
- メーターと再生位置: 描画スレッドとメインだけが読む。コールバックはメーターの原子的な格納だけを行う。

## 直す順番の案

1. RTA-04（普通の遅れで起き、音が鳴り続ける。既存のリセットと追い直しで直せる）。RTA-03 も同じ手当で覆える。
2. RTA-02 と RTA-05（制御スレッドの待ちを 1 つにまとめ、開始の条件を番号で決める）。
3. RTA-01（処理スレッドから CoreFoundation を呼ばない。RTA-02 の起床の作り直しと同じ場所を触る）。
4. RTA-08（入口を消す）。RTA-06 と RTA-07 は急がない。

2 と 3 は [ADR 0041](../decisions/0041-helper-threads.md) の決定（処理スレッドが source を起こす）を置き換えるので、修正の時に ADR を足す。
`make rtsan` が動かす範囲（名前で選ぶ）を、ヘルパーを通るテストの全部へ広げるかも、その時に決める。
