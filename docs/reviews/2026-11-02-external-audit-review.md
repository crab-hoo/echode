# 2026-11-02 外部監査 2 件の精査

## 対象と判定の境界

- 対象: ユーザーから受け取った 2 件の監査。
  1 件目は製品コードとエージェント環境（ENV-01〜08、MOD-A1・HIS-A1〜A2・DOC-A1〜A2・ENG-A1・CLI-A1・SBX-A1・PLG-A1・FFI-A1）。
  2 件目は ADR 0212 以後の `make verify` の所要時間。
- 1 件目は `4ce1ca6` を対象にしていた。精査は `b417ff4` と未コミット変更 34 件で行い、指摘箇所が変わっていないことを確かめた。
- 判定は「事実」「一部事実」「潜在（製品から未接続）」「不成立」に分けた。
- 再現はリポジトリの外で行い、リポジトリのファイルは変えていない。
  製品の CLI と release ビルド、製品のエンジンと実ヘルパー、検査スクリプトの関数そのものを使った。
- 実機・ウィンドウ・音声機器は使っていない。プラグインの窓は、テスト用プラグインの記録型の窓（`gui:<socket>`）で代用した。

## 結論

- 1 件目の製品側の指摘のうち 2 つは、実害の大きい欠陥として再現した。
  プラグインの窓での変更が、無関係な編集 1 回で失われる（DOC-A1・A2）。
  状態の保管物を失ったパッケージは、次の自動保存で読めない先端を作る（HIS-A1）。
- エージェント環境の指摘は 8 件中 7 件が事実だった。
  ENV-04 は [横断監査](2026-11-02-cross-cutting-audit.md) の XCA-06 と同じ指摘である。
- 誤りもある。数値の前提 3 つ、クラッシュ回復の不変条件、再マップの `max_frames`、窓の状態の遅延応答、「永久に停滞する」という表現である。
- 2 件目の所要時間の数値は記録と一致した。ただし 1,444.8 秒と 780 秒の回は失敗した実行であり、そのことが書かれていない。

## 前提の誤り

- `TICKS_PER_QUARTER` は 960 ではなく 705,600 である（`time.rs` 16 行）。
- `media/objects/` は SHA-256 ではなく BLAKE3 の内容アドレスである（`objects.rs` の `hash_bytes`）。
- 反例の識別に使う範囲は前後 3 行ではなく 20 行である（`SITE_CONTEXT_LINES = 20`）。
- `echode_actions::replay` は製品から呼ばれていない。不変条件の検査がないのはこの公開関数と `apply_changeset` で、製品の回復経路ではない。

## P1 の詳細

### DOC-A1 と DOC-A2: プラグインの窓での変更が失われる

- 経路: [session.rs](../../crates/echode-sandbox/src/session.rs) の `Dirty` の腕は `window_open` を付けない。
  [PluginWindows.swift](../../swift/EchodeApp/Sources/EchodeAppCore/PluginWindows.swift) は `entry.windowOpen` が真の時だけ静止を待って記録する。
  一方 [device.rs](../../crates/echode-document/src/device.rs) の `defers_saves` は `dirty` だけで保存を保留する。
- 無関係な編集が入ると、[worker.rs](../../crates/echode-document/src/worker.rs) の `turn` が `document_changed` で保留の保存を捨てる。
  その後の `replace` は古い `device.state` で `matching_states` を照合し、一致しないヘルパーを作り直す。
- 再現: 製品のエンジンと実ヘルパーで、記録型の窓を開いた。
  - 窓で `dirty` を送ると、届いた活動は `dirty=true window_open=false` だった。
  - 窓で値を 1.5 に変え、背景保存を受け取ってから、無関係なトラック追加で `replace` した。
    結果は `report.created=true`（窓を作り直した）、値は 1、`applied` は `None` だった。
- 影響: 音色の編集のうちパラメーターにならないもの（波形・サンプル・モジュレーションの割当てなど）は、Undo にも保存にも入らない。
  次の任意の編集でヘルパーが作り直され、窓が閉じ、変更が元に戻る。
  パラメーターの変更も、静止の 500 ms の間に別の編集をすると同じことが起きる。
- Swift 側の条件と順序は読解による。製品アプリでの実操作は確かめていない。
- 修正方針: `Dirty` の活動に窓の状態を付ける。
  編集の前に保留の保存を記録するか、保留中のデバイスを `preserve` に入れる。
  `document_changed` で保留の保存を捨てる前に、その扱いを決める。
- 修正条件: 上の 2 つの再現が、記録した状態と同じ値・同じヘルパーで終わること。

### HIS-A1: 保管物のない状態が読めない先端を作る

- 経路: [document.rs](../../crates/echode-history/src/document.rs) の `parse_track` は状態の保管物を読む（1137 行）。
  `replay_suffix` は読まないので、保管物がなくても文書は開く。
- 再現（製品の CLI）: 状態を付けた行を 1 つ先端より先に残し、その保管物を消した。
  開くと成功し、編集を 3 回受け付けた。ジャーナルは `[6]` まで圧縮された。
  開き直すと `recovery confirmation required: unreadable tip` で、3 回の編集は復元されなかった。
- 前提の保管物の喪失は、横断監査の XCA-03（保管物を同期しない）で起こり得る。
- 修正方針: 再生の段階で状態の保管物の存在を確かめ、なければ開く前に知らせる。XCA-03 と一緒に直す。

## P2 の詳細

### CLI-A1: オフライン書き出しが実時間の期限で判定される

- [lib.rs](../../crates/echode-cli/src/lib.rs) の `render_with_plugins` は、再生と同じ `callback_deadline` の期限で判定し、1 ブロックでも間に合わなければ書き出しを失敗にする。
- 再現（release、同梱 Sine Pad、各 8 回）: `--frames` 1 は 8 回とも `did not finish before the deadline`。
  2・3・8・64・256・257・512・513・25,600 は 8 回とも成功した。
- 257 と 513 の最後の 1 フレームは、待機していない状態では間に合った。負荷のある時の失敗率は測っていない。
- 構造の問題は端数より大きい。実時間より遅いプラグインは、オフラインでも書き出せない。
- 修正方針: オフライン書き出しは期限なしで完了を待つ。ブロック長はテールを足した後に決める。

### PLG-A1 (b): 同梱プラグインのキャッシュの競合

- [scan.rs](../../crates/echode-plugin-host/src/scan.rs) の `store_scan_cache` は既存のファイルを切り詰めてから書く。
  `resolve_installed` は「走査しない」と書かれているが、呼ばれるたびに `refresh_catalog` でキャッシュを書き直す。
- 再現（release）: 同じキャッシュで 12 個の書き出しを同時に 3 回実行し、36 回中 2 回が `missing plugin: dev.echode.sine-pad` で失敗した。
- 修正方針: 一時ファイルと名前変更で書く。内容が変わらない時は書かない。

### ENV-01 と ENV-06: 検査の選択と期待した失敗

- ENV-01: `unsafe_changes` に実際の関数で一時リポジトリを渡した。
  追加は選ぶが、`unsafe` を含むファイルの削除と `.c` の変更は空を返した。
  [検査手順](../verification.md) の「変更行（追加・削除）」と食い違う。
- ENV-06: 終了コード 101 を返すだけのコマンドで、引数に正規表現の文字列を入れた。
  `checked_commands.py` は `expected_failure`、終了コード 0 を返した。
- 修正方針: ENV-01 は削除側の差分も読む。ENV-06 は `Command:` の行と、テストの開始前の出力を照合から除く。

## 2 件目（所要時間）の精査

- `timing-history.jsonl` の該当行の値は、すべて記録と一致した。
- 行 45 と行 46 は失敗した実行である。行 46 の 1,444.8 秒には手動の `spike-history`（173 秒）が入る。
- 分割後に合格し、`check` を再実行した 11 回は 723〜1,203 秒、中央値 914 秒である。
  ADR 0212 の 540 秒は 1 行のコメント編集の値で、コミットメッセージにも「実際の編集はより長い」と書いてある。乖離は開示済みだが、実測の中央値はどこにも記録されていない。
- `check` の時間は行 30〜41 で 276 秒から 600 秒へほぼ単調に増えた。負荷平均は 1.5〜2.3 で、負荷では説明できない。
  以後は 286〜598 秒で、増加を統合テストの追加だけに帰することは確かめていない。
- 契約の通常テストのログ 239 件のうち 43 件が `Compiling` を含み、`Finished` の秒数の合計は 137 秒だった。再コンパイルは事実である。
- 精査で別の原因も見つけた。`make rtsan` は `target/debug/echode-plugin-host` を RTSan 版で上書きする。
  その版は `@rpath/libclang_rt.rtsan_osx_dynamic.dylib` を読めず起動しない。
  検査の後に `target/debug/echode render` でプラグインを使うと、`control socket closed: dyld[...]: Library not loaded` で失敗した。
  次の検査はこれを作り直すので、ビルドの往復にもなる。
- 構造の指摘（`check-verification` の `**`、Swift の 274 テストの 3 回実行、`areas` の広さ、`covered` が全体の段階だけ）は事実である。
- 追加の提案: `cargo test` は 68 個の統合テストのバイナリを順に実行する。`cargo-nextest` で並列にすれば、`check` の待ち時間を直接減らせる。
