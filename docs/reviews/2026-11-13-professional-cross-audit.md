## 総評

コードの規律は、これまでの監査の評価どおり高い。今回の精読で、新しい実装の誤りは 1 件も見つからなかった。
PDC の計算と遅延線は手で追って矛盾がなく、コールバックは確保の禁止・検査付きの算術・所有権の返送を保っている。

弱いのはコードではなく、**確かめ方の偏り**である。
自動検査は厚いが、製品が実機で鳴った確認は 10/17 から 1 件も増えていない（PCA-02）。
Phase 2 の音の意味を変える変更（フォルダバス、PDC、モノの昇格、期限の減衰、自動ミュート）は、全て耳を通っていない。
次に弱いのは、「残る範囲」に置いた項目の重み付けである。
書出しが黙って位置のずれたファイルを作る経路が、ADR の残る範囲に 1 行あるだけで、利用者の制約にも再現にも載っていなかった（PCA-01）。

## 指摘の詳細

### PCA-01 書出しの途中で遅延が変わると、ずれたファイルを成功として書く

- **事実**: `render_with_plugins` は再生を始める前に `control.latency_samples()` を 1 回読み、その数だけ先頭を捨てる。
  描画の各ブロックの後で `control.service()` を呼ぶので、ヘルパーが再起動して別の遅延を報告すると、
  `follow_latency` が計画を作り直し、マスターの遅れが変わる。先頭で捨てた数は変わらない。
- **再現**: `crates/echode-cli/tests/render.rs` の
  `audit_pca01_an_export_stays_aligned_when_a_plugin_restarts_with_another_latency`（`#[ignore]`）。
  16 フレームを報告し、最初のブロックの後に再起動を求めて 48 フレームを報告する試験用プラグイン（`delay:16:48`）を、
  同じ傾斜の音声を置いた 2 トラックの片方に挿す。2 秒を書き出すと、91,200 フレーム目は期待 0.475 に対し 0.47483334 で、
  32 フレーム前の値と一致した。`render` は成功を返す。
- **既知との関係**: [ADR 0339](../decisions/0339-plugin-delay-compensation.md) の「残る範囲」に 1 行ある。
  [現在の制約](../status.md) と [ユーザー確認の一覧](../user-checks.md) には載っていない。再現テストもなかった。
- **なぜ重いか**: 結果のデータが黙って誤る。ライブの再生は次の位置移動で揃うが、書出しのファイルは残る。
  GUI の書出しも同じ `echode render` を使う。
  状態の復元の後に遅延が決まり、最初の処理で `request_restart` を呼ぶプラグインで起こり得る。
- **直し方の案**: 描画のループで `control.latency_samples()`（または公開済みの報告値）が開始時と違ったら、
  出力を捨てて先頭から描き直す。回数に上限を置き、超えたら型付きのエラーにする。
  再起動のブロックで欠けた音も同じ描き直しで消える。完了条件は上のテストの `#[ignore]` を外して通ること。
- **それまで**: 少なくとも、変化を検出したら成功にせずエラーにする。
- **対応（2026-11-14）**: 補正が変わったら出力を捨て、新しい計画が鳴ってから先頭へ戻して描き直す。8 回で落ち着かなければ `UnsettledLatency` で終わる。
  上のテストは `#[ignore]` を外し、全フレームを比べる（[ADR 0340](../decisions/0340-latency-graph.md)）。

### PCA-02 実機・聴感の確認待ちが 74 件、確認済みが 0 件

- **事実**: [ユーザー確認の一覧](../user-checks.md) は UC-01〜74 を持ち、「確認済み」は「まだない」である。
  最後の聴感の記録は 10/17 の Phase 1 の照合である。UC-63 以降は 11/8 以降に足された。
- **なぜ重いか**: 自動の回帰が確かめるのは、製品のバッファと波形である。
  HAL の実際の周期、機器の切替、第三者プラグインの振る舞い、耳に聞こえる段差は範囲の外にある。
  未確認の変更が同じ経路に重なるほど、後で聞こえた不具合の原因を 1 つの変更へ絞りにくくなる。
  この 6 日で、同じミックスの経路にフォルダバス・PDC・モノの昇格・期限の減衰・自動ミュート・出力の安全余白が重なった。
- **提案（ユーザーへ）**: 74 件を一度に閉じる必要はない。音の意味を変えた項目から、1 回 30 分ほどの場面にまとめる。
  1. ミックスの経路: UC-72・73・74（モノの昇格、フォルダバス、PDC）と UC-47・49・51。
  2. 取りこぼしと保護: UC-50・63・64（期限の減衰、自動ミュート、期限の余白）。
  3. 再生の連続性: UC-25・17・62・67（ライブ停止、停止の戻り、テンポ境界、再生中の編集）。
  4. 書出し: UC-52・57。
- **提案（運用）**: 音声経路の確認待ちに上限を置く。上限を超えたら、音の意味を変える変更より確認の準備（場面のプロジェクト、手順の短縮）を先に行う。

### PCA-03 全文を読む資料が上限まで 6 バイト

### PCA-04 ADR に現行・置換の索引がない

- **事実**: ADR は 339 件、2.5 MB である。番号は時系列で、`docs/decisions/` に索引はない。

### PCA-05 PDC の回帰が通していない場面

- **事実**: `hosted_playback/compensation.rs` は 5 件（兄弟の合流を全ブロック長で、フォルダ、バイパス、再起動、メトロノーム）、
  CLI は 1 件（先頭の一致）である。次の場面は、遅延のあるプラグインを挿した回帰がない。
  - ループの折返し（線は空にしない設計。折返しの前後で音が 1 度だけ出ること）。
  - ライブ停止の後、線に残った遅延分が流れ切ること。停止の直後に再生した時の重なり。
  - 余韻（`tail`）と遅延の両方を持つ経路の書出しの長さ。
  - 計画の交換で容量が変わる線の引継ぎを、製品の経路で通すこと（単体テストはある）。
- **判定**: コードを読んだ範囲では、どれも設計どおりに動くはずである。誤りは見つけていない。
  ただし AGENTS の「音を作る処理を足したら、ブロック長を変えて比べるテストを足す」に対し、
  ループと停止はブロック境界に最も依存する場面で、回帰がない。
- **案**: ループの折返しと停止の 2 件を、`sibling_tracks_meet_at_master_for_every_block_size` と同じ形で足す。
- **対応（2026-11-14）**: ループの折返し（全ブロック長）、ライブ停止の時に線が持っていた音、線が伸びる引継ぎを `hosted_playback/compensation.rs` に、
  余韻と遅延を両方持つ書出しを `echode-cli/tests/render.rs` に足した。停止の直後に再生した時の重なりは回帰にしていない（ADR 0340）。

### PCA-06 release の設定が既定のまま

- **事実**: `Cargo.toml` に `[profile.release]` はなく、`.cargo/config.toml` は `strip = "none"` だけを置く。
  release はデバッグ情報なし、整数のあふれ検査なし、`panic = "unwind"` である。配布のスクリプトは dSYM を作らない。
- **既知との関係**: 最適化の設定は統合表の E4（測ってから決める）にある。診断の面は載っていない。
- **影響**: 配布物の異常終了の記録（macOS のレポートと `panic.ndjson` の backtrace）は関数名までで、行が分からない。
  第三者プラグインと実機でしか起きない失敗は、利用者の記録だけが手がかりになる。
- **案**: release に `debug = "line-tables-only"` と `split-debuginfo = "packed"` を置き、`make dist` で dSYM を版ごとに保管する。
  本体の大きさは変わらない。あふれ検査は E4 の計測と一緒に決める。

### PCA-07 `full` の赤が日をまたいで残る

- **事実**: 完了した直近 9 回の `full` は、11/9・11/11・11/13 の 3 回が失敗である。
  11/9 と 11/11 は `cargo-fuzz` の導入の失敗（LINKEDIT、`a82fca1` で修正）、
  11/13 は `output-opening` の契約の時間依存（`e54d455` で修正）だった。製品の欠陥ではない。
  11/9 から 11/12 まで赤が続き、その間に 30 件を超えるコミットが入った。
  監査の時点で、`a340f84`（モノの昇格、フォルダバス、PDC を含む）の `full` は待ち行列にあり、結果はまだない。
- **影響**: `full` は RTSan・ASan・TSan・Miri・全契約の反例の唯一の定期実行である（ADR 0327）。
  道具の失敗で赤い間、ほかのジョブの結果は読めるが、節目の「合格を確かめる」は成立しない。
  `cancel-in-progress` と短い間隔のプッシュで、途中のコミットは全体検査を通らない。
- **案**: 道具の導入の失敗と製品の検査の失敗をジョブの結論で分ける。
  `full` が赤い間は、音声経路と隔離の変更の前に赤の原因を直す、と開発手順に書く。
  プッシュの間隔はユーザーの担当（統合表 U1）のままにする。

### PCA-09 文書ワーカーが停止中も 20 ms ごとに起きる

- **事実**: `worker.rs` の `turns` は `recv_timeout(self.idle())` で待ち、`idle` は通常 20 ms、
  出力の準備中・取込み中・デバイスの往復の待ちでは 1 ms である。
  毎回、音声セッションの `service`、メーターと位置の公開、戻りの確認を行う。
- **影響**: 開いた文書 1 つにつき、停止して何も変わらない間も毎秒 50 回起きる。準備中は毎秒 1,000 回である。
  堅牢性には影響しない。電池で使う時の消費と、ほかの計測の雑音になる。量は測っていない。
- **案**: 再生中と余韻が残る間だけ周期で起き、ほかは送信側の通知で起きる。E 段の末尾で、消費を測ってから決める。

### PCA-10 HAL の過負荷通知を聞いていない

- **事実**: `echode-audio-io` は機器の一覧・既定の出力・生存・レート・バッファ長・再起動を監視するが、
  `kAudioDeviceProcessorOverload` を監視していない。音切れの記録は、エンジン自身の期限の超過（`Note::Late`）とプラグインの取りこぼしだけである。
- **影響**: コールバックの外で起きた過負荷（開始の遅れ、ほかのプロセス、機器側）は記録に残らない。
  UC-50・64 で「音が切れた」と報告された時に、エンジンの記録が空だと原因を分けられない。
- **案**: 通知を数えるだけのリスナを足し、製品のログへ時刻とブロックの位置を書く。リスナはオーディオスレッドの外で動く。

### PCA-08 確かめて問題がなかった項目

次は指摘ではない。今回確かめた範囲と結果を残す。

- **PDC の計算**: `compensate` の 2 回の走査を手で追った。子は親の合流点、根はマスターの遅れに揃い、
  バイパスした装置の分は出力の線に足される。再帰はなく、あふれは検査付きである。
- **遅延線**: 書いてから読む順、2 のべきの容量、`fresh` の区間を古い線から読む式（`delay - filled - index`）を確かめた。
  計画より長いブロックは `capacity - delay` ごとに分けるので、読む前に上書きしない。
- **コールバック**: `render_mode` は `ForbidAlloc` の中で動き、計画・フェーダーの値は返送のリングで制御側へ戻る。
  返送の枠がなければ受け取らない。枠が詰まった時の `abort` は、受け取る前に枠を確かめる分岐の後にだけある。
- **共有領域の回収**: 出力のイベント数は配置の上限で切り、フレーム数は `prepare_block` が上限で確かめる。
- **ジャーナル**: 追記の前に欠けた末尾を切り、失敗時は元の長さへ戻して同期し、戻せなければ不確定の型を返す。
  macOS の `sync_all` は `F_FULLFSYNC` である。
- **パッケージの入出力**: 保持したディレクトリからの `openat`、`O_NOFOLLOW`、書込み時のリンク数の確認、一時ファイルからの改名。
- **FFI と Swift**: 読んだ入口では、完了のコールバックは拒否の経路を含めて 1 回である。Swift の製品コードに `try!`・`as!`・`DispatchQueue.main.sync` はなく、
  `fatalError` は使わない `init(coder:)` だけ。セマフォで待つのは描画スレッドの停止（`CanvasRenderer.stop`）だけである。文書の開閉は主アクターの外で行う。
- **API**: ソケットは 0600 で、接続の相手の uid を `getpeereid` で確かめる。
- **依存の勧告**: 2026-11-13 の `cargo deny check advisories` は該当なし。
- **非正規化数**: FTZ を設定している箇所はないが、M4 で 8 本の 1 次の帰還を 4,000 万回まわした計測は、
  通常の値 0.371 秒、非正規化数 0.371 秒で、比は 1.00 だった。対象の機種（M4 以降）では本体の負荷にならない。
  プラグイン側が FTZ を前提にしている場合の振る舞いは確かめていない。
- **署名**: 硬化ランタイムで署名し、ヘルパーだけが第三者のプラグインのために `disable-library-validation` を持つ。
