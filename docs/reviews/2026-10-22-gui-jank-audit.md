# 2026-10-22 GUI のがくつきの監査

ユーザーから届いた 4 つの症状を、ソースの読み取りと画面を開かない一時計測で調べた。

1. 再生開始時に GUI ががくつく。
2. ピアノロールのリサイズにつられて、トラックリストが上下する。
3. ピアノロールを表示すると、がくつく。
4. 左ペインのリサイズでアレンジが、右ペインのリサイズでピアノロールが、がくつく。

アプリの起動、実画面の操作、表示リンク・機器を開く検査はしていない。
一時計測はスクラッチ領域の単独の Swift プログラムで行い、リポジトリには残していない（手順は各項目に記す）。
製品と同じ値を測るため、製品のコードの該当部分を写した。写した箇所はファイルと行で示す。
実画面での見え方の確認はユーザー担当である。この記録は発見時点の証拠であり、対応後も書き換えない。

## JNK-01: 前のフレームを見た目の左下に固定している

`CanvasSurface.configure`（`CanvasSurface.swift:13-19`）は、`layerContentsPlacement = .topLeft` を設定した後、
`CALayer.contentsGravity` を `.topLeft` で上書きする。
CALayer のヘッダは「top は常に最大の Y」と定める。
アレンジとピアノロールは反転した（`isFlipped`）View の中にあり、レイヤーの `contentsAreFlipped()` は true になる。
このため `.topLeft` は見た目の左下を指す。

一時計測（`CanvasSurface.configure` と同じ順で、反転した親の下に反転した表示面を作る）の結果:

| 条件 | AppKit が設定した `contentsGravity` | `isGeometryFlipped` | `contentsAreFlipped()` |
| :--- | :--- | :--- | :--- |
| ウィンドウなし | `bottomLeft` | true | true |
| 画面に出さないウィンドウ内 | `bottomLeft` | false | true |

AppKit 自身は、見た目の左上（`.topLeft` の配置）を `bottomLeft` に変換している。製品はこれを `.topLeft` で上書きしている。
ADR 0144 以前の伸縮（UIF-01）が見えていたことから、新しい drawable が届くまでの間、古い絵は新しい枠で表示される。
現在は、その古い絵が下端にそろえられ、高さの差だけ縦にずれて見えるとみられる。

- エディタ境界のドラッグ: アレンジとピアノロールの両方の行・鍵盤が、ドラッグ量だけ上下する（症状 2）。
- ピアノロールを開く: アレンジが「エディタの高さ＋区切り 5 pt」（既定では約 305 pt）低くなる。
  古いアレンジの絵が下端にそろい、トラックリストの上部が切れて上へ飛ぶ（症状 3）。閉じる時は逆向きにずれる。
- 再生開始: JNK-02 の 3 pt の変化で、アレンジの絵が 3 pt 上下する（症状 1）。
- 横方向は「left = 最小の X」で反転しないため、左右の固定は正しい。症状 4 の横方向の変化はこの項目では説明できない。

回帰の経緯: 2026-10-22 のコミット 1f7a024（[ADR 0144](../decisions/0144-unscaled-canvas-resizing.md)）で入った。
必須契約 `canvas-resize-ui` は `contentsGravity == .topLeft` という値そのものを期待するため、見た目の固定位置の誤りを通してしまう。
負の対照（引き伸ばす配置）も、上下の取り違えを区別しない。
ADR 0144 の「自動回帰は設定の確認であり、実画面はユーザー確認」という限定どおり、実画面の検証は未実施だった。

修正の方向（未決定）: AppKit の変換を上書きしないか、`contentsAreFlipped()` に応じて `bottomLeft` / `topLeft` を選ぶ。
回帰は値ではなく見た目の固定位置を確認する。製品と同じ反転した階層で、AppKit の変換と一致することを期待し、
`.topLeft` のリテラルへ戻すことを負の対照にする。

## JNK-02: 再生準備中だけ状態行が高くなる

`WorkspaceView.swift:19-25` の状態行は、`pendingPlayback == true` の間だけ小さな `ProgressView` を挿入する。
同じ構成を `NSHostingView` に載せて測った結果、行の高さは 29 pt から 32 pt になった（英語・日本語とも）。

- 再生を押すと、ペイン領域が 3 pt 低くなり、再生コマンドの完了で元に戻る。
  `WorkspaceLayout.dimensions` はピアノロールの希望高を先に確保するため、変化はアレンジの高さが吸収する。
  1 回の再生開始で、アレンジが縦に 2 回リサイズされ、JNK-01・JNK-03 が起こる。
- 一時停止では `pendingPlayback` が false になるため、状態行は変わらない。
- 最初の再生では出力とヘルパーの準備（[ADR 0136](../decisions/0136-output-opening-off-worker.md)）が入るため、高い状態が長く続く。

同じ時点で、トランスポートの再生ボタンのラベルが「Play / 再生」から「Pause / 一時停止」に替わる（`WorkspaceTransportView.swift:19-21`）。
ボタンの幅は英語で 70 → 81 pt、日本語で 69 → 93 pt になり、右側の停止・メトロノーム・位置・入力欄がその分だけ横にずれる。

修正の方向（未決定）: 状態行の高さを固定する（表示器の場所を常に確保する等）。再生ボタンは両方のラベルが入る幅に固定する。
回帰は、待機中と準備中の状態行の高さ、再生・一時停止のボタンの幅が一致することを、画面なしのホスティングで確認できる。

## JNK-03: サイズ不一致の drawable を背景色だけで提出する

`CanvasRenderer.metalDisplayLink`（`CanvasRenderer.swift:247-254`）は、受け取った drawable の大きさが最新の入力と違う場合、
既知の背景色（RGB 0.09, 0.10, 0.12）でクリアして提出し、次のコールバックで描き直す（ADR 0144 の決定）。

- ドラッグ中に、表示リンクが取得した drawable より後でサイズが変わると、その 1 フレームは内容のない暗い面になる。
  ライト表示のヘッダ（`controlBackgroundColor`）との明暗差が大きく、ちらつきとして見えやすい。
- `CAMetalLayer` は背景色を持たない。表示面が広がる時、古い drawable の外側は次のフレームまで透明になる。
- 横方向のリサイズ（左右のペイン）にも当てはまる。症状 4 の主な候補である。

`ArrangeMeasurement.sizeMismatches` はこの提出の数を数えるが、表示リンクとウィンドウが要る計測のため、今回は実行していない。
ドラッグ中の増え方の計測と見え方の確認はユーザー担当である。

修正の方向（未決定）: 不一致の drawable にも、その実際の大きさで現在の入力を描く（左上の画素位置は入力と同じ）。
レイヤーの背景色を表示面の背景にそろえる。

## JNK-04: ピアノロールのアクセシビリティ要素の作り直し

`PianoGridView` の描画の通知（`PianoRollView.swift:111-124`）は、新しい版を描くたびに `accessibilityChildren()` を呼ぶ。
この関数（同 315-344 行）は、見えている全ノートについて、6〜8 回の地域化文字列の取得、約 10 個の属性設定、
5 個の `NSAccessibilityCustomAction` の生成を主スレッドで行う。VoiceOver などの利用の有無に関わらず実行される。

同じ処理を写した一時計測（製品のリソースバンドルの文字列を使用、5 回の最良値）:

| 見えているノート | 1 回の作り直し |
| ---: | ---: |
| 64 | 1.1 ms |
| 256 | 4.9 ms |
| 1024 | 26.8 ms |

120 Hz の 1 フレームは 8.3 ms である。リサイズの各段、スクロール、ズーム、トランスポート変更、最初の表示のたびに起こる。
ピアノロールに固有の負荷で、症状 4 でピアノロール側が目立つことと矛盾しない。
アレンジは `layoutChanged` を通知するだけで、要素は問い合わせがあった時だけ作る。
ただし支援技術や画面を読むツールが問い合わせると、全要素について画面座標の変換を行う。

修正の方向（未決定）: ピアノロールも問い合わせ時にだけ作る。フォーカスの通知に必要な要素だけを先に用意する。

## JNK-05: 分割線のドラッグごとに全体を再評価する

`WorkspaceSplitter.mouseDragged`（`WorkspaceDivider.swift:34-37`）は `state.layout` を直接変える。
`WorkspaceView.panes` がこれを読むため、ドラッグの 1 イベントごとに `WorkspaceView` 全体の body が再評価される。
`WorkspaceSession` とクロージャーは毎回作り直されるため、インスペクター、中央列、デバイス、ブラウザの子 View も更新される。
両方の表示面の `updateNSView` も毎回走る。主スレッドの時間は計測していない。

修正の前に、`os_signpost` などでドラッグ 1 イベントあたりの主スレッドの時間を測り、JNK-03・JNK-04 と切り分ける。

## JNK-06: シェーダーのコンパイル（補足）

`CanvasRenderer.init` は表示面が窓に入る時（`viewDidMoveToWindow`）に主スレッドで呼ばれ、
`ArrangePainter.init` が `makeLibrary(source:)` と 3 つのパイプラインを作る。
同じ手順を写して測った結果、新しいプロセスで最初の 1 回が 333 ms（2 回目の起動では 60 ms）、同じプロセスの 2 回目以降は約 1 ms だった。
ピアノロールを開く時点ではアレンジの表示面が先にあるため、約 1 ms で済む。症状 3 の主因ではない。
プロジェクトを開いて最初の表示面を作る時の一度の停止として残る。

## JNK-07: カメラの縦位置の書き換え

`ArrangeCamera.constrain`（`ArrangeGeometry.swift`）は、高さに対して末尾を越えないよう `originTrack` を詰める。
`ArrangePaneView.updateViewport` はその結果を保存するため、末尾までスクロールした状態でアレンジを高くすると、
トラックリストが下へ動き、低くしても戻らない。症状 2 のうち、末尾付近を表示している時だけの寄与である。
ADR 0144 が `headerWidth` に対して行った「指定値と表示値の分離」と同じ考え方で直せる。

## 症状との対応

| 症状 | 確認・有力な原因 | 候補（未計測） |
| :--- | :--- | :--- |
| 1. 再生開始 | JNK-02 → JNK-01（アレンジが 3 pt 上下を 2 回）、再生ボタンの幅の変化 | JNK-03、再生中のメーターの `TimelineView`（120 Hz）と 50 ms ごとの状態取得 |
| 2. ピアノロールのリサイズ | JNK-01（1f7a024 の回帰） | JNK-07（末尾付近）、JNK-03 |
| 3. ピアノロールの表示 | JNK-01（約 305 pt のずれ） | 新しい表示面の最初の drawable までの空白、JNK-04 |
| 4. 左右のペイン | ― | JNK-03、JNK-04（ピアノロール）、JNK-05 |

症状 4 の「左はアレンジ、右はピアノロール」という対応は、コードからは説明できない。
左右どちらの分割線も、中央列の幅を変えて両方の表示面を同じ経路でリサイズする。
もう一方の組合せ（左でピアノロール、右でアレンジ）もがくつくかを、ユーザーに確認する。

## 実画面で確認してほしいこと

自動の計測では、合成後の画面と表示リンクの時刻は分からない。修正の前後でユーザーに次を確認してもらう。

- エディタ境界をゆっくり動かした時、トラックリストと鍵盤がドラッグに合わせて上下するか（JNK-01）。
- ライト表示で左右のペインを動かした時、表示面が一瞬暗くなるか、右端が一瞬抜けるか（JNK-03）。
- ノートの少ないトラックと多いトラックで、右ペインを動かした時の滑らかさが違うか（JNK-04）。

## 修正の進め方

実行役向けに、修正の順番・場所・修正前の再現・回帰・受入を置く。
各単位は AGENTS.md と [開発手順](../development.md) に従う。製品の View を画面なしで動かして修正前に失敗させてから直し、
同じ作業で ADR・必須契約・診断を更新する。
Swift の指摘なので `make known-bugs`（Rust の `audit_` テスト）の対象外であり、各単位の回帰を修正と同時に足す。
実画面の見え方はユーザー担当とし、自動検査の合格と区別して報告する。アプリの起動と表示リンクを開く計測は、依頼がない限り行わない。

単位 1・2 は原因が確認済みで小さく、互いに独立している。先に終える。3 以降は 1・2 の後に行う。
ユーザーの回答を待たずに進めてよい。回答で変わりうるのは単位 4・6 の優先度だけである。

### 単位 1: 古い絵を見た目の左上に固定する（JNK-01）

- 場所: `CanvasSurface.swift:17` の `layer.contentsGravity = .topLeft`。
- 修正前の再現: `CanvasResizeTests` で、製品の `ArrangeView` と `PianoGridView` の `layer.contentsAreFlipped()` が true であり、
  `contentsGravity` が見た目の左上に当たる `.bottomLeft` ではないことを失敗として示す。
  単独の View と、製品と同じ反転した階層（`ArrangePaneView` → `ArrangeView`、`PianoRollView` → `PianoGridView` を `NSHostingView` に載せる）の両方で見る。
- 修正: 上書きを消し、`layerContentsPlacement = .topLeft` から AppKit が決める値（反転した階層では `bottomLeft`）に任せる。
  一時計測では、AppKit は `CAMetalLayer` の表示面にもこの変換を行い、ウィンドウへ入った後も `bottomLeft` を保った。
  明示的に設定する場合は、`contentsAreFlipped()` から選び、階層が変わる時（`viewDidMoveToWindow` 等）にも選び直す。
- 回帰: `contractCanvasResizeAnchorsOldContentsAndSizesDrawablesImmediately` の `contentsGravity == .topLeft` の期待を、
  「`contentsAreFlipped()` なら `.bottomLeft`、そうでなければ `.topLeft`」へ変える。サイズ変更・ゼロ・端数の後も保つことを見る。
  `canvas-resize-ui` の負の対照に、`.topLeft` の上書きを戻すコピーを加える（既存の配置の負の対照も残す）。
- 受入: 自動回帰の合格。エディタ境界のドラッグとピアノロールの開閉で上下のずれが消えたかは、ユーザー確認。

### 単位 2: 状態行と再生ボタンの寸法を固定する（JNK-02）

- 場所: `WorkspaceView.swift:19-25` の状態行、`WorkspaceTransportView.swift:19-21` の再生ボタン。
- 修正前の再現: 状態行を `WorkspaceStatusBar` のような小さな View に切り出し（表示内容は変えない）、
  待機中と再生準備中を `NSHostingView` に載せて高さが違う（29 / 32 pt）ことを失敗として示す。
  再生ボタンも、再生と一時停止で幅が違うことを示す。
- 修正: 状態行は表示器の場所を常に確保するか、行の高さを表示器の高さ以上に固定する。表示器は準備中だけ見せる。
  再生ボタンは、両方のラベルを重ねて片方を隠す（`ZStack` と `hidden()` 等）ことで、言語に関わらず広い方の幅に固定する。
  アクセシビリティのラベルは現在の状態だけを読む。
- 回帰: 待機中と準備中で状態行の高さが等しい、再生と一時停止でボタンの幅が等しい。新しい必須契約（例: `transport-layout-ui`）にし、
  負の対照は条件付きの `ProgressView` の挿入へ戻すコピーにする。
- 受入: 自動回帰の合格。再生開始時の見え方はユーザー確認。

### 単位 3: ピアノロールのアクセシビリティ要素を問い合わせ時に作る（JNK-04）

- 場所: `PianoRollView.swift:111-124`（描画の通知での `accessibilityChildren()` の呼出し）、同 315-344 行。
- 修正: 描画の通知では `elements` と `submittedFrame` の更新、`layoutChanged` の通知だけにする。
  要素は `accessibilityChildren()` が呼ばれた時に作り、作った版を覚えて同じ版では再利用する。
  フォーカスの通知（`focusedUIElementChanged`）に要るフォーカス中のノートの要素だけは、通知の時に作る。
- 回帰: 描画の通知を複数回送っても、問い合わせがなければ要素を作らない（作成回数の数え上げ）。
  問い合わせた時は従来と同じラベル・操作・フォーカスを返す。
  現在、ピアノロールの要素を検査する自動回帰はない（`accessibilityChildren()` がウィンドウを要求するため）。
  要素の組立てを、フレームと画面座標の変換を受け取る関数に分け、ウィンドウなしで検査できるようにする。
- 受入: 自動回帰の合格。VoiceOver の操作感はユーザー確認。

### 単位 4: サイズ不一致の時も内容を描く（JNK-03）

- 場所: `CanvasRenderer.swift:247-254`、描画は `ArrangePainter.encode`、オフスクリーンの描画は `ArrangeOffscreenProbe.swift` の `renderOffscreen`。
- 修正: drawable の大きさが入力と違う時も、背景だけで提出せず、その drawable の実際の大きさで現在の入力を描く。
  画素の座標は入力と同じにし、はみ出す部分は切る。シザー矩形は drawable の範囲へ制限する。版は従来どおり消費せず、次のコールバックで正しい大きさを描き直す。
  あわせて `CAMetalLayer.backgroundColor` を表示面の背景色にそろえ、拡大時の露出部を透明にしない。
- 回帰: オフスクリーンの描画に、入力と違う大きさのテクスチャへ描く経路を足す。
  同じ大きさで描いた結果と、重なる範囲の左上の画素（ヘッダの文字・行境界）が一致することを見る。
  背景だけを描く旧実装へ戻すと失敗する。`make spike-arrange-frame` / `spike-piano-frame`（画面を開かない）の比較点も見直す。
- 診断: `ArrangeMeasurement.sizeMismatches` の意味（クリアした数 → 大きさの違う drawable に描いた数）を debugging.md で更新する。
- 受入: 自動回帰の合格。ドラッグ中のちらつきの有無と sizeMismatches の実測（表示リンクが要る）はユーザー確認。

### 単位 5: アレンジの縦位置の指定値を保つ（JNK-07）

- 場所: `ArrangeGeometry.swift` の `ArrangeCamera.constrain`、`ArrangePaneView.updateViewport`。
- 修正: 利用者がスクロール・ズームで決めた縦位置を保持し、表示の時だけ高さで制限する（ADR 0144 の `headerWidth` と同じ分離）。
  `CanvasNavigationState.arrange` にも指定値を記憶する。
- 回帰: 末尾までスクロールした後、高さを大→小と往復しても縦位置が戻る。高さ 0 を挟んでも失わない。
- 受入: 自動回帰の合格。

### 単位 6: ドラッグの主スレッドの時間を測ってから決める（JNK-05）

- 測る: 分割線の `mouseDragged` から CA のコミットまでの主スレッドの時間を `os_signpost` で区切り、`make debug-report` で読めるようにする。
  画面なしでは、`WorkspaceView` 相当の階層を `NSHostingView` に載せ、配置の値を変えて `layoutSubtreeIfNeeded` までの時間を測る。
- 決める: 1 イベントが数 ms を越えるなら、配置の状態を読む View を分けて、ドラッグで再評価される範囲を中央列と分割線に限る。
  越えないなら修正せず、測定値をこの単位の ADR か status に残す。

### 対象外

- JNK-06（最初の表示面のシェーダーコンパイル）は症状の主因ではないため、今回の修正に含めない。
  直す場合は、事前にコンパイルしたライブラリか、プロセスで共有する描画器を比べて ADR に書く。
- 再生中のメーターの `TimelineView`（120 Hz）と 50 ms ごとの状態取得は、単位 1・2 の後もユーザーが再生中のがくつきを報告した時に測る。
