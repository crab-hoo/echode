# 2026-11-02 コード品質とエージェント環境の横断監査

## 対象と判定の境界

- 対象: `0104720` と、開始時の未コミット変更 34 件。
  未コミット分は別セッションが進行中の ADR 0228 の作業であり、指摘の対象にしていない。
- コードの品質、保存の耐久性、リアルタイム処理、隔離の境界、検査基盤、CI、エージェントの環境、資料を横断した。
- 全行の通読ではない。
  精読したのは、オーディオコールバックからプラグイン収集まで、共有領域、保存・ジャーナル・復旧、API ソケット、検査の実行器、フック、CI である。
  Swift と残りの Rust は計数と抜き取りで判断した。
- 実機・聴感・実画面は対象外とした。アプリも音声機器も開いていない。
- 製品の処理は変更していない。監査の記録だけを追加した。
- 手順と出力の要約は [保存の耐久性の追跡](../evidence/2026-11-02-durability-trace.md) に置く。

## 総評

個々のコードの質と検査の厳密さは、プロの水準を超える部分が多い。
弱点はコードの外側と境界にある。
保存の同期の順序、ソースと証拠が 1 台にしかないこと、エージェントごとに違う防護、資料の量の 4 つを先に直す。

| 領域 | 評価 | 根拠 |
|---|---|---|
| リアルタイム処理の設計 | A- | 確保の検出と RTSan の二重の検査。トラック数の 2 乗の処理が残る（XCA-13） |
| プラグイン隔離 | A- | ヘルパーの値を範囲検査し、NaN は 1 トラックで止まる。走査の Seatbelt は未実装（既知） |
| モデルと履歴の正しさ | A- | 登録簿の共有、性質テスト、不変条件の検査 |
| 保存のクラッシュ耐久性 | C | ジャーナルの同期は堅いが、圧縮と保管物の順序に穴がある（XCA-01〜03） |
| Swift アプリ | B+ | Swift 6 の厳密な並行性、`try!`・`as!` は 0 件、`@unchecked Sendable` は 4 件。整形と lint がない |
| 検査の厳密さ | A | 239 契約すべてに反例があり、結果を入力のハッシュへ結び付ける |
| 検査の運用コスト | C+ | 実行時間は改善したが、高コストの罠と資料の更新量が残る（XCA-08・09・10） |
| CI と継続性 | D | リモートより 121 コミット先行し、CI の証拠がない（XCA-04・05） |
| エージェントの環境 | B- | 入口と診断は優秀。防護がエージェントごとに違う（XCA-06・07） |
| 依存とライセンス | A- | ライセンスを常時検査し、既知の脆弱性なし。バージョンの一元化は未完 |

評価は監査者の判断であり、測定値ではない。

## P1 の詳細

### XCA-01: 同期していないコミットを前提にジャーナルを圧縮する

- 場所: [host.rs](../../crates/echode-history/src/host.rs) の `finish_saves`（950 行〜）、
  [document.rs](../../crates/echode-history/src/document.rs) の `commit_tree`（659 行〜）と `compact_journal`（254 行〜）。
- 製品の経路の追跡で、次の順序を確認した。
  ジャーナルの追記は同期するが、Git のオブジェクトと参照は名前を変えるだけで同期しない。
  その後、次の要求の手番でジャーナルを同期付きで置き換え、その編集の行を消す。

  ```text
  FULLFSYNC journal.jsonl                       編集の確定
  RENAME    .git/objects/xx/...（5〜7 個）      同期なし
  RENAME    .git/refs/echode/autosave/main      同期なし
  FULLFSYNC .git/echode-commit-chain            この 1 ファイルだけ
  FULLFSYNC .journal.jsonl.tmp → RENAMEAT journal.jsonl  行を削除
  ```

- 使用中の gix-odb 0.75.0・gix-ref 0.58.0・gix-tempfile・gix-lock のソースに同期の呼出しはない。
- 影響: 確定を返した編集の唯一の同期済みの写しを、まだ同期していないコミットと引き換えに消す。
  電源断やカーネルパニックが圧縮の後に来ると、編集が失われる。
  プロセスの異常終了だけなら OS のキャッシュが残るので起きない。
- 再現: 実際の電源断は行っていない。失われ得る状態をコピー上で作り、製品の CLI で開いた。
  先端と親のコミットのオブジェクトを消すと、`third` の編集はどこにも残らない（追跡の S3）。
- 修正方針: 圧縮の前に、そのコミットで書いたオブジェクト・参照・親ディレクトリを同期する境界を 1 か所に置く。
  毎コミットの同期が重ければ、圧縮を保存時・閉じる時・一定間隔へ減らし、同期の直後だけ圧縮する。
- 修正条件: 同じ追跡で、`journal.jsonl` の置換より前に対象の全ファイルの同期が現れること。
  自動保存の時間を測り、文書ワーカーを塞がないこと。

### XCA-02: 連番の欠けを検知せず、同期済みの行を黙って無視する

- 場所: [document.rs](../../crates/echode-history/src/document.rs) の `contiguous_suffix`（1269 行〜）。
- 先端の連番の次から連続する行だけを再生し、欠けの後ろの行は理由を返さずに除く。
- 再現（追跡の S1）: 参照だけを連番 2 のコミットへ戻し、ジャーナルに連番 4 の行を残した。
  開くと `piano, first, second` で成功する。`third` と、同期済みの `fourth` が消える。
  復旧の確認も求めず、次の編集を受け付ける。
  読めない先端の場合（S3）は [ADR 0183](../decisions/0183-recovery-consent.md) の確認が働くので、この経路だけが抜けている。
- [ADR 0180](../decisions/0180-journal-replay-invariants.md) と設計書の「完結した行を黙って切り捨てず」に反する。
- 検知の材料はある。`.git/echode-commit-chain` は同期済みで、S1 では最新の行が参照の先端より新しかった。
- 修正方針: 欠けと、参照がチェーンの最新より古い状態を、読めない先端と同じ復旧の確認へ送る。
  チェーンの最新が読めるなら、参照をそこへ進めて復旧する。
- 修正条件: S1 の状態で、編集の前に通知され、同意まで書込みを拒否すること。
  正常な連続・空のジャーナル・既存の復旧の回帰を変えないこと。

### XCA-03: 保管物を同期せずに参照し、壊れると再取込みでも直らない

- 場所: [objects.rs](../../crates/echode-history/src/objects.rs) の `write_object`（30 行〜）。
  音声の取込みと、[host.rs](../../crates/echode-history/src/host.rs) の `commit_plugin_state`（257 行〜）、
  [device.rs](../../crates/echode-document/src/device.rs)（263 行）のプラグイン状態が使う。
- 追跡では `media/objects/<hash>` と `media/index.json` を同期なしで名前変更し、直後にそれを参照する行を同期している。
  保管物は `.gitignore` の対象なので、Git の履歴にも残らない。
- 再現（追跡の S4）: 保管物を 0 バイトにすると、文書は警告なしで開く。
  書出しは `audio file could not be read` で止まる。
  元のファイルから再取込みしても `object ... already holds different bytes` で拒否され、製品の操作では直せない。
- 修正方針: 参照する行を書く前に、保管物とディレクトリを同期する。
  既存の内容が名前のハッシュと一致しない時は、壊れた保管物として正しい内容へ置き換える。
- 修正条件: 追跡で保管物とディレクトリの同期が行の同期より前に現れること。S4 の再取込みで復元できること。

### XCA-04: ソースが 1 台にしかない

- `git status -sb` は `ahead 121`。`git ls-remote` でリモートの `main` が古いままであることを確認した。
- この間の設計・実装・監査のすべてが、空き 10 GiB（使用率 98%）の 1 台にある。
  Time Machine などの別経路の有無は確認していない。
- 修正方針: ユーザーの判断でプッシュする。AGENTS の規則により、エージェントは依頼なしにプッシュしない。
  以後はプッシュの間隔を決める。
- 状態: 2026-11-02、ユーザーの依頼で `main` を `origin` へプッシュした。プッシュの間隔は未決である。
  2026-11-05、GitHub の公開リポジトリへの移行を準備した（[ADR 0269](../decisions/0269-github-public-ci-scope.md)）。GitHub へのプッシュはユーザーが行う。
  同日、ユーザーが非公開の GitHub リポジトリへ `main` をプッシュした。公開への切り替えは未実施である。
  2026-11-08: プッシュとその間隔はユーザーに予約した（[ADR 0276](../decisions/0276-priority-order-and-delegated-decisions.md)）。エージェントは頼まれた時だけプッシュする。

### XCA-05: CI の証拠がない

- リモートは GitHub ではない（`origin.cursor.com`）。
  [check.yml](../../.github/workflows/check.yml) が動く経路を確認できず、少なくとも未プッシュの 121 コミットは検査されていない。
- それでも [検査手順](../verification.md) は「全体の段階も CI の全件に含む」と書く。
- ワークフローにも問題がある。`check_build_host.py` は M4 以降を要求するが、`xcode-27` のランナーがそれを満たすか未確認である。
  `push` と `pull_request` の両方で起動し、`permissions` がなく、アクションをタグで固定している。
- 合否の証拠は `target/` のローカル記録だけで、変更した本人の環境でしか作られない。
- 修正方針: 次のどちらかに決める。
  このマシンで定期的に、きれいな複製から `make verify-full` を実行して要約を残す。
  または、CI はないと資料に明記してワークフローを削除する。
- 状態: 2026-11-05、GitHub に M4 のランナーがないため、CI を `make check-portable` と advisory に限った。
  権限を読み取りに絞り、アクションを SHA で固定した（[ADR 0269](../decisions/0269-github-public-ci-scope.md)）。
  ネイティブの検査はローカルの `make verify` のままにした。
  同日、非公開のリポジトリで旧ワークフローが初めて動いた。ネイティブ検査は M1 のランナーで想定どおり止まった。
  advisory はツールチェーンの未導入で失敗したので、新しいワークフローに導入手順を足した。
  新しいワークフローの初回では advisory が合格し、`check-portable` は署名の検査で止まった。ランナーがライブラリ検証を強制しないためで、対照で判定する形に直した。
  修正後の `296be7a` で、GitHub の両方のジョブが合格した。
  同日、全体の段階（サニタイザと全契約の反例）も GitHub の M1 のランナーで実行することにした（ADR 0269 の追記）。
  `a9a0cf6` の実行 42012602915 で全 7 ジョブが合格した。作業の段階はローカルの `make verify` のままである。

## P2 の詳細

### XCA-06: 防護がエージェントごとに違う

- Claude Code: `.claude/` に設定がなく、編集の待機も終了時の検査もない。
  今回のセッションでも `make agent-context` は `lock: BUSY` を表示したが、止めるものは規律だけだった。
- Codex: [hooks.json](../../.codex/hooks.json) は開発者の絶対パスを書き、worktree からも本体のロックを見る。
  matcher は Cursor の道具名の写しで、`check-on-stop.sh` は接続されていない。
  応答の形も [wait_for_verify.py](../../scripts/wait_for_verify.py) の Cursor 向けのままである。
- Cursor: 動くが、`Shell` を一律に待たせるので、読むだけのコマンドも最大で 15,590 秒止まる。
- 回帰は上限の秒数だけを照合し（`test_hook_budgets_cover_serial_checks_and_lock_wait`）、発火は照合しない。
- 検査中の編集は結果を `stale` にするので、誤った合格にはならない。失うのは時間である。
- 修正方針: ホストごとの薄い変換を置き、Claude Code に `PreToolUse` と `Stop` を追加する。
  Codex は相対パスと実際の道具名へ直す。各ホストの入力の見本で応答の形を検査する。
- 後続対応（2026-11-02）: Claude Code の `PreToolUse`（編集ツール）と `Stop` を `.claude/settings.json` に置き、
  `test_agent_hooks.py` で応答の形と予算を検査する。Codex は道具名を確かめられず、再び信頼する手順も要るため未対応である。
  2026-11-08: 修正はエージェントが行い、Codex が設定を再び信頼する手順はユーザーが Codex を使う時に行う（[ADR 0276](../decisions/0276-priority-order-and-delegated-decisions.md)）。

### XCA-07: 同じ作業ツリーの共有で完了条件が互いに依存する

- 今回の監査中、`make verify` は別の作業の `contractHeaderResetWaitDoesNotBorrowTheNextControlsPress` で失敗していた。
  文書だけのこの監査も、相手の修正と再実行が終わるまで書込みと完了の検査を待った。
- `make agent-context` の変更 34 件は全セッションの合算で、どの作業の変更かを区別しない。
- worktree は容量の理由で避けている（`target` が 1 本で 25 GB 前後）。判断はユーザーに属する。
- 修正方針: 検査のキャッシュの共有で worktree を軽くするか、同時に走らせる作業を 1 つに制限するかを決める。
- 2026-11-08: `main` の単一の作業ツリーを既定とし、他の作業の失敗では待って再実行し、なお止まれば根拠を最終報告に残すと決めた（[ADR 0276](../decisions/0276-priority-order-and-delegated-decisions.md)）。

### XCA-08: 見送りの理由が実態と合わなくなる

- [verify.py](../../scripts/verify.py) の `--defer` は複数指定でき、`--reason` は 1 つだけである（907・908 行）。
- 監査の開始時の記録では 10 件が同じ理由を持っていた。「実ウィンドウ操作の明示依頼はなく、プレイヘッドの時計・寿命は変更していない」。
  この中には `spike-isolation` と `spike-audio` があり、理由はそれぞれの検査の目的を説明していなかった。
  監査の途中で別のセッションが再実行し、2 種類の理由（6 件と 4 件）へ書き換えた。起動を分ければ改善できるが、1 件ずつの理由にはならない。
  `advisories` の理由は「計測専用コードの分離」のままで、前の作業のものが残っている。
- AGENTS の「候補を一律に実行せず、検査の目的と今回の影響を確認します」が、仕組みとして強制されていない。
- 今回 `cargo deny check advisories` を手で実行し、結果は `advisories ok` だった。
- 修正方針: `--defer ID=理由` の組にする。最終報告に検査ごとの理由を表示する。
- 後続対応（2026-11-03）: `--defer ID=理由` にし、`--reason` は 1 件の時だけ受け付ける。
  `make verify` の最後と `report.md` に、見送りを理由と記録日時で示す（[ADR 0233](../decisions/0233-verification-deferral-reasons-and-traps.md)）。

### XCA-09: 避けられる高コストの罠

- `--defer` は記録だけの操作に見えるが、選択された自動検査をすべて実行する（`verify.py` 792 行〜）。
- `make -s verify` は `MAKEFLAGS` の違いで全検査の結果を無効にする。資料には書いてあるが、罠のままである。
- 空き容量は記録するだけで（`verification_metrics.py`）、事前確認がない。
  資料には反例の `cargo` が 26 GB に達したとあり、現在の空きは 10 GiB である。
- Swift の 274 テストに `.timeLimit` は 0 件で、1 件の待ち続けで全体の期限（1,200 秒）まで止まる。

### XCA-13: オーディオスレッドのトラック数の 2 乗の処理

- [plugins.rs](../../crates/echode-engine/src/plugins.rs) の `submit`（732 行）と `apply`（835 行）は、トラックごとに一覧を線形に探す。
- `collect`（761 行〜）は起床のたびに待ち中の全トラックを調べ、完了が順に来ると起床数はトラック数に比例する。
- [playback.rs](../../crates/echode-engine/src/playback.rs)（650 行）はトラックごとにそのブロックの全イベントを走査する。
- AGENTS は、プロジェクト全体の大きさに比例する処理を禁じ、トラック数の上限も禁じている。
- 測定はしていない。読解に基づく指摘である。[S3](../spikes/S3-plugin-isolation.md) の比較はヘルパー 1 個と 2 個である。
- 修正方針: 計画の構築時に添字を決めて探索をなくし、完了の順に処理する。
  プラグイン付き 256 トラック以上の release 計測を足し、改善前の値を先に取る。
- 後続対応（2026-11-03）: `make spike-plugin-tracks` で改善前の値を取った（[ADR 0236](../decisions/0236-callback-work-per-track.md)）。
  最大の 2 乗はイベントの走査で、プラグインなしの 256 トラックの和音で 1 ブロックの p99 が 752 µs、修正後は 208 µs だった。
  ブロックのイベントと追いかけのノートオンをトラックごとに 1 回で振り分け、`submit`・`apply` と停止の後始末はキーの索引で引く。
  `collect` の全走査は、256 トラックでブロックあたり約 1.1 回で、2 乗の形では現れなかったため変えていない。

### XCA-14: コールバックの panic

- [stream.rs](../../crates/echode-audio-io/src/stream.rs) の `render`（748 行）と試聴の `render` は `extern "C-unwind"` で、`catch_unwind` がない。
  release も `panic = unwind` のままなので、panic は CoreAudio のフレームへ伝わる。
- 経路には添字の式が残る（`plugins.rs` の `self.tracks[index]`、`output[0][..frames]` など）。
- FFI の 45 関数は `extern "C"` で、panic は即時に異常終了する。メモリの安全は保たれるが、理由が残らない。
  panic フックがなく、GUI では標準エラーの内容が見えない。
- panic は再現していない。
- 修正方針: コールバックで捕まえ、`failed` を立てて無音にする。panic フックで理由をファイルへ残す。
  音声の経路のモジュールで `clippy::indexing_slicing` を有効にする。
- 後続対応（2026-11-03）: 出力と試聴のコールバックで捕まえ、そのブロック以降を無音にした（[ADR 0238](../decisions/0238-audio-callback-panics.md)）。
  オーディオスレッドではフックが場所と文を前もって確保した領域へ写すだけで、制御スレッドが記録へ書く。
  アプリはほかのスレッドの panic も `~/Library/Logs/Echode/panic.ndjson` へ残す。
  デバッグの `GuardAlloc` が panic 自身の確保で異常終了し、理由が消えていたことも分かり、panic 中の確保を許した。
  `clippy::indexing_slicing` は未着手で、`echode-engine` だけで約 140 か所ある。

### XCA-15: `unsafe` の根拠

### XCA-17: fuzz とカバレッジ

### XCA-18: Rust 以外の整形と lint

## 監査で否定した仮説

- 出力のないプラグインで `output[0]` が panic する: `plugins.rs` 1559 行が 1〜2 チャンネル以外を拒否する。
- ヘルパーが共有領域の値を偽って範囲外を読ませる: フレーム数とイベント数はホストの配置で検査する（`region.rs` 537・891 行）。
- 1 つのプラグインの NaN で全体が無音になる: `mix.rs` 122 行が 1 トラックの範囲で止める。

- 親プロセスのライブラリ検証の無効化: ヘルパーの権限だけで、本体の権限は空である。

- Swift の強制終了: `fatalError` 12 件はすべて `init?(coder:)` で、`try!`・`as!` は 0 件。

## 保たれている構造

- `define_actions!` と項目表が、モデル・ジャーナル・保存・Swift の型を生成する。
- 239 の契約すべてに反例があり、削除・無視・0 件の実行を合格にしない。
- 検査の結果を入力とツールのハッシュへ結び付け、編集で失効させる。
- `make agent-context` の一括診断と、根拠付きの節・行の読込みは、他で見ない水準である。

- 監査で見つけた誤りを lint と回帰へ移す習慣がある。
