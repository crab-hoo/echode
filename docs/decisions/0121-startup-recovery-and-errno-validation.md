# ADR 0121: 起動復旧の終了待ちと errno 検査ランタイムを修正する

- 日付: 2026-10-19
- 状態: 採用
- 範囲: 保存初期化エラー時の終了、起動後の文書操作、機器なしの Darwin TSan 検査

## 新規作成が無効になった原因

起動時に前回の文書を復元する処理が失敗し、`Autosave` の破棄が完了しなかった。
Git の初期化に失敗したワーカーは、後続要求へエラーを返す待機ループへ入る。
このループが `Shutdown` も通常要求として捨て、再び受信待ちになっていた。
一方、破棄側は送信元を保持したままワーカーの終了を `join` で待っていた。
文書の非同期処理が戻らず、画面の `busy` が解除されないため、新規作成と開く操作が無効のまま残った。

エラー待機ループでも `Shutdown` で終了するよう修正する。
正常な保存・復元の検査だけでは、この初期化失敗後の終了待ちを検出できなかった。
実際に Git 初期化が失敗する検証用パッケージを作り、製品の `DocumentHost::open` を子プロセスで呼ぶ。
親プロセスの期限で従来のハングを検出し、修正後はエラー返却、パッケージの保持、ロック解放、再オープンを検査する。
Swift 側でも、起動復元エラー後の新規作成・開く操作の有効化、新規文書へのトラック追加を確認する。
必須契約 `startup-recovery` の負の対照は、終了条件を外して同じハングを戻す。

実アプリの起動・終了・新規作成はユーザーが担当した。
修正版 `target/Echode.app` で「作成してトラックを追加できた」と確認された。
当時の読み取り専用スタック、失敗・成功ログ、確認記録は `target/new-project-audit/` と関連ログに保持する。
ユーザーの既存文書は修復・書き換えしておらず、最初に Git 初期化が失敗した理由までは確定していない。

## errno 警告の原因

これは上記の終了待ちとは別の問題である。
`errno` は OS のエラー番号を持つスレッド固有の変数であり、通常は別スレッド間で共有しない。
終了済みと新規のスレッドの同一アドレスを競合として報告する現象は、C と pthread だけでも再現した。
Echode、Rust、Swift、オーディオ機器を含める必要はなかった。

[LLVM の Darwin TLS 範囲取得](https://github.com/llvm/llvm-project/blob/llvmorg-22.1.2/compiler-rt/lib/sanitizer_common/sanitizer_mac.cpp) は、arm64 の TLS サイズを 0 とする。
[TSan のスレッド開始処理](https://github.com/llvm/llvm-project/blob/llvmorg-22.1.2/compiler-rt/lib/tsan/rtl/tsan_rtl_thread.cpp) は、その範囲がある時だけ TLS の新しい寿命を記録する。
pthread が errno の領域を再利用すると古いアクセス履歴が残り、終了済みスレッドとの誤った競合になる。
同じ LLVM 版・同じ起動互換修正で、errno の寿命処理だけを切り替えた対照により切り分ける。
ADR 0114・0118 の当時の未解決記録と失敗証拠は変更しない。

## 検査専用ランタイム

LLVM 22.1.2 のコミット `1ab49a973e210e97d61e5db6557180dcb92c3e98` を固定する。
Apache-2.0 WITH LLVM-exception の公式 compiler-rt ソースへ、登録したパッチを適用して検査専用にビルドする。
新しい OS スレッドの開始時だけ errno のシャドウ履歴を初期化する。
実スレッドを作らない Fiber の切替では初期化せず、実行中の読み書きへの計装を保つ。
抑制、検査対象の除外、テストの直列化、偽の同期は追加しない。
TSan の通常のシャドウセル単位で処理し、errno を含むスレッド固有領域の再利用を扱う。

この LLVM 版の macOS 27 での起動には、dyld の検索が初期化途中のフレームワークを呼ぶ別の問題もあった。
SDK の公開 `TASK_DYLD_INFO` と `dyld_all_image_infos` からロード先を取得し、初期化中の再入を避ける。
この起動互換修正は負の対照と修正版の両方へ適用し、errno の修正効果と混ぜない。
公開ヘッダを使い、新しい非公開 Apple API の宣言や呼出しは追加しない。

`make setup-bridge` がネットワークを使って固定ソースを用意する。
通常の検査中は取得・再ビルドせず、準備が古ければ失敗してセットアップを案内する。
生成物は `target/toolchains/tsan/` に閉じ、Xcode・Rust のインストールや製品アプリを置き換えない。
Rust の標準ライブラリ・依存も計装し、Swift と同じ修正版ランタイムをロードする。
実際のロード先を検査し、Apple のランタイムとの混在や取り違えを失敗にする。
マニフェストと両ランタイムの実バイトを検査入力へ含め、差し替え後に古い合格を再利用しない。

## 回帰と診断

- `check-tsan-runtime` は同じ C プローブで、寿命修正を外した時の警告と、修正版での 2,400 回のスレッド生成を確認する。
- 同検査は、生存中の別スレッドの errno を意図的に共有した実競合が、修正版でも検出されることを要求する。
- `check-bridge-tsan` は Rust・Swift それぞれの実競合の検出対照と、製品の編集・保存・復旧を通す。
- 詳細ログは `target/bridge/thread/errno/` と従来の bridge 検査出力へ保存する。
  `make debug-report` はランタイムの識別情報と対照ログも収集する。

修正前の独立再現と調査ログは `target/errno-investigation/`、正式な合否は検査レポートを参照する。
この修正を、実 HAL の別の警告、全 TLS 変数のモデル化、実機・聴感検査の合格へ一般化しない。
