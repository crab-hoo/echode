# ADR 0195: 検査コストを継続記録し、反例のビルドだけを共用する

- 日付: 2026-10-29
- 状態: 採用
- 対象: 製品契約、検査実行器、検査時間の診断
- 前提: [ADR 0148](0148-verification-pipeline-speed.md)、[ADR 0166](0166-verification-failure-detection.md)

- 後続: [ADR 0198](0198-verification-launch-and-cache-cost.md) が診断コードの入力境界、反例の起動・ビルド共有を改定した。
## 調査

対象は `8ef044e` と、その上の検査基盤の未コミット変更である。
開始時の作業ツリーは変更なし、検査ロックは空いていた。
直近の保存結果で `check-product-contracts` は 1659.207 秒、通常検査は 191.241 秒だった。
同じ実行予定の ASan は 78.718 秒、TSan は 83.674 秒、基盤検査は 51.403 秒だった。
旧レポートに呼出し全体の実測はなく、この和を正確な総所要時間とは扱わない。

製品契約は Rust 75 件・反例 82 個、Swift 121 件・反例 197 個に増えていた。
その回は Rust 75 件が再利用され、Swift は 121 件とも通常実行と反例をやり直していた。
Swift のパッケージ全体は全 UI 契約の入力であり、小さな UI 変更でもこの集合が失効する。
共有コードとテスト補助の依存を証明せず、ファイル名だけで失効範囲を狭めない。

197 個の反例の保存ログでは、Swift ビルドは平均 11.381 秒、最大 30.490 秒だった。
これは並列ビルドの作業時間であり、合計を壁時計の所要時間に置き換えない。
`swift build --build-tests` はテスト以外にアプリと 2 種のプローブもリンクしていた。
ADR 0148 の計測時の Swift 反例は 38 個で、当時の所要時間を現在の件数へそのまま期待できない。
同一の反例を複数契約に登録した場合も、従来はビルドを繰り返していた。

同じ持続コピーで、通常ソースをビルドしてから `clip-gesture-document-ui` の最初の反例を入れる比較を行った。
全製品ビルドは 8.118 / 8.193 秒、テスト製品指定は 6.796 / 6.734 秒だった。
各回は元のソースをビルドし直して開始し、実テスト 1 件が期待値で失敗することも照合した。
同じ反例を連続投入しただけの値は、Swift の内容ベース再利用を混ぜるため比較から除いた。
これはウォーム状態の単一反例の測定であり、全件の改善率ではない。

3 コピーの同時ビルドで、各 Swift ビルドのジョブを既定値から 3 へ減らす比較も行った。
同じ 3 反例のビルドとテストは 23.417 / 23.388 秒に対し 22.940 / 22.945 秒で、差が小さいため固定化しない。
共有ホストで外部の仮想機械の負荷も観測したが、過去の検査の負荷は記録がなく、遅延の原因と断定しない。
他のアプリは終了・変更していない。

## 決定

- Swift 契約の `build_product` を `verification.json` に宣言し、`EchodeAppTests` をビルドする。
  通常の `check-base` はアプリとプローブのビルドを維持する。
  テスト数、期待値、警告のエラー化、機器なしの製品経路は変えない。
- 同じパッケージ・ビルド対象・ファイル・置換前後の反例はビルドだけを共用する。
  反例を混ぜず、各契約のテストは別プロセスで実行する。
  各契約の期限から共用ビルドの時間を引き、最短の期限でビルドする。
- 同じ変更ファイルの反例をまとめ、無関係なファイルの復元ビルドを減らす。
  ビルドは従来の最大 3 コピー、テスト中には他のビルドもテストも走らせない。
  全反例が完了した契約だけを直ちに保存し、中断時もソースを復元する。
- 契約の `seconds` に他契約を待つ時間を混ぜない。
  通常実行、同期、Rust 反例、Swift 反例、ビルド数・反例数、ビルド作業秒と直列テスト秒を記録する。
  並列作業秒と段階全体の実測秒は区別する。
- 呼出しごとの全体秒、実行した検査、再利用した検査、失敗、ソースとツールの識別値、契約数を残す。
  `timing-history.jsonl` は診断用の履歴であり、合格再利用の入力にはしない。
  中断して `running` のままの記録は完了した時間計測ではない。
  開始・終了時の CPU 数、負荷平均、空き容量も診断に残し、負荷変動を合格失効の条件にはしない。
- `make verification-profile` で既存結果と時間履歴を読む。検査実行や合格登録は行わない。
  古い結果の秒数を今回の所要時間へ足さず、旧形式は情報不足と表示する。
  `make debug-report` も時間履歴を収集する。
- 全件失効時に、Rust 反例だけで 1106.385 秒を要し、旧一括予算 1800 秒へ到達した。
  完了した 113 契約を再利用した再開では、残りの契約は 1241.703 秒で完了した。
  この 2 回は部分再利用と通常テストのやり直しを含むので、全件 1 回の所要時間とは扱わない。
  一括予算を 3600 秒へ合わせる。個別契約の期限と期待値は維持し、予算変更を高速化とは主張しない。
  一括検査の予算・選択用メタデータを個別契約の識別から外し、予算調整だけによる全契約の再失効を防ぐ。
  レシピ、実行器、ツール、契約定義、入力の失効は維持する。
  中断時にも反例の完了数と経過秒を保存し、どの段階で予算に達したかを次回区別できるようにする。
- OS の識別からネットワークで変わるホスト名だけを除く。
  OS、カーネル、アーキテクチャ、コンパイラー、設定、検査入力による失効は維持する。
  全件失効が別の遅延原因になることは既知だったが、従来は修正されていなかった。

## 全件実行の記録と限界

一括予算を見直した後の `make verify` では、再利用なしの製品契約が 2849.608 秒で完了した。
内訳は通常実行 302.860 秒、コピー同期 0.700 秒、Rust 反例 1077.428 秒、Swift 反例 1458.876 秒だった。
Swift の反例 197 個は 191 ビルドで検査し、直列テストは 554.723 秒を占めた。
並列ビルドの作業秒は 2565.894 秒で、壁時計の時間へ足し込まない。

開始時の負荷平均は 2.642 / 4.463 / 6.258、CPU は 10 コア、空き容量は約 14.6 GB だった。
最初に参照した 1659.207 秒は Rust を再利用した UI 変更の回であり、全件のこの値とは直接比較しない。
全件の大幅な短縮を確認したわけではなく、今後の比較に使える全件・段階別の基準を得た。
代表反例のビルド削減と、再利用・予算・診断の修正を、全体の速度保証へ言い換えない。

この全体実行は後続の TSan で既知の `DevicePreparationTests` の状態待ちが期限切れとなり、非ゼロで終了した。
競合診断はなく、同じバイナリの当該スイート単独では再現しなかった。
正式な再実行と当該検査の根因未確定は区別する（[デバッグ手順](../debugging.md)）。

## 回帰と保守

`scripts/tests/test_verification_metrics.py` で、テスト製品指定、同一反例のビルド共用、
全テストの独立判定、異なるパッケージ・製品の分離、履歴と合格記録の分離、ホスト名の境界を検査する。
既存の製品契約テストは、複数反例の一部失敗・中断・ソース復元・コンパイル失敗拒否を引き続き検査する。

今後は [検査の時間診断](../verification.md#実行時間の保守) に従い、件数と失効集合を確認してから測定する。
検査の省略、期限延長、機器操作、キャッシュの一括削除を速度改善の代用にしない。
