# ADR 0235: 読む量に上限を置き、状態とデバッグの文書を分ける

- 日付: 2026-11-03
- 状態: 採用
- 関連: [ADR 0119](0119-agent-token-efficiency.md)、[ADR 0126](0126-agent-context-and-source-reading.md)、[横断監査](../reviews/2026-11-02-cross-cutting-audit.md)の XCA-10・11

## 背景

開始時の HEAD は `3dea61a`。

- XCA-10: `make agent-context` が案内する 13 文書は 439 KB あり、最小の組でも 143 KB を読んでいた。
  - `docs/status.md`（52 KB）は制約より経緯を多く持ち、ADR・`docs/README.md`・`docs/phase2.md` と重なっていた。
  - `docs/debugging.md`（138 KB）は 125 の症状を 4 つの節に積み、最大の節は 69 KB だった。
  - `docs/development.md` の「コードの所在」は見出しのない 41 KB の 1 節で、節ごとに読んでも小さくならなかった。
  - Makefile の 97〜139 行は機能ごとのコメントの積み重ねで、契約の正本（`scripts/verification.json`）と重なっていた。
  - 2026-10-25 以降の更新回数は `debugging.md` 91、`status.md` 84、`development.md` 79、`docs/README.md` 77、Makefile 61 だった（2026-11-03 の計数）。
- 文書の中の見出しへのリンクは検査されていなかった。全角の括弧の見出しを指す 13 件が、存在しない見出しを指していた。
- XCA-11: 共通の運用知識の一部が Claude Code のメモリにしかなかった。
  文書へ移した後も、メモリへ書く前に共有の資料へ書くという規則が、どの共有の資料にもなかった。

## 決定

- 作業の開始時に全文を読むのは、`AGENTS.md`・`docs/README.md`・`docs/status.md`・`docs/agent-workflow.md` だけにする。
  ほかの資料は見出しの一覧から、必要な節だけを読む。
- 上限を 2 つ置き、`make agent-context` が毎回測って表示する。超えたら `OVER BUDGET` を表示する。
  - 全文を読む 4 文書の合計: 44,000 バイト。日本語はおよそ 3 バイトで 1 トークンなので、約 1.5 万トークンにあたる。
  - 案内する全資料の最大の節: 12,000 バイト。節は見出しから次の見出しまでで測る。`--section` で読む最小の単位である。
  - `check-verification` のテストが、実際の資料で両方の上限を確かめる。超えた時は上限を上げず、経緯を ADR へ移すか、見出しで節を分ける。
  - 上限の値は判断であり、トークン数の実測ではない。変える時は理由と測定値をこの ADR へ追記する。
- `docs/status.md` は、利用者に残る制約・未接続・未確認の項目と UC 番号だけを置く。経緯は ADR、単位ごとの進み具合は `docs/phase2.md` に任せる。
  書き直しの前に、消す文の情報がリンク先の ADR・監査・`phase2.md` にあることを項目ごとに照合した。
  どこにもなかったのは CU-04・CU-05 の番号と挙動の対応だけで、[ADR 0093](0093-product-contract-gate.md) へ移した。
  UC 番号はリンクにせず番号だけを書き、一覧へのリンクは冒頭の 1 つにする。範囲は `UC-32〜37` のように書く。
  検査基盤の区別（TSan の未確定の警告など）は利用者の制約ではないので、[検査手順](../verification.md#検査基盤で区別すること) へ移した。
- `docs/debugging.md` は、最初の診断・症状の索引・引継ぎの記録だけにする。症状は `docs/debugging/` の 5 つの領域別のファイルへ移す。
  各症状を `###` の見出しにし、`--section` とリンクで指せるようにする。索引と各ファイルの見出しが一致することをテストで確かめる。
  `make agent-context` は、変更した領域のデバッグのファイルも案内する。
- `docs/README.md` の監査の読み順は [監査の索引](../reviews/README.md) へ移す。見出し「監査の読み順」は、過去の監査のリンク先として残す。
- `docs/development.md` の「コードの所在」と `docs/architecture/ui-and-metal.md` の 13.1 に見出しを足し、節を上限の中に収める。
- Makefile のコメントは各規則の目的を 3 行以内にし、テストで 4 行以上の塊を拒否する。
- 文書のリンクの検査に、見出しのアンカーの照合を足す（GitHub の規則: 小文字にし、記号を除き、空白をハイフンにし、重複に番号を付ける）。
  既存の 13 件と、分割で消えた節を指す 7 件を直した。
- 全エージェントに要る知識は共有の資料へ書き、エージェント固有のメモリにはユーザー個人の好みだけを置く。
  この規則を `AGENTS.md` と [エージェントの手順](../agent-workflow.md) に書く。

## 測定

2026-11-03、作業ツリーの文書で測った。

| 対象 | 前（`3dea61a`） | 後 |
|---|---|---|
| 全文を読む 4 文書の合計 | 93,527 B | 43,252 B |
| `docs/status.md` | 52,101 B | 19,724 B |
| `docs/README.md` | 25,111 B | 4,002 B |
| `docs/debugging.md` | 138,147 B | 15,882 B（索引）＋ 5 ファイル 138,090 B |
| 案内する資料の最大の節 | 68,838 B（デバッグの UI の節） | 9,899 B（`ui-and-metal.md` の 14） |

デバッグの症状 125 件は、本文の全行が移った先に 1 回ずつあることを機械的に照合した。

## 残る範囲

- 更新の回数そのものは、この変更では測れない。分割で 1 回の更新で読むファイルは小さくなったが、回数の変化は今後のコミットで見る。
- `docs/phase2.md` の「現在の進捗」は、ADR の経緯と重なったままである。全文を読む組には入らないので、上限の対象外にした。
- `docs/development.md`（52 KB）と `docs/verification.md`（36 KB）は全体の大きさが変わらない。節ごとに読む前提で、節の上限だけを置く。
- 上限の 44,000 バイトに対する余裕は約 700 バイトである。次に制約を足す作業は、消えた制約を消すか経緯を移す必要がある。
