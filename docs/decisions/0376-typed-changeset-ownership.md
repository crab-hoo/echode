# 0376. 変更セットの所有関係を種類の表で宣言し、種類の追加をコンパイルで止める

- 日付: 2026-11-15
- 状態: 現行
- 領域: モデル・履歴・保存・API
- 対象: 統合表の F11（[構造の評価の精査](../reviews/2026-11-08-structure-assessment-review.md)）、P2-04 のクリップ FX・テイクの着手前
- 関連: [ADR 0278](0278-audit-backlog-order.md)、[ADR 0059](0059-clip-fx.md)、[ADR 0226](0226-model-field-registry-completion.md)

## 背景

`Project::apply_changeset` は、変更セットを種類ごとの下書きへ書き、`Draft::finish` で所有者の順序表から子を組み立てる。
どの列にも載らない子は、完成したスナップショットに現れず、後の `check_invariants` には原理的に見えない（2026-11-07 のパラメーターの消失）。
11/8 の精査では、今の 7 種類の消費の検査は回帰が守ると確かめた。
残る形は、種類を足しても型が知らせないことだった。

- `Draft::insert` と `remove` は既定の腕（`_ =>`）で拒否し、種類を足してもコンパイルが通る。
- 消費の検査は種類ごとの使用数の比較を手で並べる。デバイスは別にトラックごとの所属数も数えていた。
- 未列挙・所有者違い・重複の回帰は、種類ごとに別のファイルで手書きしていた。
- ジャーナルの種類名は、`echode-actions` が書出しと読込みの 2 つの対応表を別に持っていた。

P2-04 のクリップ FX は、配置が持つデバイスを足す。テイクも中身に所有を足す。どちらも上の形に当たる。

## 比べた案

| 案 | 内容 | 判定 |
|---|---|---|
| 1 | 既定の腕だけを除く | 不採用。消費の検査と回帰の追加は、引き続き手に頼る |
| 2 | 種類ごとの表から、下書きの格納・消費の検査・回帰をマクロで生成する | 不採用。所有者の解決は種類ごとに違い（中身の存在、デバイスの子のパラメーター）、マクロが解決の分岐まで持つと読みにくい |
| 3 | 所有の列を値の表で宣言し、下書きは汎用の格納で解決し、回帰は表から生成する | 採用 |

## 決定

- `ObjectKind` は `define_object_kinds!` の表から、列挙・全種類の `ALL`・ジャーナルの名前（`as_str`・`parse`）を生成する。
  `echode-actions` のジャーナルはこの名前を使い、別の対応表を持たない。保存される名前は変わらない。
- `ObjectKind::owners` は、その種類を持てる所有者の列（`Ownership { owner, order }`）を返す。最上位の種類は空を返す。
  今の表は、配置 ← トラックの `clip_order`、ノート ← 中身の `note_order`、デバイス ← トラックの `device_order`、パラメーター ← デバイスの `param_order` である。
- 下書き（`changeset_draft.rs`）は、所有される種類を `Children<S>` に置く。
  `resolve` は所有者の列の順に子を組み立て、所有者の一致と全体での ID の一意を確かめ、解決した数を数える。
  表にない列から解決すると debug ビルドで止まる。
- `Draft::insert`・`remove`・`complete` と `ObjectKind::owners` は既定の腕を持たない。
  種類を足すと、この 4 か所でコンパイルが止まり、格納と「最上位か、どの所有者の列から解決するか」を決めるまで通らない。
- 残った子の検査は `ObjectKind::ALL` の全種類で `complete`（解決した数と格納の数が等しい）を見る。
  トラックごとの所属数の別集計は、全体の検査と重なるため除いた。

## 回帰

`crates/echode-model/tests/ownership.rs` は、表のすべての列について同じ反例を生成する。

- 受け入れる対照: 所有者が列に載せた新しい子、全オブジェクトの所有者ごとの削除。
- 拒否: 未列挙の新しい子、不明な所有者、別の所有者の列、既存の子の削除漏れ、二重の列挙、他の所有者の列への重複、置換による所有者違い、存在しない ID、別の種類の ID、所有者になれない種類の指定、所有者だけの削除、別の種類との ID の衝突。
- フィクスチャがある種類を持たないと、追加を求めて失敗する。

変異で確かめた（2026-11-15、各終了コード 101 と該当の文面）。

- 4 種類それぞれの `complete` を常に真にすると、その種類の「unlisted new child」で失敗する。
- `resolve` の所有者の比較を外す、または一意の検査との論理和を論理積に変えると、「new child naming an unknown owner」で失敗する。
- `resolve` の一意の検査を外すと、「new child reusing the id of a Content」で失敗する。同じ種類の重複は解決数の比較でも拒否される。
- 表からデバイスの列を消すと、`resolve` の debug の検査で止まる。
- 仮の種類 `Probe` を足すと、`insert`・`remove`・`complete`・`owners` の 4 か所で E0004 になる。

## 測定

128 トラック × 64 配置（配置 8,192、変更 25,600）の作成の変更セットを空のプロジェクトへ適用した p50（release、21 回、交互に 4 回）。

| 版 | 全体の作成 | パラメーター 1 個の変更 |
|---|---|---|
| 変更前（`89bc4ca`） | 7.31〜8.16 ms | 7.17〜8.57 ms |
| 変更後 | 7.08〜8.23 ms | 6.68〜8.05 ms |

差は揺れの範囲で、ADR 0278 の E1 の再開条件（ID の索引が要る）には当たらない。下書きは既に ID のハッシュ表を持つ。

## 残ること

- クリップ FX は、デバイスの所有者にクリップの列を足す（表に `Ownership` を 1 つ加え、`ClipState` に列を持たせて解決する）。
  `DeviceState` の所有者の項目名、差分の生成、`from_project` の登録は、その時に変える。表を足せば回帰は自動で増える。
- `Draft::set` は ID で格納を探す既存の順を保つ。所有ではなく値の書込みなので、今回の対象にしない。
- トラックの親子は所有の列ではなく、`arrange_tracks` の階層の検査が扱う。
