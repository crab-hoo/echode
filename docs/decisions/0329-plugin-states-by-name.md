# ADR 0329: 記録済みのプラグイン状態を名前で比べ、読み込むヘルパーだけが読む

日付: 2026-11-12
状態: 採用
関連: [ADR 0130](0130-clap-parameter-editing.md)、[ADR 0142](0142-background-plugin-graph-preparation.md)、[ADR 0147](0147-output-prewarm-and-background-media.md)、[ADR 0229](0229-plugin-window-live-edits.md)、[ADR 0278](0278-audit-backlog-order.md)、[ADR 0031](0031-content-addressed-store.md)

## 問題と再現

開始時の HEAD は `35d54e2`。監査の R・M の段は終わり、ADR 0278 の 4 に従って Phase 2 の P2-02 に戻った。
P2-02 の応答性の残り（[進め方](../phase2.md)）のうち「保存済み状態の読込み」を、まず製品の経路で測った。

`OutputStream::replace` は、ヘルパーを保つかどうかに関係なく、全デバイスの記録済み状態を保管庫から読んでいた（`routes_with_states` の `read_object`）。
製品アプリはプロジェクトを開いた時に出力を準備する（ADR 0147）ので、出力は開いている。
プラグイン状態だけの変更を除く全ての編集（ノート 1 つの追加も）が、文書ワーカーでこの読込みを待つ。
読んだバイトは経路の複写（`set_routes`・`Pending`）と、ヘルパーの適用済みの状態の複写（`applied_state()` が毎回 `Vec` を複写）とで比べられ、ほとんどは捨てられていた。

release で `routes_with_saved_state` 1 回の時間を測った（Sine Pad の経路、状態は全て別の内容、ページキャッシュに載った後の 2 回目）。

| デバイス × 状態 | 修正前 | 修正後 |
|---|---|---|
| 16 × 64 KiB | 2.72 ms | 0.28 ms |
| 16 × 1 MiB | 21.5 ms | 0.28 ms |
| 32 × 4 MiB | 145 ms | 0.27 ms |
| 4 × 65 MiB | 280 ms | 0.24 ms |

修正後の残りは状態の大きさに依らず、走査のキャッシュからの解決（`installed_plugin_routes`）である。
修正前の値は、状態の総量に比例した。読込みの大半は保管庫の名前の照合（BLAKE3）で、ここでは約 1.2 GB/s だった（aarch64 では NEON が自動で有効）。

## 比べた案

1. **読んだ状態を `OutputStream` に名前で保持する。** 読込みは 1 回になるが、経路とヘルパーの適用済み状態の複写・バイトの比較は編集ごとに残る（32 × 4 MiB で 128 MiB の写しが 2 回）。
   全状態をもう 1 組、常駐させる。採らない。
2. **状態を名前で表し、バイトは読み込むヘルパーだけが読む。** 名前は保管庫の名前（BLAKE3-256 の 16 進）で、同じ名前は同じバイトである。
   比べるのは名前だけで、ヘルパーを保つ編集は保管庫を読まない。採る。
3. **経路に名前だけを渡し、読込み関数を `PlaybackControl` に設定する（`ClipLoader` と同じ形）。**
   書出しと検査で経路ごとに違う読み手が要る時に、制御の設定と経路が別々に変わる。
   2 の経路が読み手を持つ形の方が、書出し（CLI）とライブの同じ経路で済む。採らない。

## 決定

- `echode-engine` の `PluginRoute.state` は `Option<PluginState>` にする。`PluginState` は名前と、メモリ上のバイトか保管庫の読み手のどちらかを持つ。
  等しさは名前で決める。`load` は必要になった時に読み、読み手が返したバイトに名前を付けて返す。
- ヘルパーの適用済みの状態は `echode-sandbox` の `AppliedState` にする。バイトは `Arc<[u8]>` で共有し、名前は最初に求められた時に 1 回だけ計算して全ての複写で共有する。
  名前の計算は呼び出し側が渡す。規則は `echode_model::content_hash` の 1 か所で、保管庫の `hash_bytes` もこれを呼ぶ。
  保管庫の名前の綴りの検査（`is_content_hash`）も `echode_model::valid_state_hash` を呼び、別の論理を持たない。
- 記録済みの状態を読み込んだヘルパーは、その名前の付いた `AppliedState` を持つ（`PluginControl::restore_applied`）。次の比較でバイトを計算し直さない。
  ヘルパーが自分で保存したバイトは名前を持たず、最初の比較で 1 回計算する。
- 置換の `reconcile` と、背景の準備の前の `matching_states` は、`holds`（適用済みの名前と経路の名前、両方なしは既定）で比べる。
  新しいヘルパーと状態が変わったヘルパーだけが `spawn_stage` で読む。読込みはプロセスの起動の前に行い、読めない状態でヘルパーを起動しない。
  背景の準備（ADR 0142）では、読込みも `echode-graph-prepare` のスレッドで行う。
- 状態だけの Undo / Redo（`restore_recorded_states`）も名前で比べ、同じなら読まない。違えば読んで同じヘルパーへ読み込み、読めない・拒否はグラフの置換に回す（従来どおり）。
- 未記録の変更を持つヘルパー（ADR 0229）の経路は、そのヘルパーの `AppliedState` を共有する（`PluginState::held`）。写さない。
- 読めない状態は、そのヘルパーの起動で `PlaybackError::State { device, error }` になる。`error` は読み手の型（保管庫の `PackageError`）を原因として保つ。
  前は経路を作る時点で `AudioError` の保管庫の失敗になり、ヘルパーを保つ編集でも失敗した。今は、そのバイトが要るヘルパーだけが失敗する。
- `routes_with_saved_state` は失敗しなくなった。CLI の書出しは、読めない状態をヘルパーの起動の失敗として受ける。

## 検査

- 必須契約 `plugin-state-names`（`hosted_playback/recorded_states.rs`）: 実ヘルパーで、無関係な編集の置換が状態を読まず同じヘルパーを保つこと、
  変わった状態は 1 回だけ、制御側ではないスレッドで読まれ、新しいヘルパーに効くことを確かめる。負の対照は `holds` の名前の一致を偽にする（無関係な編集で読む）。
- 同じファイルの `an_unreadable_recorded_state_names_its_device_and_cause` は、読めない状態がデバイスと読み手の原因を持つことを確かめる。
- `stream_tests.rs` の 2 件は、経路を作っても保管庫を読まないこと、未記録のヘルパーのバイトを使うこと、欠けた状態は読込みの時だけ `PackageError` で失敗することを確かめる。
- 単体回帰は `plugin_state_tests.rs`（読込みの回数・名前の引継ぎ・`holds`）と `applied_tests.rs`（名前の 1 回の計算と共有）。
- 音の処理は変えない。ブロック長の比較と RT の検査は既存のものを維持する。

## 影響と残り

- 状態の大きいプロジェクトで、編集ごとの文書ワーカーの待ちが状態の総量に比例しなくなった。
- ヘルパーが保存した状態の名前は、最初の比較で制御側が計算する（65 MiB で 56 ms、1 MiB で 0.9 ms、保存 1 回につき 1 回）。
  文書も同じバイトを保管庫へ書く時に計算するので、計算は 2 回になる。保存の経路で名前を渡せば 1 回にできるが、今回は行わない。
- 再生中の編集の素材、計画の生成、初回の導入時の差分で増えたヘルパーの起動、同一ヘルパーへの状態の復元（Undo）の通信の待ちは、文書ワーカーに残る。
  → 再生中の編集の素材は [ADR 0330](0330-playing-edit-media-and-tempo-retime.md) で別スレッドへ移した。
- `installed_plugin_routes` は編集ごとに走査のキャッシュを読む（約 0.25 ms）。変更がなければ書き込まない（既存の `store_scan_cache`）。
