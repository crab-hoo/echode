# ADR 0335: テンポ・レートだけが変わったトラックは、ノートの番号を前回の計画から位置で引き継ぐ

- 日付: 2026-11-13
- 状態: 採用
- 関連: [ADR 0274](0274-reused-track-plans.md)、[ADR 0267](0267-current-playback-id-mappings.md)、[ADR 0278](0278-audit-backlog-order.md)、[ADR 0333](0333-install-diff-graph-off-worker.md)

## 問題と計測

P2-02 の応答性の残りの「計画生成は文書ワーカーで待つ」を測った。開始時の HEAD は `1fdff2f`。
`make spike-scale`（Apple M4、release、機器・プラグインなし）の 256 トラック × 4,000 ノートで、
テンポの編集の `replace` は約 528 ms、音符より後ろへのテンポ点の追加（`marker_adoption`）も約 527 ms だった。ノートの編集は約 6 ms である。
曲に近い大きさの行を足すと、64 × 1,000 で 9.9 ms、128 × 1,000 で 24.1 ms で、後者は ADR 0278 が GUI の停止として扱う 1 フレーム（16.7 ms）を超えた。

総ノート数を同じにしてトラック数を変えても値はほぼ同じで（128,000 ノートで 21〜29 ms）、総数に対して線形より速く伸びた（256,000 で約 82 ms）。
`sample` で 256 × 4,000 のテンポの編集を見ると、作業時間の約 7 割が `DefaultHasher`（SipHash）だった。
テンポやレートが変わると ADR 0274 の使い回しが効かず全トラックを作り直す。その時、ノートごとに約 100 万件の番号表を 3 回引いていた。
番号の照会（`PlaybackIds::note`）、作り直した区間の使用数の加算、置き換えた区間の使用数の減算である。
内容が同じなので加算と減算は打ち消し合う。表が大きいので照会はキャッシュを外れる。

## 比べた案

1. **計画生成を準備スレッドへ移す**: ワーカーは待たなくなるが、`PlaybackIds` とメーターの所有を移し、媒体・グラフの準備と合わせて要求を集約し直す。
   制御の流れを大きく変える割に、作業そのものは減らない。
2. **速いハッシュ関数に替える**: 依存を足し、プロジェクトの ID（外部の入力）に対する衝突の耐性を検討し直す必要がある。キャッシュ外れは残る。
3. **変わらないノートの番号を前回の計画から位置で取る（採用）**: トラックと全ての内容が同じ `Arc` なら、ノートを訪れる順序（クリップ順・内容内の順）は同じである。
   番号を位置で取れば照会が要らず、計画に入るノートの集合が同じなら使用数も変わらない。新しい依存も、制御の流れの変更もない。

## 決定

- `PlannedTrack::numbers` に、訪れた各ノートの番号を訪れた順に持つ。計画に入らなかったノート（クリップで聞こえない・時間に直すと長さ 0）は `UNPLANNED` とする。
- テンポ・レートだけが変わったトラック（同じ `Arc` のトラックと内容）は、同じ位置の番号を使う。
  前回は計画に入らず今回入るノートだけ、従来どおり番号表を引く（極端なテンポやレートで長さ 0 になる短いノート）。
- 計画に入るかどうかが全ての位置で前回と同じなら `same_notes` とし、確定時（`commit`）に使用数の加算も減算もしない。
  1 つでも変われば従来どおり全部を数え直す。
- 計画の内容・ノートの番号・使用数は、全体の作り直しと同じである。音と RT 区間は変えない。

## 同条件の計測

同じ作業ツリーの変更前後に、続けて `make spike-scale` を実行した（`target/focused-checks/retime/`）。

| 場合 | `replace_p50_ms` 前 → 後 |
|---|---:|
| テンポの編集 256 × 4,000（採用まで 100 ブロック） | 528.5 → 74.0 |
| テンポの編集 256 × 4,000（3,500 ブロック） | 525.1 → 74.4 |
| 後ろへのテンポ点 256 × 4,000（100 ブロック） | 526.9 → 74.7 |
| テンポの編集 128 × 1,000 | 24.1 → 10.0 |
| テンポの編集 64 × 1,000 | 9.9 → 4.9 |

ノートの編集（約 6 ms）、ループの折り返し、採用のブロック（`adoption_p50_us`）、モデルの編集は計測の揺れの範囲で変わらなかった。
単回の経過時間の比較であり、実画面の応答時間を保証する値ではない。

## 回帰と基盤

- `plan_tests::a_tempo_edit_keeps_note_numbers_without_looking_them_up` は、テンポの編集で全ノートを時間に直し直し、番号表を 1 回も引かず、
  番号と使用数が前と同じで、全体の作り直しと同じ区間になることを数える（`cfg(test)` の `looked_up_notes`）。
  位置での引継ぎをやめると、期待終了コード 101 と `a tempo edit looked up the numbers of unchanged notes` で失敗した。
- `plan_tests::notes_that_leave_or_rejoin_a_retimed_plan_keep_their_uses_exact` は、8 Hz と 48 kHz を行き来して短いノートが抜けて戻る時、
  使用数が区間の数と一致することを確かめる。抜けたノートの扱い（`same_notes` を落とす）を外すと、表の件数の不一致で失敗した。
- 既存の乱数の 400 手の回帰（`reused_track_plans_match_full_rebuilds_across_edits_and_undo`）は、表の件数に加えて各ノートの使用数も比べるようにした。
- `spike-scale` に、曲に近い大きさ（64・128 トラック × 1,000 ノート）のテンポの編集の行を足した。

## 残る範囲

- 計画生成そのものは文書ワーカーに残る。256 × 4,000 のテンポの編集の残り約 74 ms は、時間への変換・並べ替え・カーソルの索引・イベントの必要量である。
- 音符より後ろだけが変わるテンポ点でも、全トラックを作り直す。
