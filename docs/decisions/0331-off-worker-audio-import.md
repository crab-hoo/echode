# ADR 0331: 外部の音声の取込みを文書ワーカーの外で段階に置き、後の編集は取込みの後に順に当てる

日付: 2026-11-13
状態: 採用。実機の操作感はユーザー確認待ち（UC-68）
関連: [ADR 0272](0272-staged-import-media.md)、[ADR 0330](0330-playing-edit-media-and-tempo-retime.md)、[ADR 0204](0204-document-service.md)、[ADR 0145](0145-sample-browser-file-drops.md)、[ADR 0160](0160-ordered-transport-requests.md)、[ADR 0278](0278-audit-backlog-order.md)

## 問題と再現

開始時の HEAD は `d490029`。ADR 0278 の 4 に従い、P2-02 の応答性の残り（[進め方](../phase2.md)）のうち「外部の音声の取込み」を扱った。

ブラウザからのドロップ・「音声を取り込む」は `audio.import` の編集で、文書ワーカーが `DocumentHost` に渡し、その手番の中で次を行っていた。

1. 復号・有限値の検査・PCM 化と、保管庫の横への一時の名前での書込みと同期（段階、ADR 0272）。
2. 編集の確認、ハッシュへの改名、索引の書込み、保管物を読み直してのピークの作成（公開）、ジャーナルの書込み。

この間、文書ワーカーは次の手番を取らない。停止の位置の戻り・位置移動・デバイスの一覧・Undo・後の編集が待ち、再生ヘッドとメーターの公開（`LiveState`）も止まる。
停止の音そのものは、投入時に世代を進めるので待たない（ADR 0097、ADR 0160）。

`make spike-import`（release、Apple M4、macOS 27.0、180 秒・16 ビット・ステレオ・44.1 kHz の WAV、ページキャッシュに載った後、各 5 回）で、文書ワーカーの手番の長さを測った。

| 経路 | 中央値（最小〜最大） |
|---|---|
| `d490029` の取込み（段階と公開を文書ワーカーで） | 229.0 ms（221.8〜258.3） |
| 段階（この ADR で文書ワーカーの外へ） | 136.1 ms（135.3〜143.4） |
| 段階の後の文書ワーカーの手番（公開・ジャーナル・計画の更新） | 19.9 ms（19.0〜20.1） |
| 参考: ピークのための保管物の読み直し（この ADR で除いた） | 106.7 ms（106.5〜107.7） |

長さに比例するので、10 分の素材ならその約 3.3 倍になる。

## 比べた案

1. **取込みは完了時の順で当てる。** 段階が終わった時に、その時点の文書へ編集を当てる。後の編集・Undo は先に進む。
   段階の間に押した Undo は取込みより前の編集を取り消し、その後に取込みが当たって Redo を消す。利用者が最後に行った操作と Undo の対象が食い違い、Redo も失う。採らない。
2. **取込みの間の Undo は取込みの取消にする。** 履歴の先頭に未確定の段を置く仕組みが要り、ジャーナル・Redo・保存の規則が二重になる。採らない。
3. **段階だけを外へ出し、履歴に触れる後の手番は取込みの後に投入順で当てる。** 取込みは投入した時点の文書に当たり、Undo はそのドロップを取り消す。履歴の結果は従来と同じで、待たなくなるのは履歴に触れない手番だけである。採る。

案 3 で待たなくなるのは、音声の要求（再生・停止・位置・開始位置・ループ・メトロノーム・出力・フェーダーの試し値）、デバイスの要求、スナップショット、再生ヘッドとメーターの公開、出力の保守（`Session::service`）、プラグインの活動の通知である。
アプリの編集は従来から `EditTurn` で 1 つずつ送るので、アプリの後の編集・Undo は Swift 側で待つ。待ち方は従来と同じである。

## 決定

- `echode-history` に `StagedImports` を加えた。`StagedImports::stage` は編集が名指す各ファイルを段階に置き、失敗もそのファイルの結果として持つ。
  `DocumentHost::perform_staged`・`apply_staged` は、段階済みのファイルを使い、なければ従来どおり文書の手番で段階に置く。`perform`・`apply` は段階なしの同じ経路である。
  編集の確認・公開・失敗時の取消（EXT-02）・ジャーナルの順（XCA-03）は ADR 0272 のまま変えない。
  使わなかった段階は、応答の前に一時の名前を消す。
- 段階で、復号した標本からピークを作る。公開はそれを書くだけで、保管物を読み直さない。キャッシュの中身は保管物から作るものと同じである（回帰で比べる）。
- 文書ワーカー（`echode-document` の `import.rs`）は、編集を読んで取込み元を求める。単一のコマンドと、トランザクションの中の文字列の `path` が対象で、前の結果を参照する `path` は文書の手番で段階に置く。
  取込み元があれば、復旧の同意の確認の後に `echode-import-stage` スレッドで段階に置き、編集の完了を保留する。
- 保留の間の手番:
  - `Perform`・`History`・`Undo`・`Redo` は投入順に保持し、取込みの後に 1 つずつ行う。保持した中の取込みは、また段階に置く。
  - デバイスの取込み（ジェスチャーの終わりの状態）とプラグインの保存の記録も、取込みの後に行う。取込みは投入した時点の文書に当たる。
  - それ以外の手番は待たない。
- 文書を閉じる時は、段階中の取込みと保持した手番を終えてから閉じる。受け付けた投入は全て完了する（ADR 0204）。
  段階のスレッドの panic はその編集だけを `DocumentError::ImportPanicked` で失敗にし、文書は続ける。スレッドを作れない時は、従来どおり文書の手番で段階に置く。
  ワーカー自身が落ちた時は、段階を止める旗を立ててスレッドを待ち、一時の名前を消す。
- CLI・MCP（`DocumentHost` へ直接つなぐ）は従来の経路のままである。

## 検査

- 必須契約 `import-off-worker`（`echode-document` の `import_tests.rs`）: 製品の段階を門で止め、機器なしの出力で次を確かめる。
  - 段階の間に、位置移動・スナップショット・デバイスの要求が終わり、再生ヘッドが公開される。
  - 後に投入したトラックの追加と 2 回の Undo は、段階の間は終わらない。門を開けると、取込み・追加・追加の Undo・取込みの Undo の順に当たる。
  - 段階中に文書を閉じると、取込みを終えてから閉じ、開き直すとそのクリップがある。
  - 負の対照は 2 つ。履歴の手番を保持しないと、後の編集が段階の間に終わる。取込み元を求めないと、段階が門に来ない。両方とも失敗を確かめた。
- 単体の回帰:
  - `host_tests::imports_staged_off_the_document_thread_land_as_if_staged_there`: 拒否した編集と使わない段階は保管庫に何も残さない。
    ピークは保管物から作るものと同じで、保管物は文書の手番の取込みと同じハッシュになる。段階の失敗は従来と同じ要素の位置と文面で返る。
  - `import_tests::a_staging_thread_that_panics_fails_only_its_edit`: 段階の panic はその編集だけを失敗にし、保持した編集は続く。
  - `imports::tests`: トランザクションから文字列の取込み元だけを順に求め、取込みの名前を登録簿から読む。
- 音を作る処理・RT の経路は変えない。ブロック長の比較と RTSan の対象は増えない。

## 影響と残り

- 取込みの間も、停止・位置移動・デバイスの一覧・再生ヘッドとメーターは止まらない。文書ワーカーが取込みに使う時間は、180 秒の素材で 229.0 ms から 19.9 ms になった。
- ドロップしたクリップが現れるまでの時間は、ピークの読み直しをやめた分だけ短くなる（180 秒の素材で 229.0 ms から、段階と手番の計 約 156 ms）。後の編集・Undo が待つ時間も同じだけ短くなる。
- 段階は PCM 全体を一度に持つ（FCA-18）。長い素材の読込み・保管の形式は変えない。
- 計画の生成（`Prepared::new`）と、初回の出力導入時の差分で増えたヘルパーの起動は、文書ワーカーに残る（ADR 0142）。
- 取込み元が応答しない（止まったネットワークのボリューム）時は、従来と同じく文書を閉じるのも待つ。段階を止める旗は、復号の区切りでしか効かない。
- 実機での操作感はユーザー確認待ち（UC-68）。
