# 0210. サニタイザの Swift 全体実行の同時実行数を絞り、競合の検出は全テスト同時の実行で保つ

- 日付: 2026-11-01
- 状態: 採用
- 関連: [ADR 0185](0185-piano-auto-and-fixed-grid.md)、[ADR 0207](0207-continuation-handoff-tsan.md)、[デバッグ手順](../debugging.md)

## 背景と原因

全画素の走査を主アクターの外へ移した後、負荷なしの `Status did not arrive` はなくなった。
全コアに負荷をかけた TSan 全体では 29 回中 1 回の失敗が残り、同じ待ちが 2.2〜5.1 秒まで伸びて余裕がなかった。

主因は特定のテストの占有ではなく、全テストの同時実行である。

- Swift Testing は既定で全テストを同時に始める。TSan 全体では約 260 個が同時に生きる。
- `@MainActor` のテストは 1 本の主キューを順番に使う。
  `await` やポーリングの 1 回ごとに、生きている全テストの一巡を待つ。
- 文書は 1 つにつき 6 本のスレッドを作るので、スレッドは約 1100 本に達する。
  固定した TSan ランタイムのスロットは 256 本分で、足りない分を奪い合う。Darwin の内部の待ちは `sched_yield` の回転である。
- 停止の間、主スレッドが使う CPU は約 3 割だった。残りは順番待ちと、ファイルや dyld でのブロックである。

飽和の下で、主スレッドを 50 ms ごとに標本化した内訳は次の通りである（全テスト同時、1 実行で約 26〜30 秒分）。

| 活動 | 標本の割合 | そのうちブロック中 |
| --- | --- | --- |
| ファイルの削除（テストの後片付け） | 28〜30% | 68〜69% |
| フレームワークの読込み | 25〜28% | 22〜24% |
| テストのその他の処理 | 約 19% | |
| TSan の内部 | 約 12% | |
| 開閉ボタンのクリックの入れ子のランループ（12 か所） | 5.5% | 86% |

最初の 8 秒に限ると、読込みが 53%、開閉ボタンが 20% を占める。

## 比較した案

| 案 | 判定 |
| --- | --- |
| A. 5 秒の期限を延ばす、対象を除外する | 不採用。遅い応答や失われた応答を隠す |
| B. 主アクターの同期処理を分ける | 採用。削除と開閉ボタンを直したが、これだけでは余裕が戻らない（測定の表 2） |
| C. フレームワークを先に読み込む | 不採用。読込みの契機が CoreFoundation、テストの実行部、AppKit、objc、vImage、SkyLight などに散らばり、まとめて先に済ませる箇所がない |
| D. `swift test --parallel --num-workers 16` | 効かない。Swift Testing は絞られず、263 個が同時に動いた |
| E. `SWT_EXPERIMENTAL_MAXIMUM_PARALLELIZATION_WIDTH` で絞るだけ | 余裕は戻るが、テストをまたぐ競合の検出が 1 実行あたり約 4 分の 1 に落ちる（測定の表 4） |
| F. 絞った実行で合否を決め、全テスト同時の実行で競合を探す | 採用。増える時間は約 40 分の検査に約 30 秒 |

## 決定

- **合否を決める実行**: `check-bridge-asan` と `check-bridge-tsan` の製品の Swift を、同時実行数 16 で動かす。
  呼出し元の環境の値は `unset` し、検査の値だけを使う。5 秒の期限と対象のテストは変えない。
- **幅の確認**: 実験的な環境変数は、ツールチェーンの更新で黙って効かなくなり得る。
  `scripts/check_test_width.py` がイベント列から実際の同時実行数を数え、上限を超えたら失敗する。
- **競合を探す実行**: TSan だけ、全テスト同時の実行をもう一度行う。ビルドは共有する。
  `run-bridge-validation.py --races-only` は、完走してサニタイザの報告がない時に限り、テストの失敗を判定しない。
  テストの合否は前の実行で決まっており、ここは飽和の下で走らせること自体が目的である。
  報告があれば失敗で、途中で落ちた時も失敗である。`check_test_width.py --more-than 16` で本当に広いことも確かめる。
- **ASan**: 絞った実行だけにする。競合を探す検査ではないので、全テスト同時の実行を足さない。
- **待ちの短縮**: テストの一時ファイルは `removeTestFile` で主アクターの外から消し、プロセスの終了時にその完了を待つ。
  開閉ボタンは `clickWithoutAnimation` で押す。`performClick` はアニメーションの間、入れ子のランループで主アクターを止める。
  どちらも同じアクションを送り、比較の内容は変えていない。
- **診断**: `main_thread_stalls.py` は停止ごとの CPU・CPU 待ち・読込み・主スレッドの状態と、`--profile` の常時標本を報告する。
  判定には使わない。

幅を 16 にしたのは、32 より待ちの中央値が約 3 分の 1 になり、全体の所要時間が変わらないためである。
8 は待ちがさらに縮むが、最長の停止と 5 秒の窓の停止は 16 と差がなく、合否を決める実行で重なるテストの組が半分になる。

## 引数付きテストの本体を数える（2026-11-05）

FCA-12・15・19 の対応の ASan 検査で、上限 16 に対して 22 と判定されて停止した。
Swift のテスト本体は完走しており、イベントを分けると、引数付き関数の親 6 件と通常の本体 16 件の合計だった。
引数付きの親はケースが実行枠を取る前に開始し、全ケースの終了まで生きる。実行したケースと通常の本体だけの最大は 16 件だった。

幅の検査は、通常の関数の start / end と、引数付きの `testCaseStarted` / `testCaseEnded` を数える。
親を一件として数えると待機中の親を過剰に足すだけでなく、同じ関数の複数ケースが並行する時には過少に数えてしまう。
`test_check_test_width.py` に両方向の回帰を置き、親を足す側は固有のアサーションで先に失敗を照合した。
上限 16・検査対象・5 秒の期限・全テスト同時の TSan の実行は変更しない。
当初の失敗したイベントとログは作業用の `target/focused-checks/swift-width-first-failure/` に保存した。

## 限界

- ASan は同じ主キューの構造なので同じ幅にしたが、負荷の下の前後は比べていない。確かめたのは幅 16 で合格することだけである。
- 無制限の実行でも、2 個のテストの間の競合を 1 回で見つける確率は低い。今回の決定はそれを上げず、従来と同じ水準を保つだけである。
- 環境変数は実験的である。消えたら `check_test_width.py` が止めるので、その時に別の手段を決める。
- 競合を探す実行の失敗は `race-swift-tests.failed.log` に残るが、テストの失敗としては判定しない。
- まれにシステム全体が止まる場合、この対策では吸収できない。
  全テスト同時で 124 秒の停止（監視スレッドも 113 秒止まった）、幅 16 で 1 テストが 116 秒かかった実行が 1 回ずつあり、どちらも同じ約 5 分の間に起きた。
  その間は `syspolicyd`、`mds`、`mdworker`（17 個）などが動いており、以後の実行では再発していない。原因は確かめていない。
  以前の失敗の 28.2〜33.5 秒の停止も、監視スレッドが止まった点で同じ種類に見える。
