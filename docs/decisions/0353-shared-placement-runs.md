# ADR 0353: トラックの配置もノートと同じ共有の run に分ける

- 日付: 2026-11-14
- 状態: 採用。R6 の区切りを更新する。総量の予算は下の再開の条件まで入れない。
- 対象: [統合表](../reviews/2026-11-08-open-items-register.md) の R6（[FCA-19](../reviews/2026-11-03-full-code-audit.md#fca-19-減らない記録)・MOD-12）と、[ADR 0287](0287-shared-note-runs.md) の再開の条件。
- 方針: [ADR 0276](0276-priority-order-and-delegated-decisions.md) の「段を捨てない」と「同じ規則を層ごとに別の論理で実装しない」。

## 問題

- ADR 0287 の再開の条件の 1 つは「1 つのノートやトラックの編集の 1 段が 100 KB を超えた時」である。
  `measure_history_usage` に、多くのクリップを持つトラックの場面を足して確かめた。
- 2,000 個のクリップ（各々が自分の中身を持つ）の 1 トラックで、1 つのクリップの範囲を変えると、1 段が 176.6 KB を持った。条件を超える。
- 原因は、トラックが配置を `Vec<Placement>` で持ち、クリップの編集がトラック全体を写すことである。1 配置は約 80 バイトで、1,250 個で 100 KB に届く。
  ノートの編集が中身全体を写していた ADR 0287 の問題と同じ形である。
- 版ごとに持つ中身の一覧（8 バイト × 中身の数）も同じく線形に効く。64 トラック × 160 クリップ（中身 10,240）では、ゲインの編集の 1 段が 95.8 KB だった。

## 比べた案

| 案 | 内容 | 判定 |
|---|---|---|
| 1 | 予算を入れ、古い段を Git の履歴へ移す（ADR 0276・0287 の案 1） | 今は採らない。1 つの小さな編集が O(トラックのクリップ数) を持つままでは、予算に早く届き、普通の深さの Undo が Git の読み戻しになる。読み戻しの I/O と失敗の経路が増える |
| 2 | 古い段の版を捨て、変更を逆に当てる（ADR 0287 の案 2 を共有を保つ形に作り直す） | 今は採らない。案 1 と同じく総量の上限であり、1 段の大きさの原因を直さない。共有を保つ差分の適用は別の大きな作業である |
| 3 | 配置を `Arc<Placement>` の配列にする | 採らない。毎段 8 バイト × クリップ数を写し、1 万 2,500 個で 100 KB に届く。配置ごとの割当も増える。ADR 0287 の案 3 と同じ理由である |
| 4 | 配置専用の run を別に書く | 採らない。区切り・共有・数え方の同じ規則を 2 か所に持つ（ADR 0276 の入り組み） |
| 5 | ADR 0287 の `Notes` を要素の型で一般化した `Runs<T>` にし、配置もそれで持つ | 採る。区切りの規則・`Arc::ptr_eq` の共有・使用量の数え方が 1 つの実装になる。Undo の意味・失敗の経路・編集の速さを変えない |

## 決定

- `echode-model` の `runs.rs` に `Runs<T>` を置く。`notes.rs` を移して一般化した。
  - 要素は `RunItem`（区切りを決める ID と並びの順）を持つ。`Note` は `note_ord`、`Placement` は開始・ID の順（`clip_ord`）である。
  - `Notes = Runs<Note>`、`Placements = Runs<Placement>`。区切り（ID を混ぜた値の下位 6 ビット）・平均 64・上限なしは ADR 0287 のままである。
  - `push`・`retain`・`clear` を足した。`retain` は全体を一度写して、変わらない run を共有に戻す。
- `Track::clips` を `Placements` にする。
  - 範囲の変更・成長・合わせ直しは `replace_sorted`、置く・リンクは `insert_sorted`、移動の元は `remove`、ゲインとフェードは `update` で、触れた run だけを写す。
  - 移動先の切り分け・合併・付け替え・複製のように多くの配置を変える処理は `edit` で全体を写し、変わらない run を共有に戻す。
  - 重なりの判定（`overlaps_others` など）は配置の列を読むだけにし、`Placements` と配列のどちらでも呼べる。`overlaps_others` は位置でなく ID で自分を除く。
- 保存形式・`ChangeSet`・ジャーナル・API の形は変えない。どれも配置を順に読むだけである。
- `Footprint` に `placements` を足した。変わったトラックは、隣の版の同じ ID のトラックと共有しない配置の run だけを数える。
  `history.usage` の結果と、閉じる時のログ（`version_placements`）に出る。項目を足しただけなので、プロトコルの版は 1 のままにする（ADR 0286 と同じ）。

## 測定

2026-11-14、Apple M4・macOS 27.0、release。`make spike-history` の `measure_history_usage`（各 1,000 段）。
「前」は HEAD（`03c3ebd`）を別の作業ツリーで作り、同じ計測のファイルで同じ時間帯に測った。
編集の時間は 1,000 段の `perform` の平均で、場面の値を選ぶ読込みを含む。

| 場面 | 1 段（前） | 1 段（後） | 編集（前） | 編集（後） |
|---|---:|---:|---:|---:|
| 2,000 クリップの 1 トラックで、1 つのクリップの範囲を変える（新しい場面） | 176.6 KB | 23.9 KB | 402 µs | 410 µs |
| 64 トラック × 160 クリップで、ゲインを順に変える（新しい場面） | 95.8 KB | 83.1 KB | 115 µs | 115 µs |
| 1 万ノートの 1 クリップで、ベロシティを 1 つずつ変える | 11.9 KB | 12.0 KB | 1,701 µs | 1,706 µs |
| 同じクリップで、ノートを時間と音高で動かす | 18.3 KB | 15.5 KB | 1,860 µs | 1,886 µs |
| 128 トラックのゲインを順に変える | 2.7 KB | 2.7 KB | 28 µs | 28 µs |
| 128 トラックから 1,000 回トラックを足す | 6.1 KB | 6.1 KB | 266 µs | 260 µs |

- 範囲の変更の 23.9 KB のうち 16 KB は、版ごとに持つ中身の一覧（2,000 × 8 バイト）である。配置は出る run と入る run だけを持つ。
- 64 × 160 のゲインの 83.1 KB は、ほぼ中身の一覧（10,240 × 8 バイト、82 KB）である。トラックの写しは 12.8 KB から run の一覧だけになった。
- ノートの場面は ID が実行ごとに変わるので、run の長さで 1 段が揺れる（同じ版でも 12〜20 KB を見た）。前後の差はこの揺れの中である。
- 問い合わせの時間は変わらない（2,000 クリップで 39 → 41 ms、64 × 160 で 255 → 259 ms）。

描画の問い合わせ（`make spike-arrange-query`、1,000 トラック・10 万ノート、中央値）は、後と HEAD を交互に 2 回ずつ測り、後 1.90・1.90 ms、HEAD 1.97・1.95 ms だった。
描画は `track.clips[i]` を run の二分探索で読むが、この場面はトラックごとに 1 クリップで、差は出ない。

## 回帰と基盤

- `footprint_tests.rs` の `a_one_clip_edit_of_two_thousand_clips_keeps_a_few_runs_not_the_track`: 2,000 クリップのトラックで、範囲の変更・移動・リンク・複製・ノートの削除の 1 段が持つ配置が 3 本の run 以内で、64 KB 未満であること。
- `session_tests.rs`: ミキサーの編集で変わったトラックが配置の run を写さないこと（`versions.placements` が 0）。
- `runs_tests.rs`（旧 `notes_tests.rs`）は `Notes` のまま、一般化した実装の区切り・共有・`Vec` との一致を確かめる。
- `measure_history_usage` に上の 2 つの場面、`kept_placements` と `edit_us` を足した。検査の選択（`scripts/verification.json`）は変えない。対象の crate は既に入っている。
- 配置を直接書き換えていたテストの準備は、`edit`・`update`・`to_vec` を通す形にした。製品の読み手（描画・エンジン・音声・FFI）は `iter`・添字・`len` で読むだけで、変えていない。

## 残る範囲と再開の条件

- **総量の予算はない**。多くの配置やノートを変える編集は、1 段がその分を持つ。
- **中身の一覧**: 版ごとに `Vec<Arc<Content>>` を持ち、どの編集も 8 バイト × 中身の数を持つ。1 万 2,800 個の中身で 1 段が 100 KB に届く。
  同じ `Runs` で持てるが、`contents()` の読み手（約 85 か所）と編集の経路が多いので、別の作業にする。トラックの一覧（8 バイト × トラック数）も同じである。
- 次のどちらかの時に戻る。その時は、まず写す単位（中身の一覧）を同じ規則で小さくできるかを見て、それでも足りなければ ADR 0287 の案 1 と案 2 を比べる。
  - `measure_history_usage` か回帰で、1 つのノート・配置・トラックの編集の 1 段が 100 KB を超えた時（中身の一覧が届く規模の場面を足した時を含む）。
  - GUI から使用量を読めるようになり、実際の作業で段の分が 1 GB を超えた時（ADR 0287 のまま）。
