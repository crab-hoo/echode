# 0050. トラックヘッダとタイムラインの表示領域を共有する

- 日付: 2026-10-10
- 状態: 採用（表示領域の管理。左右の描画方式は [ADR 0051](0051-arrange-presentation.md) で変更）

## 問題

以下は座標の共有を決めた時点の記録である。速いスクロールでの描画時刻のずれは、座標だけでは解消せず、ADR 0051 で描画自体を統合した。

アレンジの左側は SwiftUI の `List`、右側は Metal の `ArrangeView` だった。標準リストの行の高さ・余白・スクロール位置と、タイムラインの 64 ポイントのトラック行は独立していた。そのため、初期表示でも行がずれ、スクロールやトラックの縦ズームで同じトラックを同じ位置に表示できなかった。

## 決定

- アレンジを一つの `ArrangePaneView` とし、このビューが `ArrangeCamera` を所有する。時間の原点と倍率、縦の原点と行の高さをここだけで変える。SwiftUI は文書・選択・再生の値を渡し、左右のスクロール位置を別々に保持しない。
- ヘッダとタイムラインは、同じ高さと上端を持つ縦の `NSSplitView` に配置する。仕切りはヘッダの幅だけを変え、ウィンドウの幅を変えた時は主にタイムラインを伸縮する。文書を切り替えた時は、そのアレンジの表示領域を作り直す。
- `ArrangeHeaderView` は独立したリストやスクロールビューを持たない。同じカメラの行矩形に名前を描く。矩形の上端は `(行番号 - 縦の原点) × 行の高さ` で、先頭と末尾の一部だけ見える行も扱う。現在は全トラックが同じ高さである。
- 左右のスクロール・ピンチは表示領域の所有者へ渡す。縦の移動と縦ズームは両側へ同時に渡す。通常ピンチは時間、Option は高さ、Shift は両方という既存の割り当てを保つ。ズームは指した時間・トラックを基準とし、ヘッダでの時間ズームはタイムラインの左端を基準にする。
- 原点は、トラック数と表示領域の高さから決まる範囲に収める。高さ変更やトラック削除でも末尾を越えて空白へ進まない。キーボードで画面外のトラックを選んだ場合も、両側の原点を一度だけ動かして表示する。
- ヘッダの描画・ヒットテスト・アクセシビリティは `ArrangeRows` の同じ矩形を使う。タイムラインのトラック選択も現在の行配置から決め、スクロール直後に前の描画フレームの位置で選ばない。名前を読むのは可視行だけで、トラック数の上限を作らない。アクセシビリティの要素はトラック ID で保持し、選択操作を提供する。
- タイムラインは従来の専用スレッドの Metal レンダラーを保ち、カメラは不変の入力として渡す。ヘッダは AppKit で描く。将来のフェーダーなどのネイティブな操作部品も、この行矩形内へ配置する。

## 拡張する時

トラックごとの高さ変更やフォルダの折り畳みを実装する時は、行番号と一様な高さの代わりに、ID・並び・累積した高さを持つ共有の行配置を用意する。Rust の可視問い合わせも同じ行配置を使うように変え、片側だけに高さの配列や補正値を足さない。まだ必要のない可変高さや折り畳みの状態は、今回のモデルには追加しない。

## 確認

`ArrangeTests` は、部分行と境界のヒット、スクロールとズームの基準点、サイズ変更・削除後の末尾、画面外への選択、100 万トラックの可視行の列挙を確認する。ヘッダの矩形を Rust の実際の可視トラックと比べる。ウィンドウを作らない AppKit の検査で、左右の高さ、入力の伝達、仕切りとサイズ変更後の共有も確認する。

`make spike-app` は製品と同じ複合ビューを使い、左右の原点・高さが同じことも検査する。`spike-app` と `spike-draw` の今回の実機描画・操作確認は、computer use の明示許可がないため未実施である。

## 後日対応（2026-10-18）

トラックパッドの移動量はポイントのままカメラへ渡す。マウスホイールの 1 段は、縦を 1 トラック、横を 1 拍に換算してから同じカメラへ渡す。ピアノロールは縦を 1 音高、横を 1 拍にする。
