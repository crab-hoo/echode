# ADR 0348: 背景の状態取得は変更の印を保ち、間隔を空けて取り直す

- 日付: 2026-11-14
- 状態: 現行
- 領域: プラグイン・隔離
- 関連: [ADR 0199](0199-owned-helper-control-requests.md)、[ADR 0319](0319-control-send-deadline.md)、
  [DIA-04](../reviews/2026-11-13-detailed-implementation-audit.md#dia-04-断られた背景の保存が変更の印を消す)

## 問題と再現

開始時の HEAD は `07e9063`。
背景の状態取得が拒否されると、`PluginControl::poll_state_save` は新しい変更の印も消していた。
busy は何も始めていない拒否であり、後で取り直せるのに、次の dirty が来るまで取得できない。
ヘルパーの時間切れと通信失敗も、同じ枝で変更の印を失っていた。失敗のログもなかった。

元の `audit_dia04_a_busy_refusal_keeps_the_plugins_change_waiting_for_a_save` の無視を外し、
修正前に終了コード 101 と `the change is still only in the plugin and no save was asked for again` を照合した。
利用者の文書・音声機器・実画面は使っていない。

## 比べた案

1. **全ての拒否で変更を捨てる**: 採らない。後で取得できる変更と、実行中に届いた別の変更まで失う。
2. **全ての要求を直ちに再送する**: 採らない。
   値の変更や復元は、時間切れでも既に実行された可能性がある（ADR 0199）。
   読取りだけでも毎周期の再要求は、応答の遅いヘルパーと文書ワーカーへ余分な仕事を増やす。
3. **読取りだけの背景取得に限定し、1 秒空けて取り直す（採用）**:
   busy・時間切れ・通信失敗では未取得の印を戻す。次の取得は新しい要求番号で、現在の状態を読む。
   完了済みの古い応答を採るのでも、失敗した確定を成功に変えるのでもない。
   固定の間隔は指数バックオフより状態が少なく、回復後の待ちは最大で約 1 秒に保てる。
   50 Hz のワーカーに対し、繰り返す拒否の取得要求は毎秒 1 回以下になる。

## 決定と境界

- 親の制御側に再試行の時刻と、失敗の最初の警告を出した印だけを足す。
  未取得の変更の正本は既存の `dirty_again`、実行中の要求は既存の `save_requested` のままである。
  再試行の待ちの間も通信の読取りと通知の回収は行い、スレッドを待たせない。
- busy と時間切れは取得を取り直す。送信・回収の通信失敗も印を保ち、同じ間隔でやり直す。
  途中で切れた通信をつなぎ直すものではなく、死んだヘルパーは従来の監視・再起動に任せる。
- プラグイン自身の拒否、拡張の欠落、停止、その他の拒否はその取得を終える。
  どの失敗でも、実行中に届いた新しい dirty は消さない。
  新しい変更の通知が続く場合も、失敗直後の取得要求には同じ間隔を置く。
- 失敗は成功までの最初の 1 回だけ、要求番号・型を保持した原因・未取得の印の有無とともに警告する。
  成功かヘルパーの再起動で間隔と警告の印を消す。状態のバイトはログへ書かない。
- ADR 0199 の自動再送しない規則への例外は、この読取りだけの背景取得に限る。
  復元・パラメーター変更・同期の確定は再送しない。要求番号の照合と古い適用済み状態を戻さない規則も変えない。
- ヘルパーの 2 秒の期限は変更しない。
  保存が毎回その期限を超えるプラグインでは、取得できないまま再試行を続け、保存を保証しない。
  取得後の保管庫・ジャーナルへの記録失敗（DIA-05）、文書を閉じる時の取得の完了待ちも、この作業では変えない。
- DSP、オーディオスレッド、通信の形式、保存形式、C ABI は変えない。
  実時間の性能は測定せず、再試行の間隔は時計を注入して境界を検査する。

## 回帰と基盤

- 元の監査回帰は、拒否の直後から 1 秒未満には再要求せず、1 秒で新しい番号を送り、追加の dirty なしに状態を受け取る。
- `session_save_tests.rs` は実ソケットを通し、期限の 1 ns 前と期限上の境界、時間切れ・busy、
  終了する拒否と新しい変更、成功中の新しい変更、古い応答の破棄、切断、警告の間引きと成功後の解除を検査する。
  既存の送信が詰まる回帰も、待たないまま間隔を空けて再開することを検査する。
- `tests/isolation/state_saves.rs` は既存の `slow-save` の別プロセス CLAP を使う。
  最初の 3 秒の保存で実際の時間切れを通り、追加の dirty なしに後の取得と音声処理が続くことを検査する。
  これは機能の回帰であり、実機性能の計測ではない。
- 新しい取得元・外部入力・メッセージは足していない。既存の fuzz の境界と収集する証拠の場所は変えない。
  既存の crate 単位の検査で通常回帰も選ばれるため、検査の入口・Makefile・選択条件は増やさない。
- 設計の正本、現在の制約、監査の対応、ログから取得失敗と記録失敗を区別するデバッグ手順を更新する。
  結果と手動検査の見送りは `target/verification/report.md` に記録する。
