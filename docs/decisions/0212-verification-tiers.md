# ADR 0212: 作業ごとの検査と節目の全体検査を分ける

- 日付: 2026-11-01
- 状態: 採用
- 対象: 検査の選択、製品契約の反例、Rust / Swift の基本検査、フックと報告
- 前提: [ADR 0100](0100-scoped-verification.md)、[ADR 0148](0148-verification-pipeline-speed.md)、[ADR 0195](0195-verification-cost-observability.md)、[ADR 0197](0197-verification-target-scopes.md)

## 背景

`make verify` が 1 回 57 分（3425 秒）かかり、開発とマシンの負荷のボトルネックになった。
作業の完了条件と、検査そのものの検出力の確認が同じ入口に入っていたことが原因である。

## 監査の照合

ユーザーから提供された監査（2026-11-01）を、保存済みの記録とコードで照合した。

2026-11-01T11:46:57Z の実行の内訳:

| 処理 | 秒 | 割合 |
|---|---:|---:|
| 反例（Rust 435、Swift 1058） | 1494 | 44% |
| ASan 515、TSan 273 | 788 | 23% |
| `check`（Rust と Swift の基本検査） | 542 | 16% |
| 契約の通常テスト | 181 | 5% |
| 明示実行した `spike-history` | 219 | 6% |
| Miri、`check-verification`、`check-real-hal`、フォーマット | 182 | 5% |

確認できた指摘:

- 反例は 348 件（Swift 221、Rust 127）で、ADR 0148 の時点の Swift は 38 件だった。
- Swift を触らない `echode-history` の変更で、反例 230 契約がすべて再実行された。
- `EchodeAppTests` は通常、実 HAL、ASan、TSan（幅 16）、TSan（全幅）の 5 回走る。
- 終了フックは Cursor の `stop` だけで、`.codex/hooks.json` は `preToolUse` だけである。

修正した指摘:

- 「コミットしない運用で前の作業の分まで再実行される」は半分だけ正しい。
  再実行は検査と契約ごとの入力の識別値で決まり、変更の一覧は識別値に入らない。
  一方、前の作業の変更で選ばれた検査は選ばれ続け、後の編集が入力を変えれば再実行される。
  従来はほぼ全検査が毎回選ばれたので差が小さかったが、段階を分けると無視できない。下の「合格済みの変更」で扱う。
- 「同じテストを 5 回」は重複ではない。
  ASan・TSan は別の計装の証拠で、`check-real-hal` は 1 件ずつの実行でないとテスト名を示せない（[ADR 0209](0209-real-hal-guard.md)）。
  ここでは削らず、実行する頻度を変える。
- 契約の通常テストは `check` と重複していない。feature の統合が異なり、1 件の実行の証拠も別である（ADR 0197）。
- ADR 0197 の「全反例を作り直す設計上の必要はない」の直後には、バックエンドを入力から外すと検出力を証明できないとある。
  したがって今回は入力から外さず、再検査の時期を変える。その弱さは下に記す。
- 「重い検査は CI へ」は前提を確かめられなかった。
  `origin` は GitHub ではなく、このリポジトリの環境に `gh` もないため、ワークフローの実行を確認できない。
  CI に任せず、ローカルの入口を用意する。

## 決定

### 二つの段階

検査に `tier` を持たせる。

- 作業の段階（既定）: `make verify` と終了フック。今回の変更で壊れていないかを調べる。
- 全体の段階: `make verify-full`。ASan、TSan と対照、Miri、全反例を含む自動検査の全件。

`make verify-full` は変更がない作業ツリーでも全件を選ぶ。入力が同じ合格は再利用する。
CI は従来どおり `--all --only ID` で全件を実行する。

全体の段階は、ユーザーの依頼、配布の前、Phase の単位の受入完了の前に実行する。
負荷をかけるため、定期実行は自動で入れない。

### 作業の段階でサニタイザを選ぶ条件

変更行に `unsafe` の脱出口がある時だけ選ぶ。
Rust の `unsafe`、Swift の `Unsafe`・`@unchecked`・`nonisolated(unsafe)` を、差分の追加行と削除行から探す。
その検査の入力の範囲に限り、テストのディレクトリは数えない。

ファイル単位ではなく行単位にしたのは、`unsafe` を持つファイルの無関係な編集で選ばれるのを避けるためである。
2026-11-02 の後続修正で、消したファイルの削除行と、C（`.c`・`.h`）の空行以外の変更行も数えるようにした（[ADR 0232](0232-verification-escapes-and-expected-red.md)、ENV-01）。
コンパイラーが検査するコードの範囲では、Rust の所有権と Swift 6 の厳密な並行性がメモリと競合の誤りを止める。

検査自身のスクリプトと Miri の対象は `task_inputs` で選ぶ。
`check-bridge-tsan` が選ばれれば、対照の `check-tsan-runtime` も `task_requires` で選ぶ。

### 作業の段階で反例を選ぶ条件

`check-product-contracts` は全契約の通常テストを実行し、反例は次のいずれかが差分の基準と異なる契約だけ実行する。

- 契約の定義（`purpose` を除く）。追加した契約も含む。
- 置換元とその前後 20 行。ファイルの他の場所の編集では変わらない。
- テストの関数本体。同じファイルの別のテストの編集では変わらない。

同じ置換箇所で合格済みなら再実行しない。これで未コミットの変更が残っても同じ反例を繰り返さない。
反例の合格の記録は全体の段階と共有し、全体の段階は従来どおり全入力の識別値が一致するものだけを再利用する。

全反例の置換元が現在のソースに 1 回だけ現れることは、ビルドなしで毎回確認する。
製品コードの編集で反例が適用できなくなった時に、節目まで持ち越さずその作業で分かる。

### 合格済みの変更で選び直さない

全体の段階の検査が合格した時、その時の変更ファイルの内容を結果の `covered` へ記録する。
作業の段階では、同じ内容のままのファイルを選択の根拠に数えない。
ファイルを再び編集すれば選ばれる。`make verify-full` は記録に関係なく全件を選ぶ。

### Swift のコピーを先にビルドする

全反例を毎回実行しなくなると、反例のコピーは本体から遅れる。
遅れたまま最初の反例をビルドすると、契約の期限（180 秒）を使い切って偽の失敗になりうる。
変更を入れないコピーを `SWIFT_COPY_BUILD_TIMEOUT`（1200 秒）の範囲で先にビルドし、期限に算入しない。

### Rust と Swift の基本検査を分ける

`check` から Swift のビルド・テストと橋渡しスパイクを `check-swift` へ分ける。
Swift だけの変更では `cargo test --workspace`（約 100 秒）と履歴 spike の回帰（約 50 秒）を再利用する。
リンク先の Rust が変われば `check-swift` も実行する。
`check-swift` のレシピは、テストが起動するヘルパーと CLI を自分でビルドする。

### 予算

`check-product-contracts` の期限は 3600 秒から 1800 秒へ、反例の全件は `check-contract-controls` の 3600 秒へ分ける。
`hook_timeout` は全自動検査の直列予算を覆うよう 15600 秒にする。
ロック待ちが全体の段階の実行も待てるよう、作業の段階だけの予算にはしない。

## 受け入れる弱さ

作業の段階の合格は次を保証しない。節目までこれらは検出されない。

- 遠いコードの変更で、反例の検出力が失われること。
  例: リンク先の Rust の変更で、Swift の反例がテストで検出されなくなる。
- 安全なコードの変更が、既存の `unsafe` のコードに誤った値を渡すこと。
- コンパイラーの検査の内にある、複数スレッドのロジックの誤りのうち TSan だけが示すもの。

全体の段階が失敗した時は、前回の合格以降の変更すべてが原因の候補になる。
未確認の検査の名前は `make verify`、`report.md`、`make doctor`、`make agent-context` が表示し、合格としては記録しない。

## 変えないこと

- テスト、反例、サニタイザの内容と合否基準、期限、隔離を変更しない。
- 全反例の定義を削除しない。
- 全体の段階の検査の入力は縮めない。

## 回帰と保守

`scripts/tests/test_verification_tiers.py` が次を検査する。

- 実ポリシーの全体の段階の集合と、通常の編集で作業の段階に入らないこと。
- 変更行の判定。既存の `unsafe` の隣の編集、追加と削除、新しいファイル、他のクレート、テスト、差分の基準。
- 未コミットの合格済みの変更で再実行しないこと、失敗の実行は記録しないこと。
- 作業の段階が全体の段階を合格と記録しないこと、`make verify-full` の再利用と失効、変更のない作業ツリー。
- 置換箇所の判定、定義の変更と追加、同じ置換箇所の再利用、失敗した反例を合格にしないこと。
- 全反例に関数本体が見つかること、コピーの先行ビルド、Swift だけの変更で `check` を失効させないこと。

## 計測

実リポジトリの履歴を、実際の選択関数で再生した（製品の実行なし）。
コミットは作業より大きいことがあり、作業ごとの時間の保証ではない。

| 再生 | 対象 | 結果 |
|---|---|---:|
| サニタイザの選択（変更行の条件） | 直近 120 コミット | 28 件（23%） |
| サニタイザの選択（ファイル単位の条件） | 同上 | 61 件（51%） |
| 作業の段階の反例の数の中央値 | 直近 60 コミット | 5 |
| 同 90 パーセンタイル | 同上 | 71 |
| 同 最大 | 同上 | 201 |
| 全反例に対する平均の割合 | 同上 | 11.6% |

反例 1 件は上の実行で約 4.3 秒なので、中央値で約 20 秒、90 パーセンタイルで約 5 分である。

`check-base` の各段を、ビルド済みの状態で 2026-11-01 に測った（ビルド時間を含まない）。

| 段 | 秒 |
|---|---:|
| `cargo test --workspace` | 102.2 |
| 履歴 spike の回帰 | 49.3 |
| `check-shell`（Swift のテスト） | 32.7 |
| `check-bridge` | 10.0 |
| その他 | 4.8 |

作業の段階の実時間を、実際の `make verify` の検査で測った（2026-11-01、10 コア、負荷平均 2〜3）。
ファイルの末尾へコメントを 1 行足して測り、元に戻した。

| 場面 | 秒 | 再利用と反例 |
|---|---:|---|
| 従来の `make verify`（`echode-history` の変更。明示の `spike-history` 219 秒を含む） | 3425 | 反例 230 契約 |
| `crates/echode-history/src/peaks.rs` の変更 | 540 | 反例 0 件 |
| `PianoRollView.swift` の変更 | 230 | `check` を再利用、反例 0 件 |
| 入力がすべて失効し、再ビルドなし | 459 | 反例 0 件 |

この表は常に選ばれる 6 検査の合計である。
このリポジトリの作業ツリーでは実行器の変更が未コミットだったため、`--only` で全反例を除いて測った。
`rtsan` などの領域で選ばれる検査と、変更した反例は含まない。
コメントの編集は Swift の再コンパイルが軽いので、実際の編集ではこれより長くなりうる。

全反例の `check-contract-controls` は 1682 秒だった。
Swift のコピーの先行ビルドはそのうち 26 秒である。

`make verify-full` は、製品コードの再ビルドがほぼない状態で全件 2061 秒だった。
このうち全反例が 1445 秒、ASan が 46 秒、TSan が 92 秒、Miri が 28 秒である。
Rust の変更後のサニタイザは再ビルドの分だけ長く、背景の実行では ASan 515 秒、TSan 273 秒だった。

追加した自己テストは当初 20 秒かかったため、遅かった 1 件のソースの読込みをまとめ、全体で約 8 秒へ縮めた。
