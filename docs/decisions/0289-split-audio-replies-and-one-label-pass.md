# ADR 0289: 出力の応答を位置・試聴・状態に分けて観測し、アレンジの文字は 1 フレーム 1 回で用意する

- 日付: 2026-11-09
- 状態: 採用。位置と試聴の応答、同じ画面のアレンジの文字を直した。分割線とズーム中の文字は、測って直さないと決めた。
- 対象: [統合表](../reviews/2026-11-08-open-items-register.md) の E2（[FCA-17](../reviews/2026-11-03-full-code-audit.md#fca-17-swift-のポーリングとラベル)・[JNK-05](../reviews/2026-10-22-gui-jank-audit.md#jnk-05-分割線のドラッグごとに全体を再評価する)）。
- 方針: [ADR 0278](0278-audit-backlog-order.md) の順の 2「E2 を計測する。GUI の停止に当たる値なら、堅牢性として続けて直す」。
  分割線は GUI のがくつきの監査の単位 6 の決め方（1 イベントが数 ms を越えるなら直す）に従う。

## 測定

2026-11-09、Apple M4・macOS 27.0、release、`make spike-main-thread`。
128 トラック（各 32 ノート）の `WorkspaceView` を 1440 × 900 pt の `NSHostingView` に載せ、インスペクター・エディタ・ブラウザを開いた既定の配置で測った。
窓・表示リンク・音声機器・試聴出力・ヘルパーは開かない。件数と寸法はこの計測の範囲で、製品の上限ではない。
主スレッドの値は、状態を変えてから `layoutSubtreeIfNeeded` が返るまでである。描画の値は描画器の `encode` の CPU 時間で、GPU の完了は含まない。

- debug でもほぼ同じだった（位置の応答 3.41 → 0.20 ms）。時間の大半は SwiftUI と AppKit の中にあり、Swift の最適化の設定に依らない。
- `sample` で位置の応答の繰り返しを採ると、時間は SwiftUI の属性グラフの更新・配置・表示リストに散らばっていた。
  製品のコードで目立つのはノートエディタの `body`（約 12 %）だけで、重い処理が 1 つあるのではなく、再評価する範囲が広かった。
- エディタの分割線の 12 ms は 120 回中の 36 回目の 1 回だった。5 往復・600 回にしても、8.3 ms を超えたのはその 1 回だけで、新しい高さに初めて届いた時に限られた。
- 修正前の試聴だけの応答は測っていない。修正前は位置の応答と同じ読み手へ通知したので、同じ程度だったと推定する。

## 原因

- **応答の全体を 1 つの観測の単位にしていた。** `DocumentSession.audio` は応答（位置・試聴を含む `AudioState`）をそのまま持っていた。
  `@Observable` は性質ごとに通知するので、再生中の 50 ms ごとの応答が `audio` の全部の読み手を通知した。
  `WorkspaceView` は `autoMuteReasons`（[ADR 0282](0282-plugin-nan-and-master-auto-mute.md)）と `rulerLoop` で、ノートエディタは `rulerLoop` で、
  ミックスのインスペクターは `playbackRequested` で、ブラウザは `audio.audition` で `audio` を読んでいた。結果として、応答ごとにワークスペース全体を再評価した。
  `WorkspaceView` の注釈は「ポーリングはトランスポートだけが観測する」としていた。`outputOpening`・`playbackStart` はそのために写しを分けていたが、ほかの読み手は分けていなかった。
- **文字の用意を 1 フレームに 2〜3 回呼んでいた。** `ArrangeLabelTextures.prepare` は、その呼出しのラベルだけを次へ残す。
  アレンジの 1 フレームはルーラー・ヘッダ（・選んだクリップのゲイン）の順に呼んでいたので、各呼出しが前の呼出しの文字を捨てた。
  何も変わらなくても、毎フレーム全部の目盛りとヘッダの文字を Core Text で描き、テクスチャを作り直していた。再生中は毎フレーム描くので、その間ずっと続く。
  ピアノロールは 1 回だけ呼ぶので、この問題はない。

## 比べた案

応答の観測:

| 案 | 内容 | 判定 |
|---|---|---|
| 1 | `outputOpening` と同じ写しを、ループ・再生・自動ミュート・試聴に足す | 採らない。同じ事実の状態が増える。広い View が `audio` を読むたびに写しを足す必要があり、ADR 0282 の自動ミュートはまさにそれを忘れた |
| 2 | `audio` には位置以外が変わった時だけ代入し、位置は別に持つ | 採らない。`audio.tick` が古い値のまま読め、誤用を型で止められない |
| 3 | 橋渡しの `AudioState` を状態（`AudioStatus`）・試聴・位置に分け、文書のセッションが部分ごとに持つ | 採る。`controller.audio` は位置も試聴も持たないので、読み手は型で正しい部分を選ぶ。書込みは `receive` の 1 か所 |
| 4 | ポーリングをやめ、変わった時に Rust から知らせる（FCA-17 の修正方針） | 今は採らない。FFI の通知経路と文書ワーカーの購読が要る。位置は再生中に変わり続けるので回数は減らず、案 3 の後の主スレッドの費用は 0.21 ms である |

アレンジの文字:

| 案 | 内容 | 判定 |
|---|---|---|
| A | 1 フレームの全部の文字を 1 回で用意し、描く時に領域ごとに分ける | 採る |
| B | フレームの世代で使った文字を記録し、次のフレームの始めに使わなかった物を捨てる | 採らない。始まりの呼出しを忘れると、見えない文字を持ち続ける |
| C | 幅に依らない描画か、字形のアトラス（FCA-17 の修正方針） | 今は採らない。残るズーム中の描き直しは最大 6.06 ms で、120 Hz の 1 フレーム（8.3 ms）に収まる |

分割線は、1 イベントの p50 が 2.0〜3.0 ms、p95 が 3.5 ms 以下で、12 ms は新しい高さに届いた時の 1 回だけだった。
単位 6 の「数 ms を越える」に当たらず、GUI の停止でもないので、View を分ける修正はしない。

## 決定

- 橋渡し（`Audio.swift`）: `AudioState` は `status: AudioStatus`、`audition: AuditionStatus?`、`tick` を持つ。
  `@dynamicMemberLookup` で状態の項目を `state.playing` のまま読める。JSON の形は変えない。
- アプリ（`DocumentSession.swift`）: `receive(_:)` だけが `audio`（状態）・`audition`・`position`・`outputOpening`・`playbackStart` を書く。
  `@Observable` は等しい値の代入を通知しないので、各部分をそのまま代入する。比較するのは、試聴の記録を足す時だけである。
  `ProjectController.audio` は `AudioStatus` で、位置は `position`、試聴は `audition` で読む。
- トランスポートの位置の表示は専用の View（`TransportPosition`）にし、位置の唯一の読み手にした。
- 描画（`ArrangePainter.swift`）: アレンジはルーラー・ヘッダ・ゲインの文字を、ピアノロールは自分の文字を、1 フレームに 1 回だけ用意する。
  `ArrangeLabelTextures` の注釈に、1 フレーム 1 回の契約を書いた。
- 分割線とズーム中の文字は変えない。

## 回帰と基盤

- `AudioReplyObservationTests` の `contractEachReplyPartNotifiesOnlyItsOwnReaders` は、位置・試聴・状態の各応答が、ほかの部分の読み手を通知しないことを確かめる。
  `contractPlaybackPollsReachOnlyThePositionDisplay` は、製品の `observeAudio` の経路で、再生中の応答がワークスペース・ミックス・ルーラー・ブラウザの読む値を通知しないことを確かめる。
  必須契約 `audio-reply-observation-ui` とし、状態の読み手（`controller.audio`・`rulerLoop`）が位置も読む反例で失敗する。
  「毎回代入する」は反例にならない。等しい値の代入は通知されないからである。
- `ArrangeLabelCacheTests` の `contractRedrawingTheSameArrangeRasterizesNoLabel` は、同じ画面を描き直しても文字を描かないことを製品の描画器で確かめる。
  必須契約 `arrange-label-cache` とし、2 回目の用意を戻す反例で失敗する。数は `ArrangePainter.rasterizedLabels` で読む。
- `make spike-main-thread`（`MainThreadProbe.swift`）を手動の検査に足した。`app_drawing` の変更で候補になる。
  プローブは試聴出力の設定を差し替え、機器を開かない。`ECHODE_MAIN_THREAD_PROFILE_SECONDS` を与えると、位置の応答をその秒数だけ繰り返し、`sample` で採れる。
  最初の版は差し替えを入れておらず、計測で無音の試聴出力を既定の出力機器に開いていた（音は出していない）。

## 残る範囲と再開の条件

- **状態の応答**: 再生・停止・メトロノーム・ループ・出力機器・自動ミュートの応答は、今もワークスペース全体を再評価する（4.2 ms）。
  操作の頻度でしか起きないので残す。p95 が 8.3 ms を超えた時か、再生中に応答ごとに変わる項目を状態へ足す時に戻る。
- **ズーム中の目盛り**: 文字の幅が拍の間隔に従うので、52 pt/拍より狭いズーム中は、見えている目盛りの文字を毎フレーム描き直す（56 個、最大 6.06 ms、描画スレッド）。
  `spike-main-thread` で 8.3 ms を超えた時か、ピンチ中のがくつきの報告があった時に、案 C と比べて直す。
- **分割線のドラッグ**: 1 イベントでワークスペース全体を再評価する（JNK-05）。p95 が 8.3 ms を超えた時か、ドラッグ中のがくつきの報告（UC-02）があった時に、配置を読む View を分ける。
- **50 ms のポーリング**: 応答そのものは残る。変化のない応答の主スレッドの費用は 0.007 ms である。
- **自動計測の外**: 画面の合成と表示リンクの時刻、実画面の滑らかさは測っていない。
