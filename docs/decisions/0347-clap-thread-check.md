# 0347. CLAP のスレッド判定を生成時の ID と既存の TLS から返す

- 日付: 2026-11-14
- 状態: 採用
- 対象: FCA-07 の `clap.thread-check`（`clap.log` 等は残る）

## 背景

P2-03 のホスト拡張のうち、プラグインが自身の呼出し元を照合する `clap.thread-check` が未接続だった。
スレッドを問うだけの操作が、処理スレッドにロック・確保・メイン応答の待ちを持ち込んではならない。
メイン callback が来る前の初期化と有効化でも、正しく答える必要がある。

## 比べた案と決定

- **OS のメインスレッドかを問う**: 不採用。
  CLAP のメインはそのインスタンスを生成したスレッドであり、比較用の実行やテストの呼出し元を OS の主スレッドへ限定しない。
- **診断用の `Bridge.main_id`・`audio_id` の Mutex を読む**: 不採用。
  メインの ID は初回の source 実行まで未記録で、音声からロックも取ってしまう。
- **生成時の ID と既存の処理スレッドの印を読む**: 採用。
  `HostShared` を作る時に `ThreadId` を記録する。
  音声判定は `AudioFlag` が立てる `ON_AUDIO` を使い、start・process・reset・stop とブロック間を一つの規則で扱う。
  プラグインの補助スレッドはどちらにもならない。

`HostThreadCheck` を既存の CLAP 拡張の列に登録し、`HostWrapper::handle` の共有アクセスだけで応答する。
問合せはメイン専用の handler に入らず、ロック・確保・IPC を足さない。
処理スレッドは RT 区間へ入る前に既に自身の `ThreadId` を取得している。
プロセスの境界・保存形式・C ABI と依存は変えない。

比較用の `measure_in_process` も start から stop まで `AudioFlag` を保持し、有効化・無効化はその外で行う。
ここは同じ物理スレッドでメインと音声の役割を担うため、音声区間では二つの問合せがともに真になり得る。
製品の隔離ヘルパーは別の処理スレッドを使う。

## 回帰と基盤

`echode-test-plugin` の `thread-check` fault は、初期化・補助スレッド・有効化・start・process・reset・メイン callback の判定を調べる。
処理側の結果は原子変数のビットへ記録し、状態の保存で親が読む。音声からログを書かない。
失敗ビットは以後の成功でも消さず、戻り値のない reset と callback の失敗も見落とさない。

`isolation.rs` の回帰は実ヘルパーで 1・32・127・256 フレームを通し、音声の倍増と全区間の到達を照合する。
修正前は終了コード 101 と `spawn plugin host: ... thread-check extension is unavailable` を照合した。
証拠は `target/focused-checks/thread-check-red/` である。
通常の検査では確保検出を保ち、`under_rtsan` の名前で既存の全体検査の対象にもする。
新しい検査入口や選択条件は要らない。RTSan 自体は今回の作業では実行しない。
性能の比較計測はしておらず、実機の期限内の完走を保証しない。

設計書・P2-03 の進捗・監査の現在欄と、スレッド判定の診断手順を更新する。
第三者 CLAP の実機での互換性は [UC-80](../user-checks.md) へ分け、`clap.log` 等を完了扱いしない。
