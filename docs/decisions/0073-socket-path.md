# ADR 0073: ソケットのパスは種類を見てから片付ける

- 日付: 2026-10-13
- 状態: 採用
- 範囲: ローカル JSON-RPC の Unix ソケット

## 背景

ソケットを作る処理は、指定したパスに何があっても消してからバインドしていた（監査 API-3、2026-10-08 の同項目）。通常ファイルも消える。接続相手の uid も見ず、1 行の長さと読み込みの待ちにも上限が無かった。接続は 1 本ずつなので、黙っているクライアントがいると次の接続が始まらない。

## 決定

パスが無ければ、そのままバインドする。通常ファイル、シンボリックリンク、ディレクトリなどソケット以外は消さず、エラーにする。ソケットへ接続できるときは、稼働中とみなして残す。接続が拒否される古いソケットだけを消してからバインドする。

受けた接続は `getpeereid` の uid が自分と一致するときだけ読む。1 行は 1 MiB までで、これは 1 つの JSON-RPC 行の上限であり、プロジェクトの大きさの上限ではない。無応答は 30 秒でその接続だけを終える。行が長すぎる接続も、その接続だけを終えて次を受ける。複数の接続を同時に処理する形は足さない。

## 結果

通常ファイルのパスではエラーになり、中身は残る。使用中のソケットは二度目のバインドでエラーになり、リスナーを閉じたあとの古いソケットは置き換わる。黙っているクライアントは 30 秒を待たずに検査できる短い上限で接続を返し、上限を超えた行は拒否する。画面での操作確認は未実施である。

## 後日対応（2026-10-25）

[現行コード監査 CUR-04](../reviews/2026-10-25-code-audit.md) で、応答の送信には待機上限がないことを再現した。
読込みだけでなく書込みの無進行にも 30 秒の上限を設ける。
送信失敗は `could not write API reply` としてその接続だけを閉じ、後続接続を受ける。
編集は応答送信の前に成立していることがあるため、サーバーは要求を再実行しない。
クライアントも送信エラーを編集の未成立と決めつけず、再接続して状態を照合する。
回帰は送信バッファを満たした接続の後に別のクライアントから概要を取得し、先の編集が 1 回だけ成立したことを確認する。
この短い待機上限の検査はタイムアウトの機能回帰であり、性能測定ではない。
