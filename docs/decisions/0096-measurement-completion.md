# 0096: 音声計測の進行と完走を合格条件にする

- 日付: 2026-10-15
- 状態: 採用

## 発見

10分のエンジン計測中、13:26:22 に USB EarPods の IO が停止し、既定の出力が内蔵スピーカーへ切り替わった。コールバック数は77,386で止まった。スレッドの採取では音声ワーカーは待機し、HAL の IO スレッドは存在しなかった。OS の Sleep はこの時刻には記録されていない。

調査のため検査用プロセスを SIGINT で中断したところ、旧計測器は `result: pass` を出した。既存の条件は非空の標本と処理期限・間隔の異常だけを見ていた。HAL が呼ばれなくなれば異常の標本も追加されず、少しの処理結果だけで合格し得た。中断と完走も区別していなかった。

この合格記録は無効であり、成功の証拠に使わない。記録、音声スレッドの採取、機器識別子を伏せた CoreAudio ログはローカルの `target/debug-reports/20261015T043156Z-jqe4p8m6/`。`measurement-invalid.txt` に理由を残した。

## 判断

実機と回帰検査で同じ `measure_progress` の制御ループを使う。制御スレッドでコールバック数・経過時間・既定出力・中断を観測する。2秒進まない場合、既定出力の変更・取得失敗、中断は、それぞれの終了理由として直ちに計測を終える。2秒は計測の生存確認であり、音声処理の期限ではない。

macOS の単調時計がスリープ中に進まない場合もあるため、壁時計との経過差を制御側で照合する。2秒以上の差や壁時計の逆行は `ClockDiscontinuity` として不合格にする。スリープから次の観測前に復帰してコールバック数が増えた場合も見逃さない。大きい時計補正も環境条件の不成立として区別し、音声の不具合と即断しない。

終了後は従来どおり IOProc とワーカーを閉じ、バッファ等の設定を復元する。結果は要求時間・測定時間・終了理由を出す。合格判定は `Report::passed()` を正本にし、完走、要求時間以上、ウォーミングアップ後の標本、従来の期限・間隔・Workgroup・バッファ条件をすべて要求する。結果を保存する別の bool と二重管理しない。

コールバックの中へ監視、OS の問い合わせ、ログ、割当を追加しない。既定出力の取得には既存の公開 HAL 経路を使い、手動の FFI 宣言を追加しない。デバイスを勝手に選び直して測定を継ぎ足すこともしない。製品の機器追従は `echode-audio-io` の責務であり、固定条件の負荷計測とは別である。

## 検査と運用

同じ制御ループへ観測列を与え、正常完走、初回から停止、途中停止、中断、既定出力変更、デバイス取得失敗、スリープ復帰等の時計差を通常検査にする。結果の非空・部分時間・既存の異常判定も確認する。壁時計や実機は使わない。必須契約へ登録し、完走条件を除いたコピーが期待値で失敗することを確認する。

検査の準備にも数分かかっていた。10万ノートの fixture を逐次編集で作り、増えるモデルを毎回コピーしていたため、測定前の作成が二次的に増えていた。同じ配置とノートを公開の `Project::try_assemble` で一度組み立て、不変条件を検査する。測定する製品の計画準備・バッファ要求と、その期待値は変更しない。

実機の `spike-engine` は従来どおり600秒を要求する。短いデバッグ実行や中断した記録を、その代わりの合格に使わない。実機条件を保てなければ失敗の証拠を保存し、未実行・見送り理由を現在のソースの検査記録へ残す。スリープ、イヤホンの抜き差し、OS 側の IO 停止、ワーカーのデッドロックは、同じ「音切れ」と決めつけず [デバッグ手順](../debugging.md) で区別する。
