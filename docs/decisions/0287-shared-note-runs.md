# ADR 0287: 中身のノートを共有の run に分け、Undo の段が編集した分だけを持つ

- 日付: 2026-11-09
- 状態: 採用。R6 をここで区切る。総量の予算は下の再開の条件まで入れない。
- 対象: [統合表](../reviews/2026-11-08-open-items-register.md) の R6（[FCA-19](../reviews/2026-11-03-full-code-audit.md#fca-19-減らない記録)・MOD-12）と、[ADR 0286](0286-history-usage-diagnostics.md) の残る範囲。
- 方針: [ADR 0276](0276-priority-order-and-delegated-decisions.md) の「段を捨てない。予算を入れる時は、古い段を Git の履歴へ移す方式に限る」。

## 問題

- ADR 0286 の計測では、1 万ノートのクリップでベロシティを 1 つ変えるたびに、1 段が 801 KB を持った。1,000 段で 801 MB である。
- 原因は、ノートの編集が中身（`Content`）の `Vec<Note>` 全体を写すことである。移動・追加・削除・複製も同じだった。
- トラックの編集（1 段 2.7 KB）と構造の編集（6.1 KB）より 2 桁大きく、長い作業のメモリはほぼこの場合で決まる。

## 比べた案

| 案 | 内容 | 判定 |
|---|---|---|
| 1 | 予算を超えた古い段を Git の履歴へ移す（ADR 0276 の方式） | 今は採らない。予算に届くまでは今と同じだけ持つ。Undo が移した段に届くと、読み戻しの I/O と失敗の経路が増える。ジャーナルと自動保存の間引きとの対応も決める必要がある |
| 2 | 古い段の版を捨て、ジャーナルの変更を逆に当てて戻す（`ChangeSet::invert`。復旧と同じ規則） | 採らない。`apply_changeset` は版全体を分解して組み直すので、Undo がプロジェクトの大きさに比例する。全トラックと中身が新しい `Arc` になり、計画の再利用（ADR 0274・0279）が外れる。採用はテンポの変更並み（最大 4 ms）になる。共有を保つ差分の適用を作り直す必要がある |
| 3 | ノートを `Arc<Note>` の配列にする | 採らない。1 万ノートでもポインタの配列（80 KB）を毎段写し、減るのは 10 分の 1 にとどまる。ノートごとの割当で走査も遅くなる |
| 4 | 既存の永続ベクタ（imbl・rpds。どちらも MPL-2.0） | 採らない。手元のレジストリになく、取得はダウンロードになる。位置で区切るので、同じ並びが同じ区切りになる保証がない。移動を remove と insert に書き換える必要もある。測ってはいない |
| 5 | 中身のノートを、内容で区切った共有の run に分ける | 採る。Undo の意味・失敗の経路・速さを変えず、段を捨てない |

## 決定

- `echode-model` の `Notes` が中身のノートを持つ。並びは今までどおり開始・音高・ID の順である。
  - ノートは `Arc<[Note]>` の run に分かれる。run は、ID を混ぜた値（SplitMix64 の仕上げ）の下位 6 ビットが 0 のノートの後と、列の終わりで切れる。平均は 64 ノート。
  - 区切りは並びだけで決まる。同じ並びは同じ run になるので、等しいかの比較は run ごとに `Arc::ptr_eq` で済む。
  - run の長さに上限は置かない。上限で切った区切りは、その前の挿入で全部ずれるので、1 回の編集が写す量の最悪値を減らさない。
    区切りに当たらない ID だけの列は 1 つの run になり、写す量は従来の `Vec` と同じである。
- 書込み:
  - `splice` は編集する位置を含む run だけを組み直す。組み直した末尾が区切りでなくなった時だけ、次の run も含める。古い run と等しい run は古い `Arc` を使う。
  - `update`・`remove`・`insert_sorted`・`replace_sorted` はこの上にある。多くのノートを変える編集は `edit` で、全体を一度写して変わらない run を共有に戻す。
- 読込み: `iter`、`get`（run の二分探索）、`cursor`（同じ run の中では探索しない）、`partition_point`（run と run の中の 2 段の二分探索）。
- 保存形式・`ChangeSet`・ジャーナル・API の形は変えない。どれもノートを順に読むだけで、run を出さない。
- `Footprint` は、隣の版の同じ中身と共有しない run だけを数える。どちらの run も先頭のノートの順に並ぶので、一度の走査で対にする。
- 描画の `ContentIndex` は開始位置の配列を持ち、可視の問い合わせは `cursor` で読む。`get` を毎回探索する形は 1.5 倍遅かった（下の測定）。

## 測定

2026-11-09、Apple M4・macOS 27.0、release。

Undo の段（`make spike-history` の `measure_history_usage`、各 1,000 段）:

| 場面 | 前（ADR 0286） | 後 |
|---|---:|---:|
| 1 万ノートの 1 クリップで、ベロシティを 1 つずつ変える | 1 段 801 KB（計 801 MB） | 1 段 12.8 KB（計 12.8 MB） |
| 同じクリップで、ノートを時間と音高で動かす（新しい場面） | — | 1 段 14.6 KB（計 14.6 MB） |
| 128 トラックのゲインを順に変える | 1 段 2.7 KB | 1 段 2.7 KB |
| 128 トラックから 1,000 回トラックを足す | 1 段 6.1 KB | 1 段 6.1 KB |

- ベロシティの場面で段が持つノートは 1 段あたり平均 112 である。無作為に選んだノートは長い run に入りやすいので、平均の 64 より大きい。
  残りは中身の run の一覧（約 156 本 × 24 バイト、約 3.7 KB）である。
- 移動の場面は、ノートが出る run と入る run を持つ。クリップの合わせ直しで、トラックも 1 段ごとに写る。
- 問い合わせは 1.4〜1.8 ms（前は 0.09 ms）。段ごとに中身の run を対にするからで、診断の時だけ呼ぶ。

速さ（同じ機械、同じ時間帯）:

- `make spike-arrange-query`（1,000 トラック・10 万ノートの全体の問い合わせ、中央値）: HEAD を別の作業ツリーで作り、1.49・1.51 ms だった。
  変更後は 1.55 ms。`get` で毎回探索した最初の形は 2.23 ms で、開始位置の配列と `cursor` で戻した。
- `make spike-scale` の `model_edit`（128 × 64）: 組立て 13.26 ms、ノートの編集 0.87 ms、トラックの追加 0.29 ms。
  統合表の 11/8 の値（13.4・1.08・0.26 ms）と同じ範囲である。HEAD とは同時に測っていない。
- 再生の採用（256 × 4,000）: 1 ノートの編集の最大 418 µs、基準テンポの最大 423 µs、制御側の作り直し約 0.49 秒。ADR 0279・0280 の値と同じ範囲である。
  音声側はエンジンの計画を読み、`Notes` を読まない。

## 回帰と基盤

- `notes_tests.rs`: 区切りの規則、`Vec` と同じ読込み、2,000 回の無作為な編集が `Vec` の操作と一致し区切りが規則どおりで、1 回の編集が 3 本の run を超えて組み直さないこと、1 万ノートのベロシティ編集が 1 本だけ組み直すこと、`cursor`。
- `footprint_tests.rs`: 1 万ノートのクリップでベロシティ・移動・複製・削除の 1 段が持つノートが 3 本の run 以内で、64 KB 未満であること（FCA-19 の回帰）。
- `model_scale_tests.rs` の写しの計数は、中身の写しで run の本数を、ノートの写しで run の範囲を確かめる形に改めた。
- `session_tests.rs` の使用量の不変条件は、段が持つノートを編集した run の和で確かめる。
- `crates/echode-actions/tests/history_usage.rs` に移動の場面を足した。検査の選択（`scripts/verification.json`）は変えない。対象の crate は既に入っている。

## 残る範囲と再開の条件

- **総量の予算はない**。段は変えた run を持つので、多くのノートを変える編集は 1 段がその分を持つ。
  1 万ノートを全部動かす編集を 1,000 回すると、従来どおり約 0.8 GB になる。ジャーナルの変更の記録も同じ大きさになる。
- 次のどちらかの時に予算へ戻る。その時は、案 1（ADR 0276 の方式）と、案 2 を共有を保つ差分の適用に作り直す形とを比べる。
  - `measure_history_usage` か回帰で、1 つのノートやトラックの編集の 1 段が 100 KB を超えた時。
  - ログの仕組み（統合表の M4）で GUI から使用量を読めるようになり、実際の作業で段の分が 1 GB を超えた時。
- 平均の長さ 64 は 1 つだけ測った。短くすると run の一覧が、長くすると写す量が増える。
