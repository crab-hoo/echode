# ADR 0166: 検査の失敗を隠さず、実行不能な環境と安価な失敗を先に検出する

- 日付: 2026-10-25
- 状態: 採用
- 対象: `scripts/verify.py`、`scripts/verification.json`、Makefile、作業中の個別コマンド

## 報告の監査

ユーザーは Pi と Claude Code の過去セッションから、パイプ、`;`、終了コードを表示する `echo` による失敗の隠蔽を報告した。
また、約 28 分後に古い TSan ランタイム、約 10 分後に ASan のテスト前提の不備を検出したとしている。
元のセッションログは今回の入力に含まれず、日時・所要時間・最終的な修正は独立確認していない。

現行経路を調べた結果は次のとおり。

- `verify.py` は `make` の終了コードを判定し、最初の失敗で止める。ここが失敗コードを無視していたわけではない。
- 検査用 Bash スクリプトは `set -euo pipefail` を使う。既存の `tee` 経路にも適用されている。
- ただし、任意の Make レシピやエージェントが直接作る複合コマンドでは、途中の失敗を最後の成功で隠せる。
  修正前の `run_check` に `false | cat`、`false; echo ...`、`false; true` のレシピを渡し、成功扱いを再現した。
- 現行の `doctor` は既に `tsan_runtime.prepared(context())` を使う。
  「現在も診断に確認がない」という解釈は誤りだが、`verify.py` の実行前の必須条件にはなっていなかった。
- 順序は JSON の配列順で、フォーマットは `check-base` のビルド後、ASan と TSan は製品契約の後だった。

修正前の反例は `target/verification/execution-before.log` に保持する。
過去セッションの結果を現在の製品不具合や計測値として扱わない。

## 決定

### 終了コードを最優先にする

Make レシピは Bash の `-euo pipefail` で実行し、`verify.py` も同じ指定を子の `make` へ渡す。
macOS 標準の GNU make 3.81 は `.SHELLFLAGS` に対応しないため、`SHELL` にオプションを含める。
`set -e` の例外になる条件式や、明示的に無視する失敗まで正当化する仕組みではない。

作業中に独立した複数の個別検査を実行する時は `scripts/checked_commands.py` を使う。
シェルを介さず argv を実行し、全コマンドの終了コード・完全ログを残し、一つでも失敗したら全体も非ゼロにする。
これは選択・キャッシュ・完了判定を持たない記録用ユーティリティで、別の検査系統ではない。
`make verify` の代用にも、既存結果への合格の登録にも使わない。

意図した TDD の red は 1 コマンドに限り、非ゼロの期待終了コードと、その回帰固有のアサーションを明示して照合する。
成功、別の失敗、起動不能、シグナル、タイムアウトは期待した red へ変換しない。
自由なシェルコマンドを実行できる Pi / Claude Code 自体の成否は、このプロジェクトだけでは強制できない。
危険な構造を使わない必須手順と、プロジェクト内の安全な実行経路を用意する。

### 実行予定だけを事前確認する

既存の選択と結果再利用を先に行い、実際に実行する検査が宣言した `preflight` だけを重複なく確認する。
手動検査の見送り、選択外、`--only` の対象外、同じ入力での合格再利用には準備を要求しない。
事前確認の失敗は環境の失敗として別に記録し、製品検査を実行したことにも合格にも変えない。

確認するのはツールの起動、ビルドホスト、オフライン Cargo 依存、固定 nightly の rust-src / Miri、TSan の準備状態である。
TSan は既存の `tsan_runtime.py --directory fixed` を再利用し、マニフェスト・文脈・両ランタイムの実バイトを確認する。
通常の `check-tsan-runtime` と実競合の対照は残し、準備確認で代用しない。
事前確認は取得・インストール・ビルド・機器アクセスを行わず、個別期限と復旧案内を持つ。
Miri の sysroot や nightly 標準ライブラリの全依存を準備済みと証明するものではなく、実検査側のガードも維持する。

定義は `verification.json` に一元化する。
事前確認の定義、実行スクリプト、追加の `inputs` も依存する検査の選択・識別値へ含める。
共通実行器の変更は既存の `evidence_inputs` と同様に全自動検査を失効させる。

### 同じ集合の順序だけを変える

フォーマットを `check-format` に分離し、従来の検査内容を削らず、製品ビルドより先に実行する。
`priority` の小さい準備済みの検査から選び、同順位では従来の配列順を保つ。
`after` は同時に実行対象となった検査の先行関係であり、検査を追加選択する条件ではない。
循環・不明な参照はポリシー読込み時に拒否する。

優先順はフォーマット、検査ポリシー、TSan ランタイムの実対照、選択された ASan、残りとする。
ASan が既存の変更検知で選ばれた場合だけ前へ出し、無関係な変更へ ASan を追加しない。
検査同士を並列にせず、既存の排他、期限、必須契約、負の対照、手動検査の扱いを維持する。

## 検出遅延の測定と限界

`report.json` の `execution` は実行予定順と、開始から最初の失敗を検出するまでの秒数・検査名を記録する。
`preflight` の環境失敗と製品検査の失敗を区別する。合格時の平均実行時間で代用しない。

`make spike-verification-failures` は実際の `verify.py` を一時リポジトリで使い、同じ選択集合へ失敗を注入する。
各検査の仕事だけを一定時間の待機と終了コードへ置き換え、旧配置を模した順序と現在の優先順・事前確認を比較する。
フォーマット、ポリシー、ASan、古いランタイムの各失敗について、選択集合と最初の失敗までの時間を JSON に残す。
これは製品の実測や過去の 28 分の再現ではない。冷えた ASan のビルドコストや実際の失敗頻度の優劣は未測定である。
ポリシー失敗だけならフォーマットを先行させる分だけ遅くなるため、全失敗ケースの一律改善も主張しない。

## 回帰と運用

`scripts/tests/test_verification_execution.py` は終了コードの隠蔽、期待した red、順序と集合の保持を検査する。
また、環境失敗で製品検査が始まらないこと、対象外と再利用を妨げないこと、準備定義・入力の失効を確認する。
`scripts/tests/test_tsan_runtime.py` の既存の古い文脈・改変されたライブラリの拒否も維持する。
`make debug-report` は登録済みの事前確認ログと失敗注入の計測 JSON を収集し、任意の個別コマンドのログは自動収集しない。
利用手順は [検査手順](../verification.md)、失敗時の識別は [デバッグ手順](../debugging.md) を参照する。
