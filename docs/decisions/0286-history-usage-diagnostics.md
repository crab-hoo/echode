# ADR 0286: Undo の段が持つメモリを測って診断へ出し、予算は写す単位と比べてから決める

- 日付: 2026-11-09
- 状態: 採用。使用量の診断だけを入れた。写す単位は [ADR 0287](0287-shared-note-runs.md) で小さくし、R6 はそこで区切った（予算は再開の条件まで入れない）。
- 対象: [統合表](../reviews/2026-11-08-open-items-register.md) の R6（[FCA-19](../reviews/2026-11-03-full-code-audit.md#fca-19-減らない記録)・MOD-12）。
- 方針: [ADR 0276](0276-priority-order-and-delegated-decisions.md) の「段を捨てない。先に使用量を診断へ出す。予算を入れる時は、古い段を Git の履歴へ移す方式に限り、固定の段数上限は置かない」。

## 問題

- `Session`（`echode-actions`）は、確定した段ごとに編集前の版（`Project`）を 1 つ持つ。Redo も同じで、段数の上限はない。
- 編集は変えたトラックと中身だけを作り直し、ほかは `Arc` で共有する。ある版が余分に持つのは、隣の版と共有しない分である。
- この量を見る手段がなかった。どの操作で増えるのか、予算をいくつにするのかの根拠がない。

## 測定

2026-11-09、Apple M4・macOS 27.0、release。各場面で 1,000 段を積んだ（`make spike-history` の `measure_history_usage`）。
バイト数は下の決定の推定で、割当器の丸めを含まない。件数は計測の場面で、製品の上限ではない。

| 場面 | 段が持つ分 | 1 段あたり | ジャーナル | 今の版 | 問い合わせ |
|---|---:|---:|---:|---:|---:|
| 1 万ノートの 1 クリップで、ベロシティを 1 つずつ変える | 801 MB（中身 1,000・ノート 1,000 万） | 801 KB | 0.36 MB | 0.80 MB | 0.09 ms |
| 128 トラック（各 64 ノートの 1 クリップ）で、ゲインを順に変える | 2.7 MB（トラック 1,000） | 2.7 KB | 0.36 MB | 1.38 MB | 4.6 ms |
| 128 トラックから、トラックを 1,000 回足す | 6.1 MB（トラック・中身 0） | 6.1 KB | 3.3 MB | 0.64 MB | 2.3 ms |

- ノートの編集は中身（`Content`）全体を写す。1 段がその中身の大きさ（1 ノート約 80 バイト）を持ち、1 万ノートのクリップを 1,000 回直すと約 0.8 GB になる。
  長い作業でメモリが GB 単位になり得るのは、この場合である。
- トラックの編集は、そのトラック（クリップとデバイスの一覧）だけを写し、1 段あたり数 KB である。
- 構造の編集は、どの版も自分のトラックの一覧（`Arc` の配列）を持つので、トラック数に比例する（128 → 1,128 で平均 6 KB）。
- 問い合わせの時間は、段数 × トラック数でほぼ決まる。並びの違う段で ID の表を作るからである。

## 比べた案

| 案 | 内容 | 判定 |
|---|---|---|
| 1 | 段を積む・戻す時に差分を足し引きして、使用量を常に持つ | 採らない。Undo・Redo・取消し・復元・背景の状態の取込みの全経路に足し引きが入り、1 つ忘れると値がずれる。ずれを確かめる別の論理も要る（ADR 0276 の入り組み） |
| 2 | 問い合わせの時に版の並びをたどり、隣の版と同じ `Arc` でない物を数える | 採る。規則は 1 つで、`Session` の状態を変えない。時間は問い合わせだけが払う |
| 3 | 割当器の統計から実測する | 採らない。プロセス全体の値で、履歴の分を分けられない |
| 4 | 予算も同時に入れる | 採らない。下の「残る範囲」を参照 |

- 案 2 で複数の版が持つ物を 1 回だけ数えられるのは、ある物が版の並びの連続した区間にだけ現れるからである。
  編集は新しい `Arc` を作り、Undo と Redo は版を動かすだけで、外した物を後の版へ戻さない。

## 決定

- `echode-model` に `Footprint`（トラック・中身・ノートの件数とバイト数）を置く。
  - `Project::footprint` は版の全体、`Project::footprint_beyond(neighbor)` は `neighbor` と共有しない分を返す。
  - トラックは同じ位置の `Arc::ptr_eq` を先に見て、違えば ID の表で引く。中身は ID 順なので二分探索で引く。
  - バイト数は、値の `size_of` と、その値が持つベクタ・文字列の容量の和である。版自身の一覧は長さで数え、テンポは点の配列を共有しない時だけ数える。
  - `ChangeSet::estimated_bytes` は変更の記録の大きさで、値の中の文字列と ID の一覧は数えない。
- `echode-actions` の `Session::usage` が `HistoryUsage` を返す。
  - 段数（Undo・Redo）、段だけが持つ版の `Footprint`、メモリ上のジャーナルの変更数と推定のバイト数を持つ。
  - Undo の版は今に近い側の隣（より新しい版）、Redo の版は今に近い側の隣（より古い版）と比べる。今の版は数えない。
- `echode-history` の `DocumentHost::history_usage` で、文書のスレッドが答える。
  読むだけなので、ジャーナルの耐久性が不明で編集を止めた後も答える。
- JSON-RPC の `history.usage` と、MCP の読み取り専用の `echode.history.usage`（引数なし）で出す。
  メソッドを足しただけで既存の意味は変えないので、プロトコルの版は 1 のままにする（[ADR 0034](0034-api-transaction.md)）。

## 回帰と基盤

- `footprint_tests.rs`: 版の全体、同じ版、ノートの編集で写した中身、並びのずれたトラック、テンポの編集を確かめる。
- `session_tests.rs` の `usage_counts_each_replaced_content_once_wherever_current_is` は、不変条件「段の分 + 今の版の全体」が Undo と Redo で変わらないことを確かめる。
  新しい編集で Redo の枝を捨てると、その版が数から消えることも確かめる。
- `host_tests.rs` の `history_usage_follows_undo_and_redo_and_answers_after_a_halt` は、文書のスレッド越しの段数と、止まった後の応答を確かめる。
- `rpc_tests.rs` は `history.usage` の結果と、読んでも Redo が残ることを、`mcp_arguments.rs` は引数の拒否を確かめる。
- `measure_history_usage`（`crates/echode-actions/tests/history_usage.rs`）を `spike-history` に足し、`scripts/verification.json` の対象に `echode-actions` を加えた。
  時間に依らない推定だが、1,000 段の作成に時間がかかるので `#[ignore]` にした。

## 残る範囲

- **予算は未実装**。測定から、増えるのは主にノートの編集で中身全体を写す場合と分かった。
  2026-11-09 の [ADR 0287](0287-shared-note-runs.md) でノートを共有の run に分け、1 万ノートのベロシティ編集は 1 段 12.8 KB になった。予算は同 ADR の再開の条件まで入れない。
  古い段を Git の履歴へ移す前に、中身のノートを区切って写す単位を小さくする案と比べて決める。
  移す方式は、Undo が移した段に届いた時の読み戻し、ジャーナルとの対応、自動保存の間引き（[ADR 0276](0276-priority-order-and-delegated-decisions.md)）との関係を決める必要がある。
- **GUI では見えない**。アプリの文書は JSON-RPC を開かず（[ADR 0115](0115-phase2-mcp.md)）、ログの仕組み（統合表の M4）もない。M4 で接続する。
- **推定の範囲**: 割当器の丸めとヘッダ、値の中の文字列と ID の一覧、`Action` の中身は数えない。実際の使用量はこれより大きい。
- **問い合わせの時間**: 段数 × トラック数に比例し、その間は文書のスレッドが次の編集を待たせる。診断の時だけ呼び、画面の更新ごとには呼ばない。
