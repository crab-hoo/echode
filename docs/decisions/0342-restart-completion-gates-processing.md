# 0342. 再起動の完了世代までプラグインの処理を再開しない

- 日付: 2026-11-14
- 状態: 採用
- 対象: RTA-02、RTA-05 の再起動中の待ち

## 背景

[リアルタイム監査](../reviews/2026-11-14-realtime-adversarial-audit.md)の RTA-02 は、
`activate` の中で次の `request_restart` が来ると制御スレッドが戻らなくなる。
処理側が停止を確認した番号は進むが、先の再起動で作ったプロセッサを開始すると、
制御側はそのプロセッサの解放を待ち続ける。停止の確認だけを再開の条件にしたのが原因である。

着手時の `6cf4eff` で `audit_rta02_*` を実行し、
`nested-activation 3` が来ないアサーションと終了コード 101 を照合した。
ログは `target/focused-checks/rta02-red/` に置く。
これは機器なしの再現で、実時間の性能の計測ではない。

## 比べた案

- **要求を列に積み、再起動ごとに処理器を渡す**: 不採用。
  CLAP は再起動の集約を許す。今ある世代番号と別の順序・所有の状態を持つ必要がない。
- **停止の確認とメインの完了を同じ世代で照合する**: 採用。
  既存の `restart_request`・`restart_ack`・`main_done` だけを使い、状態とスレッドを増やさない。
- **ソケットと内部の起床を新しい待ちに統合する**: 今回は不採用。
  通常のソケット待ちも改善できるが、RT 側からの起床と寿命の境界まで変わる。
  再起動の内側はソケットを読まないので、既存の内部の警報だけを待てば、空回りも余分な周期待ちも避けられる。

## 決定

処理の開始と `request_process` の消費の条件を、要求・停止の確認・メインの完了の世代が全て等しいことに揃える。
停止の確認は停止を保証するだけで、`activate` が終わったことを保証しない。
再起動の途中の `request_process` は消費せず残し、`OP_ARM` が再起動の操作を上書きすることも防ぐ。

メインは停止済みプロセッサを受け取り、再有効化して渡した時だけ完了の世代を公開する。
プロセッサを取れない・有効化できない時は、完了や再開を通知せずヘルパーを止める。
処理側は再起動中もブロックへ無音で答え、メインの処理の完了を待たない。

制御側の停止の確認とメインの完了の待ちは、`control_alarm` を使う。
親の要求は再起動後に読み、ソケットが読み出せる間の空回りを避ける。
[ADR 0041](0041-helper-threads.md) のスレッドの役割は変えない。
`request_callback` が source を直接起こす経路（RTA-01）と、通常のソケット待ちの 20 ms ポーリングは今回の範囲外である。
RTA-05 全体を完了にはしない。

## 回帰と残る確認

`audit_rta02_*` の無視を外し、再起動後の制御応答・状態保存・音声の復帰を検査する。
必須契約 `plugin-nested-restart` に登録し、再開の条件を外す反例を置く。
同じ反例を作業中にも入れ、終了コード 101 と `nested-activation 3` が来ないアサーションを照合してから戻した。
記録は `target/focused-checks/rta02-negative/` に置く。
追加のソケット付きの回帰は `activate` を保留し、そこで次の再起動と処理を要求する。
保留中の無音応答、親の保存要求、2 回の再起動通知、再開後の音声と終了を確かめる。
試験用プラグインはこの再現の時だけ、既存の 1 バイトの状態を保存できる。

実機の期限・第三者 CLAP の再起動と復帰時の聴感は自動回帰で判定しない。
確認待ちは [UC-76](../user-checks.md)、検査結果と見送りは `target/verification/report.md` を参照する。
