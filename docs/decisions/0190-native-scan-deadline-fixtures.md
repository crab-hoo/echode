# ADR 0190: 走査期限の回帰をネイティブ検査ヘルパーで再現する

- 日付: 2026-10-29
- 状態: 採用。製品の走査期限と対象は維持し、診断と回帰の実行条件を改善する
- 関連: [デバッグ手順](../debugging.md#オーディオトランスポートプラグイン)、
  [ADR 0189](0189-selected-track-mute-and-solo.md)、[検査手順](../verification.md)

## 発見と切分け

ミュート／ソロの一括操作の全体検査で、既存の `audit_rea08_descendant_pipe_does_not_extend_deadline` が再び失敗した。
最初の短い shell の JSON 出力が 2 秒を超え、子孫のパイプ保持ケースには進んでいなかった。
診断を追加した再現では、直接の子は `running`、標準出力・エラーはともに 0 byte、両パイプは開いたままだった。
検査が起動した子だけを `sample` で調べると、`/bin/sh` は大部分が `_dyld_start` にあり、出力前の起動段階にとどまっていた。
別の採取では dyld の同期通知も見えたが、OS 側の遅延の根因までは確定していない。

単独・並列・他のテストを除いた実行を比較した。単独の元の回帰が合格する場合もあったが、
子孫のケースに「JSON 出力済み・直接の子は終了済み」の検査を足すと、200 ms の間に起動しない shell だけで合格していたことも判明した。
`/bin/dash` への単純な差替えと並列数の削減では解消せず、これらを修正として残さない。

再現の一時ログと採取結果は `target/focused-checks/scan-state/`・`scan-observe/`・`scan-serial-diagnostic/` にある。
これはローカルの所在の記録であり、永続的な証拠の参照先ではない。過去の監査の証拠を更新後の合格へ書き換えない。

## 決定

- `echode-plugin-host` パッケージに `echode-scan-test-helper` を検査用バイナリとして追加する。
  `tests/support/scan_helper.rs` に置き、通常の Cargo ビルドと integration test の `CARGO_BIN_EXE_*` で同じ版を使う。
  `default-run` は既存の製品ヘルパーへ固定し、引数なしの実行先を変えない。アプリ・配布物にはこの検査ヘルパーを同梱しない。
- 検査用の同じ `--scan` 起動から、正常 JSON、80 KiB の標準エラー、パイプを保持する子孫、ハング、
  不正 UTF-8、終了コード、シグナルとエラー本文を生成する。shell・`dd`・`tr`・`sleep` の外部起動に依存させない。
  子孫は同じ検査バイナリで起動し、両パイプと走査のプロセスグループを引き継ぐ。
- 製品の `SCAN_BUDGET` は 5 秒のまま、成功ケースは 2 秒、子孫保持・ハングは 200 ms、外側の検査は 2 秒のままとする。
  子孫の保持では、期限切れに加えて JSON 全体の採取と直接の子の正常終了を要求する。
  起動しない子を止めただけでは、このケースの合格にしない。
- パイプ待ちの期限切れの診断には、子 PID、終了状態または `running`、各出力の採取 byte 数と開閉状態を残す。
  出力本文は追加せず、機密のあるプラグイン出力を広げない。期限後は既存どおりプロセスグループを停止・回収する。
- プラグインのロード・隔離・音声処理・ABI・保存形式は変えず、OS API の手宣言も追加しない。
  実プラグインの隔離回帰と既存の RT / sanitizer の範囲は維持する。

## 基盤の保守と受入

- 既存の `scan` integration test で全ケースを残し、ネイティブ fixture への変更後は、並列実行でも目的の子孫保持状態まで検査する。
- 同じテストを必須契約 `scan-deadline` に登録する。期限を 20 倍へ戻す反例と、標準エラーを排出しない反例が期待値で失敗することを確認する。
  Makefile の既存入口・検査登録・選択回帰・コードの所在とデバッグ手順を更新する。
- 検査ヘルパーは通常のビルド・clippy・ライセンス・配布物の限定したコピー先を共有する。依存クレートを増やさない。
  新しい製品ログ形式・保存先・外部サービスはなく、既存の `debug-report` が走査エラーを収集する。
- これは任意の高負荷でも起動が 200 ms 以内になる保証ではない。失敗時は出力前の起動遅延と、出力後のパイプ保持を新しい診断で区別する。
  実機・聴感・隔離の性能再計測はユーザー担当とし、自動の回帰と混同しない。
