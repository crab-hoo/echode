# 0051. トラックヘッダとタイムラインを一つの Metal フレームにする

- 日付: 2026-10-10
- 状態: 採用
- 関連: [ADR 0050](0050-arrange-viewport.md) の描画方式を変更する。表示領域の一元管理は維持する。

## 問題と検証

ADR 0050 で座標を共有しても、速いスクロール中に左右がずれるという報告があった。ヘッダはメインスレッドの AppKit の `draw`、タイムラインは専用スレッドの `CAMetalDisplayLink` で描いていた。`needsDisplay` と `CanvasRenderer.update` は異なる時計で処理され、カメラの値を同じにしても表示中のフレームはそろわない。前の単体検査が確認していたのは座標と入力の伝達であり、表示の同時性ではなかった。

Apple の [presentsWithTransaction の仕様](https://developer.apple.com/documentation/quartzcore/cametallayer/presentswithtransaction) でも、既定の Metal の表示が Core Animation の内容と同じフレームになる保証はない。現在のレンダラーは既定の非同期表示と `command.present` を使っていた。SDK の `CAMetalLayer.h` の説明も確認した。

ウィンドウを使わない再現検査で、Metal が前のフレームを保持している間にヘッダが 16 ポイント先へ進む更新順を再現した。これを実際の画面のずれの測定値とは扱わない。別々の描画経路で異なる版が表示されうることの再現である。

## 選択肢

AppKit と Metal を別々に保つこと自体は不可能ではない。同じ版のヘッダを準備し、Metal のコマンドをスケジュールしてから、`presentsWithTransaction` と明示的な Core Animation transaction で一緒に表示する方法がある。設定を一つ変えるだけでは足りず、Apple の指定する `waitUntilScheduled` と drawable の直接の `present`、ヘッダの版の管理が必要になる。メインスレッドへの調停を追加し、別のフレームを表示しないために両側を待ち合わせる構造になる。この方式の実装・性能計測は今回は行っていない。

製品は専用スレッドから描画し、メインスレッドが忙しくても継続する方針である。トラックヘッダもスクロールする編集画面の一部なので、一つの描画先へ統合する。別々の表示時刻の補正や、前後のフレームのカメラでネイティブなビューを動かす方式は採用しない。

## 決定

- `ArrangeView` の `CAMetalLayer` をアレンジ全体に広げる。ヘッダ、名前、選択、境界線、クリップ、ノート、グリッドは一つの command buffer と一つの drawable へ描き、一度だけ表示する。GPU が忙しくて更新を見送る場合も、両側が同じフレームに留まる。
- `ArrangeFrame` は一回取得した不変の入力と Rust の可視列から作る。ヘッダの ID・縦位置・高さは可視トラックの値をそのまま使う。タイムラインはヘッダの幅と 1 ポイントの仕切りだけ横へずらし、scissor でクリップをヘッダから切り離す。
- 名前は Core Text で整形・フォントの補完・末尾の省略を行い、文字の被覆を持つテクスチャとして同じフレームに描く。テクスチャは名前・幅・画面の倍率が変わった時に作り、可視の名前だけを保持する。一度 GPU へ渡したテクスチャは書き換えない。
- AppKit の `ArrangeHeaderView` と仕切りは透明な入力・アクセシビリティ領域にする。行の画素は描かない。行の高さ、スクロール、ズーム、選択の表示への移動は引き続き `ArrangePaneView` が管理する。仕切りも Metal で描き、入力用のビューはドラッグを受け取るだけにする。
- 将来の常時表示するフェーダー、ボタン、メーターも、行とともに動く画素は同じ描画フレームへ含める。入力・キーボード・アクセシビリティはネイティブの経路を残す。一時的な文字編集やポップアップを足す場合は、表示した版への配置を別途設計する。
- 不変の入力、描画スレッド、GPU 完了で返す 3 枠、静止中は再描画しないことは維持する。ピアノロールの描画内容は変えず、共通の矩形の描画器を使用する。

## 確認結果と限界

- `ArrangeTests` で部分行、スクロール、縦横のズーム、幅・高さ変更、選択への移動、Rust の可視列、文字の整形を検査した。240 回の入力を 5 回ごとにまとめて描き、古いフレームを保持しても、そのフレーム内の左右の ID・縦位置・高さは厳密に一致した。
- `make spike-arrange-frame` はウィンドウ・表示リンク・画面操作を使わず、製品と同じ `ArrangePainter` で GPU へ描いて画像を読み戻す。Apple M4、倍率 1 と 2、行の高さ 16・64・96、部分行、ヘッダ幅・全体幅の変更、選択の変更を含む 161 フレームで、50,758 走査線の不一致は 0。文字が実際に描かれた画素は 182,524。画面の手前から伸びる長いクリップがヘッダへはみ出さないことも確認した。結果は `target/spike-arrange-frame.json`、検査用の画像は同じ名前の PNG。
- `make spike-app` は縦にも表示領域を動かし、ヘッダを描いたフレーム数がタイムラインと等しいこと、共有フレームの行位置、双方のアクセシビリティも検査するように変更した。

この GPU 検査は、同じ描画画像内の左右の一致を確かめるものであり、画面への実際の表示時刻や入力から表示までの遅延を測るものではない。`spike-app` と `spike-draw` は computer use の明示許可がないため未実施。統合したフレーム全体の遅延がゼロになるという主張はしない。
