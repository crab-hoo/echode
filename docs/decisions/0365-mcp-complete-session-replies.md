# ADR 0365: MCP は検証済みセッションの完全な応答を待つ

- 日付: 2026-11-15
- 状態: 現行
- 領域: モデル・履歴・保存・API
- 関連: [DIA-01](../reviews/2026-11-13-detailed-implementation-audit.md#dia-01-mcp-が確定済みの編集を失敗として返す)、[ADR 0115](0115-phase2-mcp.md)、[ADR 0073](0073-socket-path.md)

## 問題と根拠

MCP は要求の 1 MiB 制限を接続先の応答にも適用し、編集の完了にも 30 秒の読取り期限を設けていた。
トランザクションの応答には生成した ID が加わるため、上限内の要求でも、確定後に結果不明として返る。
200 件の長い名前のトラック追加を製品の stdio → Unix ソケット → DocumentHost へ通し、修正前の失敗を再確認した。
Undo は 1 段になったが、MCP は `isError: true` と `MCP message exceeds the single-message size limit` を返した。
実ソケットの設定を検査する回帰も、版確認後の読取り期限が `Some(30s)` のままで失敗した。
計測や 30 秒の sleep ではなく、処理の待ちに固定期限が残らないことを通常テストで検証する。

## 比較と決定

1. 応答の上限・期限を引き上げる: 境目を移すだけで、大きい文書や遅い編集の確定後に同じ誤報が残る。
2. 進捗通知・非同期タスク・ページ分割を足す: 別の公開プロトコルと状態管理が必要で、今回の完了応答の修正には過大である。
3. 同じ uid の API セッションから完全な応答を読み、版確認後は読取り期限を外す: 既存の確定・単一応答の契約をそのまま守れる。

3 を採る。MCP の stdio 入力と API へ送る要求は、改行込み 1 MiB のままとする。
API の応答にはその上限を掛けず、同じ改行検証を使う。
接続先の uid・API 版 1 を確認してから読取り期限を外し、編集だけでなく概要・リソース・Undo / Redo も最後まで待つ。
版確認と要求書込みの無進行期限は 30 秒のままとする。
接続ごとの設定変更を `connect_session` に集約し、呼出しごとの新しい接続と再送禁止を保つ。
API サーバー側の要求読取り・応答書込みの無進行期限は変えない。

接続先が生きたまま応答しなければ、その MCP 呼出しと後続の stdio 要求は待ち続ける。
応答全体はメモリへ読み、同じ利用者のセッションからの巨大な応答に対する資源上限は設けない。
切断・部分行・不正な JSON や応答外枠は従来どおり結果不明として案内し、確定した編集を再送・巻戻ししない。
取消・外部 MCP クライアントの期限・非同期タスクの追加は行わない。

## 回帰と基盤

- 監査の `audit_dia01_a_committed_transaction_with_a_long_reply_is_reported_as_done` を通常回帰へ移す。
- `mcp_completion.rs` は旧・新 MCP で、大きい確定応答・単一 Undo / Redo・大きい概要と両リソース・読取り時の履歴不変・再オープンを検査する。
- `mcp_tests.rs` は実ソケットの版確認後に読取り期限がなく、書込み期限が残ることを検査する。
- 要求の上限と改行、版応答・編集応答の部分行、切断・不正応答の結果不明と再送禁止は既存の通常回帰を維持する。

応答サイズと期限設定の回帰を既存の必須契約へ登録し、元の制限を戻す反例を定義する。
新しい検査コマンドはなく、Makefile の既存の `check-product-contracts` が登録簿から実行する。
選択・依存入力のテストも登録を照合する。
設計書・制約・開発／デバッグ手順・監査と索引を更新し、診断の収集先と形式は変えない。
外部入力の入口・パーサーは増やさず、fuzz の対象追加は行わない。
音声・隔離・画面の挙動は変えず、新しい実機確認待ちは作らない。
