# ADR 0330: 再生中の編集の素材も別スレッドで読み、テンポの変わった計画は採用時に拍を保つ

日付: 2026-11-12
状態: 採用。実機の操作感と聴感はユーザー確認待ち（UC-67）
関連: [ADR 0147](0147-output-prewarm-and-background-media.md)、[ADR 0142](0142-background-plugin-graph-preparation.md)、[ADR 0136](0136-output-opening-off-worker.md)、[ADR 0155](0155-remembered-playback-start.md)、[ADR 0275](0275-shared-integer-tempo-index.md)、[ADR 0278](0278-audit-backlog-order.md)、[ADR 0329](0329-plugin-states-by-name.md)

## 問題と再現

開始時の HEAD は `7a229c2`。ADR 0278 の 4 に従い、P2-02 の応答性の残り（[進め方](../phase2.md)）のうち「再生中の編集の素材」を扱った。

ADR 0147 は停止中の置換だけ素材を `echode-media-prepare` で読み、再生中は Session の `update`（文書ワーカー）で同期に読んでいた。
テンポの変更の後に Session が送る位置移動（新しいテンポで求めたサンプルへの `Locate`）を、新しい計画より後に効かせるためである。
再生中に同期で読んでいた編集は次のとおり。

- 別の音声ファイルの配置（ブラウザからのドロップ）。
- 素材全体を共有しない配置のトリム。短いトリムは素材全体を解放するので（M27-03）、窓が変わると全体を読み直す。
- テンポの変更。全ての窓の位置と長さが変わり、共有しない素材を全て読み直す。

製品の読込み関数と同じ `load_placed_clips` の 1 回を release で測った（Apple M4、macOS 27.0、180 秒のステレオ、ページキャッシュに載った後）。

| 素材 → 出力 | 1 回 |
|---|---|
| 44.1 kHz → 48 kHz（SRC あり） | 400〜428 ms |
| 48 kHz → 48 kHz | 130〜147 ms |

この間、文書ワーカーは停止・Undo・後続の編集を処理しない。テンポの変更は、共有しない素材の数だけ掛かる。

位置の扱いにも二つの食い違いがあった。

- テンポの変更の位置移動は、読込みの前に読んだ tick へ戻る。読込みの時間だけ拍が戻っていた。
- プラグインのある曲では、置換の計画は準備スレッド（ADR 0142）から後で届く。新しいテンポのサンプルへの `Locate` が古い計画に先に効き、計画が届くまで別の拍を鳴らしていた。
  停止中も、適用の後から計画の採用までの表示の tick が古いテンポで読んだ値になっていた。

## 比べた案

1. **再生中はテンポの変更だけ同期のまま。** 変更は小さいが、テンポの変更は止まり続ける。
   読込みの途中に来たテンポの変更は既存の読込みへ集約されるので、`Locate` が古い計画に先に効く食い違いは残る。採らない。
2. **位置移動を計画の番号に結び付け、その計画の採用まで保留する（`ClearFaderPreview` の `after_plan` と同じ形）。**
   停止は待たせられるが、停止して開始位置へ戻る `Rewind` を停止と位置に分ける必要がある。読込み中の位置移動は読込みが終わるまで効かない。採らない。
3. **位置を、鳴っている計画のテンポで解釈する。** テンポの変わった計画は採用時にクロックの tick を保ち、Session の位置移動は tick で送ってコールバックが変換する。
   計画と命令がどの順で届いても、位置はその時に鳴っている計画のテンポで決まる。一つの規則で二つの食い違いが消える。採る。

## 決定

- 製品の出力（`OutputStream::assemble`）は、初回の計画の後の全ての置換で、新しい素材を別スレッドで読む。再生中も停止中も同じである。
  読込みの間は置き換えられる計画が鳴り続け、読込み中の編集・ループの変更は同じ読込みへ集約する（ADR 0147）。
  初回の準備、オフラインの書出し、CLI は従来どおり呼出し側で読む（`load_media_in_background` の既定は偽）。
- 制御側は、最後にコールバックへ渡した計画のテンポ（`published_tempo`）を持つ。渡す計画のテンポが違えば `Update.retime` を真にする。
  保留中に置き換わった計画とではなく、渡した計画と比べるので、集約された編集でもテンポの変化を落とさない。比べるのは制御側で、コールバックはテンポの点の数に比例する比較をしない。
- コールバックは `retime` の計画を採用する時、旧計画のテンポでクロックのサンプルを tick にし、新しい計画のテンポでサンプルへ戻す。
  サンプルが変われば `Locate` と同じ処理（位置の置き直しとプラグインの初期化）をする。変換は境界の二分探索で O(log T)、確保をしない。
- `PlaybackCommand::LocateTick` と `RewindTick` を加えた。tick を、コールバックがその命令を取る時に鳴らしている計画のテンポで変換し、サンプルの `Locate`・`Rewind` と同じ関数（`PlaybackAudio::locate`・`rewind`）へ渡す。
  `OutputStream::locate`・`rewind` はこれを送る。範囲の検査と、適用までに表示するサンプルは、従来どおり Session の文書で求める。
  サンプルの命令は、サンプル単位で位置を決めるオフラインの書出しと検査のために残す。
- Session の `update` は、テンポの変更の後の位置移動をやめた。ループの範囲はサンプルで計画に載るので、従来どおり送り直す。
- 導入（ADR 0136）の時に、準備中の編集の素材が読込み中で、再生するなら待つ。準備で入れた再生は一時停止し、`resume_held` で読込みの後に再開する。
  再生ボタンの保留（ADR 0147）と同じ扱いで、置き換えられる計画を鳴らさない。

## 検査

- 必須契約 `playing-edit-media`（`session_tests.rs`）: 製品のコールバックで、次を確かめる。
  - 再生中のクリップゲインの変更が、読込みの保留中に戻る。旧計画（約 0.18）が鳴り続け、解放の後に約 0.09 になる。
  - テンポを半分にする編集の保留中に 4 拍目へ移動すると、鳴っている計画でその拍に着く。採用の後も拍が続く。
  - 負の対照は 3 つ。出力の背景読込みを外すと、読込みが検査スレッドを塞ぐ。`retime` を偽にすると、採用で拍が半分へ跳ぶ。位置をサンプルで送ると、旧計画で 8 拍目へ着く。3 つとも失敗を確かめた。
- 必須契約 `output-install-held-play`: 再生中に準備した出力の導入で、準備中の編集の素材の保留中は鳴らさず、解放の後に新しいゲインで始まる。負の対照は保留をやめる（旧計画の 0.18 が鳴る）。
- 単体の回帰（`playback_command_tests.rs`）: テンポの採用で 6,400 サンプル目の拍が 12,864 サンプル目へ移り、同じテンポの計画ではクロックが動かない。
  `LocateTick`・`RewindTick` は、テンポの変更の前後で、それぞれの計画のテンポで着く。どちらも `retime` を外すと失敗した。
- `output-prewarm` の負の対照は、Session の行がなくなったので、出力の背景読込みの行へ移した。
- 音を作る処理は変えない。位置の置き直しは従来の `Locate` と同じ関数で、ブロック長の比較は既存の回帰を維持する。
  `retime` の採用のブロックは制御側の公開の時刻で決まり、ブロック長を変えて比べる対象ではない。
- `make spike-plugin-tracks`（release、機器なし）: 計画を採用するブロック（`plugin-edits`）の CPU はトラックあたり p50 4.1〜4.5 µs で、16〜256 トラックで増えない。
  256 トラックの最大は 1.31 ms、取りこぼしは 0。テンポの変わらない計画では、採用の追加の処理は真偽値 1 つの確認だけである。

## 影響と残り

- 再生中の停止・Undo・後続の編集は、素材の読込みを待たない。編集が鳴るまでの遅れは従来と同じく読込みの時間で、その間は前の計画が鳴る。
- テンポの変更は、読込みの間は旧テンポで鳴り、採用の時に同じ拍から新しいテンポで続く。読込みの時間の分だけ拍が戻ることはなくなった。
  採用の時に位置を置き直すので、鳴っているノートは従来のテンポの変更と同じく打ち直される。
- 計画の生成（`Prepared::new`）と、導入時の差分で増えたヘルパーの起動は、文書ワーカーに残る（ADR 0142）。
- 外部の音声の取込み（復号と保管庫への段階の書込み、ADR 0272）は編集の一部として文書ワーカーで行う。ドロップは取込みの分だけワーカーを待たせる。
- 実機での操作感と聴感（テンポの変更の拍の続き方、ドロップ・トリムが鳴るまでの遅れ）はユーザー確認待ち（UC-67）。
