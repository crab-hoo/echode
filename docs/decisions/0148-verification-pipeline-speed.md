# 0148. 検査の範囲と合否を変えずに `make verify` を速くする

- 日付: 2026-10-22
- 状態: 採用
- 対象: `scripts/verify.py`、`scripts/check_product_contracts.py`、`scripts/verification.json`、`check-shell`、`check-bridge`
- 後続: [ADR 0197](0197-verification-target-scopes.md) がプラグイン依存・Cargo の入力範囲・段階ごとの再利用・フック予算を改定した。
  本文の旧計測と当時の識別方式は、過去の判断の証拠として残す。

## 背景

検査基盤の監査は、1 回の `make verify` が約 2,134 秒（約 35.6 分）かかるとして作り直しを求めた。
内訳は `check-product-contracts` 約 1,085 秒（通常の実行 236.8 秒、負の対照 約 848 秒）、`check` 397.4 秒、`check-bridge-asan` 約 356 秒などだった。
監査が挙げた原因は次の 5 つである。

1. Swift の負の対照は毎回新しい一時コピーで冷えたビルドから始まり、以後も 1 件ずつ再コンパイルとリンクをしていた。
2. Rust の負の対照は元に戻すたびに更新時刻が進み、次の契約が前の契約のクレートも作り直していた。
3. 同じテストを複数回実行していた（契約の通常実行と `check-base`、`swift test` の後の `swift build`、feature の切替による再ビルド）。
4. 失効が広すぎた（契約の識別値が 1 つ、`scripts/**` と Makefile の変更で全自動検査、Makefile のコメントで全識別値が失効）。
5. `verify.py` が検査ごとにツールの識別と全ファイルのハッシュを再計算していた。

調査中に、旧方式の負の対照に隔離の欠陥も見つかった。
毎回の一時コピーは `copy2` で元の更新時刻を写していたため、前回最後の反例で作ったクレートを Cargo が最新と誤認する。
2 クレートのワークスペースで再現した。反例を入れて戻した後、`copy2` の新しいコピーでは元のソースのテストが前回の反例のビルドで失敗した。
手順と出力は `target/verification/mutation-mtime-repro.log` に残す。
旧順序では `phase1-acceptance` が最後に `echode-cli` を変えるため、次回の CLI の契約の反例はその変更を含んだまま動いていた。

## 決定

### 負の対照の作業コピーを保つ

`target/product-contract-mutations/checkouts/<N>` に持続コピーを置き、`<N>.json` に置いたファイルの一覧を残す。
同期は内容が変わったファイルだけを書き換え、削除されたファイルを消す。
書き換えと反例の復元は新しい更新時刻で行い、`copy2` で古い時刻を写さない。
これで Cargo と SwiftPM は、前の反例のビルドを現在のソースのビルドと取り違えない。
一覧が読めない時は `target/` 以外を作り直し、未知のファイルを SwiftPM がコンパイルしないようにする。
Swift の scratch もコピーの中に残すため、毎回の冷えたビルド（約 20〜50 秒）が初回だけになる。
Rust の反例のビルドは `target/product-contract-mutations/cargo` に置き、旧方式の `rust` とは共有しない。
この順序の前提は、同じビルド先へ他の書き手が古い時刻で書かないことである。

### 反例の順序と並列化

Rust の反例は、変えるファイルを持つクレートの依存の浅い順にまとめ、同じクレート内では対象パッケージ順に並べる。
戻したクレートの作り直しは群の切替ごとに 1 回になり、最後の群は下流のクレートだけを古いまま残す。
Swift の反例は 3 つのコピーで同時にビルドし、全ビルドの終了後にテストを 1 件ずつ `--skip-build` で実行する。
テストの実行中は他のビルドもテストも動かさない。
反例は常に 1 コピー 1 件で、複数の反例を同じビルドに入れない。

### 契約ごとの識別値と再利用

`scripts/verification.json` の `product_contract_inputs` に、全契約共通・Rust・Swift の入力を宣言する。
各契約の識別値は、その入力（Rust は対象パッケージのローカル依存、Swift は Swift パッケージと `echode-ffi`）、契約の定義、レシピ、ツールから作る。
反例のファイルが契約の入力の外にある定義は拒否する。各契約の入力は `check-product-contracts` 自身の入力の部分集合であることを単体検査で確かめる。
同じ識別値でテストと反例の両方が合格した記録だけを再利用し、`product-contracts.json` に `reused: true` と記す。
結果は 1 件ごとに保存し、中断しても完了した証拠は残る。
複数の反例を持つ契約では全反例の完了時に記録し、1 件でも未完了なら契約の合格として再利用しない。
Swift も最後の群を待たず、各契約の全反例が終わった時点で直ちに保存する。
2026-10-28 の ADV-04 検査で、旧実装は Swift の全契約終了まで保存せず、時間切れのたびに完了分も再実行すると判明した。
中断を模した単体回帰で、完了した契約だけが残り、途中までの複数反例は再利用されず、ソースが復元されることを確認する。
終了時に識別値を計算し直し、実行中に入力が変わった契約は `stale` として識別値を消し、再利用しない。
`verify.py --force` は `ECHODE_VERIFY_FORCE=1` を渡し、契約ごとの再利用も行わない。

### 通常の実行

Rust の契約は従来どおり 1 契約 1 プロセスの `cargo test -p` で実行する。
Swift は `swift build --build-tests` を 1 回行い、各契約を別プロセスの `swift test --skip-build --filter` で実行する。
合否の判定（実テスト 1 件の成功、無視・0 件・既知の問題の拒否）と各契約の期限は変えない。
`check-shell.sh` も `swift build --build-tests` の後に `swift test --skip-build` を実行し、別の `swift build` を除く。
`spike-bridge.sh` の非同期コールバックの版は `target/bridge/async-callback` で作り、通常の版を上書き・再ビルドしない。

### 選択と識別の範囲

Makefile はファイル全体ではなく、各検査のレシピ（前提と `$(MAKE)` で呼ぶ対象を含む）と、変数などの全体に効く行だけを識別に含める。
コメントと空行は含めない。`.PHONY` は検査が使う対象の分だけを含める。
`scripts/verification.json` と Makefile の変更は、差分の基準と比べて定義・レシピが変わった自動検査だけを選ぶ。
基準を読めない時は従来どおり全自動検査を選ぶ。`make doctor` と `make agent-context` も同じ選択を使う。
`infrastructure` は選択・記録・フック・CI の実装（`verify.py`、フックとその補助、CI）に絞り、`evidence_inputs` の変更は全自動検査を選ぶ。
自動検査は自身の `inputs` に一致する変更でも選ばれる。補助スクリプトの変更は、それを実行する検査を選ぶ。
`check` の入力は `scripts/**` から実行する補助スクリプトの一覧へ、橋渡しの ASan / TSan は `scripts/check*bridge*` から実行する 3 本へ絞る。
宣言漏れは、レシピから `$(MAKE)` をたどって補助スクリプトを探す単体検査が止める。

### `verify.py` の再計算

計測では、ツールの識別が約 0.2 秒、全体の識別値が約 0.03 秒、検査ごとの識別値が約 0.12 秒で、1 回の検証で数秒だった。
ファイルの内容ハッシュだけを、inode・サイズ・更新時刻・ctime・モードが同じ間に限り同じプロセス内で再利用する。
書込みは ctime を進めるため、検査中の編集は引き続き検出する。ツールの確認は各検査の後に残す。
GNU make の jobserver の引数は実行ごとに変わるため、ツールの識別から除く（`-j` の値は残す）。

## 見送ったもの

- `check-base` の結果を契約の通常実行に流用しない。
  `cargo test --workspace` は `echode-ffi` の開発用依存により `echode-audio-io/headless-output` を有効にし、`-p` と構成が違う。
  Swift は約 25 秒の短縮のために、別の検査の証拠を結び付けない。
- 契約のテストを 1 プロセスにまとめない。1 契約 1 プロセスの隔離と各期限を保つ。
- 検査同士を並列に実行しない。2026-10-22 に並列負荷で Sine Pad のヘルパーの期限切れが起きた。
  負荷による失敗は、反例の検出とも区別できない。
- ASan / TSan での EchodeApp 全件は計装の違う別の証拠であり、重複として削らない。
- 橋渡しの ASan / TSan / Miri の識別範囲（`echode-ffi` のローカル依存の閉包）は狭めない。
  そのコードは検査するバイナリにリンクされる。依存先の開発用依存を外しても、このワークスペースでは閉包は縮まない。
- TSan の `fault-injection` と `sanitizer-control` の切替は、定常状態では再ビルドしなかったため変えない。

## 計測

同じ M4（10 コア）で 2026-10-22 に計測した。監査時の全体は他の作業の負荷とソース変更直後の再ビルドを含み、同じ条件は再現できない。
そのため、同じ機械・同じソースで旧方式と新方式を比べた値を併記する。

| 条件 | 旧方式 | 新方式 |
|---|---|---|
| 監査時の `make verify`（変更直後・負荷あり） | 2,134 秒 | — |
| 変更後最初の `make verify`（全自動検査が失効、反例の Cargo は冷えた状態） | — | 676 秒 |
| 全件強制の `make verify`（ソース変更なし） | 約 698 秒（各部の計測値の和） | 544 秒 |
| `check-product-contracts` 全件強制 | 463 秒 | 314〜340 秒 |
| 契約の入力が変わらない時の `check-product-contracts` | 463 秒（識別値が 1 つ） | 1.1 秒 |
| Swift だけが変わった時の契約の実行（部分の計測値） | 463 秒 | 約 190 秒 |

`check-product-contracts` の内訳（全件強制、旧→新）は次のとおり。
通常の実行は Rust 14.6→15.7 秒、Swift 43.1→38.3 秒（ビルド 1 回を含む）。
反例は Rust 173.7→131.5 秒、Swift 220.2→約 150 秒（38 件、3 件同時ビルド）。
監査時の反例は、Swift の初回の冷えたビルドが 50.8 秒、以後 1 件約 10 秒、Rust の最大が 52.2 秒だった。
`spike-bridge.sh` は 11.1→4.8 秒になった（非同期版の作り直しと戻しの約 6 秒がなくなった）。
旧方式の全件強制の内訳は、`check-verification` 29.8 秒、`check` 約 115 秒、契約 463.2 秒、ASan 33.7 秒、TSan 33.8 秒、Miri 14.4 秒、その他約 8 秒である。
このうち `check` だけは、新方式の 107.9 秒に除いた再ビルド約 7 秒を足した推定値で、他は旧方式で計測した。

選択の変化（自動検査 10 件のうち選ばれる数）は次のとおり。
Makefile のコメントだけの編集は、旧 10 件・全識別値の失効から、新 3 件（常時の検査）になり `check-verification` だけが再実行する。
契約の追加は、旧 10 件から新 3 件になり、`check-product-contracts` は追加した契約だけを実行する。
`scripts/check-bridge-address.sh` は旧 10 件から新 5 件、`scripts/diagnose.py` は旧 10 件から新 3 件（`check` は再利用）になる。
持続コピーは 3 つで約 1.8 GB、反例の Cargo は約 3.8 GB、非同期版は約 0.4 GB を使う。旧方式の一時コピーは毎回約 0.6 GB を作って消していた。

## 確認

`scripts/tests/test_product_contracts.py` は、持続コピーの同期（変わらないファイルの時刻を保ち、古い時刻の編集も新しい時刻で書く、削除・中断・一覧の破損）を確かめる。
同じファイルで、復元が反例のビルドより新しいこと、Rust の反例の順序、Swift の同時ビルドと 1 件ずつのテスト、コンパイル失敗を検出に数えないことも確かめる。
契約ごとの識別値が自身の入力だけで変わること、再利用に両方の合格と同じ識別値が要ること、`--force` で全件を再実行することも確かめる。
実行中の編集で記録が `stale` になり、再利用されないことも確かめる。
`scripts/tests/test_verification.py` は、Makefile のコメントで失効しないこと、レシピ・契約・検査定義の変更が該当する検査だけを選ぶことを確かめる。
補助スクリプトによる選択、内容ハッシュの再利用条件、`--force` が外側から受け継いだ値に左右されないことも確かめる。
