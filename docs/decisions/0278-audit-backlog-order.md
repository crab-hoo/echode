# 0278. 監査の残りの順番と、FCA-05 の区切り

- 日付: 2026-11-08
- 状態: 採用
- 関連: [ADR 0276](0276-priority-order-and-delegated-decisions.md)、[監査の未完了項目の統合](../reviews/2026-11-08-open-items-register.md)、
  [FCA-05](../reviews/2026-11-03-full-code-audit.md#fca-05-モデルの線形探索と-2-乗の経路)、[Phase 2 の進め方](../phase2.md)
- 置き換え: [10/8 初期監査の優先度](../reviews/2026-10-08-audit.md#優先度) の P2「Phase 2 に入るまでに決めるか、直す」の時期。
  統合表で「機能に付随」とした項目に限る。

## 背景

監査の記録が 5 系統に分かれ、同じ問題に複数の番号があり、状態の欄が後の ADR を反映していなかった。
2026-11-08 に [統合表](../reviews/2026-11-08-open-items-register.md) で束ねると、残りは 38 行だった。
内訳は堅牢性 7（R1〜R7）、保守性 10（M1〜M10）、効率 5（E1〜E5）、機能に付随 13（F1〜F13）、ユーザーの担当 3（U1〜U3）である。

FCA-05 は 11/7〜11/8 に 13 回の先行対応を重ねた（監査の追記）。
これを続けるか、構造・品質へ移るか、Phase 2 の機能へ戻るかを決める必要があった。

## 比べた案

| 案 | 内容 | 判定 |
|---|---|---|
| 1 | FCA-05 を完了まで続ける | 採らない。効率の段で、上の段の残りより後になる。続ける根拠の測定もない |
| 2 | Phase 2 へすぐ戻り、監査の残りは触る時に直す | 採らない。機能を足すほど M 群が増え、保守性を下げる |
| 3 | 保守性（構造・品質）を先に行う | 採らない。R 群の音切れの危険を後に回す |
| 4 | 堅牢性の残り、保守性の P2 の順に行い、その後 Phase 2 へ戻る | 採る |

- 案 1: 128 トラック × 64 クリップで、ノートの編集 1 回は 1.08 ms、トラックの追加は 0.26 ms である（`make spike-scale`、2026-11-08）。
  60 Hz の 1 フレーム（16.7 ms）に十分収まり、GUI の停止の兆候はない。
- 案 2: `Result<_, String>` は 10/30 の 141 関数から 156 か所へ増え、11/2 の後に作った `echode-document` にも 16 か所ある。
  機能と同じ速さで直す量が増える。
- 案 3: R1 は測定で予算を超えている（256 トラック × 4,000 ノート、48 kHz・128 フレームで採用の最大 3.70 ms、予算 2.67 ms）。

## 決定

### FCA-05 を区切る

- FCA-05 は今の到達点で区切る。128 × 64 の値は、11/3 の監査時から次のとおり変わった。
  読込みの検証 167 → 13.4 ms、ノートの編集 36.0 → 1.08 ms、トラックの追加 1.03 → 0.26 ms。
- 残る線形の探索（統合表の E1）は効率の段に置く。次のどれかに当たった時に再開する。
  - `spike-scale` の `model_edit` の 1 回の操作が 16.7 ms を超えた時。GUI の停止として堅牢性に数える。
  - 所有関係を足す機能（F11）で、ID の索引が要ると分かった時。

### 順番

1. 堅牢性の R1〜R7 を番号順に行う。R1 は内訳（冷えた作業領域・計画の複写・声の表の初期化）を測ってから直す。
2. E2（Swift の主スレッドの負荷）を計測する。GUI の停止に当たる値なら、堅牢性として続けて直す。
3. 保守性の M3・M1・M2・M4・M5・M6・M8・M9 を、この順に行う。
   - M3（fuzz とカバレッジ）を先にする。外部の入力の欠陥を見つける手段で、見つかった欠陥は堅牢性の段へ戻る。
   - M1・M2 は crate の境界ごとに進め、境界ごとにコミットする。`echode-audio-io` から始める（M1 の最多で、時間切れの区別が要る）。
4. 上を終えたら Phase 2 へ戻り、[進め方](../phase2.md) の順に進める。
5. M7 と E3・E4 は、そのファイルに触る作業で行う（10/8 の P3 と同じ扱い）。M10 は ADR 0232 の理由のまま残す。E5 は測定値ができるまで採らない。
6. 機能に付随する F1〜F13 は、それぞれの単位の受入条件に含め、単位の着手時に決める。F11〜F13 は、その機能に着手する前に終える。
7. ユーザーの担当の U1〜U3 は進めない。

### 10/8 の P2 の時期

10/8 の P2 のうち統合表の F 群（MOD-7・MOD-14・ENG-8・PLG-7・UI-4・HIS-7）は、Phase 2 の開始前ではなく、各単位の着手時に決める。
Phase 2 は既に始まっており、機能の形が決まる前に意味を決めると作り直しになり得る（例: 拍子の格子は P2-07 のマーカーの形に依る）。
単位の割当がない ENG-8・HIS-7 は、関係する機能（長い素材の再生、プロジェクトの保管場所）に着手する時に決める。

## 理由

- [ADR 0276](0276-priority-order-and-delegated-decisions.md) の順（堅牢性 > 保守性 > 効率 > 機能）に従う。
- R 群は、音切れ（R1・R3）、次のプラグインと再生装置の保護（R2）、panic による無音（R4）、遅いプラグインの誤判定（R5）、
  長時間の作業のメモリ（R6）、記述子の漏れ（R7）であり、どれも堅牢性に当たる。
- 保守性の P2 を機能より先にするのは、機能を足すたびに直す量が増えるからである（案 2）。P3 は触る時に直す従来の扱いで足りる。
- 効率の残りは、どれも測った必要がない。測って必要が出た時に、上の再開の条件で戻る。

## 影響

- 統合表で更新した状態は、元の監査の表にも書いた。各項目の詳細と状態は、引き続き元の監査が正本である。
- 次の作業は R1 である。
- [現在の制約](../status.md) の利用者への制約は変わらない。製品のコードと検査の選択は変えていない。
