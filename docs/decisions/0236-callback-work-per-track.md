# ADR 0236: コールバックでトラックごとに全体を走査しない

- 日付: 2026-11-03
- 状態: 採用
- 関連: [ADR 0035](0035-playback-plan.md)、[ADR 0102](0102-exclusive-audio-graph.md)、[横断監査](../reviews/2026-11-02-cross-cutting-audit.md)の XCA-13

## 背景

開始時の HEAD は `2ecc601`。

XCA-13 は読解から、オーディオスレッドの 2 乗の処理を 3 つ挙げた。
`plugins.rs` の `submit`・`apply` のトラックの線形探索、`collect` の起床ごとの全トラックの走査、`playback.rs` のトラックごとの全イベントの走査である。
測定はなかった。
AGENTS は、オーディオスレッドでプロジェクト全体の大きさに比例する処理を禁じ、トラック数の上限も禁じている。

## 測定の方法

`make spike-plugin-tracks`（`crates/echode-plugin-host/tests/track_scale.rs`）を足した。機器は開かない。
release、48 kHz、128 フレーム（1 ブロック 2.67 ms）で、200 ブロックの予熱の後に 2,000 ブロックを測る。

- プラグイン: トラックごとに `dev.echode.test-gain` を 1 つ、別プロセスのヘルパーで動かす。ノートはない。
- 和音: プラグインを挿さず、各トラックの拍ごとに 4 音を置く。拍の頭のブロックには、トラックあたり 4 つのノートオンが入る。

主な値は、コールバックのスレッドの CPU 時間（`CLOCK_THREAD_CPUTIME_ID`）である。ヘルパーを待って眠る時間は含まない。
期限は 1 秒にして、遅いヘルパーの分も処理に含めた。製品の期限なら、遅いヘルパーは無音になる。
トラックあたりの CPU 時間が数とともに増えれば、2 乗の処理が残っている。

## 改善前

改善前は、この作業の `playback.rs`・`plugins.rs` だけを `2ecc601` の版へ戻したものである。
値は µs、`/トラック` は CPU の p50 をトラック数で割った ns、`記述子` はその再生のために親が開いた数である。

投入はトラックあたり約 3.2 µs かかり、トラックの順に進む。回収を始める時には、ほとんどのヘルパーが終わっている。
このため、`collect` の起床ごとの全走査は 2 乗の形では現れなかった。
投入と書戻しのトラックあたりの値は、64 から 256 トラックで 1 割ほど増えた。線形探索はその一部である（改善後を参照）。

## 決定

- `Prepared` は、ブロックのイベントをトラックの位置ごとに 1 回で振り分ける（`group_events`）。
  数える 1 巡と置く 1 巡で、各トラックのイベントはブロックの順を保つ。トラックの位置は既存の `track_indices` を二分探索で引く。
  作業領域（トラック数 + 1 の終端の列）は計画の構築時に確保する。`flush_releases` も同じ振り分けを使う。
- 計画の差替えで追いかけるノートオン（`chased_ons`）も同じく振り分け、`HostGraph::submit` にはそのトラックの分だけを渡す。
  以前は各トラックが全トラックの追いかけを走査しており、再生中の編集の直後のブロックが 2 乗になっていた。
- `HostGraph` のトラックの列を `HostTracks` にし、キーの索引を列と一緒に持たせる。
  列を置き換え・短くする操作は `HostTracks` の関数だけにし、`Vec` の操作を直接は呼べないようにした。索引の更新漏れはコンパイルで止まる。
  `submit`・`apply` と停止の後始末（`queue_cleanup`）は、この索引で引く。後始末は、イベントを 1 巡するだけになった。
- `collect` は変えない。測定で 2 乗が現れず、完了の順に処理するには、ヘルパーとの共有メモリに完了の待ち行列が要る。
  投入が速くなって回収の走査が増えた時に、計測の内訳を見て判断する。

## 検査

- `playback_tests.rs` の `grouped_events_keep_each_tracks_order_and_leave_out_the_rest` は、疎なキー・ミキサーの順と違うキーの順・トランスポートと未知のキーの除外を確かめる。
  `grouping_events_into_too_little_room_fails_instead_of_dropping_any` は、作業領域が足りない時に黙って落とさないことを確かめる。
- 必須契約 `track-event-routing`（`hosted_playback/track_events.rs`）は、音数の違う 3 トラックの数える音源をトラックごとのメーターで読む。
  ブロックのノートオン、停止のノートオフ、再生中の位置移動の後始末、鳴っている間に足したヘルパーへの追いかけを確かめる。
  反例は 4 つで、それぞれの振り分けを先頭のトラックへ渡すように変える。どれも、そのトラックの数の違いで失敗する。
- この契約の前は、トラックごとの配送を固定する回帰がなかった。全トラックへ先頭のトラックのイベントを渡す変更で、エンジンと `hosted_playback` の全件が通った。
  既存の複数トラックの試験は、どのトラックも同じノートを鳴らしていた。
- 再生中の位置移動の後始末は、ライブのコールバックが 1 回だけ確かめて待たない。試験は実時間より速く回すので、後始末の終了を実時間で待つ（上限 5 秒）。
- `spike-plugin-tracks` は手動の計測で、`isolation` の領域の変更で候補になる。時間の合否はない。

## 残る範囲

- 親は、ヘルパー 1 つにつき記述子を 4 つ持つ（上の表で 256 トラックが 1,025、1 トラックが 5）。
  launchd の既定の上限 256 では数十のプラグインで起動に失敗したので、[ADR 0237](0237-helper-descriptor-limit.md) で上限を上げた。
- 投入はトラックあたり約 3 µs で、トラックの順に進む。128 フレームでは、約 800 のプラグイン付きトラックで投入だけが 1 ブロックを使い切る。
  比例する費用であり、この ADR の範囲外である。内訳はまだ測っていない。
- `collect` を完了の順に処理すること。
- 計測は Workgroup を渡さない通常の優先度である。実機の期限と聴感は扱わない。
