# 0094: エージェントの作業資料と診断を整理する

- 日付: 2026-10-15
- 状態: 採用

## 理由

資料に過去の「未実施」と現在の対応が混在し、設計にある機能を実装済みと読めた。AGENTS の実機検査の理由要求と、実行器の理由なし完了も食い違っていた。検査に合格しても、画面が古いアプリである可能性を調べる共通の入口がなかった。

## 判断

AGENTS を必須規則に絞り、docs/README を索引にする。現在の制約、開発、検査、デバッグを分け、過去の監査は当時の証拠を保持する。通常検査で主要な作業資料のローカルリンクと実行コマンドを確認する。

選択された手動検査は自動で起動せず、実行か理由付き見送りを完了条件にする。ソースとツールが変われば見送りも失効する。自動検査の失敗は見送れない。通常の make check は基本検査と必須契約を含むが、実行器は make_target で基本部分だけを呼び、必須契約を別に記録して二重実行を避ける。対応条件は verification.json 以外へ追加しない。

doctor はソース・ツール・検査の有効期限と排他ロックを読み取り、開発用アプリの本体とヘルパーのハッシュ・ソース記録を照合する。ビルドの前後でソースを照合し、変更中の記録を作らない。debug-report は診断と既存ログを一意のローカルフォルダへ収集する。検査の生の環境設定とユーザープロジェクトは含めず、各ログは最大2 MiBの末尾と切り詰め情報を持つ。

検査中の確認で、Make が環境へ渡す VERIFY_ARGS まで識別に含まれ、後の通常実行や doctor が同じソースを古い結果と判定する問題も見つけた。Make の引数のエスケープを解釈し、選択・見送りの引数だけを除く。並列数など他のビルド設定は引き続き識別する。版の問い合わせでは rustup の自動インストールを無効にし、診断がツールチェーンを取得しないようにする。

追加の運用として、ドキュメント・テスト基盤・デバッグ基盤への影響を作業の開始時・新しい事実の判明時・完了前に確認する。必要な更新を同じ作業の範囲と完了条件に含め、内容か更新不要の理由を最終報告へ残す。必須規則は AGENTS、具体的な更新条件は [開発手順](../development.md#基盤の保守を同じ作業で行う) を正本にする。

## 限界

アプリの記録はディスク上の開発用バンドルの出所であり、起動中のプロセス・配布版の照合ではない。診断は新しいテストを実行しない。current は鮮度で、全検査の成功を意味しない。フックの直接呼出しとホストのイベント発火、ローカル検査とリモート CI は別々に扱う。ソースの識別にはファイルの実行属性も含むため、別環境の同一バイナリの再現性を証明する用途ではない。
