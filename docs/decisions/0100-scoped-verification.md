# ADR 0100: 検査の依存入力と長時間計測を分ける

- 日付: 2026-10-16
- 状態: 採用

## 理由

全ファイル共通の識別値と、HEAD からの広い変更一覧を使っていたため、以前の音声変更が未コミットで残ったまま文書を直すだけでも音声計測を再要求した。音声領域の変更は10分計測の候補となり、候補を一律に実行する運用で待ち時間が増えた。約45万回のコールバックは48 kHz・64フレームで10分動かした結果であり、停止後の音残りを検出するための必要回数ではない。

## 判断

選択条件と検査の入力を JSON に分けて宣言する。各検査は共通設定・実行器・Makefile・ツールと自身の定義、入力ファイルを識別する。Rust のローカル依存は Cargo.toml から全 feature・target・開発用・ビルド用を含めてたどり、依存先の変更を見逃さない。依存するファイルの内容・追加削除・移動・実行属性で失効させ、変更一覧やコミットの有無だけでは失効させない。

基盤と文書の検査は `check-verification` として別に記録する。文書だけならこれを再実行し、製品の依存入力が同じ検査は再利用する。必須契約の名前・実行件数・誤実装の拒否は維持する。失敗の見送り、0件の成功、失効した合格の移し替えは認めない。

通常の音声変更は10秒の `spike-engine-smoke` を候補にする。既存の10分 `spike-engine` は `extended` とし、`--run spike-engine` または `--all` で明示する。通常検査が完了しても長時間の安定性を証明したとは言わない。スレッド・スケジューラーの重要な変更、長時間でだけ起きる問題、リリース前など、必要な時には長時間を実行する。

短時間の実機確認で、現在の音声機器が96 kHzであることが分かった。機器のレートを変えず、短時間では実レートから処理期限と保存容量を決める。48 kHz専用の比較条件は長時間側に残す。短時間の記録は別ファイルへ出し、過去の10分計測の証拠を上書きしない。

実機計測では既定出力の記述・レート等もハッシュに含め、機器が変わったら該当する結果を失効させる。情報取得は読み取りだけとし、生の機器名は記録しない。制限された環境で一覧が空になっても、同じ機器の合格と見なさない。取得できない場合は未実行理由を残せるが、合格の再利用は認めない。

## 証拠と限界

修正前に、文書変更で計測の合格が消える、同じ内容のコミットでも失効する、長時間が通常の完了条件になる、の3ケースが失敗することを確認した。修正後は依存先・名前を変えた workspace 継承・target のビルド依存、追加削除・移動・属性、ツール変更・同時編集・失敗の保持・旧結果の拒否も検査する。

結果は version 2 にする。version 1 の全体識別値から依存入力は逆算できないため、新しい合格へ流用しない。診断は各検査を個別に照合し、一部だけ古い場合は `partial` と表示する。検査中の編集を止める全体の監視とロックは維持する。

依存入力の宣言が不足すれば再利用範囲を誤るため、検査コマンドや依存を変えた時には JSON の宣言も保守する。Cargo 以外の生成器・Swift・スクリプトの入力は明示する。機器・外部プラグイン・外部データの互換性を、ソース入力の一致だけで保証しない。開発用アプリの出所照合と検査結果の再利用も別である。
