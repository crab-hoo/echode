# 0208. 検査の識別計算で同じ範囲の読込みを共有する

- 日付: 2026-10-31
- 状態: 採用
- 関連: [ADR 0195](0195-verification-cost-observability.md)、[ADR 0197](0197-verification-target-scopes.md)、[ADR 0198](0198-verification-launch-and-cache-cost.md)

## 背景

`make verify` が、製品の不具合ではなく `check-verification` の 180 秒の期限で止まった。
自己テスト 262 件は、他の作業がない時は 110〜139 秒で終わる。
2026-10-31 に OpenUtau が約 3 コアを使っていた時は 201 秒かかり、3 回続けて先へ進めなかった。
期限を変えずに、検出力を保ったまま短縮する。

## 原因

`--durations` と `cProfile` で測ると、時間は次の 3 か所に集まっていた（負荷なし、合計 102〜107 秒）。

| 場所 | 所要 | 内訳 |
| --- | --- | --- |
| 実リポジトリの識別計算を繰り返す 2 件 | 36〜40 秒 | `contract_fingerprints` 1 回が 4.5 秒 |
| `EvidenceTests` 30 件 | 20〜23 秒 | うち約 15 秒が git の 1114 回の起動 |
| `test_platform` 6 件 | 15〜20 秒 | 新しいキャッシュでの Swift の構築が 13〜15 秒 |

識別計算では、契約 236 件のハッシュ範囲が 11 種類しかないのに、契約ごとに 839 ファイルを選び直していた。
1 回の計算で `fnmatchcase` が約 400 万回、`Cargo.toml` の解析が 10868 回走っていた。
`make verify` の実行も同じ関数を通るので、これは自己テストだけの無駄ではない。

`EvidenceTests` は検査の実際の流れを git ごと動かすので、流れ自体は変えない。
ただし 1 回の確認で `rev-parse` を 2 度起動し、同じ時点のファイル一覧を 2 度取得していた。

同じ政策の読込みも候補だったが、1 回 1.7 ms で 116 件でも 0.2 秒であり、変更しなかった。

## 決定

- **同じ範囲の共有**: `scoped_digest` は、1 回の計算の中で同じ範囲の選択と読取りを 1 度にする。
  ハッシュへ渡すバイト列は従来と同じなので、識別値は変わらない。
  範囲のキーは、パターン、パッケージのフォルダー、`tool_inputs`、除外の 4 つすべてである。
  共有は 1 回の計算の中に限り、次の計算では読み直すので、途中の編集を隠さない。
- **マニフェストの再利用**: `manifest` は TOML をファイルの状態ごとに 1 度だけ解析する。
  キーは `content_digest` と同じで、書込みで必ず変わる ctime を含む。
- **git の起動**: `changed_paths` の `rev-parse` を 1 度にし、`verify` の 1 回の確認で一覧を共有する。
- **Swift のマニフェスト**: `test_platform` の `package` は `dump-package` の結果を実行中に再利用する。
  どのテストも読むだけで、実行中に編集しない。

次は採らなかった。

- テストの削除・無視、検査範囲の縮小、180 秒の期限の変更。
- テストの並列実行。期限のあるテストが負荷で外れると、検出と区別できなくなる（[開発手順](../development.md#検査をまとめて進める)）。
- 新しいキャッシュでの Swift の構築と、監視の実時間の待ちの短縮。どちらもそれ自体が検査の対象である。

## 検出力の確認

- 変更前の `a68f866` のコードと変更後のコードで、同じ作業ツリーの識別値を比べた。
  完全な契約 236 件、通常の段階の契約 236 件、検査 28 件のすべてがバイト単位で一致した。
- 既存のテストは変えず、回帰を 4 件足した。
  共有と個別計算の一致、計算ごとの読み直し、マニフェストの失効、最初のコミット前と誤った基準の扱いである。
- 実装へ 13 種類の不具合を 1 つずつ入れ、すべてテストが落とすことを確認した。
  範囲のキーからフォルダー・`tool_inputs`・除外を外す 3 種類は、識別計算に関わるテストのうち新しい回帰だけが検出した。

## 測定

変更前と変更後を同じ内容のコピーに置き、交互に実行した（2026-10-31、MacBook Air M4）。
負荷は `perl` のビジーループである。単位は秒で、変更後はテストが 4 件多い。

| 負荷 | 変更前（262 件） | 変更後（266 件） |
| --- | --- | --- |
| なし | 107.0 / 102.5 | 61.2 / 59.4 |
| 3 本 | 137.1 / 138.3 | 77.1 / 77.8 |
| 7 本 | 186.0 / 183.7 | 108.9 / 106.5 |

変更前の 7 本は期限の 180 秒を超え、報告された失敗と同じ状態を再現している。
OpenUtau の実際の負荷では、変更後を測っていない。
ビジーループ 3 本は OpenUtau の 201 秒より軽かったので、同じコア数の負荷とは見なさない。

識別計算 1 回は、契約が 4.5 秒から 0.6 秒、検査が 0.39 秒から 0.25 秒になった。
`EvidenceTests` の git の起動は 1114 回から 805 回になった。

## 残る制約

変更後の上位は、新しいキャッシュでの Swift の構築（負荷なし 12.6 秒、7 本で 21.7 秒）と `EvidenceTests`（18.5 秒）である。
どちらも実物を動かすことが検査の内容であり、テストが増えれば所要も伸びる。
再び期限に近づいたら `--durations` で測り直し、短縮で足りなければ測定値を添えて期限の変更を相談する。
