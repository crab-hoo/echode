# ADR 0126: エージェントの一括開始診断と根拠付き原文読込

- 日付: 2026-10-20
- 状態: 承認

## 背景

[ADR 0119](0119-agent-token-efficiency.md) と [開発手順](../development.md#検査をまとめて進める) により、静かな検査と有効な結果の再利用は既にある。
検査以外にも、開始時の診断・検査計画・資料の探索、長い資料の全文読込、引継ぎ後の調べ直しが出力と往復を増やす。
ユーザーは、デメリットを検証し、精度と正確さを保って効果が大きいものから実装する方針を指示した。

## 候補とデメリットの評価

1. **開始診断の一括化**を最優先にする。
   毎作業の入口に効果があり、既存の診断と選択の関数を共有できる。
   要約で失敗や未実施を消す危険、古いレポートの差分基準を引き継ぐ危険がある。
   状態を省略しない表示と、現在の `VERIFY_BASE` / HEAD による選択の一致を回帰で検証する。
   資料対応の保守が増えるため、既存の検査領域との不一致を自動検査で止める。
2. **節・行単位の原文読込**を同じ作業で実装する。
   大きい資料の読込にも効果があり、新しい要約の正しさを信頼する必要がない。
   行のずれ、同名の節、コード内の見出し、無言の切捨て、外部シンボリックリンクが誤読につながる。
   原文と SHA-256、正確な範囲を返し、曖昧・古い・範囲外・予算超過は失敗にする。
3. **成果物の鮮度の絞込み**は保留する。
   現在の全体ハッシュは文書変更でもアプリを古いと判定し、余分な再ビルドを促す。
   一方、Markdown を `include_str!` 等で取り込むと、文書の一律除外は古いバイナリを最新と誤認する。
   その依存を模した回帰を追加し、全体ハッシュで失効することを確認する。
   生成物・リソースを含む依存入力の確実な収集を用意するまで、保守的な判定を維持する。
4. **長時間処理の共通ランナー**は既存のログ・待機手段と検査器を使う。
   新しいバックグラウンド管理は取消・排他・終了コードの伝播を複雑にする。
   まずバッチ実行とログ保存を標準手順にし、既存の仕組みで減らせない往復を測ってから追加する。
5. **永続的な読込・引継ぎキャッシュ**は導入しない。
   不正確な要約や別作業の決定を最新の証拠として使う危険がある。
   目的・決定・版と証拠・未解決事項・次の操作を残す形式を定め、再開時の照合を必須にする。

## 決定

- `make agent-context` は `diagnose.collect` の一回の収集と既存の `verify.select_checks` を使う。
  検査の選択条件と結果再利用・失効は変更しない。
  入口の診断は完了ゲートではなく、最後の `make verify` を継続する。
- 完全な診断・全変更・選択根拠と目的・資料のハッシュと見出しは `target/agent-context.json` に保存する。
  標準表示では成功を集計し、自動検査の未完了と失敗は個別表示する。
  手動検査は状態・鮮度・理由の三つが一致する場合だけまとめ、未実施を合格にしない。
- 資料の対応は既存の検査領域から参照先を選ぶ案内だけであり、影響範囲の証明には使わない。
  共通資料、関連 ADR・監査への入口を常に案内し、未知の領域や案内先の欠落はエラーにする。
  `--area` は案内を追加するだけで検査も既存変更も減らさない。
- Markdown の ATX 見出しと明示した行範囲を読み、要約や暗黙の切捨てをしない。
  本文予算は明示的に変更できる表示上の目安で、製品の容量制限や必須規則を省略する根拠ではない。
  見出し・メタデータ・JSON の整形後にも予算を確認し、短い行への装飾で出力が膨らむことを防ぐ。
- [エージェントの手順](../agent-workflow.md) を運用の正本とし、AGENTS・開発手順・デバッグ手順から参照する。
  新しいテストは既存の `check-verification` で実行し、新しい検査エンジンや依存ライブラリを追加しない。

## 検証と結果

`scripts/tests/test_agent_context.py` は選択・根拠の一致、ツール情報の一回収集、全非合格状態の保持、見送り理由のグループ化を確認する。
さらに過去の基準と明示した基準、途中の編集、案内の欠落、ハッシュ不一致、節の曖昧さ、外部リンク、本文予算、原文の改行保持を検証する。
`scripts/tests/test_diagnostics.py` は Markdown をビルド入力として変更した場合のアプリの失効も確認する。

出力量の比較は、同じ収集結果から旧 `doctor` と `verify-plan` の表示、および新しい入口の表示を作って行う。
節の読込は同じファイルの全文と返した原文を比較する。
測るのは UTF-8 バイト数であり、実際のモデルのトークン数や開発時間の削減率とは区別する。
完全な根拠はファイルへ保持し、検査の範囲・合否基準・実機の実施条件を維持する。

2026-10-20 の未コミット変更 94 件・選択 21 項目（自動 10、手動 11、測定時はいずれも `stale`）で比較した。
開始表示は 7,645 → 2,196 バイト（71.3% 減）だった。
開発手順の全文 12,278 バイトに対し、「検査をまとめて進める」の原文は 1,197 バイト、出所とハッシュを含む表示は 1,307 バイト（全文比 89.4% 減）だった。
測定時のソース識別、状態、各バイト数は `target/agent-efficiency-metrics.json`、比較表示は `target/agent-baseline-output.log` と `target/agent-context-output.log` に残す。
この一条件の値を、すべての作業や実トークン数の削減率には一般化しない。
