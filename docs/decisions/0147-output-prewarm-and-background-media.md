# ADR 0147: プロジェクトを開いた時に出力を準備し、停止中の編集の素材を別スレッドで読む

- 日付: 2026-10-22
- 状態: 採用。初回の再生の待ちへの対応。実機での待ちの改善量・操作感・聴感はユーザー確認待ち
- 範囲: アプリでプロジェクトを開いた時の出力準備、停止中の編集で必要になった素材の読込み・SRC、読込み中の再生

## 背景

[ADR 0136](0136-output-opening-off-worker.md) で最初の出力準備は準備スレッドへ移したが、始まるのは最初の再生かデバイス要求だった。
最初の再生は、ヘルパーの起動、全素材の読込みと SRC、HAL の開始が終わるまで鳴らない。
2 回目以降は保持した出力を再開するため、すぐ鳴る（[ADR 0097](0097-cancellable-retained-transport.md)）。
利用者には「初回の再生だけ待つ」と見える。

出力を開いた後の編集は、`PlaybackControl.reprepare` が素材を文書ワーカー上で同期に読む（[ADR 0142](0142-background-plugin-graph-preparation.md) の残る範囲）。
新しい素材の読込みと SRC は、その編集の応答と後続の手番を待たせる。
出力を早く開くだけでは、この待ちが最初の再生から停止中の編集へ移る。

修正前の経路は、機器なしの出力と読込みを保留する検査用の読込み関数で再現した。
停止中の編集の読込みを同期に戻すと、保留した読込みが呼出し側（ワーカー役の検査スレッド）を塞ぐ。
読込み中の再生の保留を外すと、置き換えられる前の計画（約 0.18）が鳴る。
どちらも下記の必須契約の負の対照として残す。

## 決定

### プロジェクトを開いた時に出力を準備する

- 音声コマンド `audio.prepare` を加える。
  デバイスビューの最初の要求と同じく、再生指令を入れずに出力・ヘルパー・素材を準備スレッドで準備し、停止のまま導入して保持する。
- ワーカーはすぐ戻る。準備中の編集・位置・ループ・再生・停止は ADR 0136 の導入時の差分で反映し、準備中の再生は導入時に始まる。
- 出力が開いているか準備中なら何もしない。準備し直さない。
- 機器がない時は再生と同じエラーを状態に入れる。失敗は自動で繰り返さず、次の再生かデバイス要求で準備する。
- 機器や Workgroup が変わると、停止中も新しい機器で開き直す。デバイス要求で開いた出力と同じ扱いである。
- `ProjectController.preparesOutput` が真の時だけ、開いた直後（前の文書を閉じた後）に送る。
  編集の手番の外から送り、応答は待たない。失敗はポーリングする音声状態で示す。
- 有効にするのは製品アプリ（`EchodeApp`）だけである。
  検査・プローブ・`spike-playhead` の controller は既定の偽のままで、機器を開かない。CLI と API のヘッドレスセッションも送らない。
- 代償: 開いた出力は停止中も無音入力でプラグインを処理する（[ADR 0133](0133-stopped-plugin-processing-and-edit-input.md)）。
  これまで最初の再生の後に生じた負荷と出力機器の使用が、プロジェクトを開いた時から生じる。

### 停止中の編集の素材を別スレッドで読む

- `MediaInputs`（テンポと全音声配置・音声参照）は素材の読込み関数が読む内容で、素材キャッシュのキーも同じ値を使う。
- 前回の読込みと `MediaInputs` が異なる置換は、`echode-media-prepare` スレッドで読込み関数を呼ぶ。
- 別スレッドにするのは、Session が停止中（再生の要求がない、または取り消された）と判断した置換だけである。
  再生中の編集は従来どおり同期で読み、テンポ変更の位置移動と計画の順序を変えない。
  → [ADR 0330](0330-playing-edit-media-and-tempo-retime.md) で、再生中も別スレッドで読むようにした。テンポの変わった計画は採用時に拍を保つ。
- 読込み中の置換・ループ変更・状態の復元は同じ読込みへ集約する。
  読込み関数を並行して呼ばず、制御側が素材キャッシュのロックを待たない。
- 読込み後に `MediaInputs` が変わっていれば、最新の内容で読み直す。キャッシュが前回の平面を再利用する。
  素材以外の編集だけがあった時は、同じ素材をキャッシュから受け取る。
- 読込みは計画の待ちとして `pending_plan` に出し、`preparing_graph` と `Session.opening()` に含める。
  新しいデバイスの要求は既存の投入順の待ちへ入る（ADR 0136）。
- 編集で確定したフェーダー試聴は、素材を載せた計画の採用まで保つ。延期の時点で要求済みの計画番号を進める。
- 計画の生成（`Prepared::new`）は従来どおり制御側で行う。
- 失敗は非同期の準備エラーとして一度だけ返し、未反映の計画を取り消す。Session は同期の置換の失敗と同じく出力を閉じてエラーを示す。
- 出力を閉じる時は読込みの終わりを待たない。読込みはパッケージのオブジェクトだけを読み、ヘルパーを起動しない。
  切り離したスレッドは結果を捨てて終わる。
- 初回の出力準備、オフライン書出し、CLI は同期の経路を保つ。`load_media_in_background` を切り替えるのは Session だけである。

### 読込み中の再生は素材を待つ

- 停止中の編集の素材を読込み中に再生を求めると、Session は再生指令を保留し、素材を載せた計画の公開後に送る。
  置き換えられる前の計画は鳴らさない。待つのは読込みの残りだけである。
- 保留中は `playing` が真で `running` が偽になる。ADR 0136 の準備中と同じ表示である。
- 停止・一時停止・出力を閉じることは保留を消す。開き直した出力は導入時に再生を始める。

## 検査と診断

- 必須契約 `output-prewarm` は、機器なしの出力で `audio.prepare` が停止のまま開き、停止中のクリップゲイン変更の読込みを保留しても呼出し側へ戻り、
  準備し直さずに新しい素材で鳴ることを製品のコールバックで確かめる（RTSan の対象）。負の対照は停止中も同期で読む。
- 必須契約 `output-prewarm-play` は同じ検査で、読込み中の再生が古い計画を鳴らさず、読込み後に新しいゲイン（約 0.09）で始まることを確かめる。
  負の対照は再生の保留をやめる。
- 必須契約 `output-prepare-worker` は、C ABI からの `audio.prepare` が準備の保留中も戻り、編集を待たせず、準備後の最初の再生が準備し直さないことを確かめる。
  負の対照は出力の保持を外す。
- 必須契約 `output-prepare-on-open` は、有効にした controller だけが開いた直後に 1 回送ることを確かめる。負の対照は送信を外す。
- エンジンの単体回帰は、保留中の後続編集とループ変更の集約、読込み関数が並行しないこと、再生中の同期の読込み、
  失敗の一度だけの報告と後続の成功を確かめる。DSP は変えないため、ブロック長の比較は既存の回帰を維持する。
- 開いた直後の `opening` は事前準備である。最初の再生がまだ待つなら、その時点の状態を分ける。
  `opening` が真なら事前準備の途中、`opening` が偽で `pending_plan` が真なら停止中の編集の素材読込みの残りである。

## 残る範囲

- 再生中の編集の素材読込み、保存済み状態の読込み、計画の生成は制御側で同期のままである。
  → 保存済み状態は [ADR 0329](0329-plugin-states-by-name.md) で名前で比べ、読み込むヘルパーだけが準備スレッドで読むようにした。
  → 再生中の編集の素材は [ADR 0330](0330-playing-edit-media-and-tempo-retime.md) で別スレッドへ移した。導入時の差分の素材も、再生するなら読込みを待ってから鳴らす。
- 導入時の差分で増えたヘルパーの起動は同期のままである（ADR 0142）。導入時の差分の素材は、停止中なら別スレッドで読む。
- 準備した出力は文書を閉じるまで保持する。停止中の負荷を下げる解放（一定時間後の閉鎖など）は持たない。
- 実機での待ち時間の改善量、HAL の開始時間、Bluetooth などの機器での挙動、聴感はユーザー確認とする。
