# ADR 0113: 製品の Workgroup 接続、M4 ビルド条件、PCM と描画の再利用

- 日付: 2026-10-17
- 状態: 採用（Swift の M4 指定の見送りは [ADR 0114](0114-m4-build-baseline.md) で解除）
- 範囲: 最適化監査 M27-01 / 02 / 03 と M27-04 の可視列・波形の再利用。M4 方針は ADR 0112。実機性能の達成値ではない

## 製品の Workgroup

HAL 出力は、選択したデバイスに `kAudioDevicePropertyIOThreadOSWorkgroup` の通知を登録してから、同じ ID の Workgroup を取得する。周期はそのデバイスのレート・バッファ長と Mach の時間単位から求める。既定デバイスを別に開かない。

制御側の所有者が OS オブジェクトを保持し、ヘルパーを作るたびに新しい送信権を渡す。音声側のスナップショットにはこの取得用の関数を持ち込まない。プラグインの追加・再作成も同じ所有者を使い、各 `PluginHost` の再起動も保持した Workgroup を再送する。送信権は RAII で管理し、共有メモリの作成や起動に失敗しても解放する。

取得や参加の失敗は準備のエラーとし、Workgroup を省略して成功にしない。ヘルパーの音声スレッドが参加前に失敗しても、メインループと制御側へ終了を伝える。準備完了の印は参加後である。I/O と同じ周期で処理しないオフライン書き出しは、デバイスの Workgroup なしの既存経路を使う。

デバイスのレート・バッファ長の変更は既存の再準備を通る。Workgroup だけが変わった場合も専用の通知から保持中の出力を無効にし、制御側のサービスで再作成する。通知の中で起動・停止や取得はしない。停止中の保持と、機器が変わったあとの再準備を区別する。

## ビルド条件

`.cargo/config.toml` は最低 OS を 27.0 に固定し、C / C++ の依存にも同じ OS と M4 の条件を渡す。Rust は固定した `apple-m4` を指定する。sanitizer の `RUSTFLAGS` にも同じ CPU を指定する。Swift の製品パッケージと橋渡し検査は、SDK と互換性のある arm64 / macOS 27 を使う。

Swift に `-target-cpu apple-m4` を加えると、この Xcode 27 の SDK では Testing の interface と SwiftShims の PCM の `+bf16` / `+sme` / `+sme2` などの機能条件が一致せず、通常の検査がコンパイルできなかった。この指定を取り除き、SDK の検査条件を緩めずに既存の Swift 設定を維持する。M4 以降の対応方針は変えず、Swift の CPU 指定は SDK が対応した条件で別に検証する。失敗ログは `target/macos27-audit/swift-m4-sdk-failure.log` に保持する。

単体の `rustc --print deployment-target` は Cargo の設定を読み込まない。検査は一時プロジェクトを実際に Cargo でビルドし、古い最低 OS を環境へ入れても LLVM IR の CPU と OS が M4 / 27.0 になることを確認する。アプリの組立前にも本体とヘルパーの Mach-O を調べ、arm64 単独・最低 OS 27.0 以外は既存バンドルを置換する前に拒否する。これはチップ名による起動拒否の実装や速度の改善量を意味しない。

Rust 1.96.1 の release の既定のデバッグ情報削除は、macOS 27 が拒否する `LINKEDIT` の配置を生成した。橋渡し生成の proc-macro だけでなく、外部 crate を含まない一時 cdylib でも `mis-aligned LINKEDIT string pool` を再現した。`.cargo/config.toml` の release は `strip = "none"` とし、最低 OS を下げずに実際の `dlopen` と公開関数の呼出を回帰へ追加する。Rust の最適化レベルは変えない。上流の [rust-lang/rust#157750](https://github.com/rust-lang/rust/issues/157750) に同じ失敗が報告されているが、手元の固定コンパイラーでは再現するため回避を残す。失敗は `target/macos27-audit/release-dylib-before.log`、詳細なローダーの証拠は `bridge-loader.log`。

`.cargo/**` の変更はすべての自動検査を選び、共通入力として過去の合格を失効させる。検査環境の識別には C++ のコンパイラーとフラグも含める。

## PCM の共有

制御側で、ハッシュ・素材のメタデータ・デバイスレートが同じ素材の変換を一度にまとめる。同じレートなら変換先の全体コピーを省く。配置の内容位置・長さ・ゲインが同じ結果も左右の `Arc` 平面を共有する。単位ゲインで素材全体を使う配置は、変換済み平面をそのまま使う。

次の準備には参照中の素材・配置だけを引き継ぐ。配置の位置・フェードの変更だけなら、同じ平面を使う。素材全体を既存の配置が保持している場合は、ゲインや範囲の編集にもそれを使える。短いトリムだけのために全素材の平面を追加で常駐させず、その場合の新しい範囲・ゲインは必要に応じて読み直す。準備中も、その素材の最後の配置を処理したら、配置が共有していない全体の一時平面を解放する。失敗した準備は前のキャッシュを壊さない。最後の参照がなくなれば制御側のキャッシュから外す。

ハッシュの検証、非有限値の拒否、左右、負オフセット、トリム、フェード、ループ先頭の保持、ブロック長に依存しない出力は維持する。音声スレッドでファイルを読んだり、mmap のページに頼ったりしない。異なる範囲・ゲインの配置をすべて一つの平面にする API の変更や、ディスクストリーミングは今回含めない。

## 描画

表示リンクは、入力の版とカメラが変わらない間、`ArrangeFrame` / `PianoFrame` の可視要素・波形・ノート・行の配置を保持する。再生位置は既存の feed から読み、トラックのピークは毎フレーム読み直す。文書、表示範囲、倍率、選択やプレビューなどの入力更新は既存の `CanvasRenderer.update` の版を進めるため、次の描画で再構成する。計測モードのカメラ移動は毎回再構成する。

入力とアクセシビリティへ渡す版は従来どおりで、飛行中の GPU バッファの 3 枠も維持する。インスタンス配列の組立・波形列の連結・GPU へのアップロードの追加削減と、Metal 4 は残る比較候補である。今回の変更を描画全体のゼロコピー化とはしない。

## 検査と保守

- Workgroup を無視する実装で製品の失敗回帰が落ちることを先に確認した。公開の `AudioWorkIntervalCreate` を呼ぶ C の検査用ライブラリで、機器を開かず製品のプラグイン追加・保持とヘルパー再起動を通す。このライブラリはプラグインを含まず、OS API を手で宣言しない。
- 古い最低 OS のバイナリが組み立てられる失敗と、同じ PCM が別の `Arc` になる失敗を先に確認した。配置の編集・失効・素材の破棄、短いトリムが全素材を保持しないことを通常回帰へ追加した。
- 実際の文書のトラック追加・表示幅・倍率・カメラ変更で、可視列の再利用と失効を確認する。Workgroup の引継ぎ、PCM 共有、可視列の失効は既存の製品必須契約へ登録し、誤りを戻すコピーも拒否する。
- 既存の `loop-head-residency` の負の対照も、準備キーの一致だけでなく準備キャッシュ全体を捨てる条件に更新する。共有する配置平面だけでも保持できるため、以前の変更では本来の誤りにならない。
- Makefile の既存の通常・製品契約・橋渡し検査の入口を使う。検査の選択は `scripts/verification.json` だけに置く。status、設計、元の監査とデバッグ手順を更新し、過去の失敗と計測値を保持する。

Swift の再生位置の世代更新テストは、以前は UI の通知確認のために実際の `.play` を送っていた。既存の `sendAudio` の差し替え口から再生要求だけに機器なしの応答を返し、位置・ループ・停止などは実際の橋渡しを維持する。期待する世代の増分も維持する。実 HAL は明示実行のプローブで扱う。

今回、その実 HAL へ入った TSan が、OS 所有の出力バッファへの f32 書込みと、別スレッドの zlib の書込みを同じアドレスとして報告した。ログは `target/macos27-audit/tsan-hal-before.log`。所有権の不具合か、OS が管理する領域の再利用を検出器が追えていないのかは未確定で、以前の errno の報告とも別である。警告の抑制は追加しない。機器なしの自動検査への修正を、この警告の解決や実 HAL の合格として扱わない。

画面なしのアレンジ検査も、ミキサー追加前の比較点 x=25 pt が M ボタン内にあることが分かった。比較点を操作部品のない x=2 pt の余白へ移し、境界とヘッダへの描画漏れの不一致数を分けて JSON に残す。全161フレーム・50,758行と不一致0の判定は維持する。ヘッダの区切りを1 ptずらした一時コピーで、実際の不一致を検出することも確かめる。製品の描画位置は変更しない。

最終の自動検査は `make verify` と `target/verification/report.md` を正とする。音声機器の実測、実ウィンドウ、聴感はユーザー担当として未確認を残す。CPU グラフの並列化、異なるプラグインのヘルパー集約、SME、Metal 4 の採用は、製品の負荷の内訳と同条件の比較から別に判断する。
