# ADR 0197: 検査の依存ターゲットと証拠の段階を区別する

- 日付: 2026-10-30
- 状態: 採用
- 対象: 契約の入力、通常テストと反例の再利用、橋渡し検査、生成ヘッダ、フック
- 前提: [ADR 0100](0100-scoped-verification.md)、[ADR 0148](0148-verification-pipeline-speed.md)、[ADR 0195](0195-verification-cost-observability.md)

## 監査の照合

毎タスクで全契約の反例を作り直す設計上の必要はない。
一方、「Swift のソースが無変更」と「Swift の検査バイナリの依存入力が無変更」は同じではない。
この区別をせずバックエンドを反例の入力から外すと、現在の製品に対する検出力を証明できない。

着手時の保存結果では、製品契約は 218 件、再利用は 0 件だった。
通常実行は 351.017 秒、Rust 反例は 435.531 秒、Swift 反例は 1232.069 秒、契約検査全体は 2027.200 秒だった。
Swift の 200 反例に対して 194 ビルドを行っていた。
直後の `report.md` は全検査の再利用だけで 2.061 秒だったため、これを全件実行の時間とは扱わない。
提供された監査の 37.8〜60.9 分という履歴値は、今回同条件で測定し直した値ではない。

コードでは次の不必要な失効と予算の不整合を確認した。

1. 全契約の `common.packages` がテスト用プラグインと Sine Pad を含み、API・保存の契約にもエンジンの依存を足していた。
2. パッケージディレクトリ全体のハッシュにより、依存先の `tests/**` だけの変更が静的ライブラリの利用側も失効させた。
3. 通常テストと反例が一つの識別値・再利用判定を共有し、反例定義の変更や反例段階の中断でも通常テストをやり直した。
4. ヘッダの内容が同じでも `cp` により更新時刻を進めていた。
5. 契約検査の予算 3600 秒に対してフックは 1800 秒、ロック待ちは 1790 秒のままだった。

## 決定

### 実際に使うプラグインの依存を分ける

`common` は契約実行器だけを含める。
Rust の実バンドル・ヘルパーを使うパッケージの追加入力は、`product_contract_inputs` の `rust:<package>` に宣言する。
API・履歴・モデル・描画の契約へ、無関係なプラグインの依存を足さない。
Swift は別プロセスのヘルパーを使う契約もあるため、ABI に加えてヘルパーと検査用バンドルの入力を保持する。
グループ全体を各契約の識別値に入れず、選択された入力パターン・依存閉包・除外の定義だけを入れる。

### Cargo のライブラリと別ターゲットを区別する

依存閉包の探索は従来どおり、全 feature・target・開発用・ビルド用のローカル依存を保守的にたどる。
閉包の外し方ではなく、そのパッケージの何をコンパイル・実行するかを区別する。

- 契約の Rust 対象パッケージは、その統合テスト・共有 fixture も含む全入力を保持する。
- ライブラリとして使う依存先の標準 `tests/**`・`benches/**`・`examples/**` は含めない。
- `src/**` は単体テスト用ファイルも含めて保持し、ファイル名だけで `*_tests.rs` を外さない。
- マニフェスト、build script、その他の素材は保持する。
  build script や明示的なターゲットの `path` があるパッケージは、安全側へ倒して全体を保持する。
- 検査が明示した `inputs` は除外より優先する。
  依存先のテストディレクトリから素材を読む場合も、そこを入力として宣言する。

橋渡しの ASan・TSan・Miri は `package_scope: targets` とし、実行しない依存先の統合テストを入力から外す。
ライブラリ内の単体テストと現在の製品コードは引き続き検査する。
`test_packages` は統合テストも実行するパッケージを追加で宣言するための欄である。
通常の workspace 検査・RTSan 等の既存の全体検査は、その範囲を縮めない。

### 通常テストと反例の証拠を独立に保存する

通常テストの識別値は実行経路・テスト・期限・ツールと全依存入力を含むが、反例の置換定義と説明文は含めない。
反例の識別値は従来どおり、これらに反例定義を加えた全入力を含む。
各段階は自分の識別値が一致する完了済みの合格だけを再利用する。
契約全体の合格には両段階の合格を必要とし、一部だけ終わった複数反例は合格にしない。

通常テストが終わった後の中断・反例失敗では、そのテストの証拠を次回に保持できる。
実行後は再利用した証拠も含めて両段階の入力を照合し、実行中の変更は `stale` にする。
`--force` は両段階を再実行する。
`execution` には通常・反例それぞれの未実行数と再利用数を残す。
旧方式の識別値は新方式の合格へ手で移し替えず、移行時は再検査する。

### 生成ヘッダと呼出し元の時間制限

通常の Swift 検査、製品契約、製品の ASan・TSan、プレイヘッドプローブのヘッダは、`cmp -s` が不一致の時だけコピーする。
内容が異なる場合の更新と、コピー失敗の検出は維持する。

フックの外側の時間制限は `verification.json` の `hook_timeout` を正本とする。
各フックの静的な設定値が一致することと、全自動検査・重複を除いた事前確認の直列予算に 120 秒以上の余裕があることを検査する。
今回は 14400 秒とし、ロック待ちは同じ値から応答用の 10 秒を引く。
これは検査の高速化でも個別契約の期限延長でもなく、呼出し元による途中強制終了を防ぐ上限である。
設定の直接検査と、実ホストが発火した証拠は引き続き区別する。

## 意図して残す境界

- Rust の製品コードが変われば、そこへリンクする Swift の通常テスト・反例は失効する。
  Swift の反例が変えるファイルだけのハッシュや、古いバックエンドでの反例結果を、現在の製品の検出力として使わない。
- Swift パッケージ内の本体・共有補助・テスト間の依存は未分割である。
  Swift テスト 1 ファイルの変更で全 UI 契約が失効する範囲は残る。
  これを縮めるには、独立した検査ターゲットや依存入力の証明を伴う後続の分割が必要である。
- workspace の通常テストを `-p` の契約テストに流用しない。
  feature の統合が異なり、同一の実行構成とは限らない。
- ASan・TSan・通常実行は別の計装の証拠であり、重複として削らない。
  契約ごとのプロセス隔離、個別の期限、反例の一件ずつの実行も保つ。

したがって、すべてのバックエンド変更を数分で終える修正ではない。
局所編集が全件失効する不必要な経路を減らすことと、実際の製品依存の変更を検査することを分ける。

## 回帰と保守

`scripts/tests/test_verification_scopes.py` が、実際の入力ポリシーと小さい依存グラフで次を検査する。

- テスト用プラグインの変更が API・履歴の契約へ伝播しない。
- 履歴の統合テストだけの編集・削除が利用側へ伝播せず、製品ソースの変更は Swift に伝播する。
- 明示した fixture、custom target、build script の入力は保持する。
- 反例定義だけの変更と、反例の失敗後の再開では、通常テストの完了記録を保持する。
- 強制実行、ヘッダの不変時刻と内容変更時の更新、フック全体の予算を検査する。

修正前の回帰は、プラグイン依存の混入と依存先統合テストの失効という固有のアサーションで失敗した。
コンパイル失敗・0 件・無視・部分反例・中断・実行中の変更の拒否は既存の検査も保持する。
正式な合否は最後の `make verify` が記録する。
検査基盤の変更自体は全自動検査を失効させるため、その初回時間を局所編集時の改善率へ言い換えない。

## 今回の照合結果と限界

全自動検査が失効する基盤変更としての初回 `make verify` は 2906.430 秒だった。
契約検査の実行器は 1724.665 秒、通常実行は 233.703 秒、Rust 反例は 369.078 秒、Swift 反例は 1103.904 秒だった。
これは現在の全件実行の記録であり、旧版との同条件比較や局所編集の時間保証ではない。

実リポジトリのポリシーと契約定義で、対象ファイルの内容ハッシュだけに仮の変更を与えた失効集合も照合した。
ソース・検査結果を改変せず、ビルドもせずに実際の識別関数で求めた件数である。

| 仮の変更 | 失効する Rust 契約 | 失効する Swift 契約 |
|---|---:|---:|
| 履歴の `tests/float_roundtrip.rs` のみ | 19 | 0 |
| プラグインの `tests/audit.rs` とテスト用 CLAP の `src/lib.rs` | 59 | 122 |
| 履歴の `src/media.rs` | 92 | 122 |

統合テストだけの変更による Swift 反例の全失効は解消する。
一方、製品コードや実行する検査用 CLAP の変更には広い失効が残り、監査の全ケースを高速化したとは言わない。
この境界と全登録反例が実効ハッシュ範囲内にあることも通常の基盤回帰へ登録した。
