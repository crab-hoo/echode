# ADR 0230: 保存の書出しを同期してからジャーナルを短縮し、欠けた再生は同意へ送る

- 日付: 2026-11-02
- 状態: 採用。実際の電源断は試していない
- 関連: [ADR 0033](0033-journal-log.md)、[ADR 0180](0180-journal-replay-invariants.md)、[ADR 0183](0183-recovery-consent.md)、
  [横断監査](../reviews/2026-11-02-cross-cutting-audit.md)の XCA-01〜03、
  [外部監査の精査](../reviews/2026-11-02-external-audit-review.md)の HIS-A1、[実行指示](../reviews/2026-11-02-fix-instructions.md)の W2、
  [保存の耐久性の追跡](../evidence/2026-11-02-durability-trace.md)

## 背景と再現

開始時の HEAD は `93fd86c`。製品の CLI の追跡で、次の順序を確認していた。

- XCA-01: 自動保存のコミットは Git のオブジェクトと参照を名前の変更だけで置き、同期しない（gix は同期を呼ばない）。
  それでも次の手番でジャーナルからその編集の行を消す。電源断が短縮の後に来ると、確定を返した編集が失われる。
- XCA-02: 先端の連番から続かない行を、理由を返さずに再生から外す。参照の更新だけが失われると、同期済みの行も消える。
- XCA-03: 保管物（`media/objects`）を同期せずに、それを名指す行を同期する。0 バイトになった保管物は、同じ音声の再取込みでも直らない。
- HIS-A1: 再生する行の名指すプラグイン状態の保管物を確かめない。保管物のない状態を含む文書が開き、次の自動保存が読めない先端になる。

`audit_durability.rs` の 3 件は修正前に固有のアサーションで失敗し、`durability_trace.py --require-durable` は終了コード 1 だった。

## 決定

### コミットの書出し（XCA-01）

- `commit_tree` は、このコミットで書いたオブジェクト（呼出し側が書いた blob・木・コミット）の各ファイル、それらの振り分けディレクトリ、
  `objects`、参照のファイルと各階層のディレクトリを `fsync` で書き出す。その後で、既存のコミットチェーンの追記が `F_FULLFSYNC` を行う。
- macOS の `File::sync_all` は `F_FULLFSYNC` で、1 回およそ 4 ms かかる。`fsync` は約 0.02 ms で、ドライブまで渡すがドライブのキャッシュは残る。
  最後の `F_FULLFSYNC` 1 回が、それまでに書き出した全ファイルを確定させる（Git の `core.fsyncMethod=batch` と同じ考え方）。
- `commit_tree` が戻った後は、コミット・新しいオブジェクト・参照が確定している。短縮は従来どおり、そのコミットの完了を受けてから行う。
  短縮の時期は変えず、短縮の前に同期の境界を 1 か所置いた。

### 参照の遅れと連番の欠け（XCA-02）

- コミットチェーンの最新の行が、チェーンの親をたどって参照の指すコミットへ戻れるなら、それを自動保存の先端とする。
  チェーンはコミットごとに同期するが、参照の更新はドライブのキャッシュとともに失われ得る。
  先端が読めれば、復旧はそこから続き、何も欠けないので同意は求めない。読めなければ、従来の読めない先端の確認になる。
- 次の保存は、gix が参照を最初の親からしか進めないため、先に参照をチェーンの最新へ進めてからコミットする。
  これがないと以後の自動保存がすべて失敗する（回帰で検出した）。
- 再生した最後の行より後にジャーナルの行が残っていれば、欠けがあるとして ADR 0183 の確認へ送る。
  同意は再生した状態を保存し、再生しなかった行を短縮で捨てる。

### 保管物（XCA-03）

- `write_object` は新しい保管物を同期付きで書き、ディレクトリを同期してから戻る。これを名指すジャーナルの行はその後に書く。
- 既にある保管物が同じ内容なら、そのまま使う。内容が名前のハッシュと一致しない保管物は壊れたものとして、同じ内容で置き換える。
- `media/index.json`（元のファイル名の索引）は同期しない。失われても表示名が欠けるだけで、音は読める。

### 状態の保管物の欠落（HIS-A1）

- 再生は各行の適用後に、その行が新しく名指すプラグイン状態を保管物から読み、ハッシュを確かめる。
  読めなければその行の手前で止め、その行と後続を適用しない。理由は ADR 0183 の確認へ送る。
  コミットから読む状態は、従来どおり `parse_track` が確かめる。

### 通知

- `RecoveryNotice` に `reason`（`unreadable_tip`・`journal_gap`・`missing_state`）を加えた。
  読めない先端以外では `tip` と `base` が同じになる。同意の照合は従来どおり `tip` と `base` で行う。
- 書込みの拒否の文は、読めない先端では従来の `recovery confirmation required: unreadable tip …` を保ち、ほかは原因を述べる。
- Swift の警告は `reason` をまだ読まず、従来の文面で先端・基点・連番を示す。既存の同意の流れは変えない。
- 保存スキーマ 6、ジャーナルの形式、C ABI の関数、依存ライブラリは変えない。

## 計測

製品の `Autosave` を使う `saving_one_edited_track_of_a_thousand_touches_only_that_file`（release、1,000 トラック）を、
書出しの有無を交互に 3 回ずつ測った。初回コミットの時間を出力に加えた。

| 版 | 初回コミット | 1 トラック編集のコミット |
|---|---|---|
| 書出しなし | 1,217〜1,239 ms | 15.6〜18.9 ms |
| 書出しあり | 1,297〜1,336 ms | 15.4〜21.8 ms |

初回は約 60〜120 ms 増え、編集はばらつきの範囲だった。どちらも自動保存のスレッドで行い、文書ワーカーと呼出し側は待たない。
`spike-history` の 1 件目は試作の `spike::History` で製品の経路を通らないため、比較に使わない。

## 残る範囲

- 作業ツリーの `project.json`・`tracks/`・`contents/` は同期しない。復旧はコミットとジャーナルから読み、`save.pending` が書き途中を示す。
- 実際の電源断・カーネルパニックは試していない。示したのは同期の順序と、失われた状態からの振る舞いである。
- Swift の警告で原因を言い分けること。

## 回帰と基盤

- `audit_durability.rs` の 3 件（XCA-02・XCA-03・HIS-A1）の `#[ignore]` を外した。
- `a_ref_behind_the_chain_recovers_from_the_newest_commit` は、参照の遅れからの復旧と、次の保存が最新を親にすることを確かめる。
- `a_journal_gap_and_a_missing_state_name_their_cause_and_hold_edits` は、理由・書込みの拒否・同意後の状態を確かめる。
- `objects.rs` の単体テストに、壊れた保管物の置換を加えた。
- `durability_trace.py --require-durable` は終了コード 0 になった。オブジェクト・参照・保管物のディレクトリの同期が、次のジャーナルの書込みより前に現れる。
- 必須契約 `recovery-consent` の負の対照は、通知の判定を移したため、`host.rs` の通知を作る行へ付け替えた。
- 新しいログ・Makefile の入口は加えない。切り分けは [デバッグ手順](../debugging.md) に追記した。
