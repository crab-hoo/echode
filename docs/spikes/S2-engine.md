# S2: 1,000 ノードのオーディオグラフ

- 日付: 2026-10-07
- 状態: 確定（2026-10-08 に確認）
- 実装: `crates/echode-engine`

## 何を確かめたか

CoreAudio の出力デバイスを 48kHz・64 フレームで開き、IO スレッドの中で 1,000 ノードのグラフを処理する。ノードは 100 本の直列チェインが 10 段で、各ノードは 16 タップのフィルタ。この件数は計測用で、製品の上限ではない。

ブロックの処理ではメモリを確保しない。デバイスのバッファサイズは計測後にもとに戻す。このプロセスはミュートし、出力バッファには無音を書く。スピーカーからは鳴らない。

締め切りは 64 / 48000 秒、つまり 1.333ms。コールバックの処理時間がこれを超えた回数と、デバイスが渡すホスト時刻の間隔が 1.5 倍を超えた回数を数える。最初の 200 コールバックはウォーミングアップとして分けた。

## 10 分間の結果

オーディオスレッドだけで 1,000 ノードを処理した。ワーカーは参加させていない。release ビルド。

| 項目 | 結果 |
|---|---|
| デバイス | 48000 Hz、64 フレーム |
| 計測コールバック | 449,909（ウォーミングアップ 200 を除く） |
| 締め切り超過 | 0 |
| ホスト時刻の飛び | 0 |
| CPU 時間の中央値 | 0.198 ms |
| CPU 時間の p99 | 0.307 ms |
| CPU 時間の最大 | 0.455 ms |

p99 は予算の約 23% だった。

## ワーカーを足した場合

同じグラフを、IO スレッドに加えて 3 本のワーカーで処理する構成も 10 分間測った。ワーカーはデバイスの Audio Workgroup に参加させる。参加の失敗は 0 だった。

定常状態は中央値 0.142ms、p99 0.204ms で、オーディオスレッド単独より短い。ただし 10 分間で締め切り超過が 40 回、ホスト時刻の飛びが 39 回あり、最大は 13.9ms だった。処理そのものが 13ms かかったのではなく、完了を待っているワーカーがカーネルに割り込まれた時間だ。

ブロックのたびに Workgroup へ参加し直す実装も試した。2 分間弱で超過が 25 回になり、起動時に 1 回だけ参加する方がましだった。採用したのは起動時の 1 回である。

ワーカー同士でグラフを分け合う処理はユニットテストで確認してある。リアルタイムのコールバックは、この計測ではワーカーを待たない。本番のスケジューラでは、オーディオスレッドが未処理のノードを自分で終わらせ、締め切りを超えて待たない。

## 再現

```sh
make spike-engine
```

並列の構成は `--workers 3` を付ける。結果は標準出力と `target/spike-s2.txt` に出る。Ctrl-C でもバッファサイズは元に戻る。
