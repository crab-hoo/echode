# S2: 1,000 ノードのオーディオグラフ

- 日付: 2026-10-07
- 状態: 確定（2026-10-09 にワーカーを測り直した）
- 実装: `crates/echode-engine`

## 何を確かめたか

CoreAudio の出力デバイスを 48kHz・64 フレームで開き、IO スレッドの中で 1,000 ノードのグラフを処理する。ノードは 100 本の直列チェインが 10 段で、各ノードは 16 タップのフィルタ。この件数は計測用で、製品の上限ではない。

ブロックの処理ではメモリを確保しない。デバイスのバッファサイズは計測後にもとに戻す。このプロセスはミュートし、出力バッファには無音を書く。スピーカーからは鳴らない。

締め切りは 64 / 48000 秒、つまり 1.333ms。コールバックの処理時間がこれを超えた回数と、デバイスが渡すホスト時刻の間隔が 1.5 倍を超えた回数を数える。最初の 200 コールバックはウォーミングアップとして分けた。

## ワーカーを足した場合

2026-10-07 は、IO スレッドに加えて 3 本のワーカーで、段ごとのバリア（1 ブロックに 10 回）を使った。ワーカーは QoS だけを上げ、時間制約は付けていない。参加の失敗は 0。定常状態は中央値 0.142ms、p99 0.204ms だが、10 分間で締め切り超過が 40 回、ホスト時刻の飛びが 39 回、最大は 13.9ms だった。処理そのものが 13ms かかったのではなく、完了を待っているワーカーが割り込まれた時間だ。ブロックのたびに Workgroup へ参加し直す実装は、2 分間弱で超過が 25 回になり、起動時に 1 回だけ参加する方がましだった。

2026-10-09 は、同じ 1,000 ノードをノードごとの依存カウンタで分けた。準備のできたノードを、IO スレッドとワーカーが同じスタックから取る。ワーカーは、デバイスの 1 バッファを period と constraint にし、computation をその半分、preemptible にした時間制約を付けてから、Workgroup に起動時の 1 回だけ参加する。本数は `os_workgroup_max_parallel_threads` の 4 から、すでに参加している IO スレッドを引いた 3。release ビルド、10 分間。

| 項目 | 結果 |
|---|---|
| デバイス | 48000 Hz、64 フレーム |
| 計測コールバック | 449,831（ウォーミングアップ 200 を除く） |
| 締め切り超過 | 0 |
| ホスト時刻の飛び | 0 |
| CPU 時間の中央値 | 0.278 ms |
| CPU 時間の p99 | 0.317 ms |
| CPU 時間の最大 | 0.723 ms |
| Workgroup の推奨スレッド数 | 4 |
| ワーカー | 3 |
| 参加の失敗 | 0 |
| 時間制約の設定失敗 | 0 |

p99 は予算の約 24%。中央値はオーディオスレッド単独の 0.198ms より長い。段のバリアをやめた分、ノードごとの原子操作が増えている。超過は 0 のままである。

## 再現

2026-10-16 から、通常の変更は `make spike-engine-smoke` の10秒確認とし、10分計測は明示実行に分けた（[ADR 0100](../decisions/0100-scoped-verification.md)）。短時間側は現在の機器のレートを使う。96 kHz・64フレームで10.188秒完走し、ウォーミングアップ後15,041コールバック、p50 0.153 ms・p99 0.203 ms・最大0.238 ms、期限超過0・間隔異常0だった。期限は実レートから0.667 msとした。短時間の結果は `target/spike-s2-smoke.txt` に出し、既存の10分記録と区別する。10分間の安定性の合格としては扱わない。

同日の機器識別を含めた最終確認は、同じ96 kHz・64フレームで10.158秒、14,984コールバック、p50 0.154 ms・p99 0.203 ms・最大0.249 ms、期限超過・間隔異常とも0だった。この計測値の文書への追記で、音声計測の入力は変わらない。

```sh
make spike-engine
```

`make spike-engine` は `--workers auto` で、Workgroup の推奨から本数を決める。オーディオスレッドだけは `--workers 0`。結果は標準出力と `target/spike-s2.txt` に出る。Ctrl-C でもバッファサイズは元に戻る。

## スリープをまたいだ計測の失敗（2026-10-15）

音声バスの製品接続後の全体検査で、48 kHz・64フレーム、ワーカー3本の計測は396,260コールバック（ウォーミングアップ200回を除く）、CPU p50 0.294／p99 0.321／最大0.716 ms、期限超過0件、ホスト時刻の間隔異常1件で不合格になった。Workgroup参加と時間制約の設定の失敗は0件だった。

OS の電源ログは10:19:59の Clamshell Sleep、途中の DarkWake / Maintenance Sleep、10:24:01の蓋を開いた Wake を記録しており、コールバック数が止まった期間と一致する。処理期限内だったことを理由に、連続再生の合格とは扱わない。失敗時の診断・ログと、補足の Sleep / Wake の抽出は `target/debug-reports/20261015T041317Z-9ows3sz0/`。これはローカル生成物である。条件を整えて再計測する時も、元の失敗と閾値は保持する。[デバッグ手順](../debugging.md) に切り分けを追加した。

## デバイス切替と旧判定の無効化（2026-10-15）

再計測では、13:26:22 の USB EarPods の IO 停止と内蔵スピーカーへの既定出力変更に伴い、コールバックが77,386で止まった。Sleep はなく、採取したスレッドに HAL の IO スレッドはなかった。調査中断後の旧レポートは測定標本77,186、p50 0.285／p99 0.311／最大0.702 ms、期限超過・間隔異常0件として合格したが、完走しておらず無効である。記録は `target/debug-reports/20261015T043156Z-jqe4p8m6/`。

[ADR 0096](../decisions/0096-measurement-completion.md) で、進行の停止・既定出力変更・中断と、要求時間未満を合格にしない制御ループ・レポートへ変更した。実機・回帰検査は同じ制御ループを使う。従来の処理期限や異常の閾値は緩めない。過去の計測値は当時の証拠として保持するが、旧判定だけでは完走を証明しない。
