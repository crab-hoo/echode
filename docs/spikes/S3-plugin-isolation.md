# S3: プラグインを別プロセスで動かす

- 日付: 2026-10-07
- 状態: 合格（2026-10-10 に、正しさと実時間の検査を分離して再確認）
- 実装: `crates/echode-sandbox`、`crates/echode-plugin-host`、`crates/echode-test-plugin`

## 何を確かめたか

2026-10-16 に検査入力の範囲を整理し、隔離の準備ビルドをヘルパーとテスト用プラグインへ絞った。既存の隔離20件と製品再生22件を実行して合格した。往復2,000回・ウォーミングアップ200回の計測は、コピー64フレームが最小5.5 / p50 8.0 / p99 10.4 / 最大15.0 µs、CLAP 64フレームが0.9 / 10.3 / 28.4 / 38.6 µs、CLAP 128フレームが1.6 / 9.7 / 15.5 / 22.0 µsだった。判定条件は維持している。これは隔離の計測であり、通常の10秒・追加の10分の機器計測とは別である（[ADR 0100](../decisions/0100-scoped-verification.md)）。

同日の機器識別を含めた最終実行も20件と22件が合格した。コピー64フレームは最小5.6 / p50 8.2 / p99 10.6 / 最大13.2 µs、CLAP 64フレームは7.2 / 10.3 / 16.3 / 26.9 µs、CLAP 128フレームは1.7 / 9.9 / 15.2 / 31.2 µsだった。数値の文書への追記後も、検査入力が同じ結果を再利用する。

DAW のプロセスとは別のプロセスで CLAP プラグインを鳴らし、音声は共有メモリで受け渡す。プラグインが落ちても、呼び出している側は落ちない。

待機と起床には `os_sync_wait_on_address` を使った。プロセス間で使う `OS_SYNC_WAIT_ON_ADDRESS_SHARED` は、仮想アドレスが違っても同じ共有ページなら届く。測定では固定アドレスへのマップはしていない。

共有メモリは一時ファイルを `MAP_SHARED` でマップしたもの。音声の本体はここに置き、ブロックごとにシーケンス番号を release で公開してから相手を起こす。ロックは取らない。

この検証のマッピングはステレオ、最大 512 フレームまで。これは検証用のバッファ長で、DAW の上限ではない。ヘルパーは 1 プロセスにプラグイン 1 つ。本番で予定している「同じヘルパーで続くデバイスは 1 往復にまとめる」はまだ入れていない。

テスト用プラグインはゲイン 2 倍。`ECHODE_TEST_FAULT=crash` で `process` の中から abort し、`hang` で `process` から戻らない。

## 測定

マシンは Apple M4、24GB。release ビルド。64 フレームと 128 フレーム、各 2,000 回（その前に 200 回のウォーミングアップ）。

2026-10-07 は、スレッドを通常の優先度のまま、Audio Workgroup には入れずに測った。同じテストを 2 回走らせた。

## Workgroup を渡した測定

2026-10-09 に、出力デバイスの Audio Workgroup をヘルパーへ渡して測り直した。デバイスは 48000 Hz、512 フレーム（周期 10.667 ms）。親の計測スレッドとヘルパーの処理スレッドは、どちらもその周期を period と constraint にし、computation をその半分、preemptible にした時間制約と、user-interactive の QoS を付けてから Workgroup に参加する。参加に失敗するとテストは失敗する。

渡し方は、ヘルパーが `bootstrap_check_in` した名前を親が `bootstrap_look_up` し、`os_workgroup_copy_port` の送信権を Mach メッセージで送る。ヘルパーは `os_workgroup_create_with_port` で作る。`posix_spawnattr_setspecialport_np` では届かなかった。Workgroup の送信権をリソース通知ポートやアクセスポートに置くと `posix_spawn` が EINVAL を返し、ブートストラップポートに置くと子から読んだポートは null だった。

release ビルドで 4 回走らせた。

## クラッシュとハング

- abort するとヘルパーは SIGABRT で終了し、呼び出している側は生きている。続けて新しいヘルパーを起動すると、再びゲインがかかる。
- `process` から戻らない場合は、指定した時間で待ちを打ち切り、ヘルパーを殺す。その後も新しいヘルパーを起動できる。
- プロセスの終了は、制御側の `kqueue`（`EVFILT_PROC` と `NOTE_EXIT`）で知る。落ちたブロックは、締め切りを待たずにヘルパーが終わった時点で戻る。abort から終了までには macOS のクラッシュレポートが入り、デバッグビルドを単独で 30 回動かすと 123 ms から 416 ms、ほかのテストと並べると 1 秒を超えることがあった。ハングはプロセスが終わらないので、呼び出し側の締め切りのままである。
- 2026-10-17 の追記: 上の終了までの時間は当時の測定のままである。`SIGSEGV`、`SIGBUS`、`SIGILL` も、終了を待たずに共有領域へ印を書く（[ADR 0111](../decisions/0111-macos-helper-notices.md)）。クラッシュレポートがプロセス終了を遅らせる事実は残る。印は、すでにカーネル待ちに入ったブロックを起こさない。

## 決めたこと

- プロセス間の起床は `os_sync_wait_on_address` の shared フラグで足りる。Mach セマフォには切り替えない。
- 中央値 30µs は、デバイスをまとめなくても達成できる見込みがある。まとめは遅延をさらに削る最適化として残す。
- Workgroup は Mach の送信権でヘルパーへ渡せる。ヘルパーが `bootstrap_check_in` し、親が `bootstrap_look_up` してメッセージで送る。特別ポートではない。親の検索は起動時の制御スレッドで、最大 5 秒まで 2 ms 間隔である。音声スレッドは待たない。この間隔の置き換えは測り直していない。
- リアルタイム優先度での末尾は、上の 2026-10-09 の表をホスティングのコストとして扱う。
