# S3: プラグインを別プロセスで動かす

- 日付: 2026-10-07
- 状態: 合格（中央値の目標は満たした。末尾の遅延は、リアルタイム優先度での再測定が残っている）
- 実装: `crates/echode-sandbox`、`crates/echode-plugin-host`、`crates/echode-test-plugin`

## 何を確かめたか

DAW のプロセスとは別のプロセスで CLAP プラグインを鳴らし、音声は共有メモリで受け渡す。プラグインが落ちても、呼び出している側は落ちない。

待機と起床には `os_sync_wait_on_address` を使った。プロセス間で使う `OS_SYNC_WAIT_ON_ADDRESS_SHARED` は、仮想アドレスが違っても同じ共有ページなら届く。測定では固定アドレスへのマップはしていない。

共有メモリは一時ファイルを `MAP_SHARED` でマップしたもの。音声の本体はここに置き、ブロックごとにシーケンス番号を release で公開してから相手を起こす。ロックは取らない。

この検証のマッピングはステレオ、最大 512 フレームまで。これは検証用のバッファ長で、DAW の上限ではない。ヘルパーは 1 プロセスにプラグイン 1 つ。本番で予定している「同じヘルパーで続くデバイスは 1 往復にまとめる」はまだ入れていない。

テスト用プラグインはゲイン 2 倍。`ECHODE_TEST_FAULT=crash` で `process` の中から abort し、`hang` で `process` から戻らない。

## 測定

マシンは Apple M4、24GB。release ビルド。64 フレームと 128 フレーム、各 2,000 回（その前に 200 回のウォーミングアップ）。スレッドは通常の優先度で、Audio Workgroup には入れていない。

同じテストを 2 回走らせた。

| 経路 | 1 回目 p50 | 2 回目 p50 | 最小 | p99 の範囲 | 最大の範囲 |
|---|---:|---:|---:|---:|---:|
| コピーだけ（64 フレーム） | 2.0 µs | 12.5 µs | 0.8 µs | 30〜36 µs | 115〜156 µs |
| CLAP を経由（64 フレーム） | 9.8 µs | 12.0 µs | 0.9 µs | 34〜78 µs | 331〜429 µs |
| CLAP を経由（128 フレーム） | 2.0 µs | 9.5 µs | 0.8 µs | 32〜52 µs | 191〜775 µs |
| 同じプロセス内の CLAP（64 フレーム、平均） | 0.1 µs | 0.1 µs | | | |

中央値はどちらも 30µs を下回った。最小値が 1µs を切っているので、割り込まれなかった時の往復自体は 1µs 未満。中央値と末尾が走るたびに動くのは、通常優先度のスレッドが他の処理に割り込まれるためで、プラグイン呼び出しのコスト（プロセス内では平均 0.1µs）では説明できない。

64 フレーム / 48kHz の 1 ブロックは 1.33ms。今回観測した最大でも、そのブロックの半分以下だった。

## クラッシュとハング

- abort するとヘルパーは SIGABRT で終了し、呼び出している側は生きている。続けて新しいヘルパーを起動すると、再びゲインがかかる。
- `process` から戻らない場合は、指定した時間で待ちを打ち切り、ヘルパーを殺す。その後も新しいヘルパーを起動できる。
- 死活の検知は、今は「締め切りまで待つ」だけ。オーディオスレッドの締め切りを 1 ブロックにしておけば、落ちたプラグインは最悪 1 ブロック無音にして迂回できる。プロセスの終了を kqueue で即座に知る処理は、制御スレッド側の仕事として残している。

## 決めたこと

- プロセス間の起床は `os_sync_wait_on_address` の shared フラグで足りる。Mach セマフォには切り替えない。
- 中央値 30µs は、デバイスをまとめなくても達成できる見込みがある。まとめは遅延をさらに削る最適化として残す。
- 末尾の遅延は、S2 でオーディオスレッドを Audio Workgroup に入れた状態で測り直す。今回の p99 は、その測定が終わるまでホスティングのコストとは扱わない。

## 再現

```sh
make spike-isolation
```
