# S3: プラグインを別プロセスで動かす

- 日付: 2026-10-07
- 状態: 合格（2026-10-09 に、共有メモリのプロトコルを替えて測り直した）
- 実装: `crates/echode-sandbox`、`crates/echode-plugin-host`、`crates/echode-test-plugin`

## 何を確かめたか

DAW のプロセスとは別のプロセスで CLAP プラグインを鳴らし、音声は共有メモリで受け渡す。プラグインが落ちても、呼び出している側は落ちない。

待機と起床には `os_sync_wait_on_address` を使った。プロセス間で使う `OS_SYNC_WAIT_ON_ADDRESS_SHARED` は、仮想アドレスが違っても同じ共有ページなら届く。測定では固定アドレスへのマップはしていない。

共有メモリは一時ファイルを `MAP_SHARED` でマップしたもの。音声の本体はここに置き、ブロックごとにシーケンス番号を release で公開してから相手を起こす。ロックは取らない。

この検証のマッピングはステレオ、最大 512 フレームまで。これは検証用のバッファ長で、DAW の上限ではない。ヘルパーは 1 プロセスにプラグイン 1 つ。本番で予定している「同じヘルパーで続くデバイスは 1 往復にまとめる」はまだ入れていない。

テスト用プラグインはゲイン 2 倍。`ECHODE_TEST_FAULT=crash` で `process` の中から abort し、`hang` で `process` から戻らない。

## 測定

マシンは Apple M4、24GB。release ビルド。64 フレームと 128 フレーム、各 2,000 回（その前に 200 回のウォーミングアップ）。

2026-10-07 は、スレッドを通常の優先度のまま、Audio Workgroup には入れずに測った。同じテストを 2 回走らせた。

| 経路 | 1 回目 p50 | 2 回目 p50 | 最小 | p99 の範囲 | 最大の範囲 |
|---|---:|---:|---:|---:|---:|
| コピーだけ（64 フレーム） | 2.0 µs | 12.5 µs | 0.8 µs | 30〜36 µs | 115〜156 µs |
| CLAP を経由（64 フレーム） | 9.8 µs | 12.0 µs | 0.9 µs | 34〜78 µs | 331〜429 µs |
| CLAP を経由（128 フレーム） | 2.0 µs | 9.5 µs | 0.8 µs | 32〜52 µs | 191〜775 µs |
| 同じプロセス内の CLAP（64 フレーム、平均） | 0.1 µs | 0.1 µs | | | |

中央値はどちらも 30µs を下回った。最小値が 1µs を切っているので、割り込まれなかった時の往復自体は 1µs 未満。中央値と末尾が走るたびに動くのは、通常優先度のスレッドが他の処理に割り込まれるためで、プラグイン呼び出しのコスト（プロセス内では平均 0.1µs）では説明できない。

64 フレーム / 48kHz の 1 ブロックは 1.33ms。このときの最大でも、そのブロックの半分以下だった。

2026-10-08 に、テストがレポートを書く条件だけを変えて（デバッグビルドでは書かない）測り直した。優先度は通常のまま。CLAP を経由した 64 フレームは p50 10.0 µs、p99 18.2 µs、最大 212.8 µs、128 フレームは p50 10.2 µs、p99 23.4 µs、最大 51.8 µs だった。

## Workgroup を渡した測定

2026-10-09 に、出力デバイスの Audio Workgroup をヘルパーへ渡して測り直した。デバイスは 48000 Hz、512 フレーム（周期 10.667 ms）。親の計測スレッドとヘルパーの処理スレッドは、どちらもその周期を period と constraint にし、computation をその半分、preemptible にした時間制約と、user-interactive の QoS を付けてから Workgroup に参加する。参加に失敗するとテストは失敗する。

渡し方は、ヘルパーが `bootstrap_check_in` した名前を親が `bootstrap_look_up` し、`os_workgroup_copy_port` の送信権を Mach メッセージで送る。ヘルパーは `os_workgroup_create_with_port` で作る。`posix_spawnattr_setspecialport_np` では届かなかった。Workgroup の送信権をリソース通知ポートやアクセスポートに置くと `posix_spawn` が EINVAL を返し、ブートストラップポートに置くと子から読んだポートは null だった。

release ビルドで 4 回走らせた。

| 経路 | p50 | 最小 | p99 | 最大 |
|---|---:|---:|---:|---:|
| コピーだけ（64 フレーム） | 1.0〜9.0 µs | 0.9 µs | 8.2〜13.8 µs | 14.3〜23.0 µs |
| CLAP を経由（64 フレーム） | 8.1〜10.8 µs | 0.8 µs | 21.4〜30.2 µs | 28.6〜35.1 µs |
| CLAP を経由（128 フレーム） | 1.0〜7.5 µs | 0.9 µs | 11.9〜14.7 µs | 20.0〜29.7 µs |
| 同じプロセス内の CLAP（64 フレーム、平均） | 0.0〜0.1 µs | | | |

中央値は 30µs 以下のまま。CLAP 64 フレームの最大は、通常優先度で測った 212.8 µs から 35.1 µs 以下になった。p99 は 30.2 µs 以下で、1.33 ms のブロックに対して約 2% である。処理をメインスレッドから外したあとの release でも、CLAP 64 フレームは p50 10.8 µs、p99 30.2 µs、最大 34.0 µs で、中央値の 30µs を下回った。

## 共有メモリのプロトコルを替えた測定

2026-10-09 に、一時ファイルのステレオ固定長をやめた（[ADR 0042](../decisions/0042-plugin-ipc.md)）。共有メモリは `shm_open` で作り、名前はすぐ消し、ファイル記述子を子へ渡す。ページは `mlock` する。ブロックは 2 スロットで、入力イベントと出力イベントは分かれている。イベントは `Event` の列として読まず、固定長のレコードを検証してから読む。制御（状態、`Dirty`、再マップ、再起動の通知）はソケットである。終了は `kqueue` の `NOTE_EXIT` で知る。

測定の条件は上の Workgroup と同じである。release で 3 回走らせた。

| 経路 | p50 | 最小 | p99 | 最大 |
|---|---:|---:|---:|---:|
| コピーだけ（64 フレーム） | 9.0〜9.1 µs | 6.3 µs | 12.3〜12.9 µs | 17.8〜18.2 µs |
| CLAP を経由（64 フレーム） | 8.9〜11.0 µs | 0.9 µs | 12.2〜27.6 µs | 18.7〜35.8 µs |
| CLAP を経由（128 フレーム） | 9.3〜9.7 µs | 1.0 µs | 13.6〜15.2 µs | 17.8〜33.9 µs |
| 同じプロセス内の CLAP（64 フレーム、平均） | 0.0 µs | | | |

中央値は 30µs 以下のままである。コピーの最小は 6.3 µs で、以前の 1µs 未満より大きかった（下の測り直しでは 0.9 µs だった）。CLAP 64 フレームの p99 は 27.6 µs 以下で、1.33 ms のブロックに対して約 2% のままである。

同じ日に、ヘルパーの起動を Workgroup の有無にかかわらず `posix_spawn` にそろえたあと、同じ条件の release で 3 回測り直した。往復の経路は変えていない。

| 経路 | p50 | 最小 | p99 | 最大 |
|---|---:|---:|---:|---:|
| コピーだけ（64 フレーム） | 1.2〜8.7 µs | 0.9 µs | 2.6〜12.6 µs | 2.8〜24.0 µs |
| CLAP を経由（64 フレーム） | 3.1〜10.4 µs | 0.9 µs | 14.9〜25.6 µs | 17.7〜30.5 µs |
| CLAP を経由（128 フレーム） | 2.3〜9.2 µs | 1.0 µs | 11.9〜16.5 µs | 15.0〜27.2 µs |
| 同じプロセス内の CLAP（64 フレーム、平均） | 0.1 µs | | | |

中央値は 30µs 以下である。コピーの最小は 0.9 µs で、上の表の 6.3 µs は、スロットとレコードのコピーで決まる下限ではなかった。CLAP 64 フレームの p99 は 25.6 µs 以下である。

## クラッシュとハング

- abort するとヘルパーは SIGABRT で終了し、呼び出している側は生きている。続けて新しいヘルパーを起動すると、再びゲインがかかる。
- `process` から戻らない場合は、指定した時間で待ちを打ち切り、ヘルパーを殺す。その後も新しいヘルパーを起動できる。
- プロセスの終了は、制御側の `kqueue`（`EVFILT_PROC` と `NOTE_EXIT`）で知る。落ちたブロックは、締め切りを待たずにヘルパーが終わった時点で戻る。abort から終了までには macOS のクラッシュレポートが入り、デバッグビルドを単独で 30 回動かすと 123 ms から 416 ms、ほかのテストと並べると 1 秒を超えることがあった。ハングはプロセスが終わらないので、呼び出し側の締め切りのままである。

## 決めたこと

- プロセス間の起床は `os_sync_wait_on_address` の shared フラグで足りる。Mach セマフォには切り替えない。
- 中央値 30µs は、デバイスをまとめなくても達成できる見込みがある。まとめは遅延をさらに削る最適化として残す。
- Workgroup は Mach の送信権でヘルパーへ渡せる。ヘルパーが `bootstrap_check_in` し、親が `bootstrap_look_up` してメッセージで送る。特別ポートではない。
- リアルタイム優先度での末尾は、上の 2026-10-09 の表をホスティングのコストとして扱う。
