# S1: 1,000 トラック・10 万ノートの描画

- 日付: 2026-10-07
- 状態: 確定（2026-10-07 に確認）
- 実装: `crates/echode-draw`、`spikes/draw`

## 何を確かめたか

Rust の静的ライブラリがシーンを持ち、見えているノートだけをピクセル座標のインスタンスに変換する。Swift の AppKit ウィンドウが、そのバッファを Metal のインスタンス描画で `CAMetalDisplayLink` に合わせて出す。

シーンは 1,000 トラック、各 100 ノート、合計 100,000 ノート。これは計測用の件数で、DAW の上限ではない。フレームごとにメモリは確保しない。出力先のバッファは呼び出し側が渡す。

ベンチマークは 540 フレームのあいだ、自動でスクロールし、いったん全ノートが画面に入るまでズームアウトしてから、またズームインする。トラックパッドのスクロール、ピンチ、縦横を分けた 2 本指の間隔も受け付ける。計測中はカメラを自動で動かすので、手の操作は使っていない。

## 測定

マシンは Apple M4 の MacBook Air。この画面の最大リフレッシュレートは 60Hz で、1 フレームの予算は 16.7ms。release ビルド。最初の 20 フレームは計測に入れていない。

| 項目 | 結果 |
|---|---|
| 計測フレーム | 540 |
| 1.5 フレームを超えた間隔 | 0 |
| CPU 時間の最小 | 0.036 ms |
| CPU 時間の中央値 | 0.208 ms |
| CPU 時間の p99 | 0.618 ms |
| CPU 時間の最大 | 0.781 ms |
| 同時に描いたノートの最大 | 100,000 / 100,000 |
| バッファからあふれたインスタンス | 0 |

p99 はフレーム予算の約 4% だった。10 万ノートを全部書き出す処理だけを Rust 側で測ると、1 回あたり 147µs だった。

60Hz への追従は、表示リンクの間隔が途切れなかったことで確認した。CPU 時間の最大が 0.8ms なので、120Hz（8.3ms）の画面でも同じシーンは予算に収まる見込みがある。120Hz の実機ではまだ測っていない。

## 再現

```sh
make spike-draw
```

ウィンドウが開き、計測が終わると閉じる。結果は標準出力と `target/spike-s1.txt` に出る。`--bench` を付けずに `spikes/draw` で `swift run -c release` すると、スクロールとピンチを手で確認できる。

## 製品アレンジの問い合わせ音高表示

2026-10-25、[ADR 0165](../decisions/0165-inspector-fx-add-and-arrange-note-pitch.md) の音高表示に合わせ、
`make spike-arrange-query` を追加した。
上記 S1 の専用シーンとは別に、製品の `ArrangeIndex` を同じ 1,000 トラック・100,000 ノートで測る。
ウィンドウ・GPU・音声機器は使わず、音域の索引作成と出力バッファの確保も計測区間に含めない。
全体表示と、13 行の一部・8 拍を表示する部分表示をそれぞれ 120 回問い合わせ、最初の 20 回を除く。
件数・繰返し数はこの計測の条件であり、製品の上限ではない。

Apple M4、release、同じ入力での開発中の比較:

| 問い合わせ | 旧版の中央値 / p99 | 音高表示の中央値 / p99 |
|---|---|---|
| 全体 | 753.542 / 828.416 µs | 766.958 / 805.125 µs |
| 部分 | 1.708 / 1.792 µs | 1.708 / 1.750 µs |

全体の中央値は約 13 µs 増えたが、p99 と部分表示は同等以下だった。
時間増加が厳密にゼロとは判定せず、この入力の問い合わせ時間とする。
当初のノートごとの除算を、配置ごとに準備した縦変換へ移してから測った。
手元の比較ログは `target/arrange-query-before/1.log`、`target/spike-arrange-query.txt` にあり、
正式な再実行は `scripts/verify.py --run spike-arrange-query` から行う。
結果の鮮度は `target/verification/report.md` と `spike-arrange-query.log` で確認する。
実画面への提出・GPU の負荷を含む S1 の再計測は未実施で、上記の過去の S1 数値を今回の合格とはしない。
